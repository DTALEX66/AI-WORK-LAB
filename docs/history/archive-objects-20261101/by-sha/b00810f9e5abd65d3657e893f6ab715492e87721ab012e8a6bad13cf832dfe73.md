# 1. 现在项目真正的问题不是“模型旧”，而是模型链路没统一

这次检查发现了一个比模型版本更重要的问题。

目前仓库实际上存在 **多套互相没有完全接通的检索/摄取路径**。

`app/rag/index.py` 最近已经升级，能够真正调用：

`qwen3-embedding:0.6b → /api/embed → 1024 维 → sqlite-vec`

这部分方向是对的。

但是实际统一知识管线 `shared/pipeline.py` 写入 KB 后调用的是：

`knowledge_base/search/vector_search.py`

而这里仍然写死：

```text
SimpleTextEmbedder(dim=384)
vec_kb_documents = 384
vec_kb_cards = 384
```

更严重的是另外两条：

```text
app/memory/episodic.py
→ SimpleTextEmbedder(dim=384)

shared/graph_rag.py
→ SimpleTextEmbedder(dim=384)
→ vec_graph_nodes dim=384
```

所以现在实际上是：

```text
RAG 新链
→ Qwen3 Embedding 1024

KB 主搜索
→ Hash 384

Episodic Memory
→ Hash 384

GraphRAG
→ Hash 384
```

**这是必须优先解决的 P0。**

否则未来会出现“同一个知识库，在不同页面/功能里检索结果完全不同”的问题。

# 2. 检索管线应该直接收成一条

建议最终变成：

```text
原始文件 / 网页 / 音视频
        ↓
格式探测 Magika
        ↓
多格式解析
        ↓
结构化块 + 来源锚点 + provenance
        ↓
结构感知 Chunk
        ↓
FTS5 BM25 ─────────────┐
                       ├→ Hybrid Recall
Qwen3-Embedding-0.6B ──┘
        ↓
候选 Top 30~50
        ↓
Qwen3-Reranker-0.6B
        ↓
Top 5~10
        ↓
Graph 邻接扩展 / Evidence
        ↓
Qwen3.5-4B
        ↓
带引用回答 / 学习 / 提炼
```

不要再允许 `vector_search.py`、`episodic.py`、`graph_rag.py` 各自实例化自己的 embedding。

应该统一成：

```text
EmbeddingProvider
        ↓
Model Registry
        ↓
所有索引消费者
```

并且每一个向量索引都记录：

```text
model_id
model_revision
model_sha
vector_dim
quantization
normalization
index_generation
created_at
```

这样以后换 embedding 模型时，系统知道 **必须 shadow rebuild → 验证 → 原子切换 → rollback**，而不是直接把新模型向量塞进旧表。

- 100+ 语言

非常适合你的本地知识库。citeturn544330search14turn230360search0turn230360search3

所以：

**不要删除 `qwen3-embedding:0.6b`。**

```text
hash-embedding
SimpleTextEmbedder(384)
```

作为**生产默认模型**的身份。

但 `SimpleTextEmbedder` 代码可以留下，改名/定位成：

```text
emergency_fallback
test_fallback
no-model-safe-mode
```

而不能再成为正式索引模型。

# 4. 当前 reranker 的错误需要直接推翻

仓库昨天的实机记录已经发现：

```text
qwen3-reranker:latest
→ 作为 Ollama embedding 调用
→ 返回 zero-norm vector
```

这不是“模型不好”。

而是**调用方式就错了**。

`Qwen3-Reranker-0.6B` 是 **CrossEncoder / Text Ranking 模型**，不是 embedding 模型。官方现在已经直接支持 SentenceTransformers `CrossEncoder`，模型约 **1.21GB**。citeturn230360search1turn230360search9

所以删除：

```text
qwen3-reranker:latest
→ /api/embed
```

改成独立 sidecar：

```text
retrieval candidates
       ↓
Qwen3-Reranker-0.6B CrossEncoder
       ↓
score(query, passage)
       ↓
Top K
```

这会比现在简单的：

```text
vector_distance + keyword_score
```

强很多。

而且当前 `ModelRoleEntryV1` 的 role 枚举里甚至**没有 `reranker`**。

应该扩展为至少：

```text
llm_text
embedding
reranker
ocr
document_parser
vision
asr
forced_aligner
file_classifier
```

# 5. OCR 整条链需要升级

现在项目仍以：

```text
Tesseract 5.5
pytesseract
RapidOCR
```

为主要 OCR 路径。

Tesseract 不应该删除，但已经不适合做 2026 年 ArcheAxis 的**主 OCR**。

PaddleOCR 在 2026 年已经更新了两条非常合适的模型：

**PP-OCRv6 Medium**：34.5M 参数，单模型覆盖 50 种语言，官方称相比 PP-OCRv5 server 检测和识别均有明显提升，非常适合大批量普通文字识别。citeturn544330search3turn544330search7

**PaddleOCR-VL-1.6**：只有 0.9B，但针对表格、公式、复杂版面、古籍、生僻字、印章、图表和真实畸变文档进行了强化，是更适合 ArcheAxis “知识摄取”的复杂文档模型。citeturn544330search4turn544330search6

所以应该改成：

```text
正常图片文字
→ PP-OCRv6

复杂 PDF / 表格 / 公式 / 图表 / 多栏
→ PaddleOCR-VL-1.6

失败
→ Tesseract

二次验证
→ RapidOCR（可选）
```

另外我检查了最新的 **GLM-OCR**：约 0.9B/1B，也很轻，官方定位复杂文档理解，值得作为 bake-off 候选，但目前没必要同时塞进正式运行库。先放候选池和 PaddleOCR-VL-1.6 做你的真实文档评测。citeturn913014search0turn913014search2

---

# 2. 不要追求“全塞显存”

这才是很多短视频/帖子容易误导人的地方。

你的配置是：

**8GB VRAM + 64GB RAM。**

正确思想不是：

> 怎么把 27B 强行压进 8GB VRAM？

而是：

> **保留高质量 4-bit 权重，让最适合 GPU 的部分进 8GB VRAM，其余权重留在 64GB RAM。**

也就是：

```text
Qwen3.8-27B
≈ 14.3GB UD-IQ4_XS

RTX 5060 8GB
├── 约 22~25 层 GPU
├── CUDA
├── Attention / 部分矩阵计算
└── KV Cache

64GB RAM
├── 剩余权重
├── Host state
├── context
└── CPU-offloaded layers
```

这就是为什么 14GB 模型可以在 8GB GPU 上运行。

---

# 3. Qwen3.8 的架构本身特别有利于低显存

传统 Transformer 27B 如果：

```text
64 layers
×
全部 self-attention
```

长上下文 KV Cache 会很恐怖。

但是 Qwen3.8-27B 是：

```text
64 Layers

48 × Gated DeltaNet
16 × Full Attention
```

也就是大致：

```text
3 × DeltaNet
1 × Attention
3 × DeltaNet
1 × Attention
...
```

只有 **16 层真正需要完整增长型 KV Cache**。citeturn962785search1

这解释了一个看起来很违反直觉的现象：

> **27B Dense + 64K context 居然真的能在 8GB VRAM 上跑。**

这是模型架构进步，不单纯是量化魔法。

---

# 4. KV Cache 再压 Q4

低显存方案另一个核心：

```text
K cache → Q4_0
V cache → Q4_0
```

已有 Qwen3.8 GGUF 部署资料测算：

256K context 的 KV：

```text
F16 KV ≈ 17GB
↓
Q4 KV ≈ 4.3GB
```

再加上 Qwen3.8 只有部分 Attention 层，因此非常适合这种方式。citeturn533122search7turn533122search9

你如果正常用：

```text
32K
```

KV 压力其实更小。

# 5. MTP 才是另一个大杀器

Qwen3.8 本身训练了：

**Multi-Token Prediction**

因此 llama.cpp 现在可以直接：

```text
--spec-type draft-mtp
```

让模型一次预测多个候选 token，然后验证。

类似 speculative decoding，但不需要另外跑一整个 1B/3B draft model。

在 5060 8GB 实测配置里：

```text
--spec-type draft-mtp
--spec-draft-n-max 2
--spec-draft-p-min 0.7
```

已经实际工作。citeturn716258search1

这也是为什么同一台机器：

```text
Ollama
≈ 2.4 tok/s

优化 llama.cpp
≈ 4.7 tok/s
```

几乎翻倍。
