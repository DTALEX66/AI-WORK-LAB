# 数字人 / 虚拟人项目全景调研

这次把范围扩到了 **50 余个产品、开源项目与技术组件**，包括实时交互数字人、虚拟伙伴、数字员工、专家分身、AI 演员、游戏角色、品牌 IP、互动展陈，以及背后的角色制作和驱动技术。

**我的判断：对你来说，最值得研究的不是“再做一个数字人口播工具”，而是“有视觉形象、能理解业务、还能调用工具的角色型 Agent”。**  
另一条值得单独考虑的路线是：**不做通用平台，做品牌虚拟角色和垂直内容服务，把你的视觉设计、视频与工作流能力组合起来。**

下面将**已经查到的项目事实**和**我的选型判断**分开说明。资料核对截至 **2026 年 10 月 12 日**，以官网、开发文档和官方代码仓库为主；没有把宣传片效果当作实际部署测试，也没有验证厂商宣称的转化率或最低延迟。

### 这里最重要的两个发现

**第一，不必把“数字人”限定成真人。**  
LemonSlice 明确覆盖卡通、拟物和品牌角色。我的判断是：你做原创品牌角色，可能比追求“像一个不存在的真人”更能形成设计差异，也更容易与品牌视觉、网站和宣传内容统一。前半句是产品能力，后半句是我的产品判断。citeturn632759view7

**第二，前沿演示不能直接当作现成供应链。**  
Tavus 在 2026 年 10 月发布的 **Griffin** 展示了更完整的实时感知与行为能力，但其官方页面明确表示：**Griffin 尚未进入 Tavus 平台**。现在做交付，应评估已经开放的产品，而不是按预览视频设计承诺。citeturn661211view3

### 最贴近你之前需求的，实际上是 OpenAvatarChat 和 Fay

**OpenAvatarChat 已经出现了明确的 Agent 集成路线。**  
其官方文档提供 **Chat Agent 模式 / OpenClaw 集成**，包括多轮工具调用、持久人格、上下文压缩、后台任务协作与摄像头感知。但该部分明确标注 **Beta，接口和配置可能变化**。citeturn632759view4

因此，你之前设想的流程——

> 对着一个角色提出目标 → 角色调用后台 Agent 或工具 → 执行任务 → 返回结果

并非只能从零开发。**已有工程项目在往这个方向走，但 Beta 集成和稳定商业交付仍是两回事。**

我的初步选型判断是：

**重视业务执行，先研究 Fay、OpenAvatarChat；重视角色感和桌面体验，先研究 AIRI；重视网页轻量集成，先研究 TalkingHead。**

这不是跑分排名，而是按用途划分的研究顺序。

## 八、这次调研中，最需要避开的几个误判

### “开源”不等于“所有内容都能无条件商用”

这里已经有明确例子：Wav2Lip 原始开源版限制商用；Duix 当前许可证包含与**超过 1,000 月活用户**有关的额外商业授权条款；Open-LLM-VTuber 的代码许可并不覆盖全部角色素材。citeturn632759view6turn702652view0turn663422view6

所以需要分别检查：**框架代码、模型权重、依赖模型、角色素材、声音和输入内容**。不能只看仓库顶部的一张许可证标签。

### “能生成视频”不等于“能实时交互”

Duix 的公开项目明确不是实时版本；InfiniteTalk 的长视频能力也不能直接作为实时对话承诺。系统选型必须从实际交互要求出发。citeturn359782view1turn936625view6

### “演示顺畅”不等于“你的完整链路顺畅”

我建议实际测试的是：用户说完一句话后多久听到回应、能否自然打断、中文专有名词是否正确、知识是否答对，以及工具执行失败时怎么恢复。

不要只拿某个模块的渲染速度，替代整个产品的交互体验。

### 真人形象、声音和 AI 标识不能留到上线后再处理

在中国大陆提供相关服务，需要按具体业务检查生成合成内容标识要求；《人工智能生成合成内容标识办法》及配套要求已于 **2025 年 9 月 1 日**实施。具体适用范围与实施义务应按服务形态核对。citeturn522653search0turn522653search2

我的产品建议是从第一版就保留授权记录、明确 AI 身份、设置内容边界，并让删除数据和撤销授权有可执行的流程。涉及对外发布、发邮件、改文件等动作，也应另设权限和确认机制，而不是让人物界面掩盖实际操作风险。

## 六、前期独立制作，应改成“可独立调试的原生模块”

我的建议不是等星栖作为完整软件做完，再想办法塞回 AAOS。那样会让两边的数据、前端和运行方式逐渐分开。

更合理的开发顺序是：

### 第一阶段：独立孵化角色能力，但按 AAOS 的接口开发

## 4. 建立星栖的最小可扩展模块

根据真实仓库现状决定目录，不机械复制以下结构。

建议至少形成明确的逻辑边界：

**Astryn Contracts**

定义角色、会话、表现状态、Host 能力和权限契约。

**Astryn Companion**

管理人格、角色配置、互动策略、场景切换和表达行为。

**Astryn Interaction**

管理输入、输出、流式响应、打断、事件时序与交互状态机。

**Astryn Avatar**

管理角色呈现、表情、动作、口型与可替换的渲染驱动。

**Astryn Presentation**

提供可复用 React UI，能够在不同 AAOS 展示形态中挂载。

**Astryn AAOS Adapter**

只通过授权 Host API 调用统一服务，不绕过 Core。

**Astryn Dev Host**

用于独立运行和测试。默认使用隔离合成数据；可通过配置切换到真实受支持的模型/宿主接口。

这些是模块责任，不要求首版创建七个 npm 包、七个进程或七个数据库。

以最小可维护结构实现，避免过度微服务化。

### 必须定义的核心接口

建立稳定、可测试的接口或等价契约：

- `AstrynHostPort`：AAOS 宿主能力。
- `AstrynConversationPort`：会话与流式对话。
- `AstrynMemoryPort`：AAOS 记忆的授权访问。
- `AstrynActionPort`：任务请求、审批、状态回执。
- `AstrynContextPort`：获准获取当前文档、选择内容和任务上下文。
- `AstrynAvatarRenderer`：可替换角色表现驱动。
- `AstrynPresentationMode`：多形态显示。
- `AstrynCharacterProfile`：角色身份与表现配置。

接口命名可以调整，但责任和数据边界不可缺失。

特别要求：

所有任务状态必须来自真实系统事件，不得由大模型猜测任务完成。

流式事件应包含会话身份、关联任务、事件序号或版本，能够处理过期事件、取消、重复响应和断线恢复。

## 5. 第一个可运行闭环：M0

本次必须尽可能完成一个真实、可演示、可测试的纵向功能切片。

### M0-A：真实角色显示

实现一个原创的“小栖”初始视觉角色。

首版可以使用自研 2D/SVG/Canvas 角色与轻量动画，后续通过渲染接口替换为合规 Live2D、VRM 或 3D 模型。

不要直接复制未经授权的成品角色模型，也不要用纯文本框冒充完整数字人。

首版角色至少应有：

- 待机状态。
- 正在聆听或输入状态。
- 正在思考状态。
- 正在回复状态。
- 出错或被打断状态。

表情和动作必须和真实事件连接。

优先保证稳定、流畅和低资源占用。

### M0-B：真实对话

实现可操作的文本会话。

优先使用已存在的 AAOS 统一模型接口。

如果 AAOS 接口暂时不可接通，允许建立**仅开发环境使用**的标准兼容模型适配器，用于验证真实请求与流式回复；后续由 AAOS 接管模型管理。

开发宿主不能在浏览器源码中暴露 API Key。

当没有配置可用模型时，必须明确显示模型不可用，不能把脚本回复冒充真实 AI。

角色对话需要具备可维护的身份、表达风格和上下文管理，不能只依赖一段不可配置的大提示词。

### M0-C：状态驱动行为

建立明确的角色交互状态机，例如：

`idle / listening / thinking / speaking / executing / awaiting_approval / completed / failed / interrupted`

其中任务完成、失败和审批状态只能由相应权威回执触发。

允许角色表达情绪和个性，但不得捏造系统状态。

验证多次请求、取消、打断、组件卸载和迟到事件，不出现错误状态串台。

### M0-D：记忆边界

实现 AAOS 统一记忆访问接口的最小契约及测试。

不得新建正式长期记忆数据库。

独立测试环境允许使用进程内合成数据或可销毁测试夹具，不将其当作第二套生产记忆库。

验证：

- 用户偏好只能从获准的作用域读取。
- 私密陪伴内容不能自动进入其他业务模块。
- 角色虚构经历不能被标记为真实知识。
- 模型生成的记忆必须经过可治理的候选处理。
- 用户未来可查看、编辑和删除相关记忆。

如果 AAOS 的实际记忆 API 尚不存在，清晰标记 `BLOCKED_BY_HOST_CONTRACT`，不要伪造已集成状态。

### M0-E：AAOS 上下文契约

设计一条最小真实集成场景：

用户在 AAOS 选中一段文字，小栖获得授权后的选中内容，解释其含义，并在可能时提供 AAOS 的真实来源标识。

当前不能直接接通时，可用明确标注的合成文档夹具完成契约测试，不得假装已经访问真实知识库。

确保以后能够替换为 AAOS 原生上下文，无需重写角色 UI。

### M0-F：可运行开发宿主

提供可复现的本地启动方法。

能够启动开发页面、进行角色交互、观察状态变化、切换基础角色呈现状态、执行测试并查看真实错误。

测试宿主应当可单独运行，但不是第二个正式产品。
