## Obsidian 要不要只当前端？

不要完全只当前端。

更准确的定位应该是：

```text
Obsidian = 使用层 + 最终知识库层
后端 = 转化引擎 + 证据核验引擎 + 写入器
数据库 = 缓存 / 状态机 / 搜索索引 / 证据索引
Open Design = UI 视觉增强和交互设计
```

如果你把课程内容全放数据库里，Obsidian 只通过插件/API 当前端调用，会有几个问题：

第一，Obsidian 的双链、Dataview、Canvas、Graph、搜索、复习卡片都依赖 Markdown 文件和 frontmatter。内容只在数据库里，Obsidian 的原生能力会被削弱。

第二，后期手动修改、复习、整理、迁移会变麻烦。Markdown 文件可以直接打开、编辑、同步、备份；数据库一旦结构变了，迁移成本更高。

第三，你现在仓库的 V4/V5/V6 规划本身就是 Obsidian-native 路线：V4 生成课程主页、课程地图、逐节总结、知识卡片、复习卡片、视觉图解、证据索引、导入报告；V5 也强调 Dashboard/MOC/Dataview/CSS，而不是先做独立 Web 后台。fileciteturn16file0L152-L180 fileciteturn25file0L7-L14

## 文件夹和数据库分别放什么？

### 文件夹放“大东西”

```text
原始文件索引
ASR 转写结果
OCR 结果
图片关键帧
PDF 页面截图
课程中间产物
导入报告
备份文件
```

### SQLite 放“结构化索引”

```text
课程 ID
课程状态
源文件路径
文件 hash
chunk 切片
证据来源
处理进度
是否已 OCR
是否已 ASR
是否已核验
是否已写入 Obsidian
```

所以不是“只用文件夹”，也不是“全塞数据库”。

正确方式是：

```text
文件夹存内容
SQLite 存索引和状态
Obsidian 存最终 Markdown 知识
```

```text
多人协作
要做独立 Web 后台
课程数量非常大
需要远程 API 服务
需要用户账号系统
需要实时同步
```

那时候可以升级成：

```text
PostgreSQL + pgvector
或者
PostgreSQL + Qdrant
```

但现在不上。现在上数据库软件会增加部署复杂度，反而拖慢开发。

## 最推荐你现在的方案

```text
第一阶段：

第三阶段：
```

```text
Obsidian = 最终知识库
```
