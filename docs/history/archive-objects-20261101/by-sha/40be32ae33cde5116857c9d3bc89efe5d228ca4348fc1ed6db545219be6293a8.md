# DTALEX66 / OPEN-DESIGN-Assistance 全面审计

## 一、核心结论

目前的 `OPEN-DESIGN-Assistance` 已经不是空项目，它具备较好的设计知识骨架、插件雏形、模板库、静态验证工具、一个可运行设计系统和一个真实落地案例。

但按照你现在提出的目标：

> 全面增强 AI 在平面设计、品牌设计、视觉设计、艺术设计、空间设计等领域的专业判断、设计质感和商业落地能力。

当前项目还只能定义为：

> **Open Design 的设计提示词、模板、插件和参考样板仓库。**

还不能定义为：

> **面向 AI 的商业设计能力增强系统。**

# 二、项目正确定位

当前文档反复强调：

- Open Design 是实际设计入口；
- 本仓库不是工作流中心；
- 本仓库只提供提示词、模板、参考实现和增强资料。fileciteturn5file0L2-L2 fileciteturn33file0L2-L2

这个定义在项目早期是正确的，它防止项目重新造一个 Open Design。

但现在这个边界收得过窄。

## 建议升级后的正式定位

> **DTALEX66 OPEN-DESIGN-Assistance 是一个 Open Design-first、Agent-compatible 的商业设计智能与生产交付增强层。**
>
> 它为 AI 提供设计理解、项目策略、创意方向、视觉语言、专业设计规则、质量评审、生产检查、交付标准和案例学习能力，使 AI 从“生成一张看起来不错的图”，升级为“完成可修改、可复用、可生产、可交付的商业设计项目”。

### 三方职责应重新划分

| 层级 | 负责内容 |
|---|---|
| Open Design | 画布、项目、模型调用、运行时、预览、导出和交互界面 |
| AI Agent / 模型 | 推理、生成、修改、文件操作、图像和代码生产 |
| OPEN-DESIGN-Assistance | 商业设计方法、专业场景管线、领域知识、质量标准、生产规范、交付协议和学习数据 |

因此，本项目不需要抢 Open Design 的主界面，但必须拥有：

- **设计任务流程定义权**
- **商业设计专业标准**
- **输出质量判定权**
- **交付格式和生产门槛**
- **领域案例与经验记忆**

最准确的一句话是：

> **Open Design 负责让 AI 进行设计；OPEN-DESIGN-Assistance 负责让 AI 像专业设计团队一样完成商业设计。**

# 四、最严重的结构性问题

## P0-1：新定位和旧项目定义发生冲突

旧定义明确表示本仓库“不负责工作流，只提供增强材料”。

但真正的商业设计增强项目必须定义：

```text
Brief
→ 调研
→ 策略
→ 创意方向
→ 设计系统
→ 生成
→ 评审
→ 修改
→ 生产检查
→ 交付
```

本项目不需要执行这些底层运行任务，但必须把它们定义成 Open Design 能执行的 `scenario/pipeline`。

否则仓库会不断增加模板，却无法形成稳定结果。

## P0-4：没有跨插件的商业项目场景

现在七个插件是并列的：

```text
品牌插件
平面插件
UI 插件
空间插件
QA 插件
```

但它们之间没有明确的数据传递合同。

例如一个品牌项目应该是：

```text
品牌 Brief
→ 竞品与受众分析
→ 品牌策略
→ 三个视觉方向
→ 方向选择
→ DESIGN.md / Tokens
→ KV
→ 海报
→ 社交媒体
→ 官网首屏
→ 品牌手册
→ 交付检查
```

现有插件不能保证上一步输出被下一步读取，也没有统一项目状态。

这会导致不同 Agent 每次都重新理解项目，设计风格漂移。

## P0-5：质量评分仍然过于主观

当前 `design-qa-critic` 使用十个通用维度，每项 1–5 分。fileciteturn13file0L2-L2

主要问题是：

1. 不同设计门类使用同一套评分；
2. 没有权重；
3. 没有参考图对比；
4. 没有像素、尺寸、对齐、对比度等自动指标；
5. 没有输出证据；
6. 没有多评审者交叉判断；
7. 没有设计修改前后的回归比较。

品牌设计、海报、UI、展厅和包装不应使用同一评分模型。

例如展厅必须增加：

- 观看距离；
- 人体尺度；
- 施工可行性；
- 材料维护；
- 消防和安全；
- 内容密度；
- 现场光照。

品牌必须增加：

- 可识别性；
- 差异化；
- 黑白适配；
- 小尺寸适配；
- 跨媒介稳定性；
- 商标和近似风险。

# 六、缺失的商业生产层

商业项目能否交付，不能只看设计是否好看。

项目至少还缺少以下五类检查器。

## 1. Asset Preflight

检查：

- Logo 是否为正确版本；
- 图片是否达到分辨率要求；
- 字体是否允许商业使用；
- 素材是否存在版权来源；
- 产品比例是否被改变；
- 参考图是否被直接复制。

## 2. Print Preflight

检查：

- RGB / CMYK；
- 出血；
- 安全边距；
- 分辨率；
- 黑色叠印；
- 专色；
- 刀版；
- 字体转曲；
- 印刷尺寸。

## 3. Digital Preflight

检查：

- 屏幕尺寸；
- 移动端适配；
- 对比度；
- 点击区域；
- 图片体积；
- 字体加载；
- 浏览器和设备兼容性。

## 4. Spatial Preflight

检查：

- 真实尺寸；
- 墙面比例；
- 观看距离；
- 人体尺度；
- 材料厚度；
- 安装方式；
- 电源与灯光；
- 施工接缝；
- 内容更新方式。

## 5. Delivery Preflight

检查：

- 是否存在可编辑源文件；
- 是否存在预览文件；
- 是否有字体和素材清单；
- 是否有版本号；
- 是否有颜色、尺寸和生产说明；
- 是否能由另一个设计师继续修改。

# 七、仓库结构问题

当前仓库同时容纳：

```text
Open Design 插件与模板
旧 Design-system
完整 MINIGAME runtime
大量游戏视觉资产
项目迁移记录
Windows/Codex 配置
```

这会导致两个问题。

### 第一，项目产品信号被稀释

一个以“全面商业设计增强”为目标的仓库，当前最成熟、最重的资产却是异常电梯小游戏。

它容易让外部使用者误判项目重点。

### 第二，仓库体积和维护成本过高

建议调整为：

```text
examples/minigame/
```

或者将完整 runtime 迁回独立项目，只在本仓库保留：

```text
examples/minigame/design-case/
fixtures/minigame/
assets/minigame-selected/
```

主仓库只保留设计验证所必需的最小样板。

此外，我在当前仓库中没有找到统一的根级：

- LICENSE
- CHANGELOG
- CONTRIBUTING
- CI workflow
- 根级项目 Manifest

虽然各插件填写了 MIT，但整个仓库吸收了多个来源和历史项目，需要建立根级许可、来源清单和资产版权台账。
