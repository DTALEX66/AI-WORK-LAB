# ArcheAxis 候选

### HIGH — GRACE：Evidence Graph 路线与 ArcheAxis 极其接近

2026 年 9 月 3 日新论文 **GRACE: Graph-Grounded Reflective Agent Copilot Engine for Expert-in-the-Loop Knowledge Expansion**，已经不是普通 RAG。

它把模型输出拆成 **atomic claims**，然后建立“Claim ↔ Trusted Prior”的加权二部图，把 Claim 分成：

**Grounded / Refuted / Boundary**

其中 Boundary 非常重要：它不是简单判为“错”，而是表示可能属于**新知识、争议知识或证据不足知识**。随后通过 Return on Attention 决定哪些 Claim 值得交给人类专家审核；审核通过后，又升级成新的 Evidence Anchor，继续扩展知识库。论文同时提供代码。citeturn798148academia48

这与 ArcheAxis 一直要求的：

**个人知识可以进入 → 不强行只收“高证据知识” → 标记证据级别 → 判断冲突/未知/未经验证 → 人工审核 → 新知识沉淀**

几乎是同一个方向。

| 判断层 | 结论 |
|---|---|
| 新颖性 | **9/10** |
| 证据等级 | 论文 + 实验 + 开源代码 |
| 可复用方式 | **ALGORITHM_DONOR → ADAPTER POC** |
| 成本 | 研究代码；主要成本来自 LLM 推理与图计算 |
| ArcheAxis | **9.8/10** |
| WORK-LAB | 5.5/10 |
| DESIGN-LAB | 1.5/10 |

**结论：必须进 POC。**

而且我不建议简单“引入 GRACE”，而是把它拆成 ArcheAxis 自己的：

`Claim Decomposition → Evidence Anchor → Evidence Graph → Grounded/Refuted/Boundary → Verification Queue → Knowledge Promotion`

这可能成为 ArcheAxis Evidence Layer 的核心算法供体。

### HIGH — RefVerifier：补上“引用是否真的支持这句话”

9 月 7 日的 **RefVerifier** 专门处理：

**论文中的 Claim → 引用 → 文献元数据 → 原始 PDF → 定位支持证据 → Verification Verdict**

其公开结果中，claim detection F1 为 **0.990**；证据定位在摘要上 hit rate **98%**、完整论文约 **68%**；8 篇论文的端到端 verdict accuracy 为 **71%**。citeturn798148academia50

这与 ArcheAxis 的“找到原始来源，而不是只看到二手网页引用”非常匹配。

可复用方式：

**ALGORITHM_DONOR + ADAPTER**

我建议以后 ArcheAxis 不只维护：

`Claim → Source`

而升级为：

`Claim → Citation → Source Resolution → Evidence Span → Entailment → Verdict → Confidence`

这样“来源存在”和“来源真的支持该 Claim”就不会混为一谈。

**适配度：ArcheAxis 9.4/10。**

# WORK-LAB 候选

### HIGH — Parsing the Stream：非常值得进入核心架构研究

9 月 1 日的新论文提出 **Live Trace Model**：

不是把越来越长的 Agent 历史反复 summary/compaction，而是：

`Raw Events → Append-only Event Ledger → Typed Run State → Consumer-specific Views`

论文实验中，给观察者提供的结构化 View 使用约 **14–15 倍更少输入 Token**、成本降低约 **5–7 倍**，同时准确率从 raw trace 条件下约 **0.48** 提升到 **0.85–0.87**。

在 120 步顺序依赖任务中，维护确定性运行状态的方法取得 **30/30**，完整上下文 prompting 是 **8/30**。citeturn798148academia49

因为它直接解决你项目里反复发生的：

**长任务漂移、上下文压缩丢信息、执行记录越来越长、恢复后不知道做到哪里、聊天摘要不能等同权威执行状态。**

## ArcheAxis 候选

### 高｜NeoMME：非常适合补入多模态文档检索层

这是本轮发现的一个**本月漏检但达到提醒门槛**的候选，而不是重复介绍历史项目。

**PDF / 截图 / 扫描文档 → 页面级视觉检索 → 多模态 RAG**

| 项目适配度 | ArcheAxis **9.5/10**；WORK-LAB **3.0/10**；DESIGN-LAB **3.5/10** |

### 紧急｜DeepSeek Harness 0.1.5 系列出现会话 v3 回归风险

DeepSeek Harness 官方当前 npm 页面仍显示 `@deepseek-ai/dsh 0.1.5-rc.1`；官方 GitHub 同时已发布 `0.1.5-rc.2` 预发布版本。citeturn358538search0turn246781search0

2026 年 **9 月 15 日**出现了新的可复现报告：在 Web 模式中，`0.1.5-alpha.2`、`0.1.5-rc.1`、`0.1.5-rc.2` 都可能在 Agent 正在执行时让会话正文变空；报告者对比发现问题与新的 v3 Session 格式及实时流折叠有关，而 `0.1.2-rc.1` 不复现。更重要的是，报告明确指出这会造成一个实际冲突：降回旧版本可以避开 Web 问题，但依赖 `0.1.5` 的新版插件又可能无法满足依赖。citeturn246781search1

另外，9 月 12 日已有另一个独立报告指出，v3 Session 在特定插件于 `agent/pre-step` 写入持久事件时，可能形成“能继续写、却不能恢复”的 Session，恢复时报迁移错误。citeturn246781search2

这不是已经由官方维护者确认的统一根因，因此不能说“0.1.5 已被证实整体损坏”；但对你的 WORK-LAB 与 DSH 执行链而言，已经足够触发升级冻结门槛。

## ArcheAxis 候选

### 中｜《Beyond the Query》：不要默认给多模态 RAG 增加复杂动态路由器

9 月 11 日的新论文专门测试一个很容易让 ArcheAxis 过度设计的问题：

> 初次检索完成之后，再把检索分数、证据统计等“检索状态”交给路由器，是否真的比只看 Query 更能决定“继续检索还是停止”？

作者在文档、音频、视频 RAG 上做了匹配实验。开发集上加入检索信号有轻微提升，但到了独立最终测试集，增益只有 **+0.00288**，置信区间包含零，不能证明这种额外复杂度能稳定改善路由。citeturn196614view0

这不是在说“Adaptive RAG 没用”，而是在提醒：

**不能因为 Retrieval Score 看起来有信息，就默认它值得成为一个新的生产路由层。**

对 ArcheAxis 很重要，因为系统未来会有：

`文本检索`
`视觉页面检索`
`GraphRAG`
`Evidence Search`
`音频/视频检索`
`二次精细解析`

如果每一级都增加动态决策器，很快会形成一个极重的复杂系统。

| 评估维度 | 判断 |

| 新颖性 | **7.8/10** |

| 可复用方式 | **算法供体 / 仅供参考** |
| 成本 | 可直接降低不必要的路由模型、推理和维护成本 |
| ArcheAxis 适配度 | **8.8/10** |
| WORK-LAB 适配度 | **4.5/10** |
| DESIGN-LAB 适配度 | **2.0/10** |

**路线图建议：小幅调整。**

以后 ArcheAxis 新增任何 Adaptive Retrieval 路由机制，都应该强制做：

`Query-only 基线`
对比
`Query + Retrieval State`

只有后者真实显著胜出，才能进入正式管线。

这能避免 Evidence/RAG 层继续“为了先进而增加架构”。
