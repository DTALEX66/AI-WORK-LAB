# 建筑学长 AI：桌面自动化操作技术深度调研

**调研对象：** <Link url="https://www.jzxz.com/home" title="建筑学长 AI 官网"/>

已经确认，你要研究的重点不是它普通的 AI 生图能力，而是它的 **「桌面智能体助手」——通过自然语言，让 AI 直接操作专业设计软件，自动完成建模、绘图和文档制作。**

官方客户端介绍明确列出了以下能力：

- **SketchUp（SU）：** AI 自动建模、构建三维场景。
- **AutoCAD（CAD）：** AI 自动绘制图纸。
- **Rhino：** 控制专业三维设计软件。
- **Photoshop（PS）：** AI 辅助绘图和图像处理。
- **PowerPoint / Excel / Word / PDF：** 自动制作、处理办公文档。

这些是官方公开宣称支持的能力，并不意味着所有操作都已经经过独立实测。<Cite refs={["turn510420search0","turn510420search6"]}/>

**核心研究结论：它值得研究，但不需要复制整个建筑学长平台。**

真正值得复用的是它背后的技术思路：

**自然语言指令 → AI 任务规划 → 专业软件控制 → 自动执行 → 结果验证。**

这套机制不仅适用于建筑设计，还可以扩展到平面设计、3D 制作、视频制作和软件开发。对于你的项目，最有价值的是研究如何让现有 AI Agent 操作本地软件，而不是重新开发一套庞大的设计平台。

## 一、它到底能自动化到什么程度？

### 1. CAD：从参考图到可编辑图纸

这是目前证据相对完整的功能。

2026 年 7 月，建筑学长发布的 CAD 自动绘图教程展示了以下过程：

| 阶段 | 操作 | AI 的职责 |
|---|---|---|
| 1. 选择任务 | 选择 CAD 自动绘图 | 切换专业能力 |
| 2. 输入材料 | 上传建筑立面图、填写要求 | 图像与需求解析 |
| 3. 规划 | 自动提出绘图策略 | 确定绘制顺序、结构与尺寸 |
| 4. 人工审批 | 点击“批准执行” | 防止直接修改文件 |
| 5. 执行 | 打开 AutoCAD | 自动绘图 |
| 6. 组织 | 对图形进行图层处理 | 生成可继续编辑的工程内容 |

演示声称可以根据参考图生成立面图、平面图并处理尺寸。<Cite refs={["turn279208search4","turn279208search2"]}/>

这与普通 AI 生图存在本质区别。

**普通 AI 生图：** 输入一张参考图，返回另一张图片。

**专业软件自动化：** 输入参考图，建立几何对象、图层和尺寸，最终在 AutoCAD 中形成可以编辑的工程文件。

后者才是真正有长期价值的方向。

不过，官方在当时的评论回复中明确表示：**还不支持生成天正软件能够直接识别为原生墙体的对象**。这说明它能绘制 CAD 几何图形，不等于已经掌握建筑设计软件的全部专业对象语义。<Cite ref="turn965870search7"/>

### 2. SketchUp：从文字或图像到三维建模

官方在 2026 年 6—8 月陆续展示了三维自动建模能力，包括通过 AI 控制 SketchUp 建模、生成构件和自动分组。

这里有三项值得重点关注的能力：

**A. 参数化几何建模**

AI 不只是渲染一张看起来像 3D 的图片，而是驱动 SketchUp 创建实际几何对象。

**B. 构件分组**

把墙体、门窗、建筑构件等按照逻辑组织起来。对后续修改很重要，因为一个可编辑、有组织的模型，比无结构的网格更有价值。

**C. 连续修改**

模型生成后，可以继续提出修改要求，而不是每次都从头生成。

官方视频：

- <Link url="https://www.bilibili.com/list/487961090?bvid=BV1n9Te6SEs4&oid=116844316923681" title="AI 自动操纵 SketchUp 建模与构件分组"/>
- <Link url="https://www.youtube.com/watch?v=-BWFTeKY8lQ" title="建筑学长桌面助手 SketchUp 更新演示"/>
- <Link url="https://www.bilibili.com/list/487961090?bvid=BV1ek7h6dESk&oid=116809655131126" title="CAD / SU / PPT 综合自动化演示"/>

需要区分的是：视频展示了具体案例，但还不能据此认定它能稳定处理任意复杂建筑、完整 BIM 或所有异形模型。

### 3. Photoshop、Rhino 与办公软件

官网将 Photoshop、Rhino、PPT、Excel、Word、PDF 列入桌面助手的支持范围。<Cite ref="turn965870search3"/>

但这些软件的操作深度存在不同的证据等级：

| 软件 | 官方公开能力 | 当前核实程度 |
|---|---|---|
| AutoCAD | 自动绘制图纸、图层处理 | 有明确操作演示 |
| SketchUp | 自动建模、构件分组 | 有明确操作演示 |
| Rhino | AI 控制专业建模 | 官网声明支持，缺少同等详细的专项实测 |
| Photoshop | 自动绘图、图像处理 | 官网声明支持，具体操作覆盖率待测 |
| PowerPoint | 自动制作演示文件 | 有综合自动化演示，复杂排版质量待测 |
| Excel / Word / PDF | 文件自动化处理 | 官网声明支持，具体功能范围待测 |

因此，**CAD 和 SketchUp 是目前最值得作为技术研究样本的两条路径**。

## 二、它的自动化究竟是怎么实现的？

首先要区分两个概念。

建筑学长平台涉及的自动化，可能包含两种不同的技术路线：

| 类型 | 核心功能 | 最终交付 | 技术重点 |
|---|---|---|---|
| 在线 AI 工作流 | 串联图片生成、修改、渲染等模型 | 图片、视频等内容 | 工作流编排、模型 API |
| 桌面 AI 智能体 | 操作 CAD、SU、Rhino、PS 等软件 | 可编辑的专业工程文件 | 软件控制、任务规划、状态反馈 |

**对你而言，第二条路线的技术价值更高。**

但这里必须明确一个证据边界：**目前没有找到足以确认建筑学长桌面助手内部使用 MCP、Windows UI Automation、软件原生 API 或自研协议的公开技术文档。**

所以接下来的内容是基于其公开功能，结合成熟技术实现进行的**技术逆向推断**，而不是已经获取了它的内部源码。

### 1. 最合理的实现架构

```text
用户输入自然语言 / 参考图片
             │
             ▼
       多模态 AI 理解
    识别对象、结构、尺寸
             │
             ▼
        Agent Planner
      分解任务、生成步骤
             │
             ▼
          人工审批
             │
             ▼
       Tool Router
      软件能力路由选择
             │
       ┌─────┴─────┐
       ▼           ▼
   软件原生接口   Windows GUI
   API / MCP      自动化控制
       │           │
       └─────┬─────┘
             ▼
       本地软件执行
             │
             ▼
       状态读取与检查
     几何 / 图层 / 截图
             │
             ▼
       文件保存与交付
```

这类系统最关键的部分，不是 AI 模型本身，而是中间的 **Tool Router + Executor（工具路由与执行器）**。

例如，你输入：

“在 SketchUp 中生成一间现代风格的客厅，长 6 米、宽 4 米，按照墙面、地面、家具、灯具分别分组。”

AI 必须将这段话转换为 SketchUp 能够执行的具体操作：

| 自然语言 | 实际软件操作 |
|---|---|
| 创建一个客厅 | 创建几何空间 |
| 长 6 米、宽 4 米 | 设置坐标、尺寸、单位 |
| 添加家具 | 创建或插入组件 |
| 分别分组 | 操作 Groups / Components |
| 给我看看效果 | 调整相机并获取视图 |
| 保存工程 | 保存原生 `.skp` 文件 |

这和“让 AI 看着屏幕点击鼠标”不是一个技术层级。

### 2. 为什么必须优先使用专业软件接口？

控制设计软件主要有三个技术层级。

| 层级 | 技术 | 可靠性 | 适合场景 |
|---|---|---|---|
| 第一层 | 软件原生 API / Scripting | 较高 | 建模、图层、尺寸、对象编辑 |
| 第二层 | Windows UI Automation | 中等，取决于控件 | 菜单、面板、文件对话框 |
| 第三层 | 截图识别 + 鼠标坐标 | 较低 | 缺少接口的功能、临时兜底 |

举个实际问题。

如果要求 AI 在 Photoshop 中新建一个 1920×1080 的画布：

使用鼠标模拟，需要识别窗口、点击文件菜单、打开对话框、填写尺寸、确认，任何一次界面变化都有可能造成失败。

使用 Photoshop 脚本，则可以直接创建指定尺寸的文档。

Adobe 官方已经支持通过 JavaScript 和 UXP 自动化 Photoshop，并且支持脚本与事件触发。<Cite ref="turn341146search1"/>

**因此，真正成熟的方案应当是：专业 API 优先，Windows 桌面控制兜底。**

## 三、已经找到可以直接复用的开源技术

这部分是本次调研最有价值的发现。

**不需要从零开发一套像建筑学长那样的桌面控制系统。多个专业软件已经存在 MCP 桥接项目，部分甚至由软件厂商自己维护。**

### 核心项目对比

| 软件 | 已找到的方案 | 许可 | 成熟度判断 |
|---|---|---|---|
| Windows 通用桌面 | <Link url="https://github.com/CursorTouch/Windows-MCP" title="Windows-MCP"/> | MIT | 较活跃，可作为通用控制底座 |
| Rhino / Grasshopper | <Link url="https://github.com/mcneel/RhinoAI" title="RhinoAI"/> | MIT | 厂商官方维护，优先级高 |
| SketchUp | <Link url="https://github.com/Ringophilia/Ringo-Sketchup-MCP" title="Ringo SketchUp MCP"/> | MIT | 有 Windows 实机回归记录，仍属早期项目 |
| AutoCAD / 国产 CAD | <Link url="https://github.com/AnCode666/multiCAD-mcp" title="multiCAD-mcp"/> | Apache-2.0 | 已覆盖多个 CAD 产品，需要现场验证 |
| AutoCAD LT | <Link url="https://github.com/puran-water/autocad-mcp" title="AutoCAD MCP"/> | MIT | 同时支持本机控制和无界面 DXF |
| Photoshop | <Link url="https://github.com/drmedia/photoshop-mcp" title="PhotoshopMCP"/> | MIT | 功能覆盖较广，但仍需要验证稳定性 |
| Blender | <Link url="https://www.blender.org/lab/mcp-server/" title="Blender 官方 MCP Server"/> | 以官方项目实际文件为准 | 厂商实验性方案，存在显著脚本执行风险 |

上表的成熟度根据公开仓库、文档、版本记录和作者测试描述判断，**不是我已经在你的 Windows 电脑上安装并完成验证的结果**。

### 重点项目 A：Windows-MCP

这是研究通用桌面操作最直接的起点。

它能够让支持 MCP 的 Agent 获取 Windows 界面状态、操作窗口、点击控件、输入文本、执行快捷键等。

截至本次检索，仓库已有约 1 万颗 GitHub Star，支持 Windows 10/11，使用 Python，提供 UI Automation 能力和截图控制。<Cite ref="turn391258search3"/>

从技术上说，它类似为 AI 提供一套“观察电脑、操作电脑”的能力。

不过它有明显边界：通用桌面控制不等于掌握 SketchUp 或 CAD 的专业模型结构。

此外，Windows-MCP 默认具备广泛系统权限，部分工具能够运行系统命令。官方安全文档明确说明这些能力没有独立沙箱。<Cite ref="turn391258search6"/>

**我的判断：适合作为通用能力底座，但不能单独承担专业设计自动化。**

### 重点项目 B：Rhino 官方 MCP

这是整个调研中最值得重视的发现之一。

Rhino 开发商 McNeel 已经直接提供 <Link url="https://mcneel.github.io/RhinoAI/" title="Rhino MCP Platform"/>。

它支持让 AI：

- 读取 Rhino 场景对象。
- 创建、修改几何体。
- 管理图层。
- 执行 Rhino 命令和脚本。
- 创建 Grasshopper 参数化定义。

而且，官方明确支持 Codex、Claude、Gemini 和本地模型等 MCP 客户端。<Cite refs={["turn154401search1","turn154401search3"]}/>

它并不是停留在概念阶段。

截至 2026 年 9 月 30 日，该项目已发布 Plugin 0.3.0，包含针对 Codex 图像接收等问题的修复。<Cite ref="turn391258search2"/>

这说明一件事：

**专业软件厂商正在主动将内部软件能力开放给 AI Agent。**

未来真正有竞争力的设计智能体，不一定要自己研究如何点击上万个按钮，而是把已经存在的专业软件接口组织起来。

### 重点项目 C：SketchUp 自动建模

<Link url="https://github.com/Ringophilia/Ringo-Sketchup-MCP" title="Ringo SketchUp MCP"/> 提供了另一种非常有参考价值的实现。

其架构是：

**MCP 客户端 → Node.js MCP Server → SketchUp Ruby 扩展 → SketchUp 模型。**

这和上面推导的专业软件控制方案基本一致。

项目当前标注为 1.3.2，作者称已经在 Windows SketchUp 26.2.243 上进行实机回归；macOS 尚未完成同等级实机验收。执行任意 Ruby 代码的能力默认关闭。<Cite ref="turn391258search0"/>

这种设计的关键不是让 AI 不受限制地运行代码，而是提供明确的建模工具，并限制高风险操作。

对于通过文字、图像自动生成可编辑 3D 场景的目标，这是一条可以实际验证的技术路径。

### 重点项目 D：AutoCAD MCP

如果更关注精确几何和工程图，可以考虑两个项目。

<Link url="https://github.com/AnCode666/multiCAD-mcp" title="multiCAD-mcp"/> 使用 Windows COM 技术，作者列出的兼容范围包括 AutoCAD、ZWCAD、GstarCAD 和 BricsCAD。公开文档描述了绘图、图层、对象修改、图块和文件管理等能力。<Cite ref="turn341146search2"/>

<Link url="https://github.com/puran-water/autocad-mcp" title="autocad-mcp"/> 则适用于另一类需求：AutoCAD LT 2024+ 的 Windows 环境，同时支持通过 `ezdxf` 在未安装 AutoCAD 的情况下直接生成 DXF 文件。<Cite ref="turn341146search0"/>

这里有个很重要的差别。

**真正需要打开 AutoCAD 进行编辑时，才需要控制桌面软件。**

如果只是生成标准二维几何图纸，完全可以采用无界面生成方式，减少启动应用、菜单交互、界面失焦等问题。

这比“所有任务都必须让 AI 亲自操作桌面”更高效。

### 重点项目 E：Photoshop MCP

这条路线对平面设计实际价值很大。

<Link url="https://github.com/drmedia/photoshop-mcp" title="PhotoshopMCP"/> 使用 Photoshop UXP 插件作为桥接层，仓库公开文档涉及图层管理、调整图层、蒙版、选择区域、滤镜、文字编辑、文件导出等能力。

项目要求 Photoshop 25.0+，作者称已经在 Windows 的 Photoshop 27.8 上验证。值得借鉴的是它把操作分为 `read`、`edit`、`external`、`destructive` 等权限等级，而不是让模型默认拥有任意执行权限。<Cite ref="turn154401search0"/>

对于商业化复用，还要特别注意许可。

例如另一项目 <Link url="https://github.com/Immersive-Media-Technologies/photoshop-mcp-imt" title="PS-MCP-IMT"/> 虽然也提供较完整的自动化能力，但其新增代码采用非商业许可；不能直接把整个项目当成 MIT 软件自由商用。<Cite ref="turn154401search2"/>

## 四、真正的技术难点在哪里？

这些开源项目解决的是“AI 怎么调用软件”。

而一个类似建筑学长的成熟产品，还必须解决另外四个问题。

### 1. AI 怎么理解参考图？

例如用户上传一张建筑效果图，要求生成 SU 模型。

AI 需要先识别空间关系、几何比例、主要构件，再建立结构化模型数据。

但一张透视图通常不能可靠推导真实尺寸。

所以正确的策略不是 AI 凭空生成所谓的精确尺寸，而是：

**先识别 → 标记未知尺寸 → 使用用户指定尺寸或明确假设 → 生成模型 → 校验比例。**

如果没有这一步，就容易出现外观看似正确、工程尺寸完全错误的结果。

### 2. AI 怎么连续操作而不失控？

一个复杂场景可能包含几十到几百个操作。

不能让模型一次输出长达数百步的鼠标操作，然后直接执行。

更可靠的是以可验证任务单元运行：

| 阶段 | 执行动作 | 验证条件 |
|---|---|---|
| 建立文件 | 新建测试工程 | 文件可读、单位正确 |
| 创建几何 | 绘制基础空间 | 尺寸和对象数量正确 |
| 组织结构 | 创建图层或分组 | 命名、层级正确 |
| 添加细节 | 插入组件 | 坐标与碰撞关系合理 |
| 输出结果 | 保存原生文件 | 文件可重新打开 |
| 最终检查 | 获取截图与结构信息 | 图像、几何与任务要求一致 |

这里最重要的原则是：

**Agent 执行成功，不等于设计任务完成。**

只有实际软件对象、文件和输出经过检查，才能认为任务完成。

### 3. 怎么知道软件到底操作成功没有？

不能只相信 AI 返回的“执行成功”。

应该同时检查三类证据：

**软件状态证据**：当前打开的是哪个文件，工具是否连接，命令是否真的完成。

**结构证据**：图层、几何对象、尺寸、组件是否符合要求。

**文件证据**：目标文件是否实际存在，能否重新打开，文件内容是否完整。

截图只能验证视觉结果，不能替代结构检查。

### 4. 如何限制权限与防止误操作？

这一点不能忽视。

Blender 官方 MCP Server 的安全警告明确指出：由 LLM 生成的脚本可能在没有防护的情况下执行，存在删除数据或将信息发送到外部的风险，官方建议使用虚拟机或没有敏感信息的环境进行测试。<Cite ref="turn391258search1"/>

因此，实际系统至少需要做到：

把工作目录限制在明确授权的测试文件夹；禁止默认覆盖原文件；对删除、批量替换、执行任意脚本和对外传输进行额外审批；记录工具调用与原始执行结果；能够取消任务并保存恢复点。

这里尤其不建议一开始就给通用 Windows Agent 完整 PowerShell、文件系统和网络权限。

## 五、如果要自己实现类似的能力，应该怎么做？

结合你现有的三个项目，我不建议另起炉灶开发第四套大型平台。

更合理的方式是建立一个**独立的本地软件自动化能力模块**，让现有系统按职责使用它。

### 各系统的职责

| 项目 | 建议承担的职责 | 不建议做的事 |
|---|---|---|
| DESIGN-LAB | 分析参考图、生成设计方案、组织执行任务、检查设计结果 | 重造 Photoshop、Rhino 等软件 |
| WORK-LAB | 展示任务状态、执行进度、错误、审批与结果 | 重复实现一套完整 Agent |
| AAOS | 提供知识、项目上下文和统一能力入口 | 耦合所有设计软件的底层操作代码 |
| 本地自动化模块 | 连接 MCP、调用软件、执行任务并返回证据 | 承担 UI、知识库、长期规划等上层职责 |

三个项目最终可以共享同一个本地自动化模块，而不是分别安装和维护三套。

### 推荐的最小可行架构

```text
DESIGN-LAB / AAOS
        │
        ▼
   Task Orchestrator
    任务规划与审批
        │
        ▼
     MCP Router
        │
  ┌─────┼────────┬─────────┐
  ▼     ▼        ▼         ▼
PS MCP SU MCP  Rhino MCP  Windows MCP
  │     │        │         │
  ▼     ▼        ▼         ▼
 PS     SU      Rhino    Windows
        │
        ▼
   Result Validator
   文件与结果验证
        │
        ▼
    Task Status API
        │
        ▼
     WORK-LAB
```

这个架构的特点是：

新增软件只需要新增 Adapter，不需要重写 Agent；软件自身的原生接口优先；通用桌面操作只做补充；WORK-LAB 只展示真实执行状态。

它同样能接入 Codex、Claude Code 或其他支持 MCP 的 Agent，不必绑定单一模型厂商。

## 六、怎么验证它是否真的达到建筑学长的效果？

我建议不要先做全软件覆盖。

**第一阶段，只做一个 Windows + SketchUp 的完整闭环。**

测试任务可以设成：

> 在新的 SketchUp 测试文件中，建立一个 6000×4000×2800 mm 的简单室内空间，墙厚 200 mm，包含一扇宽 900 mm 的门、一扇宽 1500 mm 的窗。墙体、门窗、地面分别组织为组件或分组。先输出执行计划，等待批准后生成模型，最后检查尺寸、分组与文件完整性，并保存原生 `.skp` 文件和预览截图。

这一个测试就可以检验是否具备真正的桌面自动化能力。

建议采用以下验收标准：

| 验收项目 | 合格条件 |
|---|---|
| 软件连接 | Agent 可以识别当前 SketchUp 会话 |
| 真实建模 | 生成原生几何对象，不是贴图 |
| 精度 | 关键尺寸与指定值一致 |
| 对象组织 | 分组结构正确 |
| 持续编辑 | 能继续修改已生成模型 |
| 文件交付 | `.skp` 可保存并重新打开 |
| 异常处理 | 工具失败时停止，而不是伪报成功 |
| 证据 | 有实际执行日志、尺寸检查和截图 |

通过这组测试，再将相同控制框架接入 Photoshop、Rhino、CAD。

不要一开始同时接十几款软件。那样容易获得一个演示能力很多、实际操作却不稳定的系统。

## 八、最终研究结论

这次深入调查后，有三个结论比较明确。

**第一，建筑学长的真正技术亮点不是 AI 生成建筑图片，而是让 AI 将用户需求转化为实际专业软件操作。** 尤其是 CAD 和 SketchUp 的自动绘图、建模演示，具备一定参考价值。

**第二，它展示的核心能力并非无法复现。** 现在已经有 Windows 通用控制、SketchUp Ruby MCP、Rhino 官方 MCP、AutoCAD MCP、Photoshop UXP 自动化等可以复用的技术路线，其中 Rhino 的厂商官方方案尤其值得关注。

**第三，真正的技术壁垒已经从“能不能让 AI 操作软件”，转向“能否可靠地完成复杂任务并验证结果”。** 包括精确几何、可编辑文件、异常恢复、权限控制、任务审批和跨软件衔接。

我建议你的下一步不是复刻整个建筑学长，而是优先验证：

**Codex / Claude Code → 本地 MCP → SketchUp / Photoshop → 生成真实工程文件 → 自动检查。**

先让这一条链路在 Windows 上可靠运转，再扩展到多软件协同。

**调研状态：** 已核对公开产品演示、官方技术资料和多个开源仓库；尚未安装建筑学长客户端，也未对其内部协议进行抓包、源码分析或本地实测。因此，上述方案是有公开证据支持的技术选型，**不是已经完成的系统实现或测试结果**。

## 三、发现的几个重要技术细节

### 1. 它的自动运行循环并不是特殊的黑科技

本地 IL 显示，它使用了 `Microsoft.Extensions.AI.FunctionInvokingChatClient`。

报告记录的默认参数为：

- `MaximumIterationsPerRequest = 40`
- `MaximumConsecutiveErrorsPerRequest = 3`

我进一步核对了 <Link url="https://learn.microsoft.com/en-us/dotnet/api/microsoft.extensions.ai.functioninvokingchatclient" title="Microsoft 官方 SDK 文档"/>，这两个值确实是 SDK 的默认行为。<Cite refs={["turn937277search2","turn937277search0"]}/>

也就是说：

**模型调用工具 → 接收工具结果 → 再决定是否调用工具，这部分可以直接依靠成熟 SDK 实现。**

不需要为复刻这部分机制自己发明一套工具循环。

需要注意，40 是单次请求的循环次数上限，不是整个任务只能执行 40 次工具调用。

### 2. 它的自动继续机制并不等于智能审批

报告中的 IL 证明，自动继续模式会根据 `recommendedOption` 匹配选项，并尝试自动返回。

这其实更接近：

“系统推荐使用方案 A，如果启用自动继续，就按推荐选项往下执行。”

而不是：

“AI 判断这次操作绝对安全，所以批准执行。”

因此，这种机制不能直接用于自动授权覆盖文件、执行系统命令或修改专业设计软件中的重要工程。

### 3. 它的 Skills 与子 Agent 是两个不同机制

报告指出，主对话会通过 `GetToolsExcluding(GetRouterToolNames())` 排除技能路由工具。

但仍然保留读取技能知识的工具。

这意味着，至少在分析到的主对话路径中：

**主 Agent 可以读取 Skill 并自行执行，不必每个任务都启动子 Agent。**

这个设计是合理的。简单任务不需要增加多 Agent 调度成本。

### 4. 它的进度显示不一定代表真实任务进展

本地证据显示：

- 命令和 Python 工具可以发送活动心跳。
- 前端展示步骤开始、结束、耗时和成功失败。
- 会话可以恢复待办及上下文。

其中，命令执行的活动通知间隔约为 20 秒。

但是，**心跳只能证明执行器仍在活动，不能证明模型已经完成任何有效工作**。

你以前碰到过 AI 工具口头报告完成、实际没有完成的情况。这份报告中的执行事件和产物验证机制值得借鉴，但必须由实际文件、进程退出状态及独立检查共同确认结果。

### 5. 它的三维功能不一定依赖外部 SketchUp

这一点很有价值。

报告分析的室内和场地规划模块使用内嵌 Three.js 编辑器，涉及：

- 场景对象、几何、坐标、缩放。
- 建筑、道路、绿地、墙体、门窗等结构。
- 材质、光照、展示风格。
- 直接编辑、撤销重做。
- JSON 场景保存和 GLB 导出。

这意味着，它至少存在一条完全不同于专业软件控制的技术路线：

```text
参考图片 / 文字需求
       ↓
AI 生成结构化场景数据
       ↓
Three.js 固定编辑器
       ↓
自动创建几何结构
       ↓
人工调整 / 保存 / 导出
```

与另一条路线：

```text
参考图片 / 文字需求
       ↓
AI 规划专业软件操作
       ↓
MCP / 软件 API / 脚本
       ↓
SketchUp / CAD / Rhino
       ↓
保存原生工程文件
```

**这两条路线不能混为一谈。**

第一条用于快速三维场景生成和网页交互，第二条用于控制专业软件、交付原生工程。

从目前本地报告来看，第一条的静态证据更充分，第二条仍需要补证。

## 四、报告存在的关键缺口与需要纠正的方向

这份报告本身没有明显的“虚报完成”问题，但它的**开发目标偏大，而且没有优先解决你真正关心的专业软件自动化**。

### 问题 1：42 项开发任务过于偏向完整产品复刻

`backlog.json` 规划了 42 项任务，涉及：

- Agent Runtime 和工具系统。
- 内嵌三维编辑器。
- 知识库与长期记忆。
- 语音、画布、资源管理器。
- 账户、会员、计费。
- 桌面客户端与更新器。

如果目标是重新制作整个建筑学长，这种范围可以理解。

但如果目标是让 AI 自动操作 CAD、SketchUp、Photoshop、Blender 等软件，前期开发这些能力并不必要。

**我建议保留完整审计资料，但把实际研发目标缩小为「本地专业软件自动化执行层」。**

不要重复开发 Codex 或 Claude Code 已经具备的模型调用、工具循环、Skills 和 MCP 基础能力。

### 问题 2：最小验证任务选错了方向

报告建议首先开发：

> 读取图片 → AI 生成单 HTML 汇报 → 验证结果。

这能够验证通用 Agent 工具循环，但**不能验证专业软件自动化**。

按照你最初研究建筑学长的目的，第一条测试应该改为：

> 自然语言 → AI 规划 → 启动 SketchUp → 创建真实几何对象 → 修改模型 → 保存 `.skp` 文件 → 自动验证。

如果这个闭环无法完成，就还没有解决关键问题。

### 问题 3：协议未覆盖目标专业文件

当前 `schemas/task-spec.schema.json` 允许的输出格式只有：

`html`、`scene-json`、`glb`、`png`、`json`。

但它没有定义：

`skp`、`dwg`、`dxf`、`psd` 等专业文件格式。

对于完整建筑产品复刻，这属于后续扩展问题；对于我们要研究的专业软件自动化，则应该优先修正。

同样，工具权限也不能仅使用一个宽泛的 `mcp` 分类。

需要细化到**具体 MCP Server、具体 Tool、具体操作权限、文件访问范围**。

### 问题 4：动态 MCP 工具的安全边界尚未验证

报告指出，`GetToolsExcluding` 过滤部分内部工具后，还会追加已注册的 MCP 工具。

这不一定是漏洞，但意味着目前没有证据证明所有动态 MCP 工具都受到一致的权限策略约束。

同时，已发现的内置工具包括：

- `execute_command`
- `execute_powershell`
- `launch_app`
- `InstallPackages`

这些都属于存在真实副作用的能力。

**独立实现时，统一工具权限检查应该早于真实文件写入和命令执行，而不是等工具循环建成后才补充。**
