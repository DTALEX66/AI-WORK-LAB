## 1. Agenta —— 我建议你重点研究

它以前更像 **Prompt Management / LLMOps**，但现在已经明显朝“Agent Workspace”发展。

目前官方仓库描述已经是：

> open-source workspace for building and running agents

它现在支持：

**AGENTS.md + Skills + MCP + 多模型 + Agent Harness + 文件工作区 + 权限 + 后台 Agent + 定时/事件触发 + Trace + 成本 + 版本历史**。

更关键的是，它目前明确支持 **Claude Code、Codex 等 Harness**，还允许 Agent 通过 MCP 和 Composio 接入大量应用。citeturn265089view2

这已经不是：

> “帮我优化一下 Prompt。”

而是：

> 任务 → 生成 Agent → 选择模型 → 装载 Skills → 装载 MCP → 执行 → Trace → 评价 → 改 Prompt/配置 → 再执行。

这和你 WORK-LAB 原本想做的“治理层 + Harness + Skills + MCP + Agent 编排”已经出现明显重叠。

urlAgenta GitHubhttps://github.com/Agenta-AI/agenta

# 最有意思的是 DSPy

如果你真正想要：

> **AI 自动帮 AI 写 Prompt**

就要看 DSPy。

它和普通 Prompt Assistant 思想完全不一样。

传统：

```text
人
 ↓
写 Prompt
 ↓
LLM
```

DSPy：

```text
任务
+
样本
+
评价指标
        ↓
Optimizer
        ↓
自动生成 Prompt
        ↓
运行
        ↓
评价
        ↓
再生成 Prompt
        ↓
再测试
        ↓
找到更优 Prompt
```

目前它包含 MIPROv2、GEPA、SIMBA、COPRO 等 Optimizer，可以自动优化自然语言 Instructions 和 Few-shot 示例。citeturn503587search4

这部分我认为未来应该直接进入你的 **AAOS 学习闭环**。


## 最值得你研究的是 Backstage 的思想

Backstage 本来就是 Spotify 为“软件越来越多”这个问题做出来的。

官方自己描述的核心就是：

它拥有：

**Software Catalog**

**Plugin System**

**统一搜索**

**工具入口**

+

**服务页面**

+

**组件关系**

+

**模板**

+

**文档**

Backstage 官方直接说，其 Software Catalog 可以把不同基础设施工具组织到一个 Developer Portal 里，减少用户不断在不同 UI 之间切换。citeturn629120search3turn629120search4

这其实非常像你以后 WORK-LAB 应该变成的东西。

但我**不建议你直接拿 Backstage 当最终产品 UI**。

因为它：

- 太偏 Kubernetes / DevOps

但是它的：

> **Catalog + Plugin + Entity + Unified Portal**

这套架构，非常值得直接吸收到 WORK-LAB。

# 最重要的设计原则：不要把所有软件塞进 iframe

很多“统一工作台”最后都会犯这个错：

```text
左边菜单
 ├─ n8n iframe
 ├─ GitHub iframe
 ├─ Dify iframe
 ├─ OpenWebUI iframe
 └─ ...
```

看起来统一了。

实际上只是：

> **浏览器收藏夹 Pro Max。**

正确设计应该有四种接入方式：

```text
                WORK-LAB
                    │
      ┌─────────────┼─────────────┐
      ↓             ↓             ↓
   API/MCP        UI Embed       Deep Link
   真调用         少量嵌入        打开外部软件
      │                           │
      ↓                           ↓
 Background                    Native App
 Execution
```

只有需要查看原始复杂 UI 时才真正进入对应软件。

平时所有东西都在 WORK-LAB 里完成。

比如：

```yaml
id: codex

name: OpenAI Codex

  - coding-agent
  - cli
  - external-app

  - code
  - audit
  - refactor
  - test

protocols:
  - cli
  - mcp

projects:
  - AAOS
  - WORK-LAB
  - DESIGN-LAB

open:
  mode: native

context:
  accept:
    - project
    - task
    - files
    - prompt
```

再比如：

```yaml
id: design-lab

name: DESIGN-LAB

type:
  - internal-service
  - domain-app

capabilities:
  - graphic-design
  - ui-design
  - video
  - image-generation

protocols:
  - api
  - mcp
  - web

knowledge:
  provider: AAOS

workflow:
  provider: WORK-LAB
```

这样 WORK-LAB 就知道：

> 每个软件是什么、能干什么、怎么调用、能接受什么 Context。
