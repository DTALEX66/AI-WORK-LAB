## 一、总判断

ArcheAxis OS **不应该再嵌入一个 RAGFlow、Letta、Cognee、Agno 式的完整平台**。这会形成第二套：

- 数据库和记忆系统
- Agent 生命周期
- 用户权限
- 工作流状态
- 日志与评测体系
- 前端管理台

最终会削弱你的 OS，而不是增强它。

正确路线是：

> **OS 自己掌握事实、状态、合同、作业、权限、审计和人类确认；开源项目只作为可替换能力提供器。**

建议形成以下基础结构：

```text
SQLite                 = 事实、版本、关系、Job、Outbox、审计源
Local Artifact Store   = PDF、图片、音视频、课程包、生成物
LanceDB                 = 可重建的文本/图像/多模态检索索引
Docling/OCR Providers   = 文档解析能力
llama.cpp               = 本地模型运行时
PydanticAI              = 类型化模型与工具调用
LangGraph               = 可选的长任务编排适配器
MCP                     = 外部能力与插件边界
OpenTelemetry           = 统一可观测事件
OpenInference           = LLM、检索、Agent Trace 语义
DeepEval/Ragas/Promptfoo = 质量、安全和回归测试
React Flow              = 观心工作台图谱与运行链路
marimo                  = 可复现实验与交互模拟
```

# 二、最高优先级：建议直接接入

## 1. 文档理解：Docling + PaddleOCR-VL + GLM-OCR

### 主解析器：Docling

Docling 最适合作为 ArcheAxis OS 的默认 `ParserProvider`：

- PDF、DOCX、PPTX、XLSX、HTML、EPUB、图片、音频、邮件等统一输入
- 保留版面、阅读顺序、表格、公式、图表
- 输出统一的 `DoclingDocument`
- MIT 许可证
- 支持 Windows、本地执行及 Python API

它最适合承担“标准文档 → 结构化中间表示”的主干。citeturn176561search0turn176561search1

### 中文复杂扫描件：PaddleOCR-VL 1.6

PaddleOCR-VL 1.6 是中文扫描件、表格、公式、图表、印章和复杂版面的重点补充。其模型卡显示为 Apache-2.0、约 1B 参数，可输出 Markdown 和 JSON，并重点支持中文及多语言复杂文档。citeturn146107search1turn156382search3

### 轻量第二意见：GLM-OCR

GLM-OCR 约 1B 参数、MIT 许可证，支持复杂文档、公式、表格和结构化提取，适合做：

- PaddleOCR-VL 失败后的备用
- 双模型交叉验证
- 中文页面质量仲裁

citeturn146107search4

### 推荐路由

```text
数字原生 PDF / Office / HTML
    → Docling

中文扫描件 / 复杂表格 / 公式 / 印章
    → PaddleOCR-VL

低置信度页面 / 关键文档复核
    → GLM-OCR

两次结果差异较大
    → 人工审核队列
```

不要把 OCR 结果直接写入正式知识库。应先生成：

```text
SourceArtifactV1
→ DocumentParseV1
→ ParseEvidenceV1
→ Human/Rule Verification
→ KnowledgeUnitV1
```

## 2. 网页和 GitHub 仓库摄取：Crawl4AI + Repomix

### Crawl4AI

适合把网页变成适合模型处理的干净 Markdown，并保留链接、结构和页面信息。它可以增强你的 Inspiration Research、网页捕获和证据包流水线。citeturn750230search4

但它近期发布说明中出现过 SSRF 修复及供应链依赖替换，因此必须：

- 锁定精确版本
- 单独浏览器 Worker
- 网络出口白名单
- 禁止浏览器进程直接访问主数据库
- 页面内容视为不可信输入
- 运行后净化 HTML、脚本和隐藏提示词

citeturn750230search3turn750230search4

### Repomix

Repomix 可以把一个 GitHub 仓库压缩为：

- 目录树
- 文件内容
- Token 统计
- 关键代码上下文
- Tree-sitter 压缩结果

非常适合接入你现有的：

```text
GitHub URL
→ Repository Snapshot
→ Repomix Package
→ Architecture Analysis
→ ResearchPackageV1
→ Human Review
→ Knowledge Candidate
```

它应当是代码研究的预处理器，而不是唯一代码解析器。citeturn750230search2

## 3. 本地检索：LanceDB + Qwen3 Embedding/Reranker

### 索引层：LanceDB

LanceDB 与你的本地优先、单仓模块化单体很匹配：

- 嵌入式运行，不必先部署独立服务
- 向量检索、全文检索、SQL 过滤
- 文本与多模态数据
- 数据版本能力
- Python、TypeScript、Rust 支持
- Apache-2.0

建议 SQLite 继续做事实源，LanceDB 只做“随时可以重建的派生索引”。citeturn602843search0

```text
SQLite：真实知识、版本、来源、权限、审核状态
LanceDB：Chunk、Embedding、图像向量、召回索引
```

### 常驻文本模型

建议：

- `Qwen3-Embedding-0.6B`
- `Qwen3-Reranker-0.6B`

Embedding 模型支持 100 多种语言、32K 上下文和可调整向量维度；0.6B 版本模型文件约 1.21GB，适合你的 3060 Ti 环境作为常驻或半常驻模型。citeturn242159search1turn242159search6

### 多模态检索

- `Qwen3-VL-Embedding-2B`

可处理文字、图片、截图和视频内容，适合展厅设计图、课程截图、界面、图表和多媒体知识检索。2B reranker 原始模型文件约 4.27GB，在 8GB 显存上建议量化、CPU 卸载，并与 OCR 模型串行运行。citeturn242159search0turn242159search2turn242159search3

## 5. 本地模型运行时：llama.cpp

对你的 Windows 主机和 3060 Ti，建议将 `llama.cpp` 设为正式本地推理底座：

- GGUF 量化模型
- Windows 支持
- CPU/GPU 混合卸载
- OpenAI 兼容服务

- JSON Grammar 和结构化输出
- 多模态支持

本地模型建议：

| 任务 | 推荐 |
|---|---|
| 通用本地推理 | Qwen3.5-4B GGUF Q4 |
| 文本向量 | Qwen3-Embedding-0.6B |
| 文本重排 | Qwen3-Reranker-0.6B |

# 三、记忆系统：吸收 Graphiti 思想，不整体接入

Graphiti 最值得吸收的是数据语义：

- 事实有效时间
- 事实写入时间
- Episode 来源
- 事实失效而不是直接删除
- 本体版本
- 实体、关系、证据分离
- 语义、关键词、图关系混合检索

建议自己实现：

```text
- fact_id
- subject_id
- predicate
- object_value

- valid_to
- recorded_at
```

Mem0、Letta、Cognee 都可以作为外部对照和算法研究对象，但不建议作为核心依赖，因为它们都在不同程度上提供自己的 Agent、记忆、存储和服务平台。citeturn896835search0turn896835search1turn723416view2

# 三、为什么不建议把 OpenHuman 直接当最终 OS

## 1. 它本身就是另一个完整 OS

OpenHuman已经拥有自己的：

- Memory Tree
- Obsidian Wiki
- Agent Runtime
- Workflow Engine
- Model Router
- Skills
- Goals/Todos
- Scheduler
- Integrations
- 审批系统
- 前端工作台

整合进去会产生两套事实源：

```text
ArcheAxis SQLite   ←→   OpenHuman SQLite
ArcheAxis Job      ←→   OpenHuman Run
ArcheAxis Memory   ←→   Memory Tree
ArcheAxis Audit    ←→   OpenHuman Journal
ArcheAxis Workflow ←→   TinyFlows
```

最后很难判断谁拥有最终状态。

## 2. “本地优先”不等于“完全本地”

OpenHuman 的 Memory Tree、Markdown Wiki 和部分本地模型状态保存在本机；但其默认架构中，LLM 调用、OAuth Token、Web Search、集成工具代理和 TTS 都由 OpenHuman 后端处理。官方文档还明确写到 OAuth Token 存储在后端，Core 默认不直接调用第三方集成 API。citeturn106976view1

本地 AI 虽支持 Ollama 和 LM Studio，但默认关闭；聊天、强推理、视觉、STT、TTS、Web Search 仍默认走云端。即使配置本地模型，失联时还可能自动回退远端，这和你要求的明确模型控制、DeepSeek/Kimi API 路由不完全一致。citeturn641460view0

更重要的是，最新架构文档已经写明：原来客户端本地的编排图引擎被移除，客户端正在转为“hosted brain”的薄参与者。它不是完全独立的本地 Agent OS。citeturn679225view0

## 3. GPL-3.0 许可证影响

| 项目 | 许可证 | 建议 |
|---|---|---|
| OpenHuman | GPL-3.0 | 不直接合并到 AXOS 核心 |
| TinyAgents | GPL-3.0 | 独立进程验证或只吸收设计 |
| TinyFlows | GPL-3.0-or-later | 不直接复制到非 GPL 核心 |
| TinyJuice | GPL-3.0 | 独立 CLI/Sidecar 或重写思想 |
| TinyCortex | MIT | 可以直接做核心技术验证 |

OpenHuman 自用没有大问题；但一旦未来分发融合后的软件，GPL 可能要求派生部分遵守相应开源义务。即便采用进程隔离，也仍需在正式商业化前做许可证审查。

TinyJuice 最值得吸收的不是“压缩率”，而是 **CCR 可恢复压缩**：

```text
原始工具输出
→ 压缩视图
→ 被省略内容生成 Recovery Token
→ Agent 需要时精确取回原文
```

它已经针对以下内容做专门处理：

- JSON
- Shell Log
- 测试日志
- Git Diff
- 搜索结果
- 源代码
- HTML
- Docker/Kubernetes 输出

而且不会无提示地删内容。任何有损压缩都应保留恢复入口。fileciteturn18file0L16-L29

```text
- source_artifact_id
- strategy
- original_size
- compressed_size

- expires_at
- checksum
```

适合放到：

# 应该从 OpenHuman 吸收的能力

## 1. Human-first 交互体系

吸收：

- Agent 提议任务，而不是直接执行
- 可视化查看任务计划
- 高风险动作单独确认
- 运行过程中允许暂停、修改、继续
- 用户能看到 Agent 当前在做什么
- 失败时返回原因，而不是静默停止
- 对话、任务、目标、待办形成统一上下文

这部分应该强化 **元枢·观心 Human Console**，不是引入 OpenHuman 客户端。

## 2. Durable Agent Graph

OpenHuman 使用 TinyAgents 将 Agent 运行组织成带检查点的状态图，支持暂停、恢复、条件路由、子 Agent、递归深度控制和统一成本统计。fileciteturn15file0L67-L92

AXOS 应吸收成自己的合同：

```text
AgentRunV1
├─ root_run_id
├─ parent_run_id
├─ graph_version
├─ current_node
├─ checkpoint_id
├─ recursion_depth
├─ status
├─ usage
├─ cost
├─ failure_reason
└─ resume_token
```

这会增强你现在的：

```text
TaskPack
→ Agent
→ Tool
→ Trace
→ Eval
```

使它真正具备中断恢复和运行回放。

## 3. 可视化工作流审批

OpenHuman 的工作流逻辑是：

```text
Agent 生成工作流
→ 编译与校验
→ 用户在画布审核
→ 保存
→ 按触发条件执行
→ 高风险节点暂停审批
```

TinyFlows 已包含条件、分支、并行、合并、子工作流、重试、错误路由和人工审批。fileciteturn16file0L22-L67

AXOS 应吸收为：

```text
WorkflowDraftV1
→ WorkflowValidationV1
→ WorkflowApprovalV1
→ CompiledWorkflowV1
→ WorkflowRunV1
```

前端仍由 AXOS 自己使用 React Flow 构建。

## 4. Memory Tree 与“主动遗忘”

TinyCortex 最值得吸收的是：

- Markdown 或标准知识单元作为可检查源
- SQLite、向量、图谱和摘要树作为派生索引
- 摄取前进行价值过滤
- 新鲜度衰减
- 用户互动权重
- Summary Tree
- 噪声主动淘汰
- 来源与外部数据污染标记
- 索引可以从正式内容重建

fileciteturn17file0L19-L47

这应该加入 AXOS 的记忆设计，但不能覆盖正式知识库：

```text
AXOS Knowledge Facts
    = 已审核、带版本、带证据的正式知识

AXOS Cognitive Memory
    = 偏好、交互、任务经验、临时关系、热度与新鲜度

Vector / Graph / Summary Tree
    = 可重建索引
```

## 5. SuperContext 式任务预取

OpenHuman 在用户问题正式交给主模型前，会预先检索相关记忆、文件和上下文。fileciteturn4file0L83-L89

AXOS 可以增加：

```text
Human Intent
→ Intent Classifier
→ Context Scout
   ├─ 项目知识
   ├─ 用户偏好
   ├─ 最近任务
   ├─ 文件变化
   ├─ Git 状态
   └─ 失败案例
→ ContextPackV1
→ Hermes / Codex / Agent
```

这比让 Hermes 自己漫无目的搜索整个环境更稳定。

## 6. 可恢复的上下文压缩

TinyJuice 的核心价值是：

```text
完整工具输出
→ 高信号压缩结果
→ 省略内容保留 Recovery Token
→ Agent 需要时读取原文
```

不会把被删除的信息永久丢失。fileciteturn18file0L16-L29

这特别适合：

- Codex 长日志
- Hermes 工具输出
- Git Diff
- 测试日志
- 搜索结果
- 大型 JSON
- Docker 日志
- 仓库文件扫描

应该加入 `Context Pack` 和 `Artifact Store` 之间，而不是单纯依赖模型总结。

## 7. 分层 Agent 编排

吸收 OpenHuman 的思路：

```text
Reflex Agent
→ 快速分类、判断、路由

Reasoning Core
→ 拆解任务、制定计划

Worker Agents
→ 研究、编码、验证、整理

Reviewer
→ 检查结果、证据与风险
```

但在 AXOS 中重新命名和实现：

```text
Human
→ Intent Router
→ Hermes Orchestrator
→ Codex / Research / Knowledge / Eval Workers
→ AXOS Verifier
→ Human Approval
```

不是把 OpenHuman 的 Agent 体系搬进来。

## 8. 运行日志与成本回放

OpenHuman/TinyAgents 将父子 Agent 的事件、调用量和成本汇总到同一运行链。fileciteturn15file0L44-L60

AXOS 应吸收：

- 每次模型调用
- 每个工具调用
- 输入输出 Token
- 延迟
- 模型费用
- 重试原因
- 失败节点
- 人工修改
- 文件变化
- 测试结果
- 最终交付物

全部挂载到一个 `root_run_id`。

## 9. Provider 与 Capability Registry

吸收 TinyAgents/TinyFlows 的宿主注入模式：

```text
模型、工具、HTTP、代码执行、存储、凭据
全部通过接口注入
```

TinyFlows 本身不保存真实密钥，只接受不透明的 `connection_ref`，由宿主解析。fileciteturn16file0L56-L64

对应 AXOS：

```text
ModelProvider
ToolProvider
MemoryProvider
ParserProvider
CodeExecutorProvider
CredentialProvider
WorkflowProvider
EvalProvider
```

这样 Hermes、Codex、DeepSeek、Kimi、本地模型都只是 Provider，不会绑死 OS。

# 更新后的吸收优先级

| OpenHuman 能力 | AXOS 处理方式 | 优先级 |
|---|---|---:|
| TinyCortex 记忆算法 | PoC 后拆解进入 Memory Provider | A |
| TinyJuice 可恢复压缩 | 先 Sidecar 验证，再自研兼容实现 | A |
| TinyAgents Durable Graph | 吸收运行合同、Checkpoint、递归追踪 | A |
| TinyFlows Workflow Schema | 吸收节点合同、审批和恢复机制 | A |
| SuperContext | 加入 Context Scout | A |
| Human-first UX | 融入元枢·观心 | A |
| Agent Run Replay | 融入 Audit 与 Eval | A |
| Model Routing | 借鉴规则，不照搬平台账号体系 | B |
| Obsidian Wiki 映射 | 与现有 Obsidian-Assistance 融合 | B |
| 多渠道消息 | 后期做 Channel Provider | C |
| 会议 Agent | 后期独立能力包 | C |
| Agent Economy / 支付 | 当前不吸收 | 暂缓 |
| OpenHuman 客户端和后端 | 不接入 | 排除 |

## 修正后的最终结论

**OpenHuman 整体不是 AXOS 的入口、替代品或依赖平台。**

它在你的开源调研体系中应该被定义为：

> **“综合能力参考项目”：拆解其记忆、编排、工作流、压缩、审批、可观测性和本地桌面工程能力，并按照 AXOS 自己的合同重新实现或通过 Provider 接入。**

上一轮所说的“OpenHuman 临时入口”“替换 Human Console”应当全部删除。AXOS 的线路始终是：

```text
你
→ ArcheAxis Human
→ ArcheAxis Control Plane
→ Hermes / Codex / 其他 Agent
→ 模型与工具
→ ArcheAxis Memory / Audit / Eval
→ 返回 ArcheAxis Human
```
