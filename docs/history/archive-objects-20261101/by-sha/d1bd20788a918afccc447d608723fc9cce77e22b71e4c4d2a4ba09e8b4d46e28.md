## 二、为什么你找了那么多参考、做了那么多任务包，还是没达到效果？

### 1. “能力必须保留”，被过度翻译成了“能力必须经常出现在眼前”

你要求完整保留 AAOS 的历史能力、未来蓝图，这个要求没有错。

但我建议把三件事明确分开：

**能力保留，是产品范围；入口可发现，是导航设计；当前页面显示什么，是任务设计。**

这三件事不应该绑定成一件事。

例如，你正在复习时，未来的空间记忆、仿真、其他学习能力可以继续存在，也可以通过折叠菜单和搜索找到，但不需要一直与当前问题争夺注意力。来源和版本必须可靠，也不代表每个工作面都要同时展开全部元数据。

你的 10 月 2 日任务包其实已经写明：历史能力不在当前一级导航，不等于被删除；对象详情也不应继续膨胀一级导航。问题在于，这个原则还需要真正落到屏幕的默认展开方式上。fileciteturn2file1L123-L124 fileciteturn2file4L367-L374

**保留功能，不等于保留它当前的视觉占用。**

### 2. 你有很多“设计文件”，但设计基准还没有真正稳定

这里有一个很具体的例子。

10 月 2 日的最终任务包，建议的一级分组是：

`Home / Knowledge / Learning / AI Learning / Blueprint·Explore / System`

而同日的调整总览仍是：

`工作台 / 资料与知识 / 证据 / 学习 / 机器知识 / 系统`

这是两种不同的组织方式。**我不是说其中哪一版已经获批，也不是建议你现在再换导航；而是它们不能同时成为执行器唯一的复刻标准。**fileciteturn2file4L324-L340 fileciteturn4file0L6-L7

如果执行器今天按照一套导航、明天继承另一套页面布局，后天又叠加新的主题，它可能每次都完成了任务，但最终没有形成一个统一产品。

**统一视觉，不只是大家使用同一个颜色值，而是大家服从同一套页面主次、布局和交互决策。**

### 3. 之前的交付，过于强调“完整”，没有把“好看”变成必须通过的关卡

这部分我也需要纠正之前给你的帮助方式。

回看这些材料，我之前给出的工作重点，明显偏向全历史、全能力、全页面、迁移映射、状态覆盖和工程边界。这些能减少功能遗漏，**但不能替代对一张真实界面的精修和否决。**

9 月 28 日的方案其实已经要求“逐页运行、截图、修正”，也明确说不能只交建议或 `build green`。**但文档中写了截图验收，不等于真的有一张经过你认可、被原生准确还原的质量样板。**fileciteturn1file0L142-L150 fileciteturn1file0L184-L188

所以，不能把现在的结果简单归咎于你不会描述，或者执行模型能力不够。

**前面给你的部分参考，本身就还没有达到应该要求执行器复刻的视觉上限。照着它做到很像，也不一定会变得很好看。**

## 三、网上那些好看的、好用的产品，到底多做了什么？

上面的 Linear 可以作为一个观察对象，但不是让 AAOS 变成项目管理软件。

Linear 在官方改版复盘中，重点讲的是：调整侧栏、标题栏和面板，减少视觉噪声，重新处理对齐、导航密度与层级，并在不同视图和状态中反复测试。它并不是简单给旧界面换了一个深色皮肤。citeturn607263search2

更贴近 AAOS 阅读场景的是 Readwise Reader。它允许隐藏左右侧栏、设置默认面板可见性；长篇阅读模式则让操作工具退后，突出阅读本身。**它没有因为具备很多功能，就要求这些功能在阅读时全部保持显眼。**citeturn521934search2turn521934search15

这两个例子值得借鉴的不是颜色，而是：

> **功能越多，越要认真决定“此刻不显示什么”。**

你现在比较容易得到的是一套“所有部分都合理存在”的界面；真正精致的产品，还需要进一步做到“所有部分都在恰当的时机出现”。

还有一点需要区分：**一张精心挑选的官网展示图，并不能证明软件好用。**对 AAOS 有价值的参考，应该是打开真实资料之后的工作状态，而不只是带光效的首页。

我建议参考时直接问：长标题会怎样？侧栏展开后还剩多少阅读空间？找不到内容时怎么办？打开来源后能否回到原位置？这些才是从“漂亮截图”走向“好用软件”的部分。

## 四、是不是缺更强的模型、设计技能，或者选错了 Avalonia？

**目前没有足够依据，把你看到的这些问题归因于 Avalonia。**

Avalonia 官方提供了控件主题、控件模板、交互状态样式和紧凑密度等定制机制。你现在暴露出的主次、留白、字号、边框、导航展开方式等问题，都有明确的设计与实现调整空间，不需要先通过更换桌面框架来解决。citeturn607263search3turn607263search1

但也不能假设网页设计会自动变成同样精致的原生界面。**HTML 预览和 Avalonia 实现之间，仍然需要逐项落实主题、尺寸、字体、控件状态和窗口缩放。**

至于技能和组件库，我对 AAOS 的建议是：

**它们可以帮助执行设计，不能替你决定设计。**

一个组件库能提供不错的按钮和输入框，却不会自动判断“复习页面应不应该展示整套未来能力”。一个设计技能能给出排版规则，却不会自动保证所有 Agent 都遵守同一份最终母版。你之前的调研文件也已经明确区分了 Skill、MCP 和 UI 库的职责。fileciteturn1file0L55-L70

你现在缺的，确实包括**设计负责人的工作**：选方向、做取舍、看实物、指出具体问题、不满意就不通过。

这不等于必须先雇一个全职设计师；但这份工作不能缺席，也不能全部交给工程执行器自行猜测。

## 五、AAOS 接下来应该怎么改，才不继续消耗 Token？

**不要再立即启动“全页面全面美化”。先在现有工程里，把一个高频工作面做成真正满意的样板。**

我建议选择 **阅读＋证据定位页**，而不是继续打磨首页。因为它最能检验 AAOS 的核心体验：中文长文本、导航、来源、上下文操作和内容层次。

### 第一步：先改变这张页面的主次，不加新功能

我的建议是让**正在阅读的资料成为明确主角**。

左边优先服务当前资料的目录，整体功能导航保持可收起；右边的来源、版本、关系保留，但按需要展开，涉及证据复核时可以固定显示。正文区域不要再承担大量产品原理说明。未来能力仍然可发现，但不要默认挤在阅读任务周围。

这不是删除功能，也不是另做一个壳，而是在现有界面内重新安排默认状态。

### 第二步：先修排版和层次，再处理装饰

仍然可以沿用现有黑白或低饱和深色方向，不需要先换 Logo、换主色。

这一轮应集中检查：正文是否突出，辅助文字是否过小，标题与元数据是否分得开，边框是否过多，同一条信息是否在左右重复出现，主操作是否容易找到。

**动效可以保留，但应服务于证据定位、面板展开、答案揭示和状态变化，而不是拿发光效果补救排版。**

### 第三步：用同一份资料，在同一窗口尺寸下对照原生结果

视觉预览可以使用明确标注的样例；正式体验验收必须使用真实资料，不能用假数据冒充接通。

实际检查一条很短的操作过程就够有价值：

**打开资料 → 阅读 → 定位一条证据 → 返回原阅读位置。**

这条过程中，既看截图，也看是否丢失位置、是否需要反复找按钮、面板是否挡住正文。编译通过、功能通过和视觉通过，应当分别记录，不能相互替代。你之前的方案也已经要求真实窗口、中文长文本、DPI 和交互状态检查。fileciteturn1file0L144-L150

### 第四步：你认可这张样板之后，再扩展其他页面

之后再把它的标题、列表、按钮、标签、间距、侧栏状态复用到资料库和复习页，而不是让每个页面、每个 Agent 再设计一遍。

**先让一页真正达到目标，再复制设计规则；不要先复制十几页，再一起承受同一个缺陷。**

---

所以，回答你“为什么别人做得出来，我做不出来”：

**不是你没有机会做到，而是目前投入更多发生在“描述完整系统”和“推动代码完成”上，中间那段决定产品观感的工作——挑选母版、压低辅助信息、精修排版、用真实内容反复否决和修改——没有得到同等强度的执行。**

你现在需要的不是更多“商业级、苹果风、高级感”的形容词，而是更具体的裁决：**这个菜单默认收起，这条说明移到详情，这个标题提高层级，这个边框去掉，这张页面没有达到参考质量就不能扩散。**

**下一步请发一张你现在实际运行的 AAOS 完整窗口截图，优先阅读页或资料库页，不要拼图或缩小。**这样就能把“参考设计本身的问题”和“原生实现还原走样的问题”分开，定位真正需要改的那一层。

# 一、重新判断 AAOS：哪些事情应该继续，哪些应该停止

## 1. DSH 的进展是真正的进展，但证明范围需要收窄

DSH 报告了：19 份真实资料形成来源、转换、锚点、质量与知识候选；15 条界面路由读回；Rust、Python 测试和桌面构建通过。**本轮我将这些作为 DSH 的书面回报，而不是我重新运行后的验证结果。**fileciteturn4file0L6-L11

这份回报改变了判断：不能再把 AAOS 说成“只有界面、后端几乎没有真实数据”。

但还要分清：

| 已报告的结果 | 可以支持什么 | 不能直接支持什么 |
|---|---|---|
| 19 份真实资料转换并形成候选 | 有真实输入，不只是空壳 | 提取内容完全正确、候选全部值得接受 |
| 原件字节一致 | 原件保全的完整性 | 转换内容、语义和知识结论的准确性 |
| 15 条路由读回 | 相应接口或页面数据通路有进展 | 所有操作顺畅、视觉达标、安装版完整可用 |
| 测试与构建通过 | 覆盖到的检查通过 | 未覆盖场景不存在问题、可以直接替换正式库 |

尤其“19/19 转换与原件字节全等”应该在报告中拆成**转换成功率**和**归档原件完整性**两个指标，避免被读成“转换准确率 100%”。这与文档要求“精度必须有真人真值与预测配对”是一致的。fileciteturn4file0L11-L17

## 2. 我不建议现在启动“全面 Agent 化重构”

我的明确建议是：

> **AAOS 是知识与学习工作台，Agent 是其中一种完成任务的方式，不是所有页面的替代品。**

阅读、检索、批注、编辑、复习，都应该可以直接操作，不必先向 Agent 发一句话。

Agent 适合处理的是：“整理这一组资料”“比较这些来源的冲突”“根据我的错误生成下一轮练习”这类跨步骤目标。建议以现有能力为工具，增加有限步骤、预算、取消、恢复和人工确认；**不同时新增通用多 Agent 编排、任意 Shell 执行或另一套工作流平台。**

原因很具体：DSH 已经记录了**能力映射分散三处，导致已随包发布的 worker 仍返回 503**。此时扩大调度能力，只会让更多任务依赖这条尚不稳定的链路。fileciteturn4file0L53-L53

## 3. 开源吸收应该继续，但停止用“项目数量”衡量成果

这份 DSH 文档证明了部分产品能力的进展，**没有提供逐个供体的代码、许可、接入与验收清单，因此不能据此更新为“开源池吸收完成”。**

我建议把后续吸收分成三类，而不是把所有东西都叫“集成”：

| 类型 | 成果应该是什么 |
|---|---|
| **算法／能力吸收** | 一个可调用、可评测、可替换的实现 |
| **交互／界面吸收** | 一个在 AAOS 原生界面中可实际使用的交互 |
| **参考研究** | 清楚写明借鉴点、排除点；不声称运行能力已接通 |

**从成熟软件学会一个好的证据复核流程，可能比再接入五个尚未使用的项目更有价值。**

# 三、A 组：真人复核、清理、安装与合并

先纠正分类：**A1 的知识判断必须由真实的人承担；A2/A3/A4 并不天然要求人手工输入每条命令。**它们需要明确授权、合适权限和可追溯执行，不能把“需要 Owner 决策”扩大成“所有工程动作都停下来等人点”。

## A1．19 条知识候选的真人复核

**结论：保留 human-only；不追求 19 条全部接受，追求每条都有有依据的处置。**

**理由：**路径的主要风险是跨页面后审错对象、接受了错误版本，以及把“原文确实这么写”混同为“该结论客观正确”。当前路径本身不能证明这些风险已被处理。fileciteturn4file0L25-L25

**代价／风险：**可能产生拒绝和待补证，这是正常结果。若接受后直接覆盖候选或删除旧版本，纠错成本会显著增加。

**具体下一步：**

复核界面至少同时显示**候选 ID／版本、来源 ID／版本、原文定位和将产生的变更**。最小判定清单为：

1. 原文能打开，锚点确实落在支持这条候选的段落、页码或时间段。
2. 主体、数值、单位、时间、否定词与条件没有被提取错。
3. 候选没有把作者观点升级成事实，或把局部结论推广成普遍规律。
4. 已知冲突没有被隐藏；不确定内容可以保持待补证。
5. 提交后能看到复核回执；接受记录可通过追加纠正、撤销认可或新版本替代，而不是擦除历史。

提交时校验预期版本，版本变化则要求重新查看。**“填写复核人”只是署名，不足以单独证明真人身份**；需要检查服务器的权限校验不是仅相信客户端传入的名字或 `actor=human`。

在不可逆行为尚未查清前，先在备份副本试验接受、拒绝与纠正；不能让自动化脚本冒充真人完成正式复核。

## A2．33 个临时目录、7.8 GB，是否值得夺取所有权？

**结论：默认不值得为 7.8 GB 冒险修改未知账户的数据；先证明是可再生的 AAOS 临时产物，再按目录处理。**

**理由：**SID 后缀不同只能说明账户不同，不能证明目录无用。`takeown` 会改变所有者，`icacls` 会改变访问控制；不是无损的“解锁按钮”。citeturn647965search0turn647965search1

**代价／风险：**原 ACL 读不出时，无法承诺完整恢复原权限；递归操作还可能扩大范围。禁止对磁盘根、用户目录根、项目正式数据根执行夺权。

**具体下一步：**

先用运行记录核验路径、创建时间、生成任务和可再生性；停止相关进程，核查目录树中的符号链接／目录联接。**无法排除真实库、原件或指向其他目录的链接，就保留。**

以下只适用于已核验的**一个具体目录**，在管理员 PowerShell 中执行；路径必须替换为现场确认值：

```powershell
$Target = 'X:\已核验的临时父目录\一个具体运行目录'
$Sid = [Security.Principal.WindowsIdentity]::GetCurrent().User.Value

# 保存当前能读取到的 DACL；不等于完整备份了所有权与全部安全描述符
& icacls.exe $Target /save "$env:TEMP\aaos-temp-acl.txt" /T /L

# 只对已确认可删除且无链接逃逸的目录操作
& takeown.exe /F $Target /A /R /D N
if ($LASTEXITCODE -ne 0) { throw '夺权存在失败，停止清理并检查输出' }

& icacls.exe $Target /grant "*${Sid}:(OI)(CI)F" /T /L
if ($LASTEXITCODE -ne 0) { throw '授权存在失败，停止清理并检查输出' }

# 仅预览，不执行删除
Remove-Item -LiteralPath $Target -Recurse -Force -WhatIf
```

`/D N` 会跳过无法列出的目录；**出现跳过也应停止，不改成 `/D Y` 强推**。微软文档说明 `/D Y` 在相关场景会替换目录权限。citeturn647965search0

核验无误后先隔离重命名，确认 AAOS 正常冷启动且不再依赖这些目录，最后再由操作者确认删除。清理不是当前交付主线的阻塞项。

## A3．安装／替换／回滚成品库

**结论：先“新程序＋真实库副本”旁路演练，不在唯一正式库上试迁移。**

**理由：**程序回滚与数据回滚是两件事。旧程序能启动，不代表它能读取新程序迁移后的数据。

**代价／风险：****最危险的是候选程序首次打开唯一正式库并执行不可逆迁移，其次是回滚时覆盖新产生的用户数据。**

**具体下一步：**

按这个顺序演练：

**记录旧版身份与路径 → 停止相关写者 → 备份一致的数据与资产 → 校验备份 → 在独立目录部署候选版 → 指向工作副本 → 冷启动测试 → 恢复演练。**

备份不仅包括 SQLite，还包括原件／附件、配置、模型及 worker 引用、版本清单和校验信息；短期 launch token 不应作为可复用凭据恢复。

SQLite 运行中不能只复制 `.db` 就认定得到完整备份，WAL 可能包含尚未合入主文件的事务。优先使用现有 Core 备份入口；需要实现时采用 SQLite Backup API，并协调数据库外资产的一致性。citeturn907316view0turn907316view1

冷启动通过至少要求：新 PID、新握手、正确程序版本、没有旧进程代答；真实来源可读、候选处置可回读、学习事件可保存；结束全部相关进程后再次启动仍一致。

回滚使用**旧程序＋演练前副本**，不让旧程序直接尝试降级新 schema。候选运行期产生的数据另行保留；恢复失败时停止写入，保留现场和原始备份，不反复覆盖。

## A4．直接 fast-forward，还是走 PR？

**结论：走 PR；本轮优先保留原提交的 merge commit，但服从仓库已有保护规则。**

**理由：**fast-forward 是提交图操作，PR 是审查与合并流程，它们不是严格的对立概念。这里真正该避免的是绕过审查直接推 `main`。GitHub 的 merge commit 可以保留原提交，并留下明确集成点。citeturn436044search3

**代价／风险：**需要再验证合并结果；分支自己的 CI 全绿，不证明它与另一条 UI PR 组合后仍正确。

**具体下一步：**检查 #157/#158 的实际文件重叠与依赖，确定顺序；对最新 `main` 与待合并分支的集成结果执行打包和关键旅程测试，再解除 Draft、满足审查要求、合并。仓库要求线性历史时，不擅自修改规则。Draft PR 不能直接合并。citeturn436044search4

**合并代码不等于解冻 Release，也不等于授权替换正式库。**

# 四、B 组：产品与策略裁决

## B1．Mastery、`本月掌握`、`stability`、`closed=false`

**结论：改为“本月进展”；稳定度翻译成人话；不把 `closed=false` 永久写死。**

**理由：**练习次数、不同日期答对次数和记忆调度，不足以证明“掌握”。FSRS 的 stability 是记忆模型中的时间尺度，表示回忆概率降到 90% 时的间隔，不是掌握率。citeturn647965search9

**代价／风险：**短期少了一个显得漂亮的“掌握数字”，但避免误导；未来需要有版本的掌握判定规则。

**具体下一步：**

首页显示可解释的指标，如“本月完成复习 12 次”“在 3 个不同日期答对”，不要把异质指标拼成一个假百分比。主要显示“下次复习时间”；高级详情可以显示“记忆稳定度约 2.3 天，模型估计”，不能写成“两天后必然忘记”。

`closed=false` 可以保留为**当前版本的兼容约束**，同时说明尚未评估掌握；长期应区分未评估、证据不足、达到某版标准、需要复核。**永远 false 与永远 true 一样，都可能失去信息价值。**

## B2．原创草稿是否可以成为来源，是否应该完全禁止搜索？

**结论：允许草稿持久化、允许显式提升为来源；不赞成草稿永远不可搜索。**

**理由：****可找到自己的草稿，不等于把草稿当作可信证据。**将两者绑定，会损害基本写作体验。

**代价／风险：**必须增加清楚的内容状态和检索边界，防止未经确认的内容进入默认可信回答。

**具体下一步：**

草稿自动保存，但“保存”不等于“入知识库”。提供独立的“保存为来源版本”动作，生成不可变版本与作者／AI 辅助信息；不一定需要连续两次弹窗。

全局搜索可以有“草稿”分区或明确过滤项；默认知识问答和正式证据检索不纳入草稿。作者自己的已发布文稿可以成为来源，但**来源身份也不等于其所有主张已经验证**。

保存期限建议默认不自动清除；用户删除进入可恢复回收区，保留期可设置。当前先做最小可靠持久化，不顺带重做整套编辑器。

## B3．启动输入上限：64 KiB 还是相对路径？

**结论：现在使用有上限的 64 KiB 作为缓解；长期让启动 JSON 引用单一 worker 清单，用安装根解析相对路径。**

**理由：**扩大缓冲区可以解决眼前溢出，但不解决重复声明和不可迁移路径。

**代价／风险：**需要兼容旧启动方式，还要防止相对路径逃出安装根。

**具体下一步：**

与 C1 一起改：静态 worker 路径退出启动 JSON；启动信息保留必要的运行上下文。安装根来自可信程序位置，不依赖当前工作目录。规范化路径后验证位于允许目录内，拒绝未授权绝对路径、目录穿越和链接逃逸。

64 KiB 按 **UTF-8 字节数**计算；超限明确报错，不能截断后继续解析。增加深目录、中文、空格和超限测试。数据目录、解释器等确需独立定位的路径仍按现有授权规则处理，不机械消灭所有绝对路径。

## B4．“四库”要不要落成四个数据库？

**结论：保留四个业务域，不建四个物理数据库，也不把历史概念直接废弃。**

**理由：**人类学习、机器知识、来源归档、证据账本是职责划分，不自动等于四个 SQLite 文件。

**代价／风险：**逻辑分域仍需要表、对象、权限与接口边界；但可避免额外的跨库一致性问题。尤其 SQLite WAL 模式下，多附加数据库的事务并不保证整体跨库原子性。citeturn907316view1

**具体下一步：**在现有 schema 和 Core API 中说明四域映射，原件字节沿现行保存方案承接。只有明确出现独立保留周期、故障隔离或权限隔离要求时，才评估物理拆分。

## B5．首页缺失指标：占位还是隐藏？

**结论：未实现的可选卡片默认隐藏；已经提供但暂时失效的指标保留，并说明原因。**

**理由：**“还没做”与“本来能用、现在故障”不是同一种状态。

**代价／风险：**隐藏未实现卡片会降低蓝图曝光，但持续展示多个“Core 未提供”也不会增强信任。

**具体下一步：**区分可用、加载、未实现、故障、过期数据。真正计算得到空队列可以是 0；未知不能变成 0。

未实现能力移到可发现的能力说明中；故障用用户语言，例如“复习计划暂时无法读取，点击重试”，技术原因放详情。不能把已有的真实故障悄悄隐藏。

## B6．任务状态文件要不要更新？

**结论：更新，但更新证据支持的子状态，不直接把总任务改成完成。**

**理由：**过时状态同样会误导后续执行器；“避免假完成”不等于“永不记录新进展”。

**代价／风险：**多 Agent 同改文件会产生冲突；旧测试结果也可能被误挂到新代码版本上。

**具体下一步：**由当前指定写者更新可变执行台账，记录测试对应 SHA、构建产物、运行身份、通过项、未验证项和阻塞项。原执行者已退出时应明确交接，不把权限永远绑定到某个 Agent 名字。

不可变 TaskPack 不随意重写；真人复核、正式替换、Release Gate 仍保持各自状态。

## B7．复习页是否进入即读取队列？

**结论：自动读取一次，保留手动刷新。**

**理由：**进入复习页已经表达查看意图，再点一次载入没有增加必要的控制。

**代价／风险：**需要处理取消、重复请求与过期响应。

**具体下一步：**异步获取，不阻塞界面；离开页面取消请求，旧响应不能覆盖新响应。**读取队列不应自动开始计时、提交学习事件或消耗队列项。**开始复习仍是明确动作，错误与空队列分开显示。

# 五、C 组：技术方案

## C1．三份 capability→worker 映射怎样真正收敛？

**结论：建立一份声明式 manifest，现有三个脚本继续保留入口，但都读取同一清单。**

**理由：**AST 守卫能发现三处不一致，却不能消除三处各自维护的根源。这个问题已经造成实际出厂 503，应列为优先修复。fileciteturn4file0L53-L53

**代价／风险：**直接删改整条打包链容易引入新故障，应先兼容、后移除旧常量。

**具体下一步：**

采用 JSON 等项目现有运行环境都能读取的格式，包含清单版本、worker ID、能力 ID、相对入口、运行协议和必要性。以下仅是结构示意，不是仓库现有路径：

```json
{
  "schema_version": 1,
  "workers": [
    {
      "id": "example_parser",
      "entry_rel": "workers/example_parser.py",
      "capabilities": ["parse.example"],
      "protocol": "ndjson-v1",
      "required": true
    }
  ]
}
```

第一步让打包、开发启动、候选组装的原函数统一调用读取器，保持原返回结构，比较新旧结果；第二步把清单随包发布，运行时校验能力与实际文件；最后移除重复常量。

**关键门禁不是“文件存在”，而是“从最终安装包位置调用该能力并得到合法响应”。**必需能力缺失应导致候选验证失败；可选能力缺失应明确禁用。增加安装目录移动、中文深路径和离线环境测试。

## C2．先插入事件，再更新投影，再回读，是否合理？

**结论：合理；不需要为此立刻换数据库架构。必须保证同一事务、幂等和提交成功后才回成功。**

**理由：**你修复的是“先派生导致少算一次”和“回执返回旧副本”，方向正确；但“事务内读到”不等于“已经成功提交”。SQLite 的提交仍需要单独处理成功或失败。fileciteturn4file0L55-L55 citeturn907316view2

**代价／风险：**重试可能重复记学习事件；多处各写一套派生逻辑可能产生新漂移。

**具体下一步：**

```text
接收命令及幂等键
→ 开启事务
→ 插入唯一学习事件
→ 用统一派生函数计算投影
→ 更新投影
→ 在同一事务内读最终结果／保存回执
→ COMMIT 成功
→ 返回成功
```

重复幂等键不能再增加计数。短期保留当前 `json_set` 方案，补首次事件、重复请求、事务失败和重启读回测试。

简单更新可评估 `UPDATE … RETURNING`，但有触发器时要注意：SQLite 的 RETURNING 不反映后续 AFTER 触发器修改，不能机械替换最终回读。citeturn907316view3

## C3．端口测试怎样最稳？

**结论：由真实服务绑定 `127.0.0.1:0`，保留该监听器，再报告实际端口。**

**理由：**connect 失败不证明可 bind；先探测再释放、再由服务绑定也有竞争窗口。Rust 官方支持端口 0 由系统分配，再用 `local_addr()` 查询。citeturn647965search4

**代价／风险：**需要让启动回报携带实际地址，并增加明确就绪状态。

**具体下一步：**测试启动真实服务，等待包含运行 ID、契约版本和实际端口的就绪消息，再做有认证的健康请求。不要先 bind 探测、释放 socket，再重新抢这个端口。

launch token 继续通过受保护的握手渠道传递，不写普通日志；固定端口失败时报告原因，不通过禁用防护或修改系统端口保留来“修好测试”。

## C4．截图回归怎样避免挂起进程和 0 字节图片？

**结论：分成无头控件测试、视觉回归、少量 Windows 原生旅程测试；进程生命周期由独立测试控制器负责。**

**理由：**`$null` 与挂起同时出现，不足以证明 `$null` 就是根因。要检查输出管道是否持续消费、子进程是否继承管道、退出条件是否触发。微软文档明确说明，重定向输出和不当等待顺序会造成死锁。citeturn776858view0

**代价／风险：**新增少量测试基础设施，但比持续清理残留进程更可控。

**具体下一步：**

| 层级 | 推荐模式 | 验证范围 |
|---|---|---|
| 控件与状态 | Avalonia Headless＋现有 xUnit/NUnit | 布局、绑定、输入、焦点 |
| 视觉回归 | Headless＋Skia、固定主题／字体／样例／时间 | 与已批准母版比较 |
| Windows 关键旅程 | FlaUI/UIA 与真实窗口截图；先验证控件可访问性暴露 | DPI、IME、窗口行为、真实产品流程 |

Avalonia 官方支持这种分层测试；无头像素回归不能替代真实窗口的平台集成测试。citeturn338160search4turn436044view0

进程控制器需要同时持续读取 stdout/stderr，记录 PID、构建身份与独立输出目录；等待真正布局与数据就绪，截图写到临时文件后完成发布，再检查可解码、尺寸正确，而不只检查文件存在。

设置超时与 `finally` 清理。Windows 可用 Job Object 管理本次测试进程树，设置 `KILL_ON_JOB_CLOSE`；只接管测试启动的进程，不按名字批量杀死所有 AAOS、Python 或 dotnet 进程。citeturn436044search0

## C5．`correct_streak` 与 attempts、distinct days 是否重复？

**结论：不必然重复，但当前命名容易把次数、日期和正确性混在一起。**

**理由：**连续答对次数与累计练习次数、不同日期答对次数是不同统计量；它们都不直接等于掌握。

**代价／风险：**直接重命名会破坏契约；如果数据只有 FSRS 自评，继续叫“答对”可能误导。

**具体下一步：**

| 建议语义 | 计数口径 |
|---|---|
| `attempt_count` | 有效提交的练习／复习尝试，不包括只打开页面 |
| `consecutive_correct_attempts` | 指定对象与评分规则下连续客观答对次数 |
| `distinct_correct_local_dates` | 按明确时区计算，客观答对发生在多少个不同日期 |
| `last_correct_at` | 最近一次符合该正确性标准的时间 |
| `next_review_at` | 当前调度器给出的下一次复习时间 |

**自评“想起来了”不等于客观题答对。**只有自评时应使用“连续回忆成功”等语义，保留评分来源；不要伪造客观正确计数。

先在契约说明和展示层澄清，保留旧字段兼容；记录用户、知识对象、事件顺序、时区及算法版本，避免为了改名立即迁移整库。

## 一、先明确：AAOS 接下来不应只是资料管理器，也不应成为软件大杂烩

我的产品建议是：

**AAOS 保持“可信知识与人机学习工作台”的主体，同时具备完成学习、研究和研发知识任务的 Agent 能力。**

它应该支持这样的任务：

> “围绕这个问题找资料，区分可靠来源和待核验观点，帮我读懂难点，形成学习计划，再整理成可以交给研发执行器的技术资料包。”

其中，**用户可以直接阅读、编辑、检索和复习，也可以让 Agent 串联这些操作**。不应强迫所有事情都经过聊天窗口。

这与 DSH 文档给出的核心架构是相容的：**Rust Core 唯一写入、隔离 Python workers、Avalonia 桌面端**；外部能力的加入不应变成第二个数据库写者，也不能绕过真人复核。fileciteturn4file0L7-L17

### 我会调整的优先级

**领域资料与能力接入，应高于通用社交连接、另建 Agent 管理平台和装饰性大屏。**

但它不高于已有交付故障的修复。DSH 已明确报告：同一份 worker 能力映射维护在三处，两次导致“worker 已发布，但调用返回 503”。**先把已有能力的发现和调用做可靠，才能让插件菜单展示真实接入，而不是更多看起来能用的卡片。**fileciteturn4file0L53-L53

这不意味着继续无限等待。我的建议是：**能力注册收敛与第一批只读 API 适配一起做小范围验证；不把全部外部接入塞成当前 M0 的发布前置条件。**

## 二、OpenHuman 可以重点参考，但参考对象要选对

OpenHuman 官方仓库现在同时包含 Rust 核心、桌面端、浏览器界面和终端客户端，并提供可配置的模型、记忆、搜索及工作流能力。它不是一套单纯的 UI 组件库。citeturn258307view0

### AAOS 最值得借鉴它的三个部分

**第一，能力发现与连接管理。**

让用户以“我要查论文”“我要导入文献”“我要生成练习”找到能力，再查看由哪个平台提供，而不是先研究一排不认识的软件名称。

**第二，连接状态和行动按钮。**

同一个位置能看见“未配置、需要授权、可用、受限、出错”，并提供对应的“配置、测试、重试、禁用”。这里应该借鉴 OpenHuman 连接页的组织方式，但 AAOS 要进一步显示**支持哪些具体动作**，不能一个平台连接成功就宣称所有能力都可用。

**第三，技能发现与实际执行的关联。**

用户看到一项学习或研究技能时，应知道它依赖哪些资料源、模型和工具，哪些步骤会联网，哪些会消耗费用，哪些需要本人确认。

### 不建议照搬的部分

**不迁移 OpenHuman 的整套运行时、记忆系统和通用工作流引擎，不把 AAOS 改成它的换皮版本。**已有核心职责不能因为双方都使用 Rust 就合并。

它的桌面实现采用 Tauri 等技术，前端架构文档描述的是 React 应用，并非能够直接放入 Avalonia 的原生控件。仓库标注 GPL-3.0；参考交互思路和复制代码、资源也需要分别处理。citeturn258307view0turn540789view1

**最终取舍：OpenHuman 主要负责“能力中心”的参考；阅读、学习与证据复核页面，继续按 AAOS 自己的任务需求设计。不要为加入一个参考软件，再重新设计全部导航。**

**“平台宣布开放”不等于“你的账号已经有可嵌入 AAOS 的稳定 API”。**

## 四、“接入”与“并入”，我会这样划分

这几个词现在需要有清楚含义，否则开源池又会变成状态混乱的总清单。

| 方式 | 适用对象 | AAOS 实际获得的东西 |
|---|---|---|
| **外部 API 接入** | OpenAlex、Crossref、科研平台服务 | 可授权、可限流、可替换的查询或任务能力 |
| **本地软件适配** | Zotero、已有资料目录、本地服务 | 读取和导入既有资料，不夺取对方数据库所有权 |
| **隔离服务／worker 接入** | 文档解析、课程生成、专用计算 | 一个受控调用接口，失败不会破坏核心数据 |
| **算法／组件吸收** | 确有缺口的调度、解析、教学或 UI 组件 | 经许可与测试确认的代码实现，随 AAOS 维护 |
| **界面／方法参考** | OpenHuman 的连接页、OpenTutor 的学习工作区 | 设计与流程改进，**不是正在调用该软件** |

**默认选择前三种；只有适合长期自维护的小组件，才直接吸收代码。**

例如，Docling 提供多格式解析、本地执行和统一文档表示，适合成为隔离解析供体；但是否替换现有解析器，应看 AAOS 的真实复杂文档测试，而不是因为它支持格式多就全部重做。其代码许可与所用模型许可也需分别核对。citeturn540789search0

**并入一个完整科研或知识平台，通常意味着同时接手它的用户体系、数据库、任务系统、依赖和升级节奏。我的建议不是扩大 AAOS 的“平台数量”，而是增加它能稳定完成的任务种类。**

## 五、界面里应该显示这些能力，但不要把“插件”和“技能”混为一谈

**你的这个方向值得采用，而且正好可以解决之前“能力很多、用户却看不懂”的问题。**

我的建议是在**现有插件／能力入口**里形成一个统一能力中心，不再增加一排一级导航。内部用少量标签页区分：

**已启用能力｜来源与连接｜学习与研究技能｜调用记录**

### 1. 来源与连接：回答“AAOS 能访问什么”

展示平台或本地软件，例如 OpenAlex、Zotero、GitHub。

每项显示：

**支持的动作、连接方式、授权范围、可用性、最近验证时间、费用／额度说明。**

不是只放 Logo 和“连接”按钮。没有 API 的资源，按钮应该是“打开平台”或“导入文件”，不能也叫“连接”。

### 2. 插件能力：回答“AAOS 能执行什么具体操作”

例如：

**论文检索、DOI 解析、文献导入、表格解析、练习生成、课程呈现。**

一个平台可以提供多项能力，一项能力也可以有主服务和备用服务。**平台授权成功，不自动使它的所有能力变绿。**

### 3. 技能：回答“这些能力怎样组合完成目标”

我建议 AAOS 先做三个面向任务的技能，而不是先建立一个几千项技能市场：

| 技能 | 主要输入 | 应交付的结果 |
|---|---|---|
| **资料学习** | 用户选定的来源及学习目标 | 有来源的讲解、练习、学习记录与复习安排 |
| **研究对比** | 一个问题和选定文献 | 观点、证据、分歧、局限与待核验项 |
| **研发资料包** | 技术问题、官方文档与项目资料 | 固定版本的资料集合、技术约束、许可提示和执行交接内容 |

技能应声明所需能力和权限；缺少依赖时显示具体原因。**不能用“技能已安装”掩盖“所需 API 根本调用不了”。**

### 4. 调用记录：回答“这一次到底用了什么”

这是最应该加强的部分。

以未来的“研究对比”任务为例，结果旁边可以展开看到：

> **资料来源**：检索平台、文献 DOI、原文版本。  
> **处理能力**：文档解析器与版本。  
> **模型处理**：使用的模型及提交的数据范围。  
> **人工操作**：本人接受、拒绝或保留待核验的内容。  
> **产物**：知识候选、学习材料和对应回执。

这是一份建议的展示结构，不是当前已完成状态。

**尤其要分别显示三种关系：**

**“本次调用了 DeepTutor 服务”**、**“使用了从某项目吸收的组件”**、**“界面参考了 OpenHuman”**，不能都写成“由某平台提供支持”。

仅仅参考 OpenHuman 的界面，应该进入设计来源或致谢信息，不应该出现在任务运行记录里。

## 六、能力页必须从真实注册表生成，不能再维护一份展示清单

我建议把 DSH 的单源映射问题与能力界面一起解决。

**同一份经过校验的能力声明，服务打包、启动、调用路由和界面展示；运行状态则由真实探测及调用回执补充。**

但需要分开两个维度：

**实现状态**：候选、已适配、已随包发布、已通过验收。  
**运行状态**：未配置、待授权、可用、限流、离线、失败、未检测。

这样才能避免：

> 插件曾经验收通过，但今天 API Key 过期，界面仍显示“正常”。

也能避免：

> 平台目录里有这个名字，界面就把它计算为一个“已接入能力”。

### 最小声明应该包含什么？

建议包含：**能力 ID、提供方、版本、支持的动作、协议、权限、网络目的地、输入输出结构、健康检查、限流策略、产物类型和许可信息。**

密钥只保存安全引用，不放进前端配置或日志。技能再引用这些能力 ID，而不是把每个平台配置重新抄一遍。

这直接对应 DSH 已报告的问题：**当前不是缺第四份更漂亮的能力清单，而是要消除三处声明漂移。**fileciteturn4file0L53-L53

### “已接入”的验收也要提高标准

我的建议是：

**最终安装包中能发现 → 完成必要授权 → 从真实界面发起调用 → 获得合法响应 → 保存来源／回执 → 重启后可读 → 禁用后不再调用。**

只返回 HTTP 200 不够，只有截图也不够。至少还要测试一次鉴权失败、限流或网络中断，确认不会被渲染为零结果或成功。DSH 的现行约束也明确要求未知与缺失不能伪装成 0 或成功。fileciteturn4file0L13-L18

## 七、外部能力越多，越需要明确这四条边界

### 1. 联网不等于允许上传全部资料

我建议将授权分成三个等级：

**查询关键词／公开标识符 → 提交用户选定片段 → 上传全文或附件。**

### 3. 能找到内容不等于有权复制、重分发或训练

来源记录应保存许可和使用限制。找不到许可时标记未知，不能补成“开源”。

Europe PMC 官方明确说明，即使是开放获取子集，不同文章也可能采用不同条款，需要查看逐篇许可。citeturn540789search11

### 4. 外部返回结果不能直接变成 AAOS 认可的知识

我建议把所有外部内容、模型生成内容和检索摘要都视为**带来源、可检查的输入**，而不是直接执行的指令或已认可结论。

外部服务可以提出知识候选、课程和纠正建议；**Rust Core 继续负责持久化边界，真人复核继续决定需要人工认可的转正。**这两点不因加入科研平台而放宽。fileciteturn4file0L7-L15

**你的这次建议有一部分应该上升为正式产品策略：学习、科研、研发领域的资源与能力，是 AAOS 的主要接入对象，不只是附属插件。**

## 一、视觉方向收敛成一套，不再让不同 Agent 各自设计

**我的推荐是：黑白深色、低饱和、中文优先、内容主导的知识工作台。**

**壳层安静，内容清楚。**左侧导航和工具栏稍微退后，正在阅读的资料、正在回答的问题、正在复核的证据成为主角。深色不等于所有区域都使用接近的黑色；背景、工作区、浮层必须能分清。

|---|---|
| **工作台** | 继续阅读、继续学习、最近资料、待处理事项、进行中的任务 |
| **知识** | 捕获与导入、资料库、原件阅读、知识编辑、证据、搜索、研究资料、开放互操作 |

| **系统与能力** | 插件、平台连接、产品技能、模型、适配器、能力健康、任务回执、备份恢复、设置 |

一级分组始终可见；二级能力按模块折叠，记住用户上次展开状态。允许多个分组同时展开，不强制每次只能打开一个。

**未来能力应尽量出现在它所属的业务域中；“探索与蓝图”提供汇总视图，而不是把所有未来功能都赶到一个角落。**同一个能力使用相同 ID 和详情页，多处入口只做跳转，不产生多份状态。

首页可以不摆满未来功能卡片，但导航和完整能力地图不能把它们删掉。

**菜单入口保持可点击；不满足条件的“执行动作”才被禁用。**

这能同时做到：你看得到 AAOS 的完整方向，也不会把尚未实现的功能误认为已经能用。

### 技术上还要补一个关键区别

前面的能力注册方案需要进一步区分：

**产品能力目录：包含现有与未来能力。**  
**运行实现清单：只包含实际适配、打包和可调用的实现。**  
**运行状态：来自真实配置、检测和调用回执。**

导航从完整产品能力目录生成，再关联实现和运行状态。**不能只从已安装 worker 生成菜单，否则未来能力必然消失。**

这几份信息以同一个 `capability_id` 关联，各自只维护自己负责的事实，不再复制三套 `capability→worker` 映射。DSH 文档已经记录了这种重复映射导致的实际 503 问题。fileciteturn4file0L53-L53

## 三、后端：Rust＋Python 合理，但“用了 Rust”不等于架构天然优秀

### 1. Rust Core 继续负责正式知识、权限与数据一致性

我支持保留 Rust Core 的原因，是它现在承担的职责相对集中：来源身份、证据关系、候选认可、学习记录、迁移、备份、任务状态等，都需要有一个清楚的权威边界。

Rust 的所有权机制提供内存安全方面的保证；但**业务正确性、证据可信性和事务一致性，仍然依赖程序设计、权限校验和测试，不是 Rust 自动附送的**。citeturn917291search6

换成 C# 也能实现可信内核。只是对当前 AAOS 而言，**我没有看到足以抵消重写与重新验证成本的收益**。

因此，不建议为了“语言少一种”把现有 Rust Core 改成 Python 或 C#。

### 2. Python 应当是能力执行层，不是另一个 AAOS

我建议继续让 Python 承担适合它的专用工作，例如文档处理、模型调用适配、学习算法试验及科研工具接入。

但下面这种发展方向要避免：

```text
Rust 管理一套知识状态
Python 后台又管理一套课程、用户、任务和知识状态
前端再自己维护一套“真实完成状态”
```

这会产生三个事实来源。

更合理的是：

**Python 接收任务与受控输入，返回产物、测量值或候选；Rust 决定如何校验、保存和提供给界面。**

与此同时，**不要因为接入了十个平台，就启动十个常驻 Python 服务**。简单的 HTTP API 适配，放在现有统一适配层即可；只有真正需要 Python 依赖或故障隔离的能力才运行 worker。

### 3. “唯一写者”不能演变成“所有计算都排一条长队”

SQLite WAL 支持读写并行，但同一时间仍只有一个写者。这支持保持统一写入边界，却不意味着可以长时间占住写入资源等待模型、网络或解析结果。citeturn917291search4

我建议采用：

**读取输入版本 → 事务外运行耗时任务 → 校验输入是否变化 → 短事务提交结果。**

而不是：

**拿住数据库写锁 → 等模型生成几十秒 → 最后提交。**

所以，后端下一步更值得优化的是**任务生命周期、事务长度、幂等、取消、恢复和产物版本校验**，不是语言迁移。

### 4. 现有通信方式先保留，收敛合同即可

目前的本机 HTTP 和 NDJSON 是明确的进程边界。我的建议是继续使用，不为了追求“更底层”立即改成 FFI，也不引入一整套微服务基础设施。

重点补齐请求 ID、版本、超时、取消、结构化错误、单消息大小限制和产物引用。大文件通过受控资产引用传递，避免把所有内容反复塞进 JSON。

**DSH 文档已经报告的三份 worker 映射漂移，是边界管理问题，不是 Python 或 Rust 本身选错。**fileciteturn10file0L51-L55

### 3. 现在已经不必在“纯 Avalonia”和“全量换 Tauri”之间二选一

**保留 Avalonia 桌面壳，在少数复杂内容工作区嵌入本地 Web 组件。**

但开源不等于已经与你的工程验证兼容，能嵌入也不等于体验已经合格。**这是值得测试的路线，不是已经证明最优的结论。**

## 六、我更推荐的当前演进架构

下面是**建议结构，不是已实施架构**：

```text

│

│   ├─ 应用窗口、完整折叠菜单、快捷键
```

这里的收益是**复用内容引擎**，不是把所有页面包装成 WebView。

## 八、现在怎么做，才能避免又陷入一轮架构摇摆？

对，这个边界非常重要。**我前面把“可信知识闭环”说成了几乎所有进入 AAOS 的内容都要经过 Source → Evidence → Human Review，这个表述过度了。**

AAOS 应该是**多种知识治理强度共存**，而不是“没有原件、没有外部证据就不能进入正式库”。

例如：

| 内容 | 原件 | 外部证据 | 可以进入正式库吗？ |
|---|---|---|---|
| PDF/论文/网页导入 | 有 | 通常有 | 可以 |
| 用户自己的读书笔记 | 可有可无 | 可选 | **可以** |
| 临时个人想法 | **没有也正常** | **不需要** | **可以，由用户决定** |
| 灵感/假设 | 没有 | 可能暂时没有 | **可以** |
| 用户原创文章 | 用户本身就是作者 | 不要求外部证据 | **可以** |
| AI 生成观点 | 有生成记录 | 未必有可靠证据 | 可以保存，但应标明来源性质 |
| 科研结论/事实主张 | 通常有 | 强烈需要 | 建议走严格证据流程 |
| 高风险知识 | 有则保留 | 应要求较强依据 | 应采用更严格治理 |

所以 AAOS 正确的数据思想应该从：

> **所有 Knowledge 必须有 Source + Evidence**

修正为：

> **所有 Knowledge 必须有明确的“身份与来源性质”；但不是所有 Knowledge 都必须有外部原件和证据。**

这里的“来源”甚至可以只是：

**`origin = user_created`**

而不是强行伪造一个 PDF/网页 Source。

更进一步，我建议以后把 AAOS 的知识治理做成**用户可选的 Provenance / Trust Policy**：

**自由内容**——个人想法、草稿、灵感，不要求证据；  
**来源关联内容**——可以关联来源，但不要求人工认可；  
**证据支持内容**——要求 Evidence/Anchor；  
**已复核知识**——经过明确人工确认；  
**严格可信知识**——要求来源、证据、版本、复核等更完整条件。

用户可以按内容性质选择，系统也可以提出建议，但**系统不能替用户武断地说“这条没有证据，所以不配进入正式知识库”。**

这还会影响我们刚才正在做的全网对标：不能再把“原件保全 / Evidence”作为每个知识软件都必须满足的统一门槛。它应该是 **AAOS 的一种强治理能力**，而不是整个 AAOS 的唯一工作模式。

换句话说：

> **Heavy Core 不等于 Heavy Governance Everywhere。**

底层有能力保存原件、Anchor、Evidence、Version、Review，是为了**需要严格可信时能够做到**；个人灵感、原创笔记、草稿和探索性假设完全可以走轻路径。

这条我会作为后续 AAOS 架构与任务包的**正式纠偏原则**：**证据强度按内容类型、使用场景和用户选择决定；正式库不以“必须存在外部原件/证据”为准入条件。**
