# 五、目前最大的风险

## 1. 提交速度很快，但不能直接等价为系统进度

2026年7月14日至15日出现了大量连续提交，包括合同、安全、自动化、性能和存储修复。说明执行效率很高，但也存在一个风险：

> 合同对象和基础设施增长速度，可能已经快于真实业务闭环接入速度。

例如合同已经比较完整，但 Planner、Evaluator 和真实工具证据仍然是核心缺口。fileciteturn12file2L7-L12 fileciteturn12file4L13-L18 fileciteturn12file6L19-L24

建议停止继续增加大量新 Schema，直到第一条端到端闭环真正运行。

## 2. Phase 3 不能做成无限安全重构

Phase 3 有八项任务，每一项都合理，但如果全部做到生产级再开始闭环，项目容易在基础设施阶段停留过久。

建议拆成：

### Phase 3A：最小闭环必须完成

- 无默认管理员密钥。
- 禁止用户自选管理员角色。
- 本地文件 approved roots。
- 稳定哈希。
- 最小 Migration Runner。
- 写操作审计。

### Phase 3B：Alpha 前完成

- 完整 Safe HTTP。
- Rate Limiter。
- FTS/Vector 全量重建和回滚。
- 更完整备份恢复。

这样可以将真实 Runtime 提前。

## 3. 巨型文件仍是后续开发瓶颈

审计报告显示：

- `knowledge_base/api.py` 曾达到约 1171 行、91 个直接路由。
- `shared/sleep_loop_engine.py` 约 1087 行、34 个顶层函数。fileciteturn14file0L16-L18

不建议立即进行“大拆目录”，但应在每次修改时做渐进拆分：

```text
sleep_loop/
├── repository.py
├── scheduler.py
├── executor.py
├── recovery.py
├── policy.py
└── service.py
```

重点是按责任拆，而不是为了目录漂亮而拆。

## 4. 数据库仍是系统性风险

目前 Runtime、Knowledge、Research、Sleep Loop 曾存在多套 SQLite 初始化和 DDL 入口；这会造成：

- 表结构漂移。
- 不同模块写入语义不同。
- 测试通过但升级失败。
- 恢复后索引与主数据不一致。fileciteturn14file0L13-L15

必须尽快建立唯一的：

```text
Database Composition Root
Migration Runner
Repository Boundary
Transaction Boundary
Backup/Restore Procedure
```

否则后期闭环越多，迁移成本越高。

## 5. 当前 UI 不是关键路径

现在已经有 Knowledge Dashboard，但本阶段不应投入太多设计时间。真正需要的只是一个“闭环调试台”：

- 当前目标。
- 当前计划。
- 等待审批的操作。
- 工具执行状态。
- 证据。
- Evaluation。
- Lesson。
- 重试、暂停、批准、拒绝。

不要先做完整“未来 OS 桌面”。

# 六、最应该改进的架构

## 1. 增加一个真正的 Loop Orchestrator

目前能力分散在 Runtime Facade、Sleep Loop、KB 和 shared 中。

建议建立唯一闭环编排器：

```python
class CognitiveLoopOrchestrator:
    def submit_goal(...)
    def build_context(...)
    def create_plan(...)
    def request_permission(...)
    def execute_step(...)
    def collect_evidence(...)
    def evaluate_step(...)
    def update_plan(...)
    def produce_lesson(...)
    def close_run(...)
```

所有入口最终调用它：

- `/run`
- Sleep Loop
- GitHub Research
- Document Learning
- 定时任务

否则 Sleep Loop 和实时 Runtime 最终会形成两套完成语义。

## 2. 明确定义 Run、Step、Evidence 三个一级对象

合同很多，但真正的主链对象需要收口为：

```text
Run
 ├── Goal
 ├── ContextSnapshot
 ├── PlanVersion[]
 ├── Step[]
 │    ├── PermissionDecision
 │    ├── ToolCall
 │    ├── Evidence[]
 │    └── StepEvaluation
 ├── RunEvaluation
 └── LessonCandidate[]
```

`Run` 应当是审计、恢复、UI 和评估的共同主键。

## 3. Planner 先使用规则加模型混合，不要一开始完全依赖 LLM

第一版动态 Planner 建议：

```text
任务分类器
→ 模板计划
→ LLM 补全或调整
→ 策略校验
→ 工具可用性校验
→ 权限校验
→ 形成 PlanVersion
```

这样可测试、可复现，也不会因为换模型导致整个系统失控。

## 4. Evaluation 必须从二值升级为多维评分

至少包含：

- `goal_coverage`
- `evidence_quality`
- `tool_execution_validity`
- `policy_compliance`
- `output_quality`
- `reproducibility`
- `uncertainty`
- `human_review_required`

最终状态不能只有 success/fail，应包括：

```text
completed
partially_completed
blocked
needs_review
failed_retryable
failed_terminal
cancelled
```

## 5. Lesson 不应直接写入长期记忆

推荐流程：

```text
Execution
→ LessonCandidate
→ Evidence Link
→ Review
→ Scope / Risk / Expiry
→ Active Machine Knowledge
→ Usage Tracking
→ Deprecation
```

你的路线图已经意识到 candidate 默认和可撤销的重要性，这是项目中很有价值的一点，应继续坚持。fileciteturn9file0L14-L21

# 七、接下来最合理的开发顺序

## 第1阶段：两周，完成 Phase 3A

- 完成角色提升阻断。
- approved roots。
- 稳定哈希。
- 最小 Migration Runner。
- 所有高风险写操作进入统一审计。
- 补齐当前安全任务的 CI 对应关系。

## 第2阶段：两周，建立统一 Run 模型

- Run / Step / Evidence / PlanVersion。
- Runtime 和 Sleep Loop 共用。
- 持久化与崩溃恢复。
- 不做复杂 Planner。

## 第3阶段：两周，完成第一个动态 Planner

只支持三类任务：

- 读取本地文件。
- 检索知识库。
- 生成并保存一个受控产物。

实现：

```text
Goal → Plan → Approval → Tool → Evidence → Evaluation
```

## 第4阶段：两周，完成 Lesson 反馈

- 多维评价。
- LessonCandidate。
- 人工批准。
- 下一次任务检索复用。
- 增加端到端测试。

这就是我估算 **5–8周形成最小真实闭环** 的依据。

# 最终判断

这个项目**值得继续开发，不建议换方向，也不建议推倒重来**。

它当前最大的优点不是“AI 功能多”，而是已经形成：

- 候选与可信知识区分。
- 合同版本化。
- 审计意识。
- 回滚意识。
- 本地优先。
- 单仓库边界。
- 禁止假完成。
- 外部能力吸收结束后及时收口。

这些基础比很多表面成熟的 Agent 项目更重要。

但下一步必须改变重心：

> **从“继续建设更多底层对象和治理文件”，切换到“打通一条真实、可恢复、可审计、可复用的运行闭环”。**

我的最终时间判断是：

- **最小真实闭环：2026年8月下旬至9月中旬。**
- **稳定内部 Alpha：2026年11月至2027年1月。**
- **个人长期可用版：2027年2月至5月。**
- **完整产品化 1.0：约2027年末至2028年中。**

其中最关键的验收标准不是接口数量、提交数量或测试数量，而是：

```text
同一个真实任务能否执行
→ 有证据
→ 可评估
→ 失败可恢复
→ 经验可审核
→ 下一次能真正做得更好
```
