## 二、到底还差什么：七个必须收口的环节

### 1. 设计方向和设计系统，还需要真正驱动原生生产

这是第一个核心断点。

当前已经打通并有证据的前半段是：

```text
项目 → Brief → 参考 → 方向 → 人工选定 → 设计系统绑定
```

当前源码中，方向绑定接口接收的是 `design_system_name`，原生计划接口接收的是 `host / rir / text_styles / idempotency_key`。**两组接口都存在，但接口存在不能证明“选定方向后，系统就能接着生成正确的原生对象计划并完成生产”。**当前 Authority 也仍把 `DesignSystem → DesignIR → Photoshop/Illustrator` 列为剩余工作。fileciteturn40file0L2-L2fileciteturn25file0L2-L2

需要补的不是第二套引擎，而是这段业务衔接：

> 选定方向和设计系统 → 生成可检查、可修正的对象计划 → 提交已有原生任务入口 → 产物保留与原始设计决策的关联。

**完成标准：你从工作台正常操作就能继续往下做，不需要手写一段 RIR/JSON，替软件把断开的流程接起来。**

同时，后续作品应能回答：“它来自哪个 Brief、哪个方向版本、哪个设计系统绑定？”否则设计前半段和生产后半段仍是两套分开的功能。

### 2. Adobe 真实往返，还缺完整的 E3 验收证据

这里的 E3，就是**真实任务在真实宿主里完成**，不是模拟测试。

当前仓库的能力矩阵仍把 Adobe Adapter 的可声称等级限制在结构层，真实宿主工作流尚未获得完整读回验收。既有任务要求也不只是“生成一个文件”，而是原生可编辑、局部修改、保存重开和异常恢复。fileciteturn22file0L2-L2fileciteturn26file0L2-L2

这一项需要拿一份真实设计任务证明：

**能生成原生工程；文字、形状和图层确实可编辑；连续做两次局部修改；保存、关闭、重新打开后正确读回；中断后可以对账恢复或回滚，而不重复创建对象、不影响你的无关文档。**

对你尤其重要的是：

> **整张图贴进 PSD，不算完成分层设计；生成预览图，不算完成原生生产；脚本没有报错，也不等于作品正确。**

建议先用一个宿主跑出首条真实闭环，再验证另一个宿主。**这只是实施顺序，不是把现有 Photoshop、Illustrator 双宿主验收要求偷偷删掉。**

### 3. 人工评审不是“只等你点头”，而是还缺产品入口

这是本次确认的明确工程缺口。

10 月 7 日的实施报告记录：Human Jury 合同已有，但没有对应路由和 UI。本次检查完整 HTTP 分发代码，也没有看到 Jury 审查与提交路由。fileciteturn36file0L2-L2fileciteturn40file0L2-L2fileciteturn41file0L2-L2

因此，需要先让你在界面里实际做到：

> 查看当前作品和修改前后对比 → 提出意见 → 接受、拒绝或要求修改 → 生成绑定具体作品版本的评审回执。

这里必须分清两件事：

**Agent 应该完成的：**评审界面、API、版本绑定、意见存储、修订比较、状态流转。

**必须由你完成的：**真实的审美判断与最终认可。

“Agent 不得冒充真人验收”是正确边界，**但不能拿这条边界当作不实现评审功能的理由。**仓库也明确规定，自动评价不能替代独立人工验收。fileciteturn26file0L2-L2

另外，现有预检浏览器链主要验证工具可用、工具缺失、修复后重新检查，以及交付包数量为空时的显示。它还不能证明一份真实设计作品的字体、链接、可编辑性、素材权利和生产规格已经合格。fileciteturn36file0L2-L2

**把真实产物、人审结论、权利状态、生产规格和交付文件清单，放进同一次验收。**

最终交付包至少应包含原生工程、预览、必要素材与依赖说明、版本和哈希、权利记录、评审及预检结果；并且能够在离开开发目录后解包、重开和核对。

**草稿和测试包可以继续导出，但不能显示成“已通过正式交付验收”。**

而不是：

> 找到对象 ID → 拼修改 JSON → 提交 → 切换任务 → 启动 → 查结果。

把 JSON 面板折叠到“高级”下面，只是藏起复杂性。**普通界面没有替代路径时，复杂性并没有消失。**

### 4. 多批 UI 套件同时约束实现，已经产生规范冲突

当前 CSS 自己记录了 B04、B07、B10 之间的字号、断点和圆角冲突；部分新增 token 还被注明“当前没有规则消费，因此视觉与行为零变化”。fileciteturn60file0L2-L2

这说明现在有一部分工作在满足“规范条目齐全”，而不是改善最终呈现。

**UI 套件应该提供视觉资产和起点，不能让多个批次的所有尺寸都永久有效。**

应当明确区分：

- 已确认品牌资产：保持一致。
- 当前产品的组件与布局规则：统一成一版。
- 旧稿：保留参考，不再同时约束实现。

否则，一个圆角或字号都需要跨几个版本解释，正常设计迭代会变成文档仲裁。

### 5. “机器状态不能改”，被误扩大成“用户文案不能翻译”

当前源码注释认为，机器状态词保留英文是为了避免第二套状态词表。fileciteturn57file0L2-L2

**这个推理不成立。**

数据库存 `OUTCOME_UNKNOWN`，界面显示“执行结果待确认”，不等于创建第二套状态机。只需要一份明确的显示映射，保留原始代码供诊断查看。

同样：

`持久化简报` 应显示为 **保存需求**；  
`服务器读回预览` 应显示为 **参考预览**，校验详情按需展开；  
`409 STALE_REVISION` 应解释为 **该版本已更新，请切换到最新版本继续修改**。

技术状态必须准确，但**准确不等于把内部实现直接交给用户理解**。

## 三、前端该怎么收敛？不是少做功能，而是改变组织方式

### 1. 把全局导航收敛为三个主要入口

我的建议是：

```text
项目       素材       能力
                    └─ 模板、方法、已验证技能

工具连接 / 设置 / 诊断：放在次级入口
```

“项目”同时承担首页和继续工作的入口，不再另做一套以系统指标为主的仪表盘。

进入具体项目后，才出现项目内的工作阶段：

```text
需求与参考 → 方案 → 制作 → 审阅 → 交付
```

这是**同一个项目工作区的不同视图**，不是要求用户反复离开项目、去多个全局页面重新选择项目。

对应现有功能，我会这样处理：

| 当前内容 | 建议归属 | 理由 |
|---|---|---|
| 仪表盘、最近项目、继续项目 | 合并为项目首页 | 首屏直接服务于开始与继续工作 |
| Brief、参考、研究洞察 | 项目内“需求与参考” | 研究应围绕当前任务，不是独立空模块 |
| 品牌系统 | 项目品牌设置＋可复用品牌资源 | 区分当前项目使用和跨项目复用 |
| 设计领域 | 新建项目时的模板选择、能力筛选 | 不必为每个领域保留一个入口 |
| 创作工具、模型状态 | 工具连接与能力详情 | 平时隐藏复杂配置，调用时显示必要信息 |
| 预检、交付中心 | 项目内“交付” | 检查结果直接决定下一步能否交付 |
| 证据系统 | 版本历史、操作记录、详情抽屉 | 证据附着于作品和动作，而不是另一处要手动找的页面 |
| 团队协作等未开放功能 | 未来规划区 | 未开放不等于必须占据正式导航 |

这种“先展示主要操作、再展开专业细节”的组织方式，符合渐进披露原则；不是删掉能力，而是避免所有能力同时要求用户注意。citeturn912741search7

### 2. 项目工作区必须以作品为中心

我建议采用以下布局关系，而不是继续铺同规格卡片：

**顶部：**项目名、当前作品与版本、保存状态、当前主要动作。  
**中间：**大面积作品预览、方向比较或版本对比。  
**左侧：**根据阶段切换参考素材、作品列表或版本列表。  
**右侧：**选中对象的属性、修改建议与上下文操作。  
**底部或抽屉：**运行任务、错误详情和操作记录，默认不抢占作品空间。

重点不在“三栏”形式，而在于：

> **任何时候都能看见：我正在改哪份作品、哪个版本、哪个对象，以及执行操作后会发生什么。**

Figma 的属性和评论操作依附于文件、画布与选中对象；Penpot 的素材库也把可视识别和直接使用结合起来。值得借鉴的是这种对象关联，而不是照搬它们全部的编辑器功能。citeturn912741search10turn945501view0turn945501view1

### 3. “不做第二画布”应该重新解释

我支持不再造 Photoshop、Figma 或 Blender。

但我**不支持**因此拒绝：

作品缩放查看、参考并排、版本对比、局部标注、问题定位、方案选择、受支持对象的参数修改。

这些是 DESIGN-LAB 完成设计协作和改稿必需的能力。

边界可以这样划：

> **DESIGN-LAB 提供预览、比较、批注和受控修改；复杂原生编辑仍交给专业宿主。**

不能精确映射到原生对象的区域，明确标记为“批注意见”；能映射的对象，才提供实际修改命令。**不要把视觉选区假装成已经掌握了宿主的图层结构。**

### 4. AI 应该有操作入口，但不必变成通用聊天软件

“不做通用聊天”是合理的边界，不能被理解成“不允许自然语言交互”。

我建议在选定作品或对象后提供：

> “保持版式，标题换成这段文案。”  
> “这三个方案分别解决了什么问题？”  
> “检查当前版本里哪些元素不符合品牌规范。”

系统先展示修改范围、预计结果与限制，再执行；执行后回到具体版本。

**AI 对话应附着于项目、作品和操作，而不是另开一个没有上下文的聊天大厅。**

## 四、视觉设计上，什么应该保留，什么应该改变？

**我不建议这次再换 Logo、重做整套品牌、再起一批大幅概念稿。**

当前深色、电蓝色体系本身不是主要问题。源码中已有这套颜色、间距、动效和组件基础，问题更多在使用方式和规范冲突。fileciteturn60file0L2-L2

我的视觉方向建议是：

### 让界面退后，让作品突出

深色界面可以保留，但减少大面积饱和蓝、发光边框和处处强调的状态卡。蓝色优先用于主操作、选中和焦点，不用于让所有区域都显得“重要”。

作品预览区域应允许中性灰、白色、深色和透明棋盘背景切换。**预览背景是查看工具，不应改写作品的导出背景。**

### 紧凑的是工具，宽裕的是作品区

你强调专业、紧凑和信息密度，我认为应该保留。但信息密度应来自更好的组织，而不是：

小字号＋长说明＋密集边框＋一屏多个状态码。

工具栏和属性面板可以紧凑；比较方案和检查细节的区域必须足够大。列表应提供缩略图、名称、用途、当前版本，而不是把 ID 当作最重要的识别信息。

### 产品界面和宣传页面分开设计

作品集详情页、广告片可以使用更强的光效、镜头感、品牌图形和动效。

日常工作台应强调稳定、清晰、可操作。当前源码甚至为 KPI 提供约 850 毫秒的数字递增动画；这不是错误，但对设计师的核心工作价值很低，不应比版本对比和操作反馈得到更多投入。fileciteturn57file0L2-L2

**商业级界面不是宣传视觉的缩小版。**

## 五、前端技术路线：需要组件化，但不需要全项目重写

当前 `shell.ts` 已达到 181,946 字节，集中了导航、状态处理、多个页面和展示逻辑。文件大本身不能证明架构错误，但结合保留旧 DOM、顶层变量兼容和多套样式，已经能看到维护耦合。fileciteturn49file0L2-L2fileciteturn50file0L2-L2fileciteturn59file0L2-L2

**我的技术倾向是：保留 TypeScript＋Vite，允许并采用 React 作为项目工作区渐进组件化的方向。**

不是因为原生 TypeScript 不能做好，而是未来需要维护的交互包含：对象选择、版本比较、批注、表单草稿、异步任务和多个面板的协同。继续用大模块和手工 DOM 状态维护这些交互，并不天然更简单。

但我不建议先启动“大迁移”。

应当先在现有 `apps/workbench` 中完成一个统一项目工作区，复用现有 API；确认可用后，再替换旧视图。React 官方也支持在既有项目中逐步接入，并不要求全站一次重写。citeturn945501search0

需要坚持的结果是：

**一个正式入口、一套组件体系、一份项目上下文、一条构建发布路径。**

迁移期可以短暂并存，不能再长期留下“旧工作台负责写、新界面负责看”的双产品结构。也不需要因此增加 Next.js 服务端、另写 Node 后端，或者重新包装一个大型桌面壳。

更重要的是：**即使换成 React，错误的信息架构也不会自动变好。先定工作区，再迁组件。**

## 六、后端基础基本合理，但要从“功能集合”变成“支撑操作的业务系统”

我不赞成重写 Python 后端。

已有原生任务接口、版本与交付入口；`NativeWorkers` 也已经通过子进程运行原生任务，有数量限制，并明确不结束共享宿主。这些是值得保留的基础，不是应该为了“高级架构”推倒的东西。fileciteturn40file0L2-L2fileciteturn62file0L2-L2

真正该补的是下面四件事。

### 1. 给前端一个完整的项目工作上下文

当前仪表盘要先读健康、项目、设计系统、环境，再逐项目读取任务和交付包，并在前端拼装部分业务含义。fileciteturn57file0L2-L2

我建议由后端提供一个面向工作区的聚合查询，回答：

当前作品是什么、当前版本是什么、采用哪个方向、还有什么任务、哪些操作可做、哪些操作被阻止及原因。

**它是现有数据的查询视图，不是新增第二套数据库或状态真值。**

这样前端不用在每个页面重复推断“现在到底能不能继续”。

### 2. 把用户动作接成连续业务操作

下一阶段后端工作的单位，不应该再是“增加一个模块”，而应是：

| 用户操作 | 后端必须连续完成的事情 |
|---|---|
| 采用某个方向 | 固定方向版本，形成或引用制作计划，保留来源关联 |
| 修改标题或移动对象 | 检查当前版本、生成受控修改、执行、读回、产生新版本 |
| 刷新或重启 | 恢复项目和任务状态，不重复执行、不丢失修改 |
| 接受当前版本 | 记录真实人工决定，并绑定准确的作品版本 |
| 导出交付 | 检查选定交付范围，生成完整文件包并验证可重新使用 |

**每一条都必须在界面里走得通，而不是只存在一个 API。**

### 3. 不要把统一 Design IR 做成所有设计文件的万能替代物

统一表示适合描述设计意图、受支持对象和可执行修改。

但我不建议要求它完整表达所有 Photoshop 效果、Illustrator 外观、Figma 组件和 Blender 场景。那很容易把项目变成永无止境的格式兼容工程。

更稳妥的边界是：

**设计意图和操作计划由 DESIGN-LAB 管理；实际原生结构以原生文件及真实读回为准；不能表达的部分保留原样或转人工编辑。**

不要为了证明“完全统一”，破坏原生可编辑性。

### 4. 自动化不能成为第一条实用流程的唯一前提

可以先提供有明确标识的人工辅助往返：

> 从 DESIGN-LAB 打开宿主 → 在宿主修改 → 返回后导入或读取新版本 → 比较、审查、交付。

这能先验证项目和作品管理是否好用。之后再逐步自动化高频操作。

**辅助流程不是失败，也不能冒充全自动。**两者分别标明，才能既有实用价值，又保持能力声明真实。

## 七、哪些旧规则应该保留，哪些应该改写？

你让我不要完全照旧规则，我认为最需要调整的是以下这些。

| 现有原则或执行倾向 | 我的专业裁决 |
|---|---|
| 不替代专业设计软件 | **保留**，但允许预览、批注、比较和受控修改 |
| 平台中立、不默认绑定宿主 | **保留接口中立**；当前交付版本应明确优先支持一个宿主，用户配置可以有默认值 |
| 不建第二运行时、第二账本 | **保留**；不能以此阻止现有模块重构、查询聚合和界面状态管理 |
| 保留所有旧入口、菜单与 DOM | **取消永久保留要求**；按迁移方案兼容旧链接，正式界面只保留一套 |
| 旧 UI 套件一比一 | **保留品牌语言，重新评估布局与交互**；参考图不是永恒产品规格 |
| E0–E5 和精确版本证据 | **保留真实性**；验收应按具体功能、版本和影响范围，不拿一条结果推高全产品 |
| 大量事项等待 owner 裁决 | **缩小人工决策范围**；可回滚的布局、文案和组件改进应有明确开发裁量 |
| 未完成功能长期显示在正式界面 | **移出主要工作路径**；未来能力集中展示，而不是遍布空页面 |

特别说明两个容易走偏的地方。

**不能为了收敛而去掉安全。**真实资产删除、外发客户内容、接受许可、公开发布、覆盖原生文件，仍然需要相应的授权与保护；真人验收也不能由模型伪造。

**也不能把证据管理做成每次改动都重跑一切。**应当持续记录当前提交，并依据相关代码、资源、宿主版本和依赖的变化判断哪些证据需要更新。没有建立这种影响范围机制前，不能随意沿用旧结果；建立之后，也不必让一处无关文档修改阻塞全部真实宿主测试。

**严谨应该减少误判，不应该让系统永远无法被正常使用。**

## 八、未来方向应该怎样走？先成为你的生产工具，再证明它值得扩成平台

### 第一阶段：聚焦你真实会反复使用的线上视觉工作

我建议当前优先支持的是一个相邻场景群：

> **品牌一致的线上视觉制作、系列尺寸适配、局部改稿和最终交付。**

这与你的平面设计、品牌、产品详情页和作品集需求相邻，也能验证原生编辑、版本和交付这些核心能力。

不必同时把包装、空间、音频、3D、游戏视觉全部做成独立产品线。它们可以保留在长期规划，当前不作为完成前提。

同样，先支持一个主宿主，不代表未来只能支持一个；**统一协议是为了以后扩展，不是要求今天就同时完成所有适配。**

### 第二阶段：让审美与方法真正变成可复用能力

这里才是你前面大量调研最有价值的地方。

一项值得进入正式能力库的方法，应当能够展示：

适合什么任务、使用了哪些来源、输入是什么、结果是什么、比原来改善在哪里、失败边界是什么、如何撤回。

审美不能简单压成一个总分。排版、品牌适配、可读性、视觉新意和可制作性应能分别解释，模型评价与人的判断也应分开。

**先让少量方法在真实案例中证明价值，再扩展分类和覆盖面。**当前能力库代码主要做只读来源投影，资格化证据没有真正接入，这与“已经拥有一套会设计的技能系统”还有明显区别。fileciteturn43file0L2-L2

### 第三阶段：验证多人需求，再扩宿主、插件和商业化

是否值得成为独立商业产品，不能只从架构推导。

建议用少量外部设计师的真实任务检验：他们是否愿意导入已有作品，是否理解修改流程，是否在第二次任务中再次使用，是否觉得它比直接使用宿主加通用 Agent 更省事。

这是待验证的产品假设，不是目前已经成立的市场结论。

**我不建议现在做插件市场、团队权限体系、通用节点编排器或独立模型管理平台。**当具体使用需求出现，再扩这些能力。

你的长期优势应当是：

> **设计方法能影响作品，作品能被可靠修改，修改过程能留下可复用经验。**

而不是支持的模型最多、收集的仓库最多、导航里展示的领域最多。

## 九、接下来怎样推进，才不会又变成一轮文档和页面扩张？

我建议按三个交付目标推进，而不是继续按页面平均补齐。

### 先交付“统一项目工作区”

把新建、导入、查看、选择、修改入口收进同一套正式界面。首页先能继续项目，诊断信息退到次级位置。解决 UI 套件冲突，但不重做品牌。

这一阶段可以用明确标记的演示项目检查完整状态，不能只验证空页面，也不能把演示数据算成生产证据。

### 再交付“一次真实改稿”

拿你已有的一份真实作品：选中目标、修改、预览、生成新版本、对比、恢复。

这是检验前后端是否真正协同的最好切口。**连改一次标题都绕，继续增加领域和模型没有意义。**

### 最后交付“下一次还能接着用”

关闭、重启、恢复同一项目；找到正确版本；完成审核；导出；重新打开交付文件。

此后再扩大真实场景，而不是用更多菜单证明产品在成长。

**统一的是设计意图，不是强行统一所有软件的内部对象。**

## 二、你说的“资产库”，不是简单的素材库，也不是收藏了很多 SKILL 文件

我理解你最重视的资产，首先是**可以反复调用的设计专业能力**，图片、模板、脚本和案例都是它的载体。

建议将资产组织成以下六类。它们是同一资产体系里的类型，不是六个独立产品。

| 资产类型 | 应该保存什么 | 调用时解决什么 |
|---|---|---|
| **设计规范** | 品牌规则、版式约束、输出规格、适用范围、版本与出处 | 什么必须遵守，什么不能随意改变 |
| **设计方法** | 构图、排版、配色、视觉层级、材质与灯光、镜头节奏、声音设计等方法 | 怎样把目标转化为设计选择 |
| **风格与案例** | 多维风格标签、局部特征、案例拆解、正反例 | 参考属于什么类型，为什么有这种感觉 |
| **软件与制作知识** | 软件的对象模型、脚本接口、格式、限制、操作方法 | 用哪个工具、通过什么方式实现 |
| **提示词与执行配方** | 参数化提示词、脚本、节点流程、批处理方案、输入输出约定 | 把设计方案变成可以执行的内容 |
| **验证与修正经验** | 输入、结果、错误、人工修正、适用边界、复用条件 | 下次怎样更准确，而不是重复踩坑 |

这里有一个重要区别：

> **一条素材告诉你“它长什么样”；一条方法告诉你“为什么这样设计”；一个执行配方告诉软件“具体怎么做”。**

三者必须关联，而不是混成一个文件列表。

例如，一份“高对比几何海报”的能力资产，不应只有几张参考图和一段提示词。还应能关联到：适合的版式规律、字体层级、构图限制、可编辑对象组织方法，以及图像生成和矢量制作两种不同路线。

### 分类也不能只靠“风格名”

建议至少分开以下几种属性：

**设计品类、使用场景、风格特征、表现媒介、制作方法、交付形式。**

“科技感”不能代替全部分类。一份作品可以同时是：

> 品牌发布主视觉＋编辑式排版＋冷色高对比＋三维金属主体＋二维文字编排＋最终需要分层工程。

这些属性组合起来，才能真正检索到合适的方法和制作路线。

还应把**正式规范、经验方法、审美偏好**分开。某个案例很好看，不代表它的做法适用于所有任务；某种风格很流行，也不等于质量更高。

## 三、当你发截图、文件或音视频时，它应该具体做什么？

不是直接看一眼，然后返回“高级、简约、电影感、8K”。

我建议让它先形成一份**中立的设计分析与制作说明**，再决定输出。

### 第一步：判断输入能提供哪些信息

截图、原生工程、视频、音频，不应走完全相同的处理方式。

有可读取的原生工程，就优先利用其中真实的文字、对象、图层、场景、时间轴或素材关联；只有截图时，则分析可见构图、色彩、形态、字体特征和层次。视频还需要时间上的变化，音频需要声音与节奏分析，不能拿一张关键帧代替整个作品。

并且区分：

**实际读取到的结构、根据外观作出的推断、输入中无法确定的信息。**

例如，截图里可以观察到文字外观，但未必能唯一确定原字体；同一张渲染图也可能由多种模型、材质和灯光组合产生。因此，不能把“重建一个相似且可编辑的工程”说成“恢复了原工程”。

### 第二步：回答“是什么，以及为什么”

假设你发来一张海报，它的回答应类似：

> 这是一张活动主视觉。主要特征是非对称版式、大字号信息层级、低色数高对比和局部材质点缀。  
> 风格判断依据是这些具体特征，而不是只给一个风格名。  
> 参考里最需要保留的是标题比例、主体位置和留白关系；纹理、装饰和局部配色可以调整。

**分类需要解释依据，也应允许混合风格与不确定结论。**

### 第三步：从资产库找出“适用的方法”

不是只检索视觉相似的图片，而是同时寻找：

与当前品类匹配的规范、与构图匹配的方法、与目标输出匹配的制作知识，以及在相似任务上验证过的配方。

如果库中没有足够依据，应明确说明哪些建议来自模型推断，不能把临时生成的意见冒充已验证资产。

### 第四步：根据你想要的结果，决定制作路线

**“我想要什么文件”应当在制作前确定，而不是做完再想办法转换。**

同一张参考，你可能要：

> 只要风格分析；只要提示词；一张最终图片；可编辑矢量；分层 PSD；三维场景；动画工程。

这些是不同任务。它们可以共享分析结果，但不能共享一条不加区分的生产路线。

---

## 四、提示词不是自动化失败后的安慰品，而是一种正式交付

这是你本次澄清中非常重要的一点。

DESIGN-LAB 应当同时拥有三条正式输出路径。

### A. 分析与提示词输出

你选择目标生成软件或模型，DESIGN-LAB 输出适配内容。

应该包含：主体与内容、构图关系、文字要求、色彩与材质、镜头或运动要求、必须保持的部分、允许变化的部分，以及该目标实际支持的参数和参考素材使用方式。

**精准来自明确的约束和目标适配，不来自提示词越长越好。**

同一个设计意图，图像生成提示词、视频分镜提示词、三维场景说明和软件操作指令，应当分别生成，而不是换几个软件名称。

例如，你提出“主体和透视不要变，只调整材质”，系统需要把这变成明确的保留约束；如果目标工具没有足够的结构控制手段，就应指出风险，不能承诺靠一句话必然锁死。

### B. 软件自动化输出

目标软件具备可用接口、脚本或插件时，DESIGN-LAB 生成执行方案，通过适配器调用软件，再读取实际结果。

这条路径的完成标准是：

> **作品实际生成，目标格式正确，要求的编辑结构存在，结果可以打开和核对。**

不能把“脚本已生成”“请求已发送”“文件扩展名正确”当作制作完成。

### C. 混合输出

一项任务可以由多个软件接力：

> 外部生成工具制作背景或主体素材 → 原生设计软件组织文字、矢量和图层 → 动效软件制作动画 → 输出成片或工程。

这正是你的中立适配层可以发挥价值的地方。

但必须明确：**哪些部分是生成素材，哪些部分是原生对象，哪些部分仍需要人工操作。**

还有一个边界需要说清楚：

**用户只要求提示词，交付提示词就可以完成；用户要求 PSD，自动化失败后给出提示词，只能算替代方案，不能算 PSD 已交付。**

对于本身没有生成式输入能力的软件，也不能假设它能“粘贴提示词就开始工作”。此时应返回操作方案、脚本包，或者面向另一个现成生成工具的提示词。

---

## 五、你强调的“矢量、图层、分层、软件工程”，必须按真实结构验收

这是产品不能含糊的核心能力。

我建议每次任务都确定一个**交付约定**，明确格式之外还需要哪些结构：

| 你要求的结果 | 应该核对的内容 | 不能冒充它的东西 |
|---|---|---|
| **矢量文件** | 路径、形状、文字等是否满足约定；是否包含被允许的位图 | 把整张图片放进 SVG 或 AI 容器就称为全矢量 |
| **分层文件** | 分层粒度、图层语义、文字编辑、蒙版与效果是否符合要求 | 多复制几层整图，或者只有一张扁平图 |
| **三维工程** | 需要的对象、材质、灯光、相机与依赖是否存在 | 把一张渲染图放在平面上，就称为完成三维重建 |
| **动画／视频工程** | 约定的时间轴、合成、素材、关键帧或可调参数是否存在 | 只有最终视频，却声称交付可编辑工程 |
| **最终图片、视频或音频** | 尺寸、透明度、时长、编码等是否符合需求 | 有文件就认为合格，不检查内容和规格 |

**分层本身也有等级差异。**

“主体、背景、文字分开”与“每个装饰、文字、路径和效果都能独立修改”，工作量和制作方法不同。系统应当理解你要的编辑粒度，而不是只勾选一个“分层”标签。

对截图重建，应明确使用“重建的可编辑工程”；只有确实获得并读取原工程时，才讨论保留其原始结构。

这并不是降低目标，而是让“可编辑”变成可检查的能力，而不是宣传用语。

---

## 六、通过现成软件实现，技术路线是成立的，但要按操作适配

这不是只能停留在设想中的方向。现成软件已经提供了多种正式自动化入口。下面只是入口示例，**不代表 DESIGN-LAB 当前已经完成这些适配**：

| Illustrator | JavaScript、ExtendScript 等脚本环境 | 可以建立矢量文档与对象操作配方，实际支持范围需要逐项验证。citeturn901958search7 |
| Figma | 插件 API 可创建文字、矢量、Frame 和组件等节点 | 可以进行原生对象生成，但插件通常需要用户发起，不能默认当成无人值守后台服务。citeturn181765search0turn181765search6 |

因此，**我建议默认优先采用官方 API、插件、脚本和命令行；界面自动操作作为有界补充；提示词与人工执行包始终保留。**

“有界补充”意味着只对已验证的操作路径自动执行，识别到未知弹窗、文档不匹配或执行结果不确定时停止确认，而不是继续盲点。

适配器也不应该只有“支持 Photoshop：是／否”这样粗糙的状态，而应记录：

> 支持哪些操作、适用软件版本、是否需要用户启动、能读取什么结果、能输出什么结构、哪些情况会降级。

**中立适配是统一能力描述和交接方式，不是承诺所有软件都能一样自动化。**

## 七、按照这个定位，前端和后端都要重新调整主次

### 前端：资产库与分析入口，不是项目工作台

你明确说“不是工作台”，就不应该再把项目看板、审批队列、执行仪表盘和生产进度作为产品主体。

我建议前端主要服务于三个场景：

**查能力。**  
按品类、风格、方法、软件、目标格式查找资产。卡片应能看到案例或样本、适用场景、来源和验证程度；点进去能直接用于当前分析或生成方案。

**发内容。**  
上传截图、文件、音视频，或者直接描述需求；选择“分析”“提示词”“可编辑文件”“调用软件”等目标。简单任务不要求先创建项目、填写完整流程表单。

**取结果。**  
查看风格分析、参考依据、提示词、软件方案、实际产物与限制。需要执行时再显示软件连接、权限和运行结果。

软件连接、执行历史和诊断可以存在，但属于辅助功能。**有任务记录，不等于产品必须成为任务管理工作台。**

此外，你可以通过已有 Agent、软件插件或其他入口调用这套能力，不必强迫每次都打开 DESIGN-LAB 自己的页面。

### 后端：重点是知识调用与方案转换，不是再建一套通用 Agent 平台

建议把后端核心收敛成：

```text
截图／文件／音视频／文字需求
              ↓
       内容解析与设计分析
              ↓
  检索规范、方法、案例和制作知识
              ↓
       中立的设计任务说明
              ↓
    根据目标选择交付方式
       ↙       ↓       ↘
   精准提示词  执行包   自动调用现成软件
       ↘       ↓       ↙
       结果检查与反馈记录
              ↓
      经筛选更新能力资产
```

这个结构中，最需要自己建设的是“从设计理解到可执行方案”的连接。

现有模型负责理解与推理，现成软件负责生产，已有 Agent 可以承担执行载体；DESIGN-LAB 持有专业知识、设计约束、工具适配和验收方法。

**不需要为此训练一套独立基础模型，也不需要自建通用聊天平台或全功能编辑画布。**

反馈沉淀也不是“生成过一次就自动成为正确知识”。失败记录、模型建议和人工认可应分开保存；真正可复用的方法，要带着适用条件和结果证据进入资产库。

## 八、真正需要收敛的，是建设方式，而不是你的设计品类范围

我现在对“收敛”的建议，与上一轮不同。

### 不应该收窄的

**全品类目标、软件中立、可编辑交付、自动化与提示词双路径。**

这些不是多余需求，而是产品定义。

### 应该收敛的

**第一，知识保持一份，输出可以很多种。**  
不要针对每个 Agent、每个软件复制一套设计知识。中立知识与方法共用，软件专用部分放在适配配置和执行配方中。

**第二，统一交付语义，不统一全部软件内部格式。**  
统一描述“我要怎样的作品、哪些部分可编辑、哪些必须保留”，不要试图先造一个能完整替代 PSD、AI、三维场景和视频工程的万能格式。

**第三，提示词能力与自动化能力并行推进。**  
某个领域暂时没有自动化适配，不应阻止该领域的分析、方法检索和提示词服务；但也不能用“会写提示词”冒充已具备原生文件生产能力。

**第四，先证明资产被使用，而不是追求收藏数量。**  
每批知识建设都应回答：它影响了哪一次分析、让哪个方案更准确、减少了哪类制作错误。否则再多资产也只是库存。

据此，项目应有三条独立的验收线：

| 验收线 | 真正要证明什么 |
|---|---|
| **知识与分析** | 能找到相关规范和方法，风格判断有依据，不确定信息可辨认 |
| **提示词与方案** | 能针对目标工具和输出要求形成可用内容，并通过案例反馈改进 |
| **自动化与交付** | 能实际调用软件，生成符合结构约定的文件，重开核对，并妥善处理失败 |

**这三条不能互相冒充，也不应互相无条件阻塞。**

---

## 我的最终理解

你希望 DESIGN-LAB 具备的，不是“里面有很多设计功能”，而是：

> **里面掌握了大量设计知识与方法；你给它参考和需求，它能理解、判断、选择方法，并把方案交给合适的现成软件执行。你需要提示词，就给精准提示词；你需要图片、动画或原生工程，就在具备条件的情况下自动生成并验证。**

因此，项目真正应该优先补的是：

**可调用的专业资产、可信的设计分析、面向不同软件的方案转换，以及按交付目标验证的自动化能力。**

而不是先把一个“工作台”做得越来越大。

**一句话：DESIGN-LAB 应该成为跨设计品类、跨软件的专业能力层——知识归它组织，方案由它形成，生产交给现成软件，结果由它协助检查。**

## 一、先明确最重要的分工：知识归 AAOS，不等于 DESIGN-LAB 失去自己的专业能力

这里必须分开三个问题：

**谁保存这条知识？谁负责它的专业含义？谁把它用于实际制作？**

例如，“某种版式方法”的正文、出处、案例解释和修订历史，可以长期保存在 AAOS；但它适合什么设计问题、怎样转换成排版参数、怎样用于 Photoshop 或 Illustrator，仍由 DESIGN-LAB 负责。

因此，合理关系不是：

```text
AAOS：存文件
DESIGN-LAB：读文件，然后让模型随便发挥
```

而是：

```text
AAOS：长期知识、来源、关系、版本与学习

DESIGN-LAB：设计领域理解、方法选择、方案转换、
            软件适配、结果检查与专业反馈

现成软件：图形、图层、场景、时间轴、音视频与最终产物
```

**AAOS 是知识基础，DESIGN-LAB 是设计专业能力层。**

### 资产应该按性质分配，而不是全部搬往同一个地方

| 内容 | 长期放在哪里 | DESIGN-LAB 保留什么 |
|---|---|---|
| 设计教程、研究资料、规范文档、案例解释 | **AAOS** | 授权引用、任务所需片段、专业分析 |
| 设计方法正文、风格定义、原则与反例 | **AAOS** | 设计领域维护职责，以及对应的执行方式 |
| 软件专用提示词模板、自动化脚本、制作配方 | **DESIGN-LAB 的能力包** | 版本、参数、支持范围、测试和降级方式 |
| 已部署的方法摘要与规则 | **DESIGN-LAB 的有界只读快照** | 离线使用所需内容及其知识来源版本 |
| PSD、AI、三维工程、动画工程、音视频产物 | **所属设计任务与用户指定资产位置** | 产物引用、版本、检查结果和交付记录 |
| 可复用的纠正与制作经验 | **先成为候选，再进入 AAOS** | 本次任务的完整执行记录 |
| 个人学习记录、跨任务偏好 | **AAOS** | 当前任务使用的偏好和临时覆盖项 |

**统一资产目录，不等于所有资产必须物理集中存储。**

你在 DESIGN-LAB 中看到的一张完整能力卡，可以同时展示 AAOS 的知识、DESIGN-LAB 的执行配方，以及授权案例的预览。用户看到的是连贯的能力，底层不需要把资料、代码、模型和作品混进一个仓库。

另外，**知识保存在 AAOS，不代表只能打开 AAOS 才能编辑。**你可以在 DESIGN-LAB 中纠正风格或补充方法，由 DESIGN-LAB 通过 AAOS 的正式接口提交修订。关键是同一条知识只有一个长期主版本，而不是两端各改一份。

---

## 二、DESIGN-LAB 真正需要建设的，是“知识变成能力”的转换层

知识联合之后，项目最有价值的部分不再是“收藏多少资料”，而是完成三次转换。

### 第一次：从资料中提炼设计知识

AAOS 可以负责通用的原件保存、解析、版本与定位；DESIGN-LAB 负责识别设计专业含义。

一张参考图，不能只得到“极简、科技感、海报”三个标签，而应该能拆解成：

> 信息层级怎样建立，主体与留白如何分配，字体与图像怎样形成关系，哪些特征构成风格，哪些只是这张图偶然出现的装饰。

这一步还要区分：

**画面实际可见的事实、来源明确讲过的原则、模型推断、你的个人偏好。**

这些内容可以一起保存，但不能混成同一种“知识真相”。

同样，不是所有输入都必须进入 AAOS。你临时上传一张图，只要求分析和生成提示词，可以只在 DESIGN-LAB 的任务范围处理。**知识联合不能变成“上传即永久入库”。**

### 第二次：把知识整理成可调用的能力包

我建议把 **“能力包”作为 DESIGN-LAB 的主要复用和部署单位**。

它不是一个庞大的插件，也不要求每个领域做一套软件。它是一份能被实际调用的设计方法及其执行方式。

一个合格的能力包，至少应该回答这些问题：

| 组成 | 必须回答的问题 |
|---|---|
| 解决的问题 | 它帮助完成什么设计任务？ |
| 适用条件 | 适合哪些品类、媒介、输入和目标？ |
| 参数与约束 | 哪些能调整，哪些必须保持？ |
| 方法步骤 | 为什么按这个顺序处理？ |
| 输出方式 | 返回提示词、执行包，还是调用软件？ |
| 检查方式 | 怎样判断结果是否满足要求？ |
| 失败与降级 | 做不到什么，失败后怎么继续？ |
| 知识来源 | 使用了 AAOS 中哪些知识及哪个版本？ |

例如，“保持品牌一致性的多尺寸视觉适配”可以是一个能力包。它可引用 AAOS 中的品牌规范、版式原则和相关反例，再提供不同软件的执行方式。

**这比把几十份 SKILL 全文塞进一次提示词更接近你要的能力。**

### 第三次：把中立能力转换为目标软件可用的内容

设计方法本身不绑定软件，但它的执行形式可以不同。

同一个设计目标，可以生成：

```text
图像生成工具：参考使用说明＋生成提示词＋可用参数

矢量软件：对象计划＋文字与路径操作＋保存与检查步骤

分层图像软件：图层组织＋蒙版／效果处理＋局部修改方案

三维软件：场景对象＋材质／灯光／相机＋渲染与工程检查

音视频软件：素材组织＋时间／节奏关系＋合成或剪辑操作
```

这些都是**适配输出**，不是 DESIGN-LAB 自己实现绘图、建模、剪辑和渲染引擎。

这里的核心要求是：

> **一份设计意图，多种目标适配；一份长期知识，不为每个软件重复建库。**

## 三、全品类能力应该怎么增强？靠组合，不靠不断增加独立模块

你的全能型目标应该保留。

但不建议把“平面、包装、空间、三维、视频、音频……”全部提前做成独立模块，每个模块再复制一份知识库、提示词库和执行系统。

我建议形成一个可组合的能力结构：

### 通用方法作为基础，专业领域增加约束，软件适配负责执行

例如，构图、层级、对比、节奏、色彩关系、视觉一致性，可以作为跨场景的方法基础。

到了具体领域，再增加不同的专业条件：

> 平面作品需要考虑文字与版式；三维作品需要对象、空间、材质和相机；动画需要时间关系；音视频需要素材与节奏组织。

这不是把所有领域粗暴混合，而是让可复用部分只维护一次，专业差异明确表达。

### 分类要采用多个维度，而不是一棵越来越深的目录树

建议使用以下组合：

| 分类维度 | 作用 |
|---|---|
| **设计领域与使用场景** | 判断问题属于什么专业范围 |
| **感知特征** | 描述构图、字体、色彩、材质、空间、运动与声音特征 |
| **风格与流派** | 描述风格关联、混合关系和判断依据 |
| **设计方法** | 关联具体解决问题的方法 |
| **目标产物** | 图片、矢量、分层文件、场景、工程、成片等 |
| **工具与条件** | 软件、版本、接口、硬件和人工参与要求 |
| **实际能力范围** | 能分析、能给提示词、能自动执行、能交付原生工程 |

AAOS 管理共同概念的标识、别名、关系和版本；DESIGN-LAB 维护设计领域的定义及适用性。

分类语义可以借鉴 SKOS 的首选名称、别名、上下位和关联关系。**借鉴这些概念，不意味着必须新装一套图数据库或实现完整本体系统。**citeturn529303search0

最重要的是，不要再用一个笼统的“已吸收”表示所有能力。一个方法可能已经能准确解释和生成提示词，却还不能自动操作某个软件；另一个脚本可能执行稳定，却不具备复杂参考图的理解能力。

**这些差异应当显示出来，而不是强行归成一个总完成度。**

## 四、AAOS 与 DESIGN-LAB 的联合，需要的是双向循环，而不只是搜索接口

只让 DESIGN-LAB 搜索 AAOS，仍然只是单向取资料。

你真正需要的长期循环应当是：

```text
资料、研究与经验
        ↓
AAOS：保存、组织、关联、修订
        ↓
为当前设计任务提供有范围、有版本的知识
        ↓
DESIGN-LAB：分析、选方法、生成提示词或执行方案
        ↓
现成软件：制作与输出
        ↓
DESIGN-LAB：检查、记录你的修改和实际问题
        ↓
可复用且允许共享的经验候选
        ↓
AAOS：保存候选、补充反例、修订知识
        ↓
DESIGN-LAB：验证并更新相应能力包
```

### 用一个具体例子说明

假设你提供一张**允许用于个人研究的品牌主视觉**，要求：

> 判断风格，生成适配某个工具的提示词，同时尝试制作可编辑分层文件。

系统首先分析可见特征，再向 AAOS 请求相关的版式、品牌与制作方法；固定这次使用的知识版本，形成提示词和原生制作方案。

你随后纠正：

> “这个不是科技风，主要是编辑式排版。材质只是局部表现，不要让它主导判断。”

这次纠正不应该只留在聊天记录里，但也不能立即变成“以后遇到金属都不是科技风”的通用规则。

更合理的处理是：

**DESIGN-LAB** 保存本次判断、你的修正和对应依据，提出“风格判断中应区分版式主特征与局部材质”的候选经验。

**AAOS** 保存候选，关联原方法与反例，按适用范围处理后形成新版本。

**DESIGN-LAB** 再用相关案例检查：新方法有没有减少误判，有没有同时损害其他场景。确实改善后，再更新正式能力包。

**这才是从使用中增长能力，而不是简单积累聊天记录。**

## 五、联合接口先做窄，不要又变成一项庞大的平台工程

我建议第一阶段只建立三个语义能力。下列是建议契约，不是我已经核实存在的 API 名称。

| 联合能力 | 作用 |
|---|---|
| **获取知识上下文** | 查询或读取授权知识，返回相关内容、版本、出处、适用条件和限制 |
| **提交候选与修正** | 提交经过允许的观察、纠正或方法草稿，不自动升级为已验证知识 |
| **读取回执与变更** | 确认是否受理，读取新版本、冲突、拒绝、撤销或失效信息 |

第一批不需要消息中间件、分布式事务和复杂服务编排。有界的本机接口、版本化合同，必要时加导入导出包，就可以开始验证。

### 每次知识调用要固定“这次用的是什么”

至少应该保留：

```text
知识标识＋具体版本
来源与片段位置
内容摘要或哈希
允许用途与原作用域
适用条件与不确定性
必要的新鲜度／失效信息
```

这些信息不必全显示在普通界面里，但系统要能回答：

> 这份提示词为什么这么写？这个操作方案基于哪个方法？方法更新之后，哪些能力需要重新检查？

来源关系可以参考 PROV 对“使用、生成、派生、修订和失效”的表达。这里同样是借用语义，不是先做一套庞大的知识追踪平台。citeturn376251view0

### 数据写入必须由各自系统完成

DESIGN-LAB 向 AAOS 提交内容，不应直接打开并修改 AAOS 的数据库；AAOS 也不应该直接修改 DESIGN-LAB 的任务、工程和适配代码。

AAOS 当前实现方向已经明确由 Core 管理正典写入，并将跨项目仓库和业务状态分开。联合应该接在这种边界上，而不是绕过它。fileciteturn60file0L2-L2fileciteturn61file0L2-L2

写入还要能安全重试：同一个请求重复发送，不能重复产生多条知识；基于旧版本的修正发生冲突时，应返回冲突，而不是覆盖新内容。

### MCP 可以接，但不能把 MCP 当成整个架构

MCP 的资源与工具机制可以分别承载知识读取和设计能力调用，但它只是接入方式。知识是否可信、当前是否允许使用、脚本是否可以执行，仍须由你的产品合同与权限机制判断。citeturn376251view1turn376251view2

**协议中立，比“所有功能必须走某一种协议”更重要。**

## 六、知识交给 AAOS 后，DESIGN-LAB 仍应独立可用，但不再建设第二套长期知识库

这两件事不矛盾。

我建议 DESIGN-LAB 保留一个很窄的知识读取接口，背后可以接：

**AAOS 实时知识服务，或者已授权的固定知识快照。**

快照是部署时需要的有限内容，不是另建一套可任意编辑、持续扩张的知识系统。

### AAOS 不在线时

已经取得、仍适合当前用途的知识和能力包，可以继续用于分析、提示词生成与允许的执行任务，同时显示使用的版本和新鲜度。

需要发送的合规反馈暂存，恢复连接后再提交。

但是，**涉及必须复核的最新条件、未知权利或已知失效内容时，不能因为离线就假装检查通过。**可以继续的创意探索和必须停下的正式操作，要分别处理。

### AAOS 更新知识时

不能直接让所有正在运行的设计任务突然改变行为。

建议采用：

> **当前任务使用固定快照；新知识用于后续任务；需要重算时明确创建新一轮。**

某条方法被撤销或某个执行配方被禁用时，应影响后续调用，并让依赖它的能力进入需要检查的状态，而不是继续显示“正常”。

### AAOS 还未具备接收条件时

设计方法可以暂存，但从现在起就按未来的知识标识、来源、版本与候选合同整理。

**暂存是迁移过渡，不应成为再造第二知识库的理由。**

也不必等 AAOS 的所有远期功能全部完成。第一条联合只需要它能可靠地完成本次所需的保存、读取、引用、修订和回执。

## 七、前端应该变成“联合能力入口”，而不是把 AAOS 和 DESIGN-LAB 拼成两个工作台

你不希望 DESIGN-LAB 成为工作台，这一点应当继续保持。

我建议主要界面只围绕三个使用场景组织。

### 1. 能力资产库：查找并使用专业能力

你看到的不是大量仓库名和状态码，而是：

> 它能解决什么问题，适合什么风格和品类，有什么示例，能返回提示词还是能操作软件，能交付什么。

一张能力卡可以联合展示：

**AAOS 的方法与案例解释＋DESIGN-LAB 的执行配方＋实际测试结果＋当前软件条件。**

搜索和展示可以统一，底层归属不用强行统一。完整知识阅读和关系整理可以跳转 AAOS；小范围纠正也可以在 DESIGN-LAB 内完成，再通过接口保存。

### 2. 分析与生成：直接发内容，直接选目标

入口应该很直接：

> 上传截图、文件、视频或音频，或者描述需求 → 选择要分析、要提示词、要可编辑文件或要调用软件。

系统可以根据输入推断默认目标，但重要信息不清楚时再询问。**不应要求每次先创建项目、填完整 Brief、选流程、再进入分析。**

输出先给真正有用的内容：风格与品类判断、依据、所采用的方法、适配的提示词或执行方案、可获得的结果。

来源与技术细节可以展开查看，但关键局限不能藏起来。

### 3. 历史与纠正：找回结果，并让经验能够复用

这里保存之前的分析、提示词、执行结果和你的修正。

你可以明确表达：

> “只对这次任务有效。”  
> “记为我的偏好。”  
> “这是对方法的纠正，提交到知识库。”

**这三个含义不一样，不能由系统自行混成永久记忆。**

软件连接、AAOS 连接、执行诊断和版本信息放在次级设置里。一次任务可以有进度面板，但进度面板不应成为产品主体。

## 八、双向学习要增强，但必须防止“越积累，越固化错误”

我建议把学习分为两条。

### 给人使用的学习

AAOS 可以围绕设计方法组织原理、实例、反例、练习和你的学习记录。

DESIGN-LAB 不只是返回结果，还可以按需要解释：

> 为什么这个构图更合适？为什么这个参考不能直接推断为某种风格？为什么矢量路线和图像生成路线会产生不同的编辑能力？

你完成了一次制作，也可以沉淀为一次可理解的学习经历。

### 给 AI 使用的改进

AI 侧主要改善的是：

**检索到的知识、选择方法的条件、提示词模板、操作配方和结果检查。**

不能把这些变化说成“模型权重已经自动训练”，也不能把“一次结果更好”说成能力已经全面提升。

建议至少区分以下评估：

| 评估对象 | 检查什么 |
|---|---|
| 知识 | 来源、版本和解释是否可靠 |
| 风格分析 | 判断依据是否充分，是否能识别混合风格和不确定性 |
| 提示词 | 是否真正适配目标工具与输出要求 |
| 软件操作 | 是否完成指定动作，是否影响无关内容 |
| 原生交付 | 对象、图层、场景或时间轴是否达到约定 |
| 人工使用 | 是否减少错误和返工，下一次是否愿意继续使用 |

**收藏量、使用次数和自动评分，都不能单独证明专业能力。**

同时，不要让知识治理重新变成操作障碍。AAOS 当前的内容原则已经明确：原创笔记、灵感、假设和未复核结果可以先保存；识别核验、专业依据与人工认可分别处理。这个原则应该延续到联合设计中。fileciteturn60file0L2-L2

---

## 九、客户隔离与权利边界，必须进入数据流，而不是写在文档末尾

未来联合最容易出问题的，不只是接口失败，而是资料在不知不觉中跨域。

**客户原件、客户名称、客户方法、产物、私人会话与未授权素材，不进入默认的 AAOS 回流路径。**

“我把客户名字删掉了”不等于获得了知识迁移授权。客户项目继续隔离；任何允许出域的独立通用条目，都需要另外有明确的适用授权与审查。

而且权限过滤不能只在最后下载文件时发生。受限内容的标题、缩略图、摘要和搜索片段，同样不应出现在不允许访问的地方。

还要防止另一个问题：

> **收录了一份软件脚本教程，不等于允许系统执行教程里的脚本。**

第三方 SKILL、安装命令、脚本与文档先是输入材料。只有经过明确的能力适配、版本和操作范围确认，才成为可执行内容。

这能同时满足你要的“大量吸收”和“自动化操作”，又不把两者之间最重要的资格步骤省掉。

## 十、现有项目怎么改，才能既增强，又不再无限扩张？

我建议按三个阶段推进，不重新推倒整个工程。

### 第一阶段：先纠正定位和归属，把联合接口做出来

当前 DESIGN-LAB 的边界文件仍然把 `apps/workbench/` 定义为唯一设计控制面，并将项目、方向、版本、评审和交付编排作为主要职责。**它与这次你明确的“能力资产系统，而非工作台”确实存在需要更新的差量。**fileciteturn62file0L2-L2

这里应该做一次明确的定位与职责调整，而不是再叠加一份同样自称最终权威的蓝图。

保留已经有价值的服务、适配、原生任务、版本恢复和检查逻辑；重新组织它们的入口和对外能力。

这一阶段的实际成果应当是：

**一种统一知识引用方式，一条 AAOS 知识读取路径，一条候选回流与回执路径。**

不是先迁移所有资料。

### 第二阶段：提示词和自动化两条产品能力并行验证

**提示词链：**

```text
输入内容 → 相关知识 → 专业分析 → 目标提示词 → 用户纠正 → AAOS 候选
```

**自动化链：**

```text
目标与约束 → 知识＋执行配方 → 现成软件 → 原生结果
→ 重开检查 → 可复用经验候选
```

用不同设计品类的代表案例检查能力。它们是覆盖测试，不是把项目永久收窄为某个品类。

**自动化没完成，不阻止提示词功能；提示词完成，也不替代原生文件交付。**

### 第三阶段：分批迁移长期知识，停止双主维护

每批迁移都要完成：

> 分类与权限检查 → 保留旧标识和原件 → 导入 AAOS → 读取核对 → 建立旧新引用映射 → 切换读取与写入归属 → 验证恢复。

切换后，该批在 DESIGN-LAB 中的旧知识源应变成只读档案或可追溯快照，不再与 AAOS 同时接受独立修改。

脚本、能力包、适配代码和用户作品，不因为这一批知识迁移就整体跟着搬走。

**旧资料先保留为恢复档案，删除与大文件清理另行处理。**

### 这些内容现在不要再扩建

不再建设独立的通用笔记系统、长期知识图谱引擎、第二套完整检索库；不再发展大型项目工作台；不自研生成式设计软件；不因联合增加一套模型权重库；不让所有调用必须绕经 WORK-LAB。

WORK-LAB 在需要跨 Agent、跨项目调度时提供公共治理即可。它不是 AAOS 与 DESIGN-LAB 之间每一次知识读取的必经中间层。

---

## 最终增强后的项目定义

这些属于**设计专用自动化**，不是重建编辑器。

同样，下面两个概念也不矛盾：

**不做大型工作台**，但可以有轻量的资产界面、请求入口、预览和运行记录。

**知识长期交给 AAOS**，但 DESIGN-LAB 可以保留运行需要的方法快照、执行配方和软件适配代码。

因此，应该撤回的不是安全边界，而是过度扩大的限制：

> “不做通用 Agent 平台”可以保留；  
> “因此不允许任何规划、执行、观察和恢复循环”应该取消。

**否则项目会出现一个根本矛盾：你要求它自动设计和自动操作，架构规则却把执行能力全部排除掉。**

---

## 二、现成 Agent 确实能操作软件，但不能因此省掉你的专业基座

本次复核中，有几个直接影响路线的事实。

### Codex：可以操作桌面，但执行环境有约束

OpenAI 当前官方文档确认，满足地区、版本和权限条件时，ChatGPT 桌面应用中的 Work/Codex 可以使用 Computer Use 操作桌面软件。Windows 下使用的是当前桌面，会占用前台鼠标键盘；官方也建议，对重复性操作和数据访问，优先采用合适的结构化集成。citeturn982145view5

所以，正确理解是：

**Codex 可以成为执行器，不代表 DESIGN-LAB 只需把一句需求转发给它。**

项目仍需要管理目标文件、修改范围、允许使用的工具、输出位置、失败状态和验收标准。

### Figma：已经不只是“给 Agent 截图和设计信息”

Figma 官方 `use_figma` 能通过远程 MCP 创建、修改原生 Frame、组件、变量和自动布局。与此同时，席位、文件编辑权限，以及图像、自定义字体等当前限制仍需分别核对。citeturn982145view6

这证明：**有些原生制作不需要让 Agent 模拟鼠标；也不能用普通插件的生命周期限制，推断整个软件不能自动化。**

### 豆包：要区分普通产品、模型与 UI-TARS

字节跳动的 UI-TARS Desktop 是可以核实的公开电脑操作项目。它值得进入执行器候选池。citeturn112181view2

但它不能直接证明你的豆包账户已经具备某种本机设计软件控制能力。**豆包普通客户端、豆包工作、UI-TARS、云电脑和模型服务，应分别记录接入方式，不能混写成一个“豆包已支持自动操作”。**

### 软件接口“正常返回”，甚至都不一定代表操作成功

Photoshop 官方文档明确说明：某些动作失败时，`batchPlay` 的 Promise 仍可能正常完成，但返回结果中带有错误。citeturn982145view7

这件事对项目很重要：

> **请求发送成功 ≠ 软件动作成功 ≠ 文件生成成功 ≠ 设计交付合格。**

这四层判断不能省。**DESIGN-LAB 的价值，恰恰可以建立在比通用 Agent 更了解这些专业条件之上。**

## 三、建议采用“双向接入、同一套核心”，而不是选择唯一执行器

你的系统应该同时支持两种使用方式。

### 方式 A：你在 Codex 等环境里使用 DESIGN-LAB

例如，你直接对 Codex 说：

> 用 DESIGN-LAB 分析这张图，按照品牌规范制作可编辑版本，文字保持可修改。

此时：

```text
你 → Codex
      ↓
调用 DESIGN-LAB 的知识、分析、制作和检查能力
      ↓
通过适配器操作现成软件
      ↓
实际产物与检查结果返回给你
```

DESIGN-LAB 不必成为你每次都要打开的独立界面。

### 方式 B：你从 DESIGN-LAB 发起，系统选择执行器

你上传文件并说明目标，DESIGN-LAB 判断哪些步骤自己有可靠配方，哪些需要外部 Agent。

```text
你 → DESIGN-LAB
          ↓
形成设计目标、约束和制作计划
          ↓
自有操作／外部 Agent／外部生成服务
          ↓
现成软件生产
          ↓
DESIGN-LAB 检查与交付
```

**这两种方式必须共用能力库、任务约束和结果检查，不能各写一套。**

还应有一条工程规则：

> **同一个任务在同一时刻，只能有一个负责推进流程的主体。**

外部 Agent 正在负责一个步骤时，DESIGN-LAB 不应同时重新规划并修改同一个文档；反过来也一样。否则很容易出现相互重试、重复创建对象和状态覆盖。

## 四、“基座地基”具体是什么？不是提示词文件夹，而是六项专业能力

### 1. 设计需求理解

首先判断用户到底要做什么：

**风格分析、借鉴某种表现、原创设计、参考重建、局部改稿、格式转换、原生工程交付，还是质量检查。**

这些任务不能共用一条默认流程。

例如，“参考这张图的材质”不等于“照着这张图重新构图”；“把它做成矢量”也不等于“输出一个 SVG 扩展名”。

这一层应该把模糊要求转成明确目标，但不要求用户先填一整套项目表单。

### 2. 方法与规范选择

它不只是找到相似图片，而是选择：

> 哪些规范必须遵守，哪些方法适用于当前任务，哪些只是参考风格，哪些属于个人偏好。

同一个设计结果可能同时涉及版式、字体、材质、镜头和运动。知识调用应该保留这些分工，不把它们压成一个“科技感”或“高级感”标签。

分类结构可以借鉴 SKOS 的概念标识、别名与关联方式，但不需要先建设一个庞大的本体工程。citeturn351721view3

### 3. 设计方案到软件操作的转换

这是最应该由 DESIGN-LAB 掌握的核心。

例如：

| 你的表达 | 系统应该形成的可检查操作 |
|---|---|
| 保持版式，只改文案 | 定位目标文字对象，更新内容，检查溢出，保持约定的其他对象不变 |
| 不改透视，只调整材质 | 固定相机与对象变换，修改允许的材质参数，再核对固定条件 |
| 做成分层文件 | 明确分层粒度、文字是否可编辑、哪些是位图、哪些需要蒙版 |
| 动画更有呼吸感 | 将意图转成可调的时间、幅度和节奏方案，而不是只添加一句形容词 |
| 按品牌规范适配多个尺寸 | 引用同一品牌规则，按不同画幅重新检查层级、留白和内容完整性 |

**这层不能只靠“给模型写一个更长的系统提示词”。**它需要任务结构、参数、软件能力和检查规则共同参与。

### 4. 可复用的原生操作

我建议从“语义操作”组织能力，而不是从点击轨迹组织能力。

不要只保存：

> 点击某个坐标，再按某个快捷键。

应该保存：

> 在已确认的目标文档中，找到当前版本对应的可编辑标题对象，修改文字，核对字体和溢出，保存新副本，并检查其他对象是否被意外改变。

一个语义操作可以有不同实现：原生 API、脚本、插件、界面操作，或者暂时人工完成。

**方法保持中立，实现可以专业化。**

### 5. 实际结果验证

验证至少分三部分：

**结构正确吗？**文字、路径、图层、相机、时间轴和依赖是否符合要求。

**视觉或听觉结果合适吗？**构图、清晰度、节奏、品牌一致性是否达到目标。

**交付完整吗？**文件能否重开，素材是否缺失，导出是否符合要求。

结构检查可以更多自动完成；复杂审美判断可以由模型辅助，但不能把模型自评当成你已经认可。

### 6. 中断、接管与恢复

自动化不是只有顺利运行的一条路径。

它还必须处理：

**目标文件变化、未知弹窗、软件忙碌、用户接管、操作超时、生成失败和重复请求。**

关键原则是：**先查上次有没有完成，再决定是否重试。**

不能通过盲目重新执行解决一切，也不能因为任务超时就关闭共享宿主或删除用户作品。

## 五、怎样让本项目真正比外部 Agent 更强？

不应该把目标设成“在所有电脑任务上超过 Codex”。

更合理、也更有价值的目标是：

> **在经过适配和验证的设计操作上，比通用 Agent 从头探索更稳定、更准确、更省返工。**

这种优势可能来自四个地方。

**第一，知道设计约束。**  
通用执行器可能完成“改标题”，但你的能力包还要求保持文字可编辑、检查文字溢出、保持其他对象不变。

**第二，知道软件对象。**  
可以读取真实对象时，就不必反复根据截图猜测控件和图层。

**第三，知道如何验收。**  
不是看到一个新文件就结束，而是重新打开、检查结构和依赖。

**第四，知道失败后的继续方式。**  
能够对账并恢复，不是每次失败都从头再来。

这也给出一条很重要的积累路线：

```text
外部 Agent 探索新流程
          ↓
记录真实操作、错误和人工修正
          ↓
提炼成参数化的专业操作候选
          ↓
在不同输入上测试
          ↓
成为 DESIGN-LAB 的正式能力
```

**外部 Agent 可以帮助探索，DESIGN-LAB 负责把经验变成稳定能力。**

但不能把一次成功录屏直接转成永久脚本。需要去除固定账号、临时路径、私人内容和偶然坐标，增加前置检查、结果断言及恢复方法。

---

## 六、执行路线怎么选？建议采用原生、界面、生成三路协作

| 路线 | 适合承担什么 | DESIGN-LAB 应控制什么 |
|---|---|---|
| **原生 API／脚本／插件** | 已明确对象与参数的制作、批处理和局部修改 | 目标身份、操作范围、版本兼容、结果读回 |
| **视觉 GUI／外部 Agent** | 缺少结构化入口、复杂导航、临时操作和受限恢复 | 桌面占用、步骤预算、权限、暂停与接管 |
| **生成服务／工作流** | 图像、视频、声音及中间素材生成 | 参考输入、参数、费用、任务状态和实际产物 |
| **人工接续／提示词包** | 暂无可靠自动化入口的任务 | 未完成原因、可继续的材料、不能冒充已交付 |

这些路线可以组合。

例如，ComfyUI 已有提交、队列、历史和 WebSocket 接口；它适合被外部调用，而不需要 DESIGN-LAB 重建节点编辑器。与此同时，提交进入队列只表示请求被接受，仍需读取执行结果和文件。citeturn351721view1

动效和音频也有现成软件的脚本路线，例如 After Effects 脚本和 REAPER 的 ReaScript。它们证明可采用现成生产软件的方向成立，不代表你的本机版本和每个目标操作已经验收。citeturn351721view2turn982145view4

**选择顺序建议是：先看目标所需能力，再看已验证接口，最后才看哪个执行器最方便。**

---

## 七、能力包应该怎样设计，才能真正交给其他软件使用？

建议每个可执行能力包含以下内容，但普通知识条目不需要强制填写全部执行字段。

```text
能力用途与不适用范围
输入、参数与目标产物
使用的 AAOS 知识版本
必须保持／允许改变的条件
目标软件、版本和执行方式
操作步骤或生成方案
权限、预算和人工介入点
检查规则、失败和恢复方式
验证案例与已知限制
```

对外可以有几种入口：

**给人使用的能力卡，给 Agent 使用的 Skill，给程序调用的 API／CLI／MCP。**

但底层必须是同一套能力实现。

Agent Skills 的规范适合封装说明、脚本、引用和资产并按需加载；MCP 适合工具发现与调用。**二者都是接入方式，不是专业知识、权限系统或验收本身。**citeturn982145view0turn982145view1

还有一条必须严格区分：

> **第三方资料里的脚本，是待审阅的输入；本项目已经批准和验证的操作配方，才是可执行能力。**

不能因为从某个高星仓库下载了 SKILL，就让其中的命令自动获得对本机软件、文件和网络的权限。

---

## 八、AAOS 联合不改变专业能力归属，而是让知识积累不重复

我建议保持这组分工：

**AAOS 保存长期知识，DESIGN-LAB 负责设计专业使用，现成软件负责生产。**

具体来说：

| 内容 | 长期归属 |
|---|---|
| 规范正文、方法解释、研究资料、来源、概念关系、个人学习 | AAOS |
| 软件适配、操作配方、生成模板、专业检查器与能力发布 | DESIGN-LAB |
| 原生工程、客户素材、任务产物 | 所属用户与任务的资产位置 |
| 经允许的专业纠正、反例和可复用经验 | 作为候选回流 AAOS |
| 当前执行所需的知识内容 | DESIGN-LAB 的有限版本快照，不形成第二主库 |

**知识保存在 AAOS，不等于必须离开 DESIGN-LAB 才能纠正知识。**你可以在结果页提出修正，由系统通过 AAOS 的接口提交。

但应区分：

> 只对本次有效；记为个人偏好；提出通用方法修订。

不能将三者自动合并。

联合也不能成为每次执行的硬性联网前提。固定且仍允许使用的知识快照可以继续支撑部分任务；需要最新授权、已知撤销检查或强制复核的操作，则不能假装通过。

**客户素材和私人会话不默认回流，删除客户名称也不等于获得共享许可。**

---

## 九、原生交付要提前确定，不要先生成图片再想办法“套格式”

这条对你尤其重要。

如果一开始就需要可编辑文字和矢量，制作路线应该从原生结构出发；如果只要最终图片，可以使用更自由的生成路线。

“分层”也要讲清楚：

**主体与背景分离、文字可编辑、每个装饰对象可修改、效果可调整，是不同的结构要求。**

目前已有专门做多层 RGBA 分解的候选组件，例如 Qwen-Image-Layered。但 RGBA 分解不等于恢复原始字体、矢量路径、智能对象和效果结构。citeturn351721view6

因此，建议把交付结果明确显示为：

> **实际得到什么结构，哪些结构未恢复，哪些内容经过重新制作。**

同样，不需要先发明一个替代所有工程的万能格式。OpenUSD 与 OpenTimelineIO 分别解决三维场景和剪辑时间轴等问题，不能据此承诺所有设计软件工程无损互转。citeturn351721view4turn351721view5

**中立的是目标和能力描述，原生文件仍尊重各自软件的结构。**

---

## 十、界面问题怎么解决？让界面服务于能力，不再反过来规定能力

前面的工作台方向，应当退出产品中心。

我建议保留三个主要场景：

### 能力资产库

用户看到的是“这项能力解决什么问题、适合什么输入、能输出什么、有什么案例”，而不是默认面对大量来源 ID、证据代码和未开放模块。

可以按品类、风格、方法、软件和交付类型筛选，但不能把不同分类轴混成同一层目录。

### 分析与执行入口

直接提交截图、文件、音视频或文字目标，选择要分析、要提示词、要自动制作还是要某种原生结构。

简单任务不要求先创建完整项目；持续改稿时再保留任务会话和版本。

### 结果与经验

显示分析依据、提示词或方案、实际文件、未完成事项、继续修改和知识纠正入口。

运行日志、软件连接和诊断退到次级界面。预览、比较和批注可以存在，但不延伸成第二套完整编辑器。

**更换 React、重新绘制全部 UI 套件、增加桌面壳，都不应该成为这次路线调整的前提。**先确定正确的任务与能力接口，再决定需要怎样组件化。

---

## 十一、接下来不再增加大蓝图，而是做五个能验证方向的单元

### 第一单元：一张能力卡真的能使用

选择少量有真实需求的方法，完成来源、适用条件、参数、目标生成包和检查说明。

不是先整理几百条，再等某天接入执行。

### 第二单元：一项自有原生操作完成往返

沿用现有适配基础，完成一次目标对象修改、保存新副本、关闭重开和结构检查。

这里是验证自有能力的起点，不是要求首先支持全部软件。

### 第三单元：一个外部 Agent 接入同样的目标和检查

让外部路线与自有路线处理同样的任务，比较结果，而不是给其中一方更多上下文和工具。

不能程序化接入的客户端，先保留人工交接，不标为无人值守服务。

### 第四单元：一次真实失败后能够继续

至少实际验证一种情况：超时但操作已完成、重复提交、目标文档被修改、未知弹窗或用户接管。

顺利完成一次，不够证明自动化可靠。

### 第五单元：一次允许的经验回流 AAOS

把一条真实纠正作为候选提交，获得回执，并在后续任务中读到准确的知识版本。

**不是复制整个运行目录，也不是把所有作品自动上传知识库。**

之后再按能力缺口扩展平面、矢量、三维、动效、音频等。**首批取样不改变你的全品类定位。**

---

## 最终判断

你补充的“自有自动化更强也可以”，让项目方向更完整了。

**我建议 DESIGN-LAB 既能被其他 Agent 当作专业能力底座调用，也能主动通过现成软件完成设计操作。**

最重要的不是先证明它整体比 Codex 或豆包更强，而是逐步做到：

> **同样的设计要求，有了 DESIGN-LAB，方法更明确、约束更准确、操作更稳定、原生结果更可信；已经跑通的专业流程，下次不必重新探索。**

这样积累下来的，才是你自己的长期能力，而不是某个模型版本的一次性表现。

本次没有在你的电脑上执行设计软件、安装候选、修改仓库或迁移 AAOS 知识。豆包账户的具体操作范围仍未核实；公开 UI-TARS 项目不能替代这一确认。

# 一、先把本次对话的真正结论收敛下来

本次对话并不是你在反复改变方向，而是在逐步纠正一个概念偏差：**我们之前过早把“专业能力系统”理解成了“设计项目工作台”。**

| 对话中明确的诉求 | 现在应采用的解释 | 不应继续沿用的理解 |

| 掌握大量设计规范、方法、风格与资产 | 建立可检索、可解释、可执行的专业能力体系 | 收集大量链接、图片和 SKILL 就算能力完成 |
| 不管什么设计品类 | 保留全品类目标，按实际能力深度分级 | 为了容易落地，永久变成海报或 UI 工具 |

| 给精准提示词 | 交付适配目标软件的完整生成方案 | 所有软件共用一段长提示词 |
| 自动操作现成软件 | 原生接口、脚本、插件、界面操作可以组合使用 | 自动化必须是模拟鼠标点击 |

应该收敛的是重复基础设施、产品形态和实现方式，而不是你的长期专业覆盖面。

# 二、重新定义项目：不是单纯资产库，而是“可执行的设计能力底座”

“资产库”这个说法没有错，但不足以覆盖你的目标。

一个普通资产库回答：

> 我有哪些素材、规范和方法？

你需要的系统还要回答：

> 当前问题应该用哪种方法？怎样落实到目标软件？怎样证明结果符合要求？失败后如何继续？

因此，我建议采用下面这个产品定义：

## DESIGN-LAB：全品类设计知识应用与专业自动化能力系统

它把四件事连接起来：

**设计理解 → 方法与规范调用 → 提示词或软件操作 → 结果验证与经验回流。**

我把其中最重要的一层称为**“设计方案转换层”**：将人的要求和设计知识，转换成目标软件能够执行、结果能够检查的方案。它不只是拼接提示词。

例如，你说：

> 保持参考图的构图和透视，只调整材质，最后给我可编辑工程。

系统必须进一步形成：

- 哪些对象、位置、相机或画面区域不能改变。
- 哪些属性允许调整。
- 输入中哪些结构真实存在，哪些只能推断。
- 哪种软件路线能保留所需编辑能力。
- 完成后检查哪些内容，而不是只看预览“差不多”。

**这层能力，才是你所说的“地基”。**

另外还要区分四个角色：

**模型负责理解与推理，执行器负责动作，设计软件负责生产，DESIGN-LAB 负责把专业意图和验收要求贯穿起来。**

一个模型很聪明，不等于它已经获得操作本机软件的能力；一个执行器能点击菜单，也不等于它知道什么才是合格的分层设计。

# 三、全网调研后的关键判断：外部 Agent 可用，但不能替代专业能力层

## 1. Codex 的电脑操作路线成立，但有具体环境边界

OpenAI 当前官方文档明确支持在相应桌面环境中使用 Computer Use；Windows 下操作发生在当前桌面，不能一边让它占用鼠标键盘，一边在同一会话中正常做其他工作。官方也建议，对数据访问和重复性操作，优先采用专用插件或结构化接口。citeturn714064view0

这意味着：

**Codex 可以是执行器之一，但“把任务发给 Codex”还不是完整的设计自动化架构。**

DESIGN-LAB 仍需知道执行环境、目标文件、允许修改范围、软件版本、产物位置和完成条件。

也不能默认所有消费级 Agent 都提供稳定的程序化调用接口。能在产品里手动发起一项任务，与能被 DESIGN-LAB 自动调用、取消并取得结构化回执，是不同能力。

## 2. 豆包相关能力需要拆开看，不能混用产品名称

字节跳动的 **UI-TARS Desktop** 提供了公开的多模态电脑操作基础，这是可核查的技术路线。citeturn714064view2

但“豆包普通客户端”“豆包工作”“UI-TARS”“远程电脑环境”和“模型本身”不能互相代替。

**本轮没有取得足够的一手产品资料来确认你当前豆包账户能操作哪些本机设计软件、能否被外部调用，以及能否可靠交付原生工程。**因此，可以把它列为执行器候选，不能直接写成已支持。

## 3. 专业软件的结构化操作，应该成为自有能力的优先方向

例如，Photoshop 官方提供 DOM 和 `batchPlay`，并建议优先使用较明确的 DOM 方法，必要时再使用底层动作描述。citeturn555812view1

对“修改指定文字图层”“保持其他图层不变”这种任务，我的判断是：**基于真实对象的受控操作，通常比每次重新截图找按钮更值得优先封装。**

但这不代表所有设计操作都有 API，也不代表有 API 就能无条件后台并发。必须按操作、宿主版本与运行方式记录能力。

## 4. Figma 的路线需要更新，不能继续套用旧限制

Figma 官方远程 MCP 的 `use_figma` 已能创建和修改原生 Frame、组件、变量与自动布局，并支持相应客户端。它仍有权限和功能限制，不能因此声称完整覆盖所有素材、字体和发布操作。citeturn714064view1

**普通插件不能后台运行，不等于 Figma 没有可用的 Agent 写入能力。**

这也说明：DESIGN-LAB 的适配知识需要持续更新，不能把一次调研的限制永久写成架构铁律。

## 5. 真正值得借鉴的，不只有 AI 设计软件

本轮有几类更贴近你目标的参考：

| 参考对象 | 值得吸收什么 | 不建议做什么 |
|---|---|---|
| **Eagle 的资产接口** | 视觉资产检索、元数据、预览与正式读写入口 | 直接修改软件私有数据库或元数据文件。citeturn800980search1 |
| **AYON 的生产发布流程** | 收集、检查、提取和整合产物的分阶段处理 | 为个人项目整套搬入大型影视管线平台。citeturn320978search4 |
| **OpenAssetIO** | 用稳定资产身份解析位置与发布关系 | 把它误当成现成知识库、文件库或完整管线。citeturn320978search1 |
| **Agent Skills、MCP** | 能力的可携带描述、按需加载和标准接入 | 认为套上 SKILL 或 MCP 就自动获得可靠性与权限控制。citeturn723740view0turn723740view1 |
| **Midscene、UI-TARS 等** | 作为可替换的界面操作基础 | 同时部署多套功能重叠的通用 Agent 框架。citeturn800980search8turn714064view2 |

**借鉴的是它们已经解决的局部问题，不是再拼出一个越来越重的平台。**

# 四、最终推荐：自有专业执行内核＋可替换外部 Agent

我不建议选择“只做资料库”，也不建议从零挑战通用电脑操作模型。

推荐结构如下：

```text
用户／现有 Agent／软件插件／轻型网页入口
                    ↓
        DESIGN-LAB 理解需求与交付目标
                    ↕
          AAOS 提供授权、版本化知识
                    ↓
       设计判断＋生成方案＋检查方案
                    ↓
              选择执行路线
       ┌────────────┼────────────┐
       ↓            ↓            ↓
  自有原生操作   外部 Agent 操作   提示词／人工执行包
  API/脚本/插件   GUI/复杂任务      无可用自动接口时
       └────────────┼────────────┘
                    ↓
               现成设计软件
                    ↓
      内容、原生结构、规格与完整性检查
                    ↓
       结果交付／恢复／允许回流的经验
                    ↓
                   AAOS
```

## 两种调用方向都应支持

**外部 Agent 调用 DESIGN-LAB：**

你在 Codex 等环境里提出需求，Agent 调用 DESIGN-LAB 的分析、知识、原生操作或检查工具。

**DESIGN-LAB 委派外部 Agent：**

你从 DESIGN-LAB 发起任务，遇到尚未封装的复杂操作时，系统向具备正式接入能力的执行器提交受限任务。

两种模式共用同一套专业知识、目标约束和结果检查，不能各建一套逻辑。

**一次任务只有一个负责推进流程的主体。**不要让 DESIGN-LAB 和外部 Agent 同时对同一文档自行规划、反复互相调用，形成无法解释的执行循环。

## 路线选择应按任务决定，而不是按品牌决定

建议默认顺序是：

> **已验证的原生操作 → 已验证的插件或工具接口 → 界面自动化 → 人工接续或提示词交付。**

这是优先级，不是死规则。某个外部 Agent 在特定任务上更好，就用它；某个操作原生 API 不完整，界面操作反而覆盖更多，也可以使用。

**真正的中立，是能够根据证据替换执行方式，而不是强迫所有工具表现一样。**

# 五、自有自动化内核应该拥有多强？重点不是“多会点击”，而是这六项能力

## 1. 理解和固定设计约束

不仅记录“生成一个 PSD”，还要记录：

> 文字是否要可编辑？背景和主体是否独立？是否保留蒙版？是否允许位图？哪些内容禁止修改？输出只要最终图片，还是还要工程？

这些约束应影响制作路线和最终检查。

**精准文字优先考虑原生文字；固定几何优先考虑结构化修改；只要求最终视觉时，生成路线可以更自由。**

不能对不同交付目标使用同一套“先出图再转换”的流程。

## 2. 感知真实软件状态

执行前确认当前软件、文档、选中对象、可用资源和保存状态；执行后读取变化。

如果能从宿主获取对象结构，就不只靠截图猜。如果只能观察界面，就降低确定性，不能编造图层 ID、对象结构或执行结果。

**截图是观察渠道之一，不是所有任务的唯一事实来源。**

## 3. 把长任务拆成可检查的小操作

例如，不一次性执行“完成整套品牌设计”，而是：

> 读取需求 → 建立文字与版式 → 检查 → 插入或生成素材 → 检查 → 适配尺寸 → 保存 → 重开验证。

本项目可以自己拥有这种设计专用的规划与执行循环。

它与“自建通用 Agent 平台”的区别是：操作对象、可用工具、数据范围和验收规则都有明确边界。

## 4. 管理桌面、宿主与文档的使用权

这是多 Agent 环境下非常容易漏掉的基础问题。

**分析可以并行，同一桌面的输入操作不能随意并行，同一原生文档的写入也不能随意并行。**

Photoshop 的修改操作本身就存在模态执行等生命周期约束。citeturn431629search1

因此，需要的不只是“最多运行两个任务”，而是知道哪个任务正控制哪个桌面、软件实例和文档；用户接管时暂停，状态不确定时先确认。

当前仓库的 `NativeWorkers` 已经有任务检查、子进程启动和容量限制，也明确不结束共享宿主。这是值得复用的基础，但它本身还不能证明跨进程、跨 Agent 的桌面与文档协调已经完成。fileciteturn72file0L2-L2

## 5. 失败后先对账，再重试

一次请求超时，不等于软件没有完成操作。

直接重试可能重复生成图层、重复导出、重复调用收费服务。

建议每次操作记录任务身份、目标版本、执行前后状态与产物。恢复时先查实际结果，再决定继续、重试或人工处理。

回滚也不能只有一个“Undo”按钮。不同操作应分别使用新副本、检查点、可逆修改或明确的恢复步骤；无法自动恢复时就说明，而不是保证万能回滚。

## 6. 不让执行器自己给自己判定成功

执行器说“已完成”只能作为一条陈述。

结果检查应尽可能来自：

**真实文件、宿主读回、对象结构、重新打开后的状态，以及必要的人类视觉判断。**

OSWorld 2.0 的研究也把长链电脑任务中的隐含状态、约束和执行结果核验作为重点。它不能替代你的设计测试，但说明只看动作轨迹或最后一句成功报告是不够的。citeturn555812view0

**你的自有能力最可能优于通用 Agent 的地方，不是更通用，而是对固定设计任务更懂约束、更能检查、更容易恢复。**

目前这是应当验证的目标，不是已经成立的性能结论。

# 六、资产体系要升级为“知识＋能力包＋案例”，否则自动化仍然没有地基

## 1. 一条知识，不等于一个可执行能力

建议明确区分：

**知识条目**：解释某种方法、风格或规范。  
**参考案例**：展示这种方法在什么情况下有效或失效。  
**能力包**：告诉系统如何应用方法、调用工具并检查结果。

一个真正能被部署的能力包，应包含：

```text
要解决的问题与适用范围
输入、参数和必要前提
引用的 AAOS 知识版本
必须保持与允许改变的条件
目标软件与支持的执行方式
生成提示词／操作配方
输出约定与检查规则
预算、隐私、失败与恢复方式
验证案例、限制及撤销入口
```

这不是要求每个条目都填一大张表。纯知识条目不需要执行字段；只有准备投入自动化的能力，才需要相应约束。

**不能要求“风格词条”先跑 Photoshop，也不能因为某个脚本能执行，就认定它具备专业审美。**

## 2. 全品类应采用组合结构

不建议为每个品类复制一套系统。

更合适的是：

> **通用设计方法＋领域约束＋软件操作配方＋交付检查。**

同样是“层级”，在版式、空间、动效和声音里有不同表现；可以共享概念关系，但专业评价不能强行统一。

分类也应是多维组合：领域、用途、风格特征、媒介、方法、产物、工具和能力范围。可以参考 SKOS 的概念、别名和关联方式，但不必先建设复杂图谱平台。citeturn723740view2

## 3. 知识检索不能只靠“视觉相似”

我建议一次设计检索至少兼顾：

**看起来是否相关、解决的问题是否相关、目标产物是否可实现、当前是否允许使用。**

你找的是能帮助完成任务的方法，不只是外观相似的图片。

热度、高星和收藏可以用于发现来源，不能直接决定它是否进入生产能力。正式吸收需要经过：

> 来源核对 → 专业拆解 → 中立整理 → 适配 → 案例验证 → 投入使用或明确延后。

也不要一次把全部资料塞给模型。先检索相关资产，再按当前步骤提供必要内容，保留出处和版本。

## 4. 还要支持原创，而不仅是识别和复刻

从你的整体目标看，DESIGN-LAB 不应该因为入口经常是截图，就变成“截图转提示词工具”。

它还应支持：

**没有参考的原创需求、多张参考的组合、已有工程的局部改稿、既有风格的跨媒介延展。**

尤其多参考场景，需要区分：

> A 图提供构图，B 图提供材质，C 图提供配色，品牌文件提供禁止改变的规范。

不能把几张图混成一段模糊的“融合风格”。

# 七、“精准提示词”和“可编辑文件”，要分别建立正式交付标准

## 提示词应升级为“目标生成包”

它可以包含正文、结构参考、风格参考、遮罩、保留区域、实际支持的参数和检查要求。

这不是我凭空扩展概念：Firefly 官方将结构参考与风格参考分开；Runway 的图生视频指导则强调图像承担视觉内容，提示词重点描述运动等变化。citeturn723740search0turn723740search1turn723740search4

因此：

**精准不是词多，而是选对控制手段、减少歧义，并且匹配目标工具。**

目标不支持某个参数，就不生成看似专业但无效的参数；自然语言不能确保的约束，改用结构控制或明确风险。

## 原生文件必须按“可修改什么”检查

| 用户要求 | 应证明什么 | 不能冒充什么 |
|---|---|---|
| 矢量文件 | 约定的路径、形状和文字真正可编辑 | 把整图嵌入 SVG／AI 就称全矢量 |
| 分层文件 | 图层分工、文字、蒙版和编辑粒度符合要求 | 拆成几层位图就称恢复原工程 |
| 三维工程 | 所需对象、材质、灯光、相机和依赖存在 | 用单张图推断不存在的背面结构 |
| 动画／音视频工程 | 约定的时间轴、素材关系和可调参数存在 | 只有成片却称交付可编辑工程 |
| 最终媒体 | 内容、尺寸、透明度、时长等满足要求 | 有文件就认为合格 |

Qwen-Image-Layered 的官方项目提供了多层 RGBA 分解能力，可以作为重建链的候选组件；但多层 RGBA 或 PSD 导出，不能证明恢复了原设计的文字、矢量、智能对象与效果结构。citeturn714064view3

**这类组件值得利用，不值得夸大。**

此外，中立适配不需要先创造“万能工程格式”。DTCG、OpenUSD 和 OpenTimelineIO 分别处理设计 token、三维场景和时间线等不同问题，不应被理解成一个能够无损替代所有软件工程的统一格式。citeturn686460view2turn686460view1turn686460view0

# 八、AAOS 联合：知识只有一个长期主版本，专业执行能力仍在 DESIGN-LAB

我建议固定以下分工：

| 层次 | 主要职责 |
|---|---|
| **AAOS** | 长期资料、知识正文、来源、关系、版本、研究与学习 |
| **DESIGN-LAB** | 设计专业语义、方法选择、生成方案、能力包、适配器、执行和检查 |
| **现成设计软件** | 原生文档、对象编辑、渲染、合成、剪辑与生产 |
| **WORK-LAB／外部 Agent** | 需要时提供跨任务调度、公共治理或执行能力，不成为每次知识读取的必经层 |

**知识归 AAOS，不等于 DESIGN-LAB 只能做搜索界面。**它仍负责判断某条方法在当前设计任务中是否适合、如何落实和怎样验证。

## 联合先做三个窄接口

第一，获取当前任务需要的授权知识上下文。  
第二，提交允许回流的方法候选、观察和纠正。  
第三，取得受理回执、版本变化与撤销信息。

这些是建议能力，不是宣称仓库已经存在相应 API。

不要直接读写对方数据库，也不要先做复杂消息平台。AAOS 当前的正式方向已经明确由 Core 管理正典写入，普通内容保存和进一步核验也应分开。fileciteturn70file0L2-L2

## 运行时可以有快照，但不能有第二套知识主库

正在执行的任务固定所用知识版本。AAOS 更新后，后续任务使用新版本；需要重新计算时，显式建立新一轮。

AAOS 离线时，可使用仍允许用于当前任务的有限快照；不能把“离线可用”变成无限期使用已撤销或必须重新检查的内容。

## 反馈必须区分三个含义

你说“这次我更喜欢另一种配色”，可能是：

**这次任务的选择、你的长期偏好，或者对某条设计方法的纠正。**

系统不能自行把它们合并成永久规则，更不能把一次成功自动升级成通用方法。

客户资料、客户产物与未授权素材继续隔离。所谓“匿名化”不是自动获得跨项目迁移许可。

# 九、前端与后端现在该怎样改？先换产品中心，不先换技术栈

## 前端：三个主要使用场景足够承载这个定位

**能力资产库**：查方法、看案例、了解能做什么，选择并调用。

**分析与生成**：直接上传内容或描述目标，选择分析、提示词、原生文件或软件执行。

**结果与历史**：查看分析、方案、产物、限制、修正和恢复记录。

软件连接、AAOS 连接、诊断和完整执行日志放在次级入口。

首页最重要的问题应该是：

> 你要我分析什么，或者帮助完成什么？

而不是：

> 系统现在登记了多少来源、多少工具、多少未开放模块？

可以有任务进度、取消、预览、对比和批注，但这些服务于一次需求，不把产品重新变成项目管理工作台。

## 当前界面推进不下去，有真实的结构原因

本轮回读的代码仍保留旧单页工作台，再叠加 12 项导航；注释直接提到保护原有 DOM、测试定位方式与一比一侧栏结构。这说明界面迭代的一部分成本来自旧实现兼容，而不仅是缺几个组件。fileciteturn69file0L2-L2

而当前能力库代码仍主要投影来源和模型记录：资格结果固定为空；分类函数主要输出“哪些轴未分类”，并没有完整返回这些分类轴的实际值。它离“可以选择并调用的专业能力库”确实还有实现差量。fileciteturn68file0L2-L2

所以建议：

**保留必要业务与数据兼容，允许重组页面、导航和测试；不要永久保留错误产品形态。**

## 技术栈不应再次成为主要工程

保留已有 Python 服务和 TypeScript／Vite 基础，先形成清晰的分析、能力调用和结果接口。

React 可以作为组件化手段，但不是本次定位成立的前提。也不需要为这个变化重写 Rust、另加一个 Node 后端或马上换桌面框架。

当前边界文档仍强调“唯一设计控制面”和禁止第二运行时，需要按你的最新意图澄清为：

> **不新建通用 Agent 平台，允许设计专用执行内核；不新建编辑器，允许预览、分析、受控操作与验收。**fileciteturn67file0L2-L2

应该做一次清楚的决定替代，而不是继续增加互相竞争的“最终版蓝图”。

# 十、怎样证明自有能力更强？用同任务对照，不凭感觉下注

我建议把“本项目自动化更强”转成一个可测试的问题。

| 对照组 | 测什么 |
|---|---|
| **A：直接使用外部 Agent** | 不提供 DESIGN-LAB 方法和执行包时的基线 |
| **B：同一个 Agent＋DESIGN-LAB** | 专业知识、约束与验收包究竟带来多少改善 |
| **C：自有原生操作配方** | 重复性任务是否更稳定、返工更少 |
| **D：混合执行** | 原生操作与界面 Agent 接续能否解决更复杂任务 |

保持输入、软件版本、权限、目标和预算尽量一致。某条路线不支持该任务就记为不适用，而不是改题目制造胜利。

真正要看的是：

**交付是否合格、约束是否保留、原生结构是否正确、人工接管与返工次数、成本、耗时和失败恢复。**

不能只比较模型输出长度，也不能因为换了更强模型，就把所有改善归功于自己的系统。

## 最值得形成的长期机制

我建议建设这样一条持续改进路线：

> **用通用 Agent 探索尚未掌握的操作 → 保存实际动作与问题 → 抽取可复用步骤 → 参数化并补验证 → 在不同输入上重测 → 成为 DESIGN-LAB 的正式操作能力。**

这不是录一次鼠标轨迹就宣布自动化。

被固化的应该是：

**操作意图、对象定位、前置条件、实际动作、结果断言和恢复方式。**

这样，外部 Agent 不只是一个付费执行器，还可以帮助发现新流程；但正式使用不必每次从头推理同一套操作。

**这比从零训练通用电脑操作模型，更符合你现在的成本、维护和专业积累目标。**

# 十一、建设顺序：保留全品类，但一次只增加能证明价值的能力

建议按成果分阶段，不按“把所有页面补齐”推进。

## 第一阶段：能力资产真正能用于分析和提示词

完成从输入、知识检索、风格判断到目标生成包的完整链；接上最小 AAOS 知识读取与反馈接口。

覆盖不同类型的代表案例，包括混合风格、多参考、原创需求和工具不支持的情况。

**验收重点不是分类数量，而是依据能否解释、目标适配是否正确、你的纠正是否能被正确处理。**

## 第二阶段：建立一条自有操作路线和一条外部委派路线

选择已有基础的原生操作，再选择一种外部执行器，使用同一个目标合同和检查器。

完成真实文件生成、两次局部修改、保存重开、失败接续和必要的取消。

首批选哪些案例只是实施取样，不能反过来取消三维、音视频等长期范围。

## 第三阶段：把验证过的流程沉淀成能力包

补齐适用条件、参数、软件版本、检查、恢复和退出机制，再扩大软件与任务覆盖。

新能力必须能回答：

> 它比直接问通用 Agent 多提供了什么可验证价值？

## 第四阶段：逐批迁移长期知识到 AAOS

先分类、核对权限和建立旧新标识映射，再导入、读取核对和切换主版本。

脚本、运行配方、模型权重和用户工程不跟着“一键全迁移”。旧资料保留恢复路径，不以目录整洁为由删除作品或证据。

---

## 最终裁决

**DESIGN-LAB 值得继续做，但应该从“很多模块的设计平台”转向“能被人和 Agent 调用的专业设计能力底座”。**

它可以有自己的自动化，而且我建议有。只是这个自动化应建立在真实软件对象、明确设计约束、可复用操作和独立检查上，而不是再包装一个通用点击助手。

最终定位可以固定为：

> **DESIGN-LAB 以 AAOS 为长期知识基础，面向全设计品类理解需求、调用规范与方法，生成适配目标工具的提示词和制作方案；通过自有专业执行能力与可替换外部 Agent 操作现成软件，并验证实际产物。可复用的经验在权限允许的范围内回流 AAOS，持续改善知识与能力。**

**知识让它知道该怎么做，执行让它真的做出来，验证让它知道到底有没有做对。三个部分缺一，都会再次回到“资料很多、功能很多，但推进不下去”的状态。**

## 三、完整的互补关系，至少包含四条循环

### 1. AAOS ↔ DESIGN-LAB：知识用于设计，设计又帮助人理解知识

AAOS 提供设计规范、方法、风格知识、案例与来源。

DESIGN-LAB 将它们用于分析、提示词生成、软件操作和设计制作；使用中发现方法不准确、边界不清或案例不足时，提交修正候选。

与此同时，AAOS 可以提出教学需求：

> “这个知识点很难理解，请制作一个对照图、过程动画或可以操作的演示。”

DESIGN-LAB 返回的不只是漂亮图片，还应包含适合学习的结构、可修改的源工程、必要说明和知识对应关系。

**这是一条专业能力互补关系，不是 AAOS 给资料、DESIGN-LAB 出图就结束。**

### 2. AAOS ↔ WORK-LAB：知识指导工作，工作检验和补充知识

WORK-LAB 可以从 AAOS 获取编程知识、工具使用方法、AI 治理经验和已知问题。

实际任务中的发现，再经过整理、适用范围判断和必要验证，成为 AAOS 的候选内容。

这里不应只回流成功经验。失败原因、无效方案、版本差异和适用条件同样有价值。

例如：

> 某种配置在什么环境下有效？为什么一个任务表面成功却没有完成交付？某个修复只是绕过问题，还是解决了根因？

**运行日志是原始记录，从记录中提炼的经验才是知识候选。两者不能自动等同。**

### 3. WORK-LAB → AAOS → DESIGN-LAB → AAOS：把工作经验转成学习资源

这就是你这次特别强调的路径。

例如，WORK-LAB 整理出一组“AI 编程任务怎样验收”的经验。

AAOS 将它们组织成有来源、有条件、有正反例的知识，并确定学习目标。

DESIGN-LAB 制作流程图、动画、操作演示、交互练习或课件。

AAOS 组织学习，记录哪些概念仍然不清楚，再把问题分别交还给知识维护者、技术验证者或 DESIGN-LAB。

**WORK-LAB 产出的专业知识，不只用于下一次自动化，也可以帮助你真正理解这些工具为什么这样工作。**

### 4. DESIGN-LAB ↔ WORK-LAB：设计和技术能力直接互补

不需要所有事情都绕 AAOS 一圈。

例如，DESIGN-LAB 制作一个 AI 治理教学演示，需要可复现的运行样例，WORK-LAB 可以提供或协助验证；WORK-LAB 需要解释自身流程、制作培训材料或改善复杂信息的表达，可以调用 DESIGN-LAB。

AAOS 负责其中值得长期保留和复用的知识，但**不是每次软件调用的强制中转站**。

## 四、DESIGN-LAB 应增加一类重要能力：知识可视化与教学生产

这应当成为 DESIGN-LAB 的一个正式能力域，但**不能把 DESIGN-LAB 整体改造成教育软件**。

它仍是全品类设计与自动化能力系统。教学生产只是一个重要应用方向，而且能够复用已有的排版、图形、三维、动效、音视频和软件操作能力。

### 不是所有知识都应该变成动画

我建议按照理解目标选择表达形式：

| 要解决的学习问题 | 可以采用的设计形式 |

| 分不清几个相近概念 | 对照图、层级图、正反例 |
| 理解不了先后顺序或状态变化 | 分步演示、过程动画、可暂停的时间序列 |
| 看不懂空间与结构关系 | 三维视图、剖面、分解展示 |
| 知道操作步骤，但不会判断 | 分支情境、错误案例、选择后反馈 |

AAOS 不能只丢来一段长文，让 DESIGN-LAB 自动配图；DESIGN-LAB 也不能只给漂亮动效，不关心概念是否讲对。

涉及专业内容时，还要保留条件、单位、因果关系和时间顺序。为了好看而省略的内容应明确标注为简化示意，不能悄悄改变知识含义。

**讲解动画也不等于交互仿真。**AAOS 原蓝图已经要求仿真具有参数、算法版本、初始条件和可验证结果，而不是仅播放预先渲染的视频。fileciteturn74file0L86-L93

## 六、反馈要回到正确的位置，不能全部塞进 AAOS 后就算闭环

我建议区分三类问题。

**知识或技术问题：**概念错误、前提缺失、代码样例失效。由 AAOS 组织知识修订，WORK-LAB 或其他专业来源参与验证。

**表达与教学问题：**动画过快、图解歧义、重要步骤没解释、互动设计不合理。由 DESIGN-LAB 改进，AAOS提供相应学习反馈。

**运行与集成问题：**课件无法加载、资源缺失、操作演示不能复现。由实际负责的运行和集成模块修复，需要时由 WORK-LAB 协助。

同一个问题可能需要联合处理，但不能出现：

> 学习者没看懂 → 自动认定知识错误；  
> 动画播放完成 → 自动认定已经学会；  
> Agent 运行成功 → 自动认定课件内容正确。

还有一个特别重要的防循环错误规则：

> **同一份知识生成了文章、图解、视频和课件，仍然只是同源派生成果，不能拿它们互相引用，伪装成四份独立证据。**

生成成果可以帮助解释知识，真实学习和实践结果可以形成新的观察；是否足以修改通用知识，仍然需要判断。

“判断后入库”也要分清层次：**可以先保存为候选或观察，再判断是否正式用于教学或自动执行。**不能因为尚未验证，就连失败经验和个人笔记都无法保存。

## 五、不是所有文件都应该“改成最新说法”

建议每份被纳入清点的文件，只采用一种明确处置：

| 处置 | 适用情况 |
|---|---|
| **更新当前内容** | 仍然负责指导当前产品、实现或执行 |
| **明确替代关系** | 旧决定仍需追溯，但相关条款已被新决定取代 |
| **保留历史原件** | 旧审计、旧运行证据、冻结任务包、签名或哈希绑定资料 |
| **重新生成** | 状态投影、索引、部署包和其他派生输出 |
| **确认无需修改** | 依然正确、与新定位无冲突的技术与安全约束 |

特别是历史材料：

**不能把旧审计里的“当时未完成”改成“当时已完成”；不能给哈希冻结的原件直接加一段文字，破坏其原始身份。**

可以通过外层说明、索引和替代映射，让读取者知道它的适用范围。

对于可能被自动发现的旧 `AGENTS.md`、`SKILL.md` 等，还需要检查真实的加载路径。**只在首行写“历史文件”，不等于已经从 Agent 的指令发现范围中隔离。**

另外，这次对话前面产生的报告和压缩包，也应纳入来源追溯。它们是阶段性分析资料，不应该都自称“最终权威”。新入口可以指出哪些结论继续有效、哪些已被你的后续澄清替代，不需要删除全部旧附件。

## 六、最重要的防漂移规则：把四件事分开记录

很多漂移不是“没读文档”，而是把不同性质的信息当成同一件事。

| 信息 | 回答的问题 | 不允许被什么冒充 |
|---|---|---|
| **当前产品目标** | 我们要做什么、不做什么？ | 不能由旧代码反过来取消你的最新目标 |
| **当前实现事实** | 哪个版本实际上做到了什么？ | 不能因为蓝图更新就自动变成已完成 |
| **当前执行任务** | 这一批具体改什么、怎样验收？ | 不能变成无限扩张的长期产品定义 |
| **操作授权范围** | 此次允许修改、安装、发布或迁移什么？ | 产品目标不能自动授权所有有副作用的操作 |

例如：

> “长期知识归 AAOS”是目标。  
> “知识桥接尚未完成”是实现事实。  
> “本批接通一个知识读取接口”是任务。  
> “是否允许迁移现有客户资料”是另一个授权问题。

四者可以同时成立，没有矛盾。

**正确审计应该报告“目标与实现之间还缺什么”，而不是因为目标已调整就判定所有旧代码都应删除，也不是因为代码暂时没有就说这个目标不属于项目。**

对这次定义变更，应明确写成：**目标按最新意图整理，实现处于迁移阶段。**不能用文档更新冒充产品迁移完成。

## 七、怎样更新才不会再做成一轮无休止的治理工程？

我建议用一个有限的迁移批次，分四步完成。

### 第一步：建立影响清单，而不是先批量替换文字

每项至少记录：

**文件或配置位置、当前用途、谁读取它、冲突条款、处置方式、替代目标、验证方式。**

扫描要看语义，不能全局搜索“workbench”就替换。这个词可能出现在需要修改的产品定位中，也可能只是当前真实目录名、历史记录或兼容路径。

范围首先是 DESIGN-LAB 仓库，以及明确属于它的部署副本。其他两仓和用户 Library 的修改不应自动纳入同一写入权限。

### 第二步：同步当前定义、配置、任务映射和校验规则

完成一份清晰的决定差量，写明本轮哪些旧条款被替代，再同步现有有效文件。

**不需要每份文档重复一遍全部定位。**建议每类事实只有一个负责维护的来源，其他文档引用它。Authority 保持入口和关键边界作用，不继续膨胀成塞满动态状态的大书。

旧任务按实际影响处理：

> 继续有效的保留；仅界面表达变化的重映射；不再需要的标明替代原因；新能力加入既有账本。

已经完成的安全、恢复和数据校验，不应因为产品改名而重新打开重做。

### 第三步：按新用户旅程迁移前端及必要接口

先让“能力查询—内容输入—方案与执行—结果反馈”至少有一条真实路径，前端和后端一起验收。

旧入口可短期兼容，但应有明确退出条件，不能长期保持：

> 新界面只能看，旧工作台才能操作。

技术栈、目录和品牌大改都不是必需前提。**改变产品语义，不等于为了词语一致而暴力搬目录。**

### 第四步：验证新会话、部署副本和三项目交接

新会话不带这次聊天摘要时，仍应能从正式入口读出正确定位。

已部署入口要报告它实际读取的规则版本；尚未检查的副本标为待核对，不能宣称全部同步。

三项目合同由各自仓库维护自己的实现与状态，交换版本和能力确认。**不要求三个项目锁在同一个发布节奏，也不让 DESIGN-LAB 擅自改另两仓的私有状态。**

## 八、怎样验收“以后不再被旧文件带偏”？

不能承诺永远不漂移，但可以让漂移更容易被发现和阻止。我建议优先补下面几类针对性检查，而不是继续增加几十个形式门禁。

| 检查 | 应验证什么 |
|---|---|
| **入口一致性** | README、Authority、Agent 指令能到达同一当前定位与任务入口 |
| **历史不复活** | 旧工作台规划、旧 handoff 和第三方 SKILL 不会重新获得默认执行权 |
| **定义与实现分离** | 更新定位不会把未运行功能自动标为完成 |
| **真实用户旅程** | 能力查找、输入分析、自动执行、产物检查和反馈确实能用 |
| **三项目归属** | 教学生产不接管学习状态，知识引用不变成数据库直写，调度不越权 |
| **迁移可恢复** | 旧数据、作品和证据可找回；新入口失败时有明确恢复方法 |

检查还应包含负向用例：

例如，放入一份历史上自称“最终权威”的旧任务包，系统应能识别其已被替代，而不是按文件名采信；模拟把未经执行的能力标为可交付，检查应当拒绝。

但**自动检查不能仅靠禁用几个词判断语义**。“工作台”出现在历史说明或目录名中，不应失败；新页面偷偷要求用户走旧生产流程，即使没出现这个词，也应被用户旅程测试发现。
