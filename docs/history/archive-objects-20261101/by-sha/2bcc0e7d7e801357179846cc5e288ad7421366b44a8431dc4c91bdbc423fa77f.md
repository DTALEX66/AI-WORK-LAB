# 4. P3 新增的 CI 回归已经定位

今天修改后的：

`scripts/launch/desktop_launch.py`

在 `prepare_launch()` 一开始无条件执行：

`check_resource_boundaries(REPO, purpose="test")`

但资源索引的 canonical 路径是你的真实 Windows 环境：

`D:\All projects\Model library`

`D:\All projects\OS External Configuration`

`D:\All projects\ArcheAxis.Knowledge.Green-x64`

`D:\All projects\资料库`

`D:\All projects\ceshi`

GitHub Linux Runner 自然不存在这套 `D:\All projects`。

于是 CI 报：

> `ValueError: resource index drift or missing entry: shared_models`

造成三个 Desktop Launch 测试失败。

这不是 AAOS 产品逻辑坏了，而是**本机资源边界验证和跨平台单元测试没有隔离干净**。

正确修复方向不是取消资源保护，而是：

**真实 Launcher继续 fail-closed；单元测试通过 mock/fixture 验证调用行为；专门的 Windows / machine-local integration gate 再验证真实 D:\ 路径。**

不能为了 CI 绿灯把资源安全检查删掉。

# 5. Rust 还有一个真正值得处理的失败

两套 Rust CI 都在同一个测试失败：

`crates/archeaxis-domain/tests/backup_safety.rs`

失败用例：

`verify_counts_rejects_sqlite_integrity_failure_even_when_counts_match`

测试预期：

> 一个 SQLite 数据库即使计数相同，只要 integrity 已损坏，`backup::verify_counts()` 就必须拒绝。

但当前实际没有返回 error。

结果：

**5 passed / 1 failed**

这个比普通测试漂移重要，因为它正好落在你最重视的：

**数据库备份 → Green 替换 → 回滚 → 资料安全**

链路上。

因此这个不能简单删测试或改 expected。

应该修 `backup::verify_counts()` 或确认 Windows SQLite 对当前构造的 corruption fixture 行为发生了变化。

# 7. 当前最严重的架构问题：Tauri 与 Avalonia 权威冲突

这是我重新审计后认为目前**比 UI 样式本身更应该先解决的问题**。

现在仓库同时存在这些“权威声明”：

| 位置 | 声明 |
|---|---|
| `README.md` | React/Tauri canonical shell |
| `docs/truth/ARCHITECTURE_FINAL.md` | Presentation Plane = Tauri + React |
| `M0` 新方向 | Avalonia 是 canonical desktop |
| 今天 P3 UI Spec | `apps/ArcheAxis.Desktop` 是唯一 canonical product shell |
| `release.yml` | 名字上验证“formal Avalonia release architecture” |
| `release.yml` 实际打包 | **仍然从 Tauri `ArcheAxis.exe` + frontend-dist 制作 Release** |
| `ci.yml` | Avalonia + Tauri 两套桌面链同时跑 |

所以现在不是简单地“还有旧代码”。

而是：

> **开发权威已经切到 Avalonia，但发布权威还在 Tauri，README/Final Architecture 又停留在旧时代。**

这是 P0。

但我不建议现在直接把 Tauri 删掉。

更合理的是明确过渡状态：

**Stable Legacy Release = React/Tauri 0.6.14**

**vNext Product Shell = Avalonia**

**Rust Core = 新 canonical truth**

**Python = Worker / Adapter / Legacy bounded runtime**

等 Avalonia 的真实 GUI + Green + clean-machine + rollback 全部闭环后，再完成 release cutover。

# 9. AAOS 产品闭环还差的不是“更多页面”

R6 当前状态已经说明得很清楚。

真正没有关掉的是：

**人类闭环 + 机器闭环 + 失败纠错闭环。**

现在已有：

`Source → Knowledge → Assessment → Answer → Review/FSRS → SQLite → Restart Readback`

已经相当不错。

但还缺：

`真实资料 → Knowledge → 人类学习 → 机器实际使用 → 用户发现错误 → Correction → Retest → Machine Growth → Restart Readback`

尤其是：

**真实模型仍没有形成 P4 真执行闭环。**

现在还存在 stub/local-stub，以及 Provider lifecycle authority 没完全进正式宿主。

所以我认为 AAOS 接下来最重要的工作不是再接十个 RAG 项目，也不是先做 20 个页面。

而是先把这一条真正跑通。

---

# 10. DeepTutor 的定位也要再收一次

今天的 Avalonia `MainWindow` 里仍然有：

`DeepTutorSupervisor`

并且 Home 可以启动 DeepTutor，再打开独立学习工作台。

技术上没问题。

但是产品语义必须固定：

**DeepTutor = 可吸收学习能力 / Sidecar / 外置参考实现**

而不能变成：

**AAOS 学习模块 = 点按钮跳 DeepTutor。**

否则就会再次出现两个 Learning Truth / 两个 UX / 两套学习工作台。

真正的 AAOS Learning 主界面应该继续收进 Avalonia；DeepTutor 的成熟算法、流程、Tutor 能力放在后端/能力层吸收。
