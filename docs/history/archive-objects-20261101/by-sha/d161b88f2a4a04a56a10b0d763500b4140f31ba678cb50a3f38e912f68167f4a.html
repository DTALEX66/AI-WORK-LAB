02　既有定位：相近的辅助逻辑，各自的专业领域

10 月 19 日权威已经把 WORK-LAB 定义为：面向个人 AI 工作环境、客户端中立的工作流管理、治理、运行监测与问题闭环系统。职责包括软件与 Adapter 登记、通用规则和受管配置、监测、问题归并、建议与任务包、结果验证、维护方案复用。因此，把它只概括成监控面板是不完整的；把这些职责说成今天新增的定位也不准确。

与 DESIGN-LAB 的共通逻辑是：管理领域方法和工具资料，结合用户目标与实际条件，提供适配材料，用户自主选择，外部软件或 Agent 落地，再积累可复用经验。WORK-LAB 还观察实际运行状态，并对问题处理结果做证据核验。

这里的知识管理有明确范围：AI 软件、配置、插件、规则、工作流、兼容性和维护方法，以及这些方法所需的操作说明与提示词。它不扩成全领域学习系统、长期上下文总管、通用聊天应用或第二个 AAOS。日常工具使用指南可作为该领域方案的一种类型；更广泛的资料采集和研究自动化，并没有因“与 DESIGN-LAB 相似”而自动获得实现授权。

建议在产品说明中使用这段易懂表述：WORK-LAB 帮助用户管理和用好个人 AI 工作环境，整理软件与工作流的方法和方案，观察运行状态，汇总问题，准备可交给外部 Agent 的处理材料，并核验和保存有效经验。

04　距离闭环还有多远：五个必须跨过的环节

已有零件可以复用，当前主要缺口集中在连接这些零件，而不是重写整个项目。最小可用版仍需要跨过以下五个环节：

  1. 用户能在界面看到真实问题、证据、归属和具体下一步；无源与无问题清晰区分。
  2. 用户能选择一个常用外部执行工具，预览并带走完整交接材料；重启后找得到对应问题与材料。
  3. 外部执行后，用户能导入结果或关联证据；“已交接”“对方声称完成”“待核验”分别记录。
  4. 后端依据事先声明的验收条件核验，记录失败、缺失、过期和版本变化；不凭一句完成或 HTTP 200 关闭问题。
  5. 已验证的处理方法能保存为方案，重启后可查，下次相同或相似问题可找到，并提示适用版本与限制。

SOLUTION-001 证明仓内出现过一例可复现的真实修复；它不能代替上述五个环节的通用产品验收。修复包能导出也不代表外部已执行。首次人工交接完全可以接受，无须为闭环先建设自动派发。

用户已强调先可使用，再扩展。下一阶段建议只选一个有证据来源的实际环境问题和一个常用执行工具，跑完这一条链；不同时展开所有适配器、复杂迁移、自动更新、跨项目记忆和 AAOS 接收。

工作台默认是一条简洁状态摘要、一张工作／项目列表、一块需要处理的事项。没有问题时显示最近使用的方案或软件变化，不放空图表。每个问题详情先展示“发生了什么、影响什么、下一步”，再展开来源、原始日志、合同和摘要。主操作依据阶段变化：查看处理建议、复制交接材料、查看核验结果。涉及状态修改时明确进入控制面。

图形风格沿用珍珠白／深色、克制的苹果玻璃质感。玻璃用于导航外壳、浮窗和短暂弹层；正文用稳定底色和清楚对比。单层列表与详情面板替代多层卡片。图表按需展开，字段缺口先给一句原因和可行下一步，工程说明收进证据抽屉。状态同时用文字和颜色，灰色表示未知或未接入，红色留给确有证据的失败。

前端当前是 React／TypeScript／Vite + Tauri，保留该栈。viewRegistry.ts 是静态导入全部视图，不是按页面懒加载。可在保持路由和合同的条件下，对低频高级页做动态加载、只展开可见详情、长列表分批显示。隐藏侧栏条目本身不会减少已静态打包的代码。当前没有本轮性能测量，不把“导航多”直接等同于 CPU／显存过高。

06　HUD 的职责与落地限制

既有 Observer HUD 应保留。当前配置为 440×680、固定尺寸、默认隐藏、置顶、跳过任务栏、无原生边框；标签为用量、会话、审批。主窗口为 1280×820，可调整大小，最低 900×600。HUD 是桌面浮窗，不是手机端。

HUD 首要价值是少打断用户：观察已知用量和会话、提示需要回到原软件处理的事项、清楚展示更新时间与断连。它不承担长日志、方案编辑、审批决定、执行重试和配置修改。实际审批仍回原软件；用户返回主窗口查看详情。

以后可把已接通的问题摘要加入 HUD，但需要明确的数据合同与数据源，不能把“没有问题字段”画成“当前一切正常”。不能用假演示数据填满浮窗。用户可关闭 HUD，关闭窗口不应误被解释为停止外部软件。

当前 Tauri 两个窗口均为 transparent=false。因此效果图中的玻璃视觉不等于已经实现桌面背景穿透。真透明、模糊及其性能属于单独待测项；不能为玻璃效果先引入持续渲染和复杂动效。

问题处理记录关联问题指纹、项目身份、软件及版本、采样时间；交接包另有不可变 packId／revision／摘要；外部结果必须绑定这一次交接和目标版本，不能把旧日志贴给新问题。方案引用其来源问题、交接和核验记录，同时有自己的身份和修订。重启恢复、幂等与版本冲突拒绝必须可测。

人工复制交接和原生 invoke 要区分。目前生成器拒绝没有声明 invoke 的适配器，WorkBuddy 等因而不能直接作为当前包的执行目标。若要支持纯人工复制给任意工具，应新增明确的人工目标语义及验证，不应伪造适配器 invoke 能力，也不能以“交接成功”暗示外部调用成功。

未来 AAOS 仅预留版本化候选／回执接口，当前不调用，不依赖它启动，不把没有 AAOS 接收状态渲染成系统故障。模型服务同样按需：常态监测无需 LLM，方案整理可后续接可选模型；模型不可用时，规则投影、历史检索、人工交接与本地记录仍能使用。

08　方案与提示词的最小可用结构

方案库应服务实际使用，先把已验证的维护方案与必要使用方法做好。方案可以是使用指南、受管配置说明、工作流配方或修复案例；提示词是其中可复制的交接材料，不再单独创建一套与方案重复的知识真源。

每项至少包含：标题与用途、软件／插件／模型服务身份、适用版本和平台、前提条件、来源与更新时间、具体步骤、预期现象、验证方法、失效条件、风险与恢复办法、关联证据。没有验证过的指南或新方法可以保存，但应显示“资料／待试用”，与“本机验证”“已解决某个具体问题”区分。

提示词模板使用明确变量，例如项目路径、目标软件、症状与证据、允许范围、禁止操作和验收标准。生成时检查缺变量，不默填未知命令，不携带密钥或私人会话。复制不代表发送，采用不代表通过验证；用户可以修改、放弃和再次使用。

新版本不覆盖旧方案。保留不可变修订和当前推荐标记；软件版本变化时提示需复核，不能只因为发布日期更新就替换成功方案。先用结构化筛选和全文／关键词检索，实际验证中文短词“配置”“阻塞”等；不把向量库、大模型或联网作为基本查找的前置条件。

  9. Windows 主窗口、HUD、托盘、缩放和键盘导航实测，样例状态不混入正式路径。
  10. 性能按基线实测再比较：冷启动、初始 JS 传输体积、空闲 CPU／内存、连续观测成本、页面切换延迟和数据新鲜度。结构上只保留共享采集／事件流，低频页面按需加载；目前没有本轮实测数字。

验收使用一个真实场景以及足够暴露误判的反例，不靠堆测试总数、文档数量或绿色状态灯证明可用。出现新修改或失败再补相应测试，不为静态文字和可逆视觉微调写镜像测试。
