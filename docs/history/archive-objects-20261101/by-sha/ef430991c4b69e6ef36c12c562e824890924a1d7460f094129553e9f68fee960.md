## 三、需要“一句话自动接力”时，再加 n8n

### 方案 B：n8n＋官方 CLI/API——固定流程的自动化层

n8n 已经提供内置 MCP Server：支持兼容客户端查找、触发、测试已开放的工作流，也支持相应的工作流构建操作；可以逐个开启哪些工作流允许通过 MCP 使用。citeturn853542view0

对你来说，它可以承担这样的流程——**下面是建议搭建的流程，不是声称你本机已经跑通：**

```text
你在支持的客户端下达任务
        ↓
调用一个已配置的 n8n 工作流
        ↓
读取任务说明和授权范围
        ↓
通过本地执行器调用官方 CLI / API
        ↓
执行代码任务，或提交 ComfyUI 工作流
        ↓
收集文件、日志、测试结果
        ↓
需要时等待你审核
        ↓
回传结果与通知
```

这里存在一个容易被忽略的工程环节：

**n8n 不会因为安装了，就自动认识你桌面上的全部软件。**

有官方 CLI/API 的，可以配置调用；本地程序通常还需要一个受限的执行入口。没有公开接口的，仍需要文件交接或界面操作。**这层适配需要做，但不等于重新开发一整套 Agent 平台。**

我建议先把少数重复工作封装成明确动作，例如“生成一组素材”“运行项目验收”“读取项目状态”，而不是一开始就向所有模型开放任意命令执行。

另外，n8n 的实例级 MCP 权限不能简单理解为“每个客户端都能拥有完全独立的工作流名单”。官方文档说明了用户范围、已开放工作流和客户端授权的边界；需要强隔离时，必须按其实际权限模型设计。citeturn853542view0

**我的判断：n8n 适合放在第二阶段。先把一条人工可验收的流程做稳定，再自动化，收益更明确。**

## 五、哪些“联动效果”不要被宣传带偏？

**第一，统一模型配置，不等于统一全部软件。**  
CC Switch 的支持范围有明确清单；不能因为它能管理某个 CLI，就推断同品牌的所有桌面程序、网页登录态和聊天记录都能同步。其用量统计也依赖它能获取的日志或查询接口。citeturn961573view7

**第二，技能能搬过去，不等于能力自动搬过去。**  
技能描述的是“怎样做”，MCP 或其他工具接口提供“能做什么”。迁移技能时，目标软件还要有相应工具、权限、运行环境和资源路径。TRAE 的官方文档也明确区分了 Skills 与 MCP 的职责。citeturn654898search14

**第三，设计原型交接，不等于生产项目已经完成。**  
Open Design 能产生和交接可编辑文件，但原型转成正式应用仍需要工程实现与验收；不要让联动过程直接覆盖你的现有项目结构。citeturn565558search1

**第四，接通接口，不代表值得同时运行。**  
按照你之前提供的 **64GB 内存、8GB 显存** 配置，我建议把 ComfyUI 与占用较多显存的 LM Studio 推理错峰执行，先实测资源占用，再决定并发。没有必要为了“联动”让所有客户端和模型同时满负荷运行。

## 六、结合你的三个项目，怎样接才不会越做越乱？

我建议把上述工具作为**可替换的外部执行能力**接入，而不是重新定义三个项目：

**AAOS** 继续负责长期知识、来源、版本与可信事实。各软件产生的经验先作为知识候选回流，不能直接把它们各自的记忆库当成 AAOS 的权威知识。

**WORK-LAB** 继续负责项目状态观察、插件与技能使用情况、资源指标和可复用执行经验。它可以接收这些工具的运行回执，但不需要扩张成所有软件的永久总控制器。

**DESIGN-LAB** 继续负责设计领域知识与制作流程，使用 Open Design、MiniMax Design、ComfyUI 等现成软件完成设计生产，不另造通用设计编辑器。

### 我的落地建议

**先跑通这一条最有实际价值的链路：**

## 一、这次最值得用的，是三种现成连接

### 1. PAL MCP 的 `clink`：让一个编程 Agent 调用另一个

项目是 **`BeehiveInnovations/pal-mcp-server`**，其中的 **`clink`** 就是你在找的功能：主控不退出当前会话，启动外部 CLI Agent，交付任务，再接收结果。文档列出了 Gemini CLI、Claude Code、Codex，并支持规划、代码审查等角色以及后续续接。citeturn875049view0

例如，你可以让主控按这样的分工执行：

> “把模块依赖梳理交给 Gemini CLI；把得到的结论用于实施；完成后由你检查修改和测试结果，不要直接接受执行者的‘已完成’声明。”

**这里调用的是另一个 Agent 的执行环境，不只是询问另一个模型。** 对方可以使用其自己的文件、搜索和其他已配置工具。citeturn875049view0

但 PAL 有两类路径，不能混淆：

| 使用方式 | 实际调用对象 | 成本应当怎么看 |
|---|---|---|
| **`clink` 调用 CLI** | 已安装、已配置的外部 Agent | 核对那个 CLI 当前使用的登录方式及计费来源 |
| **PAL 的直接模型调用** | 配置的模型 API 或本地模型服务 | 按对应 API／本地服务计算，不会自动继承桌面软件套餐 |

PAL 的安装指南包含 API 提供方和本地模型配置，因此不能把“装上 PAL”理解为所有调用都免费。**你的目标应当优先验证 `clink` 路径，而不是顺手开启一堆付费 API。**citeturn498008view0turn498008view1

作为免费执行端，**Gemini CLI 值得加入测试**。当前官方文档列明：符合条件的个人 Google 账号登录方式，最高为每天 1,000 次模型请求；这不是 1,000 个完整任务，也不代表任意模型无限使用，仍受服务可用性和相应限制约束。citeturn210539view1

> **Codex 能通过这座桥直接把任务交给 WorkBuddy，收回结果并继续审计，不需要 DSH 夹在中间。**

桥提供三个主要工具：

| 工具 | 用途 |
|---|---|
| `codebuddy_run` | 下发任务，可选择 `workbuddy` 后端 |

**普通在线 Bot 适合先承担“返回信息”的工作；能操作工作区的 Agent 才承担“实际执行”的工作。**

例如，Bot 返回代码建议，不等于它已经修改了你的项目；返回“测试通过”，也不能代替本地测试记录。我建议先把外部 Bot 用于资料整理、方案候选、边界条件分析和独立复核，代码落地与验证留在受控工作区。

## 二、其他网上 Bot 也能接，但不能把“有聊天窗口”当成“能自动调用”

筛选时，我会按这个顺序处理：

| Bot 提供什么 | 建议 |
|---|---|
| **正式 API、MCP 或公开的任务接口** | 优先接入，便于取得状态、结果和计费信息 |
| **官方 CLI 或明确允许自动化的客户端** | 作为执行端验证，保留它自己的认证和运行环境 |
| **只有网页聊天入口** | 先核查自动化许可、文件交付方式和稳定性，不放进关键执行流程 |
| **只能在群里聊天的机器人** | 不能默认让另一个机器人直接调用，需看平台与该 Bot 的规则 |

例如，Telegram 官方 FAQ 说明，普通 Bot 看不到其他 Bot 发出的消息；Discord 则禁止在官方 OAuth2／Bot API 之外自动化普通用户账号。**所以“让几个群机器人互相发消息”不是通用方案，优先寻找 Bot 背后的授权调用接口。**citeturn167982view4turn498008view3

这不妨碍利用低价 Bot，但我不建议把方案建立在抓取登录令牌、绕验证码或未经许可模拟用户账号上。

## 三、为什么我现在选 Codex，而不是让你改用 Hermes 或 Open WebUI？

**选择依据是接入成本和你的现有工作方式，不是声称 Codex 在所有任务上都更强。**

你已经在用 Codex 执行任务。继续让它负责项目理解、派单和验收，只需要增加执行工具；其本地客户端支持共享 MCP 配置，也支持 ChatGPT 订阅登录与 API Key 两种不同的计费入口。**保留现有订阅登录，不要为了联动误切成额外付费的 API 模式。**citeturn167982view5turn498008view2

**Hermes 是后续长时间、多任务调度的有力候选，但现在不用急着换主控。** 它已有持久化 Kanban、审核和退回修改流程；然而官方文档也明确写着，把非 Hermes 的外部 CLI 直接接成 Kanban 执行通道，仍需要逐项处理启动、退出状态、工作区和认证适配，尚不是全面铺好的现成路径。citeturn496945view4turn514961view0

我的分阶段建议是：

| 阶段 | 主控安排 |
|---|---|
| **现在：你发任务，执行完成后验收** | **Codex 主控＋现成 MCP／CLI 执行端** |
| **以后：跨天排队、定时运行、很多任务持续流转** | 再引入 Hermes 记录和调度任务，保留明确的审核角色 |
| **需要统一聊天界面时** | Open WebUI 作为可选入口，不让它成为第一阶段的前置条件 |

**不要同时让 Codex、Hermes、DSH 各当一遍总控。** 我建议每个任务只有一个负责人，其他软件是被调用的执行者或独立审查者。

## 四、怎样才会真正省钱，而不是“免费执行端＋昂贵的反复审计”？

我建议把调度规则写成下面这套，而不是“永远找最便宜的模型”。

**第一，按任务风险分配。** 文件整理、说明文档、批量格式调整、初稿等边界清楚的任务，优先给通过测试的低价执行端；关键架构、权限逻辑和最终验收保留给较强模型。对于很小的修改，主控直接完成可能更划算，不必为了联动而联动。

**第二，限制沟通量。** 主控发出任务目标、允许修改范围、必要文件与验收标准；执行端返回摘要和证据位置。不要让所有 Agent 反复读取整个项目历史，也不要让主控高频询问“做完了吗”。

**第三，设置硬性停止条件。** 第一阶段建议最多两个并行执行任务，失败后最多两轮定向返工；出现额度不足或限流时，停止或切换到已授权的备用执行端，**不自动购买积分、不自动转入新的付费 API**。这些是建议配置，不是平台默认值。

**第四，未知余额就标为未知。** 例如 WorkBuddy 这座 MCP 桥明确说明，目前没有套餐／剩余额度查询 API，能够记录的是运行次数和 token 用量等信息。**不能根据这些记录凭空算出“你还剩多少免费额度”。**citeturn335554view4

我建议最终比较的是：

> **完成一个验收合格任务的总成本＝主控开销＋执行开销＋审核开销＋失败返工开销。**

这比单看模型单价、免费请求数量更符合你的实际目标。

## 五、返回什么，Codex 才能真正审计？

我建议所有执行端都按同一份交接要求返回：

```text
任务编号、执行端、完成状态
产物位置或修改文件清单
代码差异或对应提交
实际执行的验证命令、退出结果及日志位置
未完成内容、已知风险
可续接的会话 ID（执行端支持时）
```

**Codex 应审计产物，不是审计执行端的自我评价。**

代码任务要检查差异、重新执行关键测试；研究任务要检查来源是否支持结论；图片和视频任务要实际打开产物，检查尺寸、内容及交付要求。我的建议是：把“没有文件”“没有验证证据”“修改超出范围”直接判为需要返工，而不是继续让两个模型互相解释。

### 权限上有一个必须提前处理的坑

PAL 的 `clink` 默认配置包含放宽权限的参数；WorkBuddy 桥也默认以跳过确认的方式运行。这意味着下游程序可能拥有比你预期更大的执行权限。**上层 Codex 开着沙箱，不代表它启动的每个第三方工具都自动受到同样的隔离。**citeturn875049view0turn335554view4

第一轮我建议只用独立项目副本或受限执行环境，不接生产密钥、不接客户敏感资料。桥里的允许工作目录设置只能作为一层检查，不能代替操作系统级隔离。

当前任务登记中，也已经记录了并行派工、持久化收发消息与回执、执行状态等工作的实现；但同时保留了**真实外部执行链路、取消与重启、真实 Windows 桌面验收**等尚需实证的边界。**这些记录不能等同于你现在已经拥有完整可用的“一句话组织 Agent 团队”。**fileciteturn16file0L2-L2

因此，接下来不应该重新造一套“多 Agent 总控”，而是先核对：

**现有派工与回执底座，还缺哪些真实执行适配、目标拆解能力和前端交互？AionUi 能补哪一块？**

你的顶层规范本来就将 WORK-LAB 定义为**不绑定某个客户端的工作流、Agent 运维与治理控制面**，负责协调、任务协议、权限、回执和完成判定；明确不负责别的 Agent 的推理循环，也不建设通用聊天产品。fileciteturn12file0L2-L2

**所以，吸收第三方能力符合你的原定方向；让第三方反过来接管你的任务与权限体系，才会偏离。**

## 二、真正值得研究的，不只是 AionUi，而是它背后的 AionCore

这是本轮最关键的新发现。

**AionUi 的团队协作后端已经独立为 AionCore。** 官方架构文档明确列出：它是 Rust 后端，通过 HTTP REST 和 WebSocket 服务前端，其中分别有团队协作、会话、Agent 管理、进程管理、MCP 等模块。citeturn178666view0

我还查了它的团队路由源码，不只是首页宣传。源码中确实存在：

| 能力 | 已看到的接口示例 |
|---|---|
| 创建团队 | `POST /api/teams` |
| 向团队发送任务消息 | `POST /api/teams/{id}/messages` |
| 读取运行状态、子任务、活动 | `run-state`、`tasks`、`activity` |

这些证明了：**它的团队能力有程序接口，不是只能靠鼠标点击 AionUi 窗口使用。**citeturn203232view2

由此，我认为可以验证一种更适合你的组合：

> **WORK-LAB 自己的界面 → 现有控制后端与适配器 → 外部 AionCore 团队服务 → 不同 Agent。**

但这里有一条界限：**看到源码接口，不等于已经确认它是稳定、长期兼容、面向第三方的嵌入式 SDK。** 仍需锁定版本，验证认证、权限、事件与取消语义，并做适配层，不能直接当成“复制几行地址就完成集成”。

### 为什么不直接复制整个 Team 模块？

因为它不是一个完全独立的小库。

`aionui-team` 依赖数据库、项目、API 类型、实时事件、Agent 管理、角色提示和认证等多个内部模块。**直接搬团队模块，很可能把对方的一整套基础设施一起带进来。**citeturn203232view3

所以，我建议的顺序是：

**先通过接口使用 → 验证实际收益 → 再决定是否提取少量独立代码。**

不是先大规模合并，之后再花时间解决两套架构冲突。

## 三、WORK-LAB 的“超级入口”继续做，但拆清两层

你此前的前端方案把 Quick Entry 定义为 **`Ctrl/Cmd+K` 全局命令面板＋系统托盘入口**，负责搜索和打开项目、任务、Agent、工作流，并通过已有后端发起受控操作；它不是另一个独立聊天软件。fileciteturn10file4L245-L268

你这次提出的：

> “我发布目标，多个模型和 Agent 自行讨论、拆解、执行、审计。”

是在这个入口上增加的**目标驱动协作能力**，不需要因此推翻原来的产品外壳。

我的取舍如下：

| 部分 | 建议 |
|---|---|
| **WORK-LAB 主界面、Quick Entry、托盘、任务详情** | **继续完成，不因寻找第三方方案而暂停。** |
| **输入目标后生成计划、选择执行团队** | 做一个能真实运行的最小流程，优先调用外部 Agent，不新建推理引擎。 |
| **多 Agent 会话与协作适配** | 优先验证 AionCore 或更轻的接口方案，复用已有执行联邦。 |
| **自研通用聊天产品、模型运行时** | 不列入这次建设范围，也不是简单推迟到下一轮再重复造。 |
| **整套 AionUi 界面、数据库、运行时并仓** | 当前不做。 |

**你最终只需要面对一个 WORK-LAB 入口；后台使用外部程序，不意味着前台一定要出现两套产品。** 这是可以实现的集成目标，前提是接口和生命周期验证通过。

## 四、怎么“吸收”，才能真正帮你省开发成本？

我建议采用**接口融合为主、局部代码复用为辅、交互参考同步进行**的方式。

### 1. 接口融合：最先做

把 AionCore 暂时视为**可替换的外部团队执行端**，挂在你已有适配体系下。

建议的职责分工是：

```text
WORK-LAB 超级入口
    ↓
现有控制后端：记录目标、限定范围、处理授权
    ↓
现有执行联邦 / 适配器
    ↓
外部团队执行端
    ├─ 负责人：组织讨论、提出拆分方案
    ├─ 执行者：完成各自被授权的任务
    └─ 审查者：检查产物与验证证据
    ↓
标准化回执、执行状态、产物引用
    ↓
WORK-LAB：记录、验收、退回修改或完成
```

**这是建议实施的结构，不是已经完成的连接。**

其中最重要的是：**AionCore 可以报告“执行结束”，但不能直接把 WORK-LAB 的任务判为“验收完成”。** 你的完成权威、真实证据要求和单写入者原则，仍然保留在现有体系里。fileciteturn12file0L2-L2

外部程序自己的会话和团队记录可以存在，但不要与 WORK-LAB 双向同步成两份互相争夺权威的任务表。WORK-LAB 保存任务关联、执行编号、标准化状态和必要回执即可，**不是收集所有软件的完整聊天历史。**

### 2. 局部代码复用：通过核对后再决定

值得检查的候选包括：独立的协议转换、能力识别、事件处理、错误分类，以及相应测试。**是否直接采用，要以逐模块依赖检查为准，不提前保证每一项都能干净地抽出来。**

AionUi 和 AionCore 当前主仓库采用 Apache-2.0，具备按许可证条件修改、复用和分发的基础；分发时需要保留相应许可证、归属声明、修改说明及适用的 NOTICE。**具体依赖和素材还要分别核对，主仓库许可证不能替它们全部担保。**citeturn203232view0turn203232view1

### 3. 交互参考：可以直接开始，不必复制整套 UI

可以研究它怎么呈现团队成员、待审批动作、任务分配和运行活动，再用你自己的组件实现。

AionUi 当前工程使用 Electron，并依赖 Arco Design 等组件；你的 WORK-LAB 则明确采用 React/TypeScript、Tauri/Rust 外壳和 Python 控制面。**即使都用了 React，也不代表整套页面可以无成本搬过来。**citeturn994655view2turn994655view3fileciteturn12file0L2-L2

因此，我不建议为了借它的团队功能，引入第二套桌面外壳或设计系统。

## 五、那还有没有比 AionUi 更适合“并入”的？

**有可能。作为完整软件好用，与作为 WORK-LAB 的依赖好用，是两个标准。**

这轮核对后，我会这样划分：

| 候选 | 更适合的用途 | 对 WORK-LAB 的判断 |
|---|---|---|
| **AionUi** | 立即体验完整的团队协作产品 | 适合做体验对照和交互参考，不优先整仓吸收。其团队模式明确支持负责人拆分、派发、消息交换与汇总。citeturn635592view0 |
| **AionCore** | 调用现成的团队后端能力 | **优先验证的外部团队执行端候选**；接口边界与依赖需要实测。citeturn178666view0turn203232view2 |
| **acpx** | 统一调用不同 ACP Agent，处理会话和结构化结果 | 需要的只是“调用与续接”时，可能比引入整套团队后端更合适；但它明确处于 pre-1.0，接口仍在演进。citeturn994655view5 |
| **Paperclip** | 管理组织、目标、任务、权限、预算和多个 Agent | 能力范围广，但与 WORK-LAB 的控制面职责重叠更多。我倾向于参考其机制，而不是再叠加一套管理系统。citeturn994655view6 |

**所以，不能现在就把“吸收 AionUi”定成唯一技术路线。** 应该先确认差距：

- 缺的是**团队讨论和协作组织**，重点测 AionCore。
- 缺的是**真实 Agent 调用、会话续接和结果返回**，先检查现有适配器，再比较 acpx 等轻量接口。
- 缺的是**界面把已有能力串起来**，就直接完成 WORK-LAB 前端，别引入不必要的后端。

这才不会因为发现一个新项目，又把你的开发计划整体推倒。

## 六、这一轮怎么推进，才不会再次拖延？

**把第三方验证做成一个有限范围的接入任务，不让它成为整个 WORK-LAB 上线的前置条件。** 这也符合你当前顶层规范中“可选验证不阻塞核心产品收敛”的原则。fileciteturn12file0L2-L2

我建议只验收一条完整链路：

> **从 WORK-LAB 输入目标 → 实际调用不同执行后端 → 返回真实产物 → 独立检查 → 定向返工 → 完成记录。**

通过标准不看“Agent 聊得热不热闹”，而看下面这些事实：

| 验证项 | 通过条件 |
|---|---|
| **真实协作** | 确实调用了不同执行后端，不是同一个模型扮演多个名字。 |
| **权限落实** | 审查者不能修改执行者的成果；并行写入有独立工作区或明确所有权。 |
| **生命周期完整** | 能取得执行编号、状态、回执；中断和取消能得到真实结果，不只改界面文字。 |
| **额度可解释** | 保持执行端原有认证方式；收费来源有依据，不知道的显示未知，不自动切到新的付费接口。 |
| **可退出、可替换** | 关闭或移除 AionCore 后，WORK-LAB 原有启动、任务记录与其他执行端仍可工作。 |

这些是建议的验收条件，不是我声称已经通过的测试。尤其**外部执行端有自己的工具权限，不能仅凭 WORK-LAB 前面出现一个审批按钮，就认定后面的所有操作都受控。**

成本策略也应继续按**每个任务的质量、成本、隐私和时延要求**处理，保留你的原生模型选择，不新增全局限额或静默降档；你的仓库规范对此已有明确要求。fileciteturn11file0L2-L2

## 最终决策

**超级入口继续做。AionUi 不作为替代 WORK-LAB 的理由，而作为外部能力与代码参考来源。优先核验 AionCore 能否通过现有适配体系补上团队协作；轻量接口足够时，就不引入完整后端。**

用一句话概括：

> **保留 WORK-LAB 的产品入口和控制权，吸收第三方已经做好的执行能力；不重复造，也不整套吞。**

本轮完成的是仓库规范、部分源码与上游接口的只读核对，尚未完成本机端到端测试，也没有修改你的仓库。**现在适合确定的是这条融合方向，而不是提前宣布 AionUi 已经是最终底座。**

## 三、最重要的融合原则：场景必须反映后端事实

### 1. 角色、软件、模型和工具必须分开

“研究员”是角色，Codex 或其他客户端是执行环境，某个模型是推理来源，搜索或文件接口是工具。**不能画了六个角色，就宣称六个不同模型正在协作。**

未来成员详情应能回答：它负责什么任务、由哪个执行端承载、使用什么模型或提供方、关联哪次运行、能访问哪些资料。

角色数量随真实任务变化，不固定六个；未启动的计划成员明确标为“待启动”，不能提前播放“正在执行”的动画。

### 2. 状态变化不能靠动画猜测

建议把状态表达写入未来规划：

| 实际情况 | 场景应当怎样表现 |
|---|---|
| 已连接但没有任务 | 空闲，允许轻微待机动作 |
| 已接到任务、正在执行 | 工作状态，并显示实际任务摘要 |
| 等待授权、依赖或额度 | 明确显示等待原因，不统一表现成“睡觉” |
| 连接中断或只有旧快照 | 标明离线／状态过期与最后更新时间 |
| 执行端提交了成果 | “待验证”，不是直接庆祝完成 |
| 验证未通过 | 显示问题与返工状态 |
| 最终验收通过 | 显示完成和可打开的交付物 |

用户点击“取消”后，也要区分**取消请求已提交**与**下游实际停止**。没有进度依据时，显示阶段和已完成步骤，不编造百分比。

这与 WORK-LAB 现有规范要求一致：前端呈现后端事实，不能虚构成功、额度、价格或零值；Observer 始终只读。fileciteturn15file0L2-L2

### 3. “团队讨论”应当展示实际交流，而不是生成表演

未来可以在工作室里看到规划、质疑、结论和交接，但应来自实际消息或明确标注的摘要。没有发生通信，就不播放“他们正在开会”。

展示重点是**决策、分歧、任务分配、证据和结果**，不要求收集所有私人会话，也不依赖展示模型内部思维链。

### 4. 场景不成为新的执行后端

你当前规范采用 React／TypeScript 前端、Tauri／Rust 原生边界，以及 Python 控制面和适配层；状态通过 Runtime Descriptor、Snapshot、SSE 等路径投影。这个方向不需要因为参考 Marvis 而推翻。fileciteturn15file0L2-L2

未来合理的关系是：

> **真实执行事件 → 现有标准化状态与回执 → 同时呈现为工作室、列表和任务详情。**

下达任务、审批、取消、重试等写动作，仍走独立 Control 路径。**角色走到某个工位，不代表系统已经获得了访问权限。**

AionUi／AionCore 等候选解决的是未来协作能力来源；Marvis 提供的是表现与交互参考。**两条研究线可以关联，但不能互相变成强制依赖。**

## 2. 未来产品定位

将“场景化 Agent 工作室”作为 WORK-LAB 既有超级入口的未来增强方向。

建议规划名称：

**WORK-LAB Agent Studio — Visual Collaboration Experience**

中文名称可暂用“智能体工作室”或“场景化 Agent 工作室”，不在本轮改动 WORK-LAB 正式产品名称。

未来产品的核心体验：

用户只需要提出目标。

系统利用已有的任务与权限机制，组织符合条件的执行者，并以直观的工作室场景呈现任务与协作状态。

用户能够快速看到：

- 谁负责总体规划。
- 哪些 Agent 正在参与。
- 每个 Agent 当前承担什么任务。
- 任务是并行执行还是依赖其他结果。
- 哪些执行端不可用或遇到错误。
- 哪些操作正在等待授权。
- 哪些结果已经返回、等待审查。
- 哪些结果未通过审查，需要返工。
- 最终交付物和验证证据在哪里。
- 实际调用了哪些客户端、模型和工具。
- 已知的 Token、成本和额度状态。

设计目标不是让多个卡通人物热闹地工作，而是让用户能够**看得见执行过程、理解协作关系、发现问题、掌握控制权、检查最终成果**。

未来 WORK-LAB 应当是一个拥有可视化团队体验的工作流控制系统，而不是虚拟宠物游戏。

## 3. 深化腾讯 Marvis 的参考方式

主要研究来源：

- https://marvis.qq.com/
- 腾讯 Marvis 官方公开介绍与发布资料
- 腾讯产品团队关于虚拟办公室和 Agent 可视化的公开访谈
- 公开可核验的产品截图、演示和使用资料

补充研究来源：

- https://github.com/Drok1015/marvis-office

该 GitHub 项目属于第三方复刻示例，**不是腾讯官方源码**。

可以参考它展示的 React / Lottie / SSE 等实现思路，但不能推断腾讯原版使用同样技术，也不能在未经许可核验的情况下复制其代码和素材。

未来研究应区分：

### 3.1 值得吸收的产品表达

- 主入口以用户目标和任务为中心。
- 独立的全局办公室，显示整体 Agent 团队。
- 单个任务中的缩略办公室，显示参与成员。
- 角色、工位、动作和监视器共同表达工作状态。
- 工作日志、产出物和预览分开组织。
- Agent 消息与工具执行记录明确标识发起者。
- 任务列表、统计信息和工作场景组合展示。
- 轻量待机动画增强角色辨识度和产品温度。
- 精确操作仍通过常规按钮、面板和表单完成。

### 3.2 需要进一步优化的方向

WORK-LAB 不必固定六个角色。

工位数量、团队规模和职责应根据真实任务动态形成。

角色不应固定绑定某个模型品牌。

工作场景要反映项目状态，而不是只反映是否打开了某个程序。

用户应能查看成员背后的真实执行端、任务、日志、产物与审计情况。

不要为了拟人化而模糊错误、权限、费用或失败状态。

未来交互要支持简单目标和复杂项目两种情况，不要求用户为了一个小任务先组建完整团队。

### 3.3 不采用的方向

- 直接复制腾讯的小马形象、工位素材或办公室资产。
- 把工作场景做成所有任务的唯一交互方式。
- 把娱乐动作作为任务状态判断依据。
- 用前端动画模拟未真实发生的 Agent 协作。
- 未经证据确认就声称掌握腾讯客户端源码或渲染技术。
- 为实现视觉效果而重建整个 WORK-LAB 前端。

## 4. 未来交互体验：三种形态、同一套事实

未来规划应明确三个互补入口。

### A. 全局工作室：Agent Studio

面向用户查看整体团队和项目情况。

建议布局：

**顶部**
- 当前项目与工作范围。
- 统一目标输入。
- 当前任务摘要与关键提醒。
- 必要的工作模式、授权和预算入口。

**中央**
- 可交互的微缩 Agent 工作室。
- 动态工位和角色。
- 当前任务分配、等待和交接。
- 工作区与项目边界的视觉提示。
- 必要的协作连接和事件提示。

**侧边**
- 选中成员的信息。
- 正在执行的任务。
- 执行端、模型和工具信息。
- 最近运行事件。
- 当前阻塞与待处理事项。

**辅助区域**
- 今日或当前周期任务统计。
- 已知 Token 和成本。
- 待验证的交付物。
- 可继续执行的任务。
- 最近完成或失败的任务。

不要求所有信息同时展开。

优先保证用户第一眼能够理解：**正在发生什么、哪里需要处理、下一步应该去哪里。**

### B. 任务内工作室：Mini Agent Studio

当用户进入具体任务时，工作室缩小为任务侧栏组件。

主区域保留给：

- 用户目标与当前计划。
- 实际任务步骤。
- 执行与交接消息。
- 工作日志。
- 产出物。
- 预览。
- 验证与审查。
- 返工记录。

迷你工作室只展示与当前任务相关的成员。

用户可从迷你成员跳转到相应任务、原生执行记录或产物，不重复实现一套聊天系统。

建议研究“工作日志 / 产出物 / 预览 / 审查”如何组织成清晰的信息层次，避免所有内容混杂在一个聊天记录中。

### C. 轻量入口：Quick Entry / HUD / Tray

保留现有 Quick Entry、全局快捷唤起和托盘方向。

未来可在轻量入口中完成：

- 输入新目标。
- 选择项目。
- 查看当前任务摘要。
- 继续之前的任务。
- 跳转到完整工作室或任务工作台。
- 查看明确标识的阻塞和待确认事项。

不在轻量入口塞入完整办公室、全部成员、完整日志和所有控制按钮。

三种形态共享同一业务事实。

场景切换、关闭动画、最小化窗口或者退出工作室，都不能改变后端执行状态。

## 5. 视觉设计与品牌融合

未来视觉应参考 Marvis 的微缩工位和角色化表达，但形成 WORK-LAB 独立原创的品牌语言。

设计研究方向：

**视觉形态**

- 优先比较 2D、2.5D、等距轴测和轻量预渲染方案。
- 维持专业工作台所需的视觉清晰度。
- 场景具有适度空间纵深和柔和光影。
- 以清晰的层级和留白控制复杂度。
- 与 WORK-LAB 已有品牌、配色、排版和组件系统统一。

**角色系统**

未来可为不同工作职责设计原创抽象角色或符号。

建议结合 WORK-LAB 已有视觉资产，研究节点、连接、星图、数字生命感与工作角色之间的融合方式；具体资产必须先核实仓库里的正式品牌规范。

角色差异可通过轮廓、局部配色、装备、工位和状态表达，不依赖大量文字。

不强制采用动物形象。

不能把外部产品的商标、角色或贴图直接纳入项目资产。

**工位系统**

工位可包含：

- 工作桌。
- 屏幕。
- 角色。
- 当前任务摘要。
- 状态提示。
- 必要的协作标记。

屏幕显示内容优先使用经过授权的任务摘要或受限缩略预览。

不默认获取真实桌面画面、客户文件内容或其他项目窗口。

**氛围与动效**

可以研究：
- 空闲待机。
- 阅读。
- 工作。
- 等待。
- 交接。
- 成果提交。
- 休息与非任务相关的轻量氛围动作。

但必须明确：氛围动作不等于真实任务状态。

所有重要运行状态仍需要文字和明确标识。

未来规划应包含减少动态效果、静态场景和传统列表模式。

## 6. 核心交互与任务旅程深化

规划中至少描述以下完整用户旅程。

### 场景一：发布一个简单目标

用户输入一个无需团队协作的小任务。

系统应能够选择合适的单个执行端完成，而不必强制启动多个 Agent。

工作室只显示必要成员及实际执行过程。

### 场景二：发布复杂项目目标

用户提出跨研究、设计、开发和测试的目标。

未来流程：

目标输入  
→ 读取有效项目规则  
→ 生成规划候选  
→ 判断是否需要团队协作  
→ 组织适合的执行者  
→ 在必要时讨论、比较和拆分任务  
→ 检查权限、成本与依赖  
→ 派发允许执行的子任务  
→ 收集执行结果  
→ 验证、审查和必要返工  
→ 依据 WORK-LAB 的完成标准交付。

场景中呈现真实成员、任务关系和执行状态。

不要把“多模型讨论”作为每个任务的强制流程。

### 场景三：用户点开一个 Agent

展示该成员的角色、当前任务、实际执行客户端、原生运行身份、可用能力、最近事件、已知模型来源和产物引用。

允许从成员跳转到对应任务详情。

如果该信息没有被实际采集，应标记不可得，不生成推测值。

### 场景四：Agent 之间发生交接

可视化表示从一项工作到下一项工作的依赖或交接。

交接信息包括任务身份、输入和成果引用、状态，以及必要的未完成事项。

避免使用长篇重复聊天模拟协作。

不呈现未经公开的模型内部推理过程。

### 场景五：执行失败与返工

显示真实失败原因、影响任务、可重试范围及返回的验证结果。

执行端自报完成后仍需经过适用的验收流程。

未通过时能够看到审查意见与返工记录。

### 场景六：执行中断与恢复

场景正确区分运行、断线、状态过期、取消请求中、实际停止、待恢复和未知状态。

旧事件不得覆盖新修订任务。

任务恢复必须依据后端真实检查点，不能靠前端动画继续播放来冒充恢复成功。

以上均属于未来交互需求，不在本轮实现。

## 7. 角色、执行端、模型与工具的身份体系

未来工作室的核心对象必须明确分层：

| 层次 | 含义 |
|---|---|
| Role | 任务中的工作职责 |
| Agent / Executor | 实际承担工作的执行端 |
| Model / Provider | 推理模型与提供方 |
| Tool / Skill | 使用的具体能力 |
| Session / Run | 原生会话和运行身份 |
| Work Unit / Attempt | WORK-LAB 的任务及执行尝试 |
| Artifact / Receipt | 真实成果和执行证据 |

例如，“研究员”是一个逻辑角色，可以由不同已授权的模型或 Agent 承担。

同一个客户端也可以在不同任务中承担不同职责。

未来工作室不能因为出现六个角色，就默认有六个独立模型正在运行。

不能因为某个程序已安装，就标记为已连接、已授权和可执行。

需要研究动态团队、单 Agent、多人协作与执行端替换时的身份保持方式。

## 8. 前端场景必须绑定真实后端状态

未来场景不建立第二套任务状态机。

必须复用 WORK-LAB 的有效任务协议、状态投影和观测机制。

研究如何将现有后端的：

- Runtime Descriptor
- Snapshot
- SSE / 实际事件源
- Work Unit
- Attempt
- Executor
- Receipt
- Completion
- Health
- Token / Cost

映射为场景所需的显示数据。

建议的概念性呈现信息：

- 项目与任务身份。
- 任务修订及 attempt。
- 执行者与原生运行引用。
- 状态与状态来源。
- 事件时间和接收时间。
- 最近有效状态。
- 阻塞与错误。
- 验证结果。
- 可访问的产物引用。

这里只说明数据职责，不在本轮制定生产 Schema 或修改 API。

### 必须保留的真实性规则

**UNKNOWN 不等于 0。**

**STALE 不等于 LIVE。**

**请求已受理不等于任务已执行。**

**执行结束不等于验收完成。**

**取消请求不等于执行已停止。**

**动画完成不等于真实交付成功。**

未来实现还必须考虑事件乱序、重复事件、网络断线、过期快照、恢复和执行端不可用。

场景只是后端真实事实的投影。

## 11. 性能、可访问性与运行边界

工作室未来应优先保证业务功能可靠和轻量化。

研究方向包括：

不能提前断言某种渲染技术是最终选型。

未来性能预算、目标硬件和测试方法应由真实环境及实测决定，不编造固定指标。

## 14. 未来验收要求

把这些条件列入未来验收规划，而不是本轮运行测试。

### 体验真实性

- 场景、列表、任务详情呈现一致的任务事实。
- 用户能够识别成员、工作职责和执行状态。
- 状态过期、失败和不可用有明确表达。
- 关闭场景不影响任务执行。
- 不通过动画虚构实际完成情况。

### 执行真实性

- 真正调用的执行端有可核验身份。
- 子任务和原始工作单元关联。
- 结果能够返回、读取和审查。
- 外部 Agent 的完成声明不能自动代替 WORK-LAB 验收。
- 取消、恢复和返工有实际回执。

### 权限与成本

- 真实写操作继续使用正式 Control。
- Observer 不获得额外执行权限。
- 外部执行端受适用权限与数据边界约束。
- 用户模型和认证选择受到尊重。
- 不静默免费转付费。
- 不知道的额度和成本如实显示未知。

### 独立性与可恢复性

- 外部协作服务停用后核心任务数据仍可读取。
- 其他可用执行端仍可继续获准的任务流程。
- 不引入第二套正式任务真值。
- 组件和上游变更有明确退出路径。
