# 一、Q1：codex 放在 Hermes 目录 —— 判断

## 当前方案问题成立

```
packages/client-neutral-core/bin/
 ├ codex
 ├ codex.cmd
 ├ hermes-npx

- 部署后：

```

但是：

> codex 是 OpenAI/Codex 入口，却进入 Hermes 家目录。

| 类型 | 应该位置 |
|-|-|
| 软件自身文件 | 软件目录 |
| 用户级统一入口 | 用户 PATH 目录 |
| 项目管理脚本 | 项目仓库 |

所以：

```
%LOCALAPPDATA%\hermes\bin
```

不适合作为 codex 长期入口。

│
├─ AI-Bin
│   ├─ codex.cmd
│   ├─ hermes.cmd
│   ├─ dsh.cmd
│
├─ Hermes
│
├─ OpenAI
│
└─ Programs

你的目标不是单个项目，而是：

# 2. 通用项目治理基线

## 定位

这是 WORK-LAB 项目最核心的职责。

不是管理某个项目。

而是：

> 提供所有项目都可以继承的治理框架。

例如：

未来：

```
项目A
项目B
项目C
```

都可以接入：

```
Common Project Governance
```

---

## 通用项目治理内容

统一：

```
Project Governance Framework

├── 项目结构规范
├── 文件组织规范
├── 文档规范
├── 任务管理规范
├── Agent协作规范
├── Skill管理规范
├── Plugin管理规范
├── MCP管理规范
├── 配置管理规范
├── 版本管理规范
├── 验收规范
├── 证据规范
└── 发布规范
```

---

例如：

所有项目都应该有：

```
.project/
├── rules/
├── skills/
├── plugins/
├── workflows/
├── reports/
├── manifests/
└── validation/
```

但是：

里面具体内容由项目自己定义。

---

举例：

通用层规定：

> 项目必须有 rules 目录。

但是：

AAOS：

```
rules/
├── knowledge-rule.md
├── evidence-rule.md
```

DESIGN-LAB：

```
rules/
├── design-rule.md
├── asset-rule.md
```

WORK-LAB：

```
rules/
├── execution-rule.md
├── agent-rule.md
```

这是项目自行扩展。

# 3. 软件生态适配基线

## 定位

解决：

> 如何让不同官方软件接入统一治理体系。

不是替代软件。

---

关系：

```
通用治理规则

        ↓

软件适配层

        ↓

官方软件

```

---

例如：

通用规则：

```
代码修改必须验证
```

适配：

Codex：

```
AGENTS.md
```

Hermes：

```
workflow / skill / config
```

Claude：

```
CLAUDE.md
```

---

软件自己负责：

- Agent能力
- 模型调用
- Runtime
- 工具调用

WORK-LAB负责：

- 规则映射
- 配置生成
- 状态检查
- 兼容验证

                 Personal AI Architecture

# 最终一句话定义

> **WORK-LAB不是三个项目的总管理器，也不是单独执行项目；它提供个人 AI 体系中的通用治理能力：统一规则、技能、插件、配置和软件适配标准，让不同项目和不同官方软件能够在同一治理框架下运行。**

3. **软件生态适配基线（连接官方工具生态）**

而 AAOS、DESIGN-LAB、WORK-LAB 本身，只是这个体系下的不同项目实例。
