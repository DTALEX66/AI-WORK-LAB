“**Hermes 只适合跑普通模型**”这个说法不准确，至少按 **2026 年 9 月现在的 Hermes Agent** 来看已经明显过时了。

真正的问题不是“普通模型 vs 顶级模型”，而是：

> **Hermes 最擅长的是：把一个模型当作“大脑”，由 Hermes 自己掌控 Agent Loop、工具、记忆、Skill、MCP、子 Agent、上下文压缩等。**
>
> 对那些本身已经带有完整 Agent Runtime 的模型/系统，例如 Codex、Claude Code 一类，如果只是把“模型 API”塞进 Hermes，反而可能丢掉一部分它们原生宿主的能力。

### 先把“模型”和“Agent Runtime”分开

| 类型 | 例子 | 放进 Hermes 的情况 |
|---|---|---|
| 普通聊天/推理模型 | DeepSeek、GLM、Kimi、Qwen、普通 Claude/GPT API | **非常适合** |
| 强 Tool Calling 模型 | Claude、GPT、Gemini、DeepSeek 等 | **非常适合** |
| 推理模型 | GPT reasoning、Claude thinking 等 | **支持很好** |
| 原生 Coding Agent 模型 | Codex 系列 | **能跑，但运行方式很重要** |
| 自带完整 Agent Harness | Codex CLI / Claude Code / Copilot ACP | 不应该简单降级成“一个 API 模型” |

Hermes 当前甚至要求主模型至少有 **64K context**，官方明确列出了 Claude、GPT、Gemini、Qwen、DeepSeek 等作为正常适配对象。citeturn281247search4turn281247search7

而且现在 Hermes 已经支持 OpenAI、Anthropic、Gemini、OpenRouter、本地 Ollama/vLLM，以及任意 OpenAI-compatible endpoint。citeturn281247search1turn281247search11

所以它绝不是“只能跑普通模型”。

---

## 为什么会有人这么说？

核心原因是 **Hermes 最初/基础架构的抽象层是通用 Agent Harness**。

Hermes 内部把会话历史保存成接近 OpenAI Chat Completions 的统一结构，然后不同 provider 再通过 transport 转换：

- `chat_completions`
- `codex_responses`
- `anthropic_messages`

官方开发文档现在仍明确说明：Hermes 内部 conversation history 使用 OpenAI chat-completions 形态，再由其他 transport 转换成各家原生协议。citeturn281247search2

这意味着：

**普通 Tool Calling 模型 → Hermes**
非常自然。

流程基本就是：

`模型 → function call → Hermes tool → result → 模型 → 下一步`

但是：

**Codex 这种“模型 + Agent Runtime”体系 → Hermes**

问题就复杂了。

因为 Codex 原本可能已经拥有：

`模型`
`+ shell`
`+ patch`
`+ sandbox`
`+ MCP`
`+ plugins`
`+ context management`
`+ programmatic tool calling`
`+ 原生 coding loop`

如果你只把 Codex 当成：

> `model="xxx-codex"`

然后塞进一个普通 Chat Completion Agent Loop，

就可能变成：

> **把一个完整 Coding Agent 拆掉，只取里面的模型。**

这才是“顶级模型放 Hermes 里不一定发挥完全”的真正来源。

---

# 但 Hermes 现在已经在解决这个问题

这是非常关键的变化。

Hermes 现在已经有：

### Codex Responses 原生 transport

不是单纯把 OpenAI/Codex 当普通 `/chat/completions` 模型。

Hermes 会自动判断某些模型需要 Responses API，然后切换到：

`codex_responses`

甚至现在支持 GPT-5.6 Responses 的 **server-side native compaction**。citeturn712527search8turn712527search9

也就是说现在已经开始：

> **保留 OpenAI 原生模型特性，而不是全部压成普通 Chat Completion。**

---

# 更重要的是：Hermes 已经加入 Codex App Server Runtime

这个其实直接改变了“只适合普通模型”这个判断。

现在 Hermes 可以直接运行：

**Codex App Server Runtime**

这种模式下，不再是：

`Hermes Agent Loop`
→ `Codex 只是模型`

而是：

`Hermes`
→ `Codex App Server`
→ `Codex 原生 Agent Runtime`

Codex 自己的：

- shell
- 文件操作
- patch
- sandbox
- 原生插件

继续保留。

与此同时 Hermes 再通过 MCP callback 把：

- web search
- browser
- vision
- image generation
- skills
- TTS

注入 Codex。citeturn712527search1

这个架构其实非常接近我们一直在给 **WORK-LAB** 规划的：

> **不要把各 Agent 全部强行同质化，而应该 Federation / Adapter / Native Runtime 优先。**

# 但现在依然存在“能力损耗”

所以那句话不能说完全毫无依据。

例如目前 Hermes 官方文档明确写着：

Codex App Server Runtime 下，通过 Hermes MCP callback 时，目前有一些 Hermes 工具不能直接使用：

`delegate_task`
`memory`
`session_search`
`todo`

因为这些工具依赖 Hermes 正在运行的 AIAgent 上下文，而 Codex MCP callback 是 stateless 的。citeturn712527search1

反过来也一样。

目前 Hermes 的普通 Codex Responses transport，虽然已经支持大量 Codex 特性，但 **OpenAI 原生 Programmatic Tool Calling 还没有完全映射进 Hermes**。

Hermes 官方 GitHub 目前还有专门的 feature issue，说明现有 `codex.py` 仍然主要把 Hermes 工具投影成普通 Responses function tools，还没有完整实现原生 `programmatic_tool_calling`。citeturn712527search11

所以这里实际上存在一个非常重要的区别：

### 模型能不能跑

和

### 模型能不能发挥 100% 原生 Agent 能力

完全是两回事。

# 因此我会把 Hermes 的模型适配分成这样

| 模型/体系 | Hermes 适配判断 | 原因 |
|---|---|---|
| DeepSeek V4 / R 系 | ★★★★★ | Hermes 自己提供 Agent Harness，正合适 |
| GLM / Kimi / Qwen | ★★★★★ | 同上 |
| Gemini | ★★★★☆～★★★★★ | Tool calling / 长上下文很好 |
| Claude API | ★★★★★ | Hermes 有 native Anthropic Messages transport |
| GPT 普通 API | ★★★★★ | Responses/Chat 两种路径 |
| GPT reasoning | ★★★★★ | Hermes 已有 reasoning effort 管理 |
| Codex 模型作为 Responses 模型 | ★★★★☆ | 很强，但部分 Codex-native runtime 能力仍有差异 |
| Codex App Server | ★★★★★，但属于另一种架构 | 保留 Codex 原生 Agent runtime |
| Claude Code 本体 | 类似 Codex | 应优先保持其 native harness，而不是只抽模型 |

注意这里的星不是“政治/价值判断”那类评分，而只是我对**技术适配完整度**的简化表示。

## 所以你现在 Hermes 用 DeepSeek，其实不是“降级”

反而从架构上非常合理。

你现在这套思路：

**Hermes**
→ 强通用模型 / DeepSeek / 免费模型  
→ Hermes 自己负责 Skill、Memory、MCP、Web、Delegate、Bot、Cron

属于 Hermes 最原生的工作方式。

而：

**Codex**
→ GPT/Codex
→ Codex 自己的 Coding Runtime

也合理。

问题会出现在这种设计：

`Hermes`
→ `Codex 模型`
→ 再用 Hermes 重建一套 Codex 已经拥有的 Coding Agent Loop

这时候就出现：

**Agent 套 Agent**

甚至：

**Harness 套 Harness**

不仅不一定更强，还可能增加：

- token
- latency
- 上下文重复
- tool schema 重复
- tool routing 冲突
- memory 冲突
- sandbox 冲突
- system prompt 冲突

# 这也正好说明你 WORK-LAB 的方向为什么应该继续坚持

不应该：

```text
WORK-LAB
    ↓
Hermes
    ↓
所有模型
    ↓
所有 Agent
```

更合理的是：

```text
                 WORK-LAB
          Governance / Federation
                    │
        ┌───────────┼───────────┐
        │           │           │
      Hermes       Codex       DSH
        │           │           │
   Hermes Loop   Codex Loop   DSH Loop
        │           │           │
   DeepSeek      GPT/Codex   DeepSeek
   GLM/Kimi
   Qwen/Claude
```

然后通过：

**MCP / ACP / Task Protocol / Session Federation / Registry**

互相协作。

这样就不会为了统一而把 Codex、Hermes、DSH 都削成最低公共能力。

这也是我认为你之前坚持的：

> **WORK-LAB 是 Federation Control Plane，而不是第二个 Agent Runtime**

这个定义非常关键。memcite

> “Hermes 只能拿来套普通 API 模型。”

> **Hermes 不是只适合“普通模型”，而是最适合“让 Hermes 自己承担 Agent Runtime 的模型”；遇到 Codex 这种已经自带强 Runtime 的体系，则应该走原生 Runtime / Adapter / ACP/MCP 联邦接入，而不是把它强行降级成普通 LLM。**

这其实和你现在 **Hermes + Codex + DSH 三角体系**非常匹配。

```text
强模型 / 主智能体

       │ 规划、判断、拆任务
       ↓
   Hermes
       │
       ├── delegate_task
       │       ↓

       │       ↓
```

而且 `openrouter/free` 现在就是 OpenRouter 官方的 **免费模型 Router**。它会从当前免费模型池里选择模型，并且会先根据请求要求筛选，比如是否支持 **tool calling、图片输入、structured output** 等。OpenRouter 当前说明它会在符合要求的免费模型中进行路由，所以你不必手工每天追踪哪个 FREE 模型还活着。citeturn736108search10turn736108search11

### 但这里有一个很重要的区别

现在 Hermes 原生可以做到：

> **主模型 → 自动委派 → FREE 子智能体**

但目前还不能原生做到这种非常细粒度的：

```text
代码任务
→ Nemotron Free

网页调研
→ Ling Free

文档整理
→ Gemma Free

复杂推理
→ DeepSeek Free

视觉任务
→ multimodal Free
```

原因是 Hermes 当前正式的 `delegation.model` **仍然是全局配置**。官方文档明确写了：

> `delegate_task` 当前没有 per-task model 参数，所有 child agent 使用配置好的 delegation model。

也就是说：

```yaml
delegation:
  model: openrouter/free
```

是可以的。

但是：

```text
子Agent 1 → 模型A
子Agent 2 → 模型B
子Agent 3 → 模型C
```

让 Hermes 自己根据任务类型精确选择，目前仍不是正式的原生能力；社区也一直在推进 per-task / per-skill model routing。citeturn119510search0turn119510search1turn119510search8

## 不过 `openrouter/free` 恰好绕过了这个问题

因为我们可以把：

```text
Hermes 负责：
要不要创建子智能体
        ↓
OpenRouter 负责：
这个子智能体具体跑哪个 FREE 模型
```

所以实际上形成了**两层 Router**：

```text
                 主模型
                    │
              Hermes Planner
                    │
          ┌─────────┼─────────┐
          ↓         ↓         ↓
       Child A   Child B   Child C
          │         │         │
          └─────┬───┴─────┬───┘
                ↓
          openrouter/free
                │
        Capability Filter
                │
     ┌──────────┼──────────┐
     ↓          ↓          ↓
 FREE模型A   FREE模型B   FREE模型C
```

这个配置我认为比：

```text
Hermes 主模型也是 FREE
```

合理得多。

因为真正重要的：

**任务规划、拆解、检查、合并结果**

仍然由强模型负责。

而 token 消耗最大的执行层：

**搜索、整理、初稿、提取、批处理、简单代码、并行分析**

全部丢给 FREE 子智能体。

Hermes 官方文档自己就把这种模式称为类似：

> **frontier planner + inexpensive workers**

因为并行子智能体通常才是 token 消耗的大头。citeturn119510search0

## 还有第二种：FREE 模型固定池

如果你不喜欢 `openrouter/free` 每次可能切不同模型，也可以固定：

```yaml
delegation:
  provider: openrouter
  model: 某个具体的-free模型
```

目前 OpenRouter 免费模型池仍然很大，并且会变化；它的免费模型页面现在直接按最近 7 天真实 token 使用量更新。citeturn736108search10

这样：

```text
主Agent = 强模型
子Agent = 固定 FREE 模型
```

会比随机 Free Router **稳定性、结果一致性更好**。

## 还有一个坑你必须知道

Hermes 有：

```yaml
fallback_providers:
```

可以实现：

```text
模型A失败
→ 模型B
→ 模型C
```

Hermes 当前已经支持跨 provider fallback。citeturn837870search0

但是官方目前说明：

> **Delegation 本身只有 provider/model override，并没有独立 automatic fallback。**

也就是说：

```text
Main Agent
→ Hermes fallback chain
```

可以。

但：

```text
delegate_task
→ Free A失败
→ Free B
→ Free C
```

Hermes 自己目前并不会完整地这样逐级切。citeturn837870search4

所以这里反而：

```yaml
delegation:
  provider: openrouter
  model: openrouter/free
```

特别有价值。

因为**子智能体的模型池/可用性问题直接交给 OpenRouter Router**。

| 方案 | 能否实现 | 特点 |

| WORK-LAB 自己做 Task Router → Hermes 多模型 | ✅ | **最终最强方案** |

你现在如果目标就是：

> **“强模型只负责思考，FREE 模型疯狂干活。”**
