# 二、这次审计发现的核心问题

这是我认为当前最应该处理的 10 个问题，按优先级排。

1. **P0：当前宣称的 `Project → Brief → Reference → Direction → DesignSystem` 并没有真的包含 Reference。** Workbench 创建 Brief 时直接固定发送 `reference_asset_ids: []`；Design Layer UI 中也没有 Reference 选择/绑定步骤。HTTP 测试虽然传了一个 `img-aaaa...`，但这只是字符串，后端既没有查资产表，也没有校验资产属于当前项目。因此当前真实纵切应写成 **`Project → Brief → Direction → DesignSystem`**。这属于当前最大的一处产品能力过度表述。

2. **P0：Direction 的“唯一选择”状态机存在真实 bug。** SQL 没有“一个项目/Brief 只能有一个 chosen direction”的约束，`choose_direction()` 只是把目标行设成 `chosen=1`，不会把旧方向改回 0。用户连续选择 A、B 后，数据库可以同时存在两个 `chosen=1`。而 `get_design_layer()` 又只返回第一个 chosen，形成歧义。现有测试没有覆盖“连续选两个方向”。

3. **P0：`chosen_direction` 还能产生假选择。** 当前代码在没有任何 `chosen=1` 时，会退化成 `directions[-1]`。也就是说用户还没有做方向决策，API 仍可能返回一个 `chosen_direction`。这和 Authority 中把 Human Choice 当作事实节点的设计相冲突。

4. **P0：后端允许给“未选定方向”绑定 Design System。** SQL 注释写的是“chosen direction binds exactly one design system”，但 `bind_design_system()` 只验证方向存在，不验证 `chosen=1`。Workbench 前端虽然挡住了这种操作，但 API 本身没有 fail-closed；绕过前端即可形成非法状态。

5. **P0/P1：Brief constraints 存在实际前后端类型错误。** TypeScript 合同定义 `constraints: string | null`；创建时后端却把字符串存成 `{"constraints":"xxx"}` JSON 对象，读回来也是 object。Workbench 用字符串插值显示时会出现类似 **`[object Object]`**。现有测试一直传 `constraints=None`，因此 CI 没抓到。

6. **P1：数据库号称“版本化”，但当前版本机制大部分只是字段。** `brief/direction/binding` 都有 `version`、`superseded_by`，SQL 注释也明确写“revision append new version”；但现有 API 只创建 `version=1`，没有 Brief/Direction revision API，也没有真正维护 superseded chain。Design System rebinding同样会新增记录，却仍然都是 `version=1`。这部分目前应定义为 **schema-ready，而不是 versioning complete**。

# 3. P0-01：修复 Direction 单选 invariant

当前已发现：

`choose_direction()` 只会把新方向：

`chosen = 1`

但不会取消旧方向。

因此同一 Project / Brief 可以存在多个：

`chosen = 1`

这是状态机缺陷。

必须实现：

同一决策范围内任何时间只能存在一个 active chosen Direction。

优先语义：

**同一 Brief 只能存在一个 chosen Direction。**

若现有 Authority / 产品定义明确要求 Project 级唯一，则遵循正式合同。

1. 校验目标 Direction 属于当前 Project
2. 校验属于合法 Brief
3. 将当前 Brief 下其他 chosen Direction 原子置为未选中
4. 设置新 Direction chosen
5. 写 actor / actor_kind
6. 保证事务失败时不出现“全部取消但新方向没选上”的中间状态

必须增加回归测试：

- 创建 Brief
- 创建 Direction A
- 创建 Direction B
- choose A
- choose B
- 最终只能 B 为 chosen
- A 必须为 false
- API readback 只能返回 B
- 重试同一操作不得产生异常状态

不要只在前端隐藏旧 chosen。

**Invariant 必须由 backend/state 层保证。**
