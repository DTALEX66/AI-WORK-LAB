# 二、#2 DSH 的 401：认证机制已经可以说明白，但不能据此判定完整健康

## 2.1 这是哪一种认证？

我读取了 **DSH Desktop v2.0.4** 的 `package.json`，其中运行时依赖指向随包提供的 **DeepSeek Harness `0.1.2-alpha.1`**，随后检查了对应标签的认证源码，而不是直接用最新版行为替代你安装版本。fileciteturn10file0L2-L2

对应源码：

```text
packages/client/connection/src/browser-auth.ts
```

机制是：

**进程生成启动 token → 根页面启动链接携带 token → 服务端校验后签发 Cookie → 303 跳转到不带 token 的 `/` → 后续使用 Cookie 认证。**

这个 Cookie 是签名会话 Cookie，带有 `HttpOnly`、`SameSite=Strict`，并绑定请求的主机和端口。没有有效认证时返回 401。**它不是把某个模型 API Key 放进 Authorization 头就能调用的接口。**fileciteturn11file0L2-L2

要区分两个东西：

- **启动 token**：按进程生成，源码中保存在内存，不应去凭据文件里找同名 token。
- **Cookie 签名密钥**：由 CredentialProvider 持久保存；实现说明指向 `$DSH_HOME/.credentials.yaml` 中的对应凭据记录。**这说明存储归属，不构成读取许可。**citeturn278232view6

所以，你的请求直接打到 `127.0.0.1:43120` 返回 401，**与匿名请求没有建立浏览器会话的情况一致，并不自动意味着 DSH 坏了**。同时，`localhost` 与 `127.0.0.1` 也不能随意混用，因为认证绑定的 authority 可能不同。fileciteturn11file0L2-L2

## 2.2 怎样合法治理而不读取凭据正文？

优先使用**产品自身已经认证的界面或正式支持的调用渠道**，由产品持有和使用凭据，不把 token、Cookie 或认证文件内容暴露给模型。

但是，**“界面能够调用内部接口”不等于“已经提供一个面向 Hermes 的稳定外部管理 API”**。我没有找到足以确认你当前安装支持独立、只读、细粒度授权管理 token 的证据；现有浏览器会话也不能当作只读管理凭证使用。citeturn278232view6

对 WORK-LAB 的具体建议是：

> 当前先通过受支持界面和现有 Adapter 完成元数据级观察；没有正式认证集成的外部调用，标为认证接入待验证，而不是去读 `.credentials.yaml`、复制浏览器 Cookie，或关闭认证。

这也符合当前 WORK-LAB 禁止读取、复制、输出认证存储和浏览器数据的边界。fileciteturn2file0L2-L2

## 2.3 最低成本复核，不需要把所有层都硬凑成一次付费闭环

建议把验收分开：

| 验收层 | 能证明什么 | 不能代替什么 |
|---|---|---|
| 进程与监听检查 | 进程存在、端口可响应 | 不证明插件、任务和模型正常 |
| 已认证 UI 与元数据检查 | 界面可用、需要的插件已加载、状态可读 | 不证明任务真实执行成功 |
| 隔离的确定性任务或模拟 Provider 回归 | Adapter 契约、事件、任务状态和恢复机制 | 不证明真实模型与供应方链路 |
| 真实模型任务 | 当前模型、工具和运行时的实际端到端行为 | 仍不等于独立审计完成 |

**本轮可以完成前面明确授权、零模型费用的部分，把真实模型行为验收保留为未执行。** 不需要为了把一个“健康检查”写成绿色，强行再付费跑一个 LLM turn。

但“任务板可写”本身已经是写操作，**不能归入只读检查**；是否会进一步触发调度、插件或模型，还要看实际调用实现。没有授权时，不应往真实任务板塞测试任务。

同样，**执行主体收拢到 Hermes，不等于 DSH 的真实行为已经由 Hermes 替代验证，也不等于取消独立审核要求。** 当前 `AGENTS.md` 本来就要求将结构检查与真实执行检查分开。fileciteturn2file0L2-L2

# 三、#3 顺序依赖 flaky：先找污染源，不先上“跑绿插件”

## 3.1 `0xb2` 不能证明读到了 `.pyd/.exe`

我接受附件已经完成的“非本轮 patch 引入、具有顺序依赖”的归类，但问题区里的进一步推断：

> `0xb2` → GBK → 读取了二进制文件 → 前序测试污染。

**这条因果链尚未成立。** 目前只能确认：某个线程收到的字节序列，不能按当时采用的 UTF-8 规则成功解码。

另一种应优先排查的可能性是：**子进程输出使用了 Windows 本地编码，而父进程以 UTF-8 文本模式读取 stdout/stderr。** Python 的 `subprocess` 在设置 `text`、`encoding` 等参数后，会对管道进行文本解码；这并不要求它读取过磁盘上的二进制文件。citeturn557270view2

因此需要的是完整线程 traceback，至少明确：**哪个测试创建的线程、哪个 `decode`、数据来自文件还是管道、异常发生时正在执行哪个测试。**

## 3.2 根治顺序建议

| 顺序 | 做法 | 裁决 |
|---|---|---|
| 1 | 固定原始失败顺序，缩小到“污染测试 → 受影响测试”的最小组合 | 首选，先保住复现条件 |
| 2 | 修复该组合涉及的编码契约、线程生命周期和共享状态 | 真正的根治 |
| 3 | 对确认修改全局状态的测试，增加有明确范围的 fixture 恢复 | 合适，但不要全仓无差别重置 |
| 4 | 对确实无法在进程内恢复的组件，使用新的解释器进程隔离 | 局部隔离措施，不是默认全量改造 |
| 5 | 用固定种子的随机顺序回归检验修复 | 防复发，不替代前面的定位 |
| 6 | 重试、flaky 标记、隔离跳过 | 只能临时缓解，不能当根治或原始通过证据 |

pytest 官方也将状态未清理和线程生命周期列为重点，并要求测试或 fixture 最终等待自己创建的线程结束。citeturn557270view0

**线程清理尤其要注意顺序：**

```text
通知测试自有线程停止
→ 等待它退出，回收异常
→ 再恢复 cwd / 环境变量 / monkeypatch
→ 最后清理临时资源
```

不能主线程先恢复工作目录、删掉临时文件，后台线程却还在读写。也不要用 `errors="ignore"` 让报错消失后就宣告修复。

### `--dist=worksteal` 不是每文件全新解释器

这一点需要明确纠正。

`worksteal` 是 worker 间的调度策略；`loadfile` 只保证同一文件的测试放在同一个 worker。**它们都不等于“每个文件运行后销毁解释器，下个文件另开一个”。** 贸然改调度可能只是改变污染条件，让问题暂时看不见。citeturn557270view1

## 3.3 三个优先排查假设

这不是经过统计验证的“行业发生率前三”，而是针对现有线索的排查排序：

**第一，子进程管道的编码不一致。**  
定位到 `subprocess` 读取线程时，检查生产者的真实输出编码；明确文本协议，或先保留 bytes，再由正确的边界负责解码。不要把所有输出武断改成 GBK。citeturn557270view2

**第二，前序测试污染路径或环境。**  
例如 cwd、`PATH`、`PYTHONPATH`、环境变量或模块级缓存被留下，导致后一个测试调用了不同程序、读了不同文件。采用 fixture 恢复时，应只覆盖已确认被修改的状态。citeturn557270view0

**第三，线程或共享资源跨越了测试生命周期。**  
例如旧 reader 线程、线程池、日志 handler、管道或临时资源仍被占用。通过显式收尾和异常回传，让错误归属于真正的创建者。citeturn557270view0

附件还有一个需要对账的小问题：文字写“5 项”，括号列举却是 **1＋4＋1＝6 项**。只需根据既有报告核对准确的 test node ID 和参数化数量，不需要为此重跑全仓。fileciteturn19file7

**建议验收标准：原始失败顺序能通过、最小污染组合能通过、没有遗漏的后台线程异常；随机顺序与分区回归作为补充。不是只拿 deselect 后的绿色数字结束这个遗留问题。**

# 四、#4 Hermes 升级：守卫拦得对，而且必须分清两种“自锁”

## 4.1 上游已经有相关修复，但不是所有锁都能因此消失

Hermes 上游 PR **#90192** 已于 **2026 年 8 月 19 日合入**。它处理的是 Windows 上 `hermes.exe` 启动器自身参与升级时的锁定问题，方向是把升级交接给模块形式的 Python 入口，让原启动器退出。**这属于已有的产品级带外启动方案，不需要 WORK-LAB 再造一套同类升级器。**citeturn278232view5

但你的附件描述的是另一个问题：

> 执行会话的 Hermes kernel 仍在运行，持有 venv 中的 native `.pyd`。

**换一个升级入口，不会自动解除另一个活动 kernel 的文件占用。** 对此，我还读取了你记录的 **`53c57871`** 提交中的 `hermes_cli/subcommands/update.py`：`--force-venv` 的帮助文字明确警告，活动解释器会锁住 `.pyd`，依赖同步可能中途失败，留下半升级安装；该选项仅面向确认占用检测是假阳性的情形。fileciteturn18file0L2-L2

**你这次不是“升级守卫妨碍完成任务”，而是“当前执行环境不适合进行这次原地升级”。**

## 4.2 `--force-venv` 的具体风险

风险不一定是“某个被锁文件写了一半”。更典型的是：

```text
源码已经更新
部分旧依赖已经移除
部分新依赖已经安装
某个 native 文件替换失败
入口脚本、依赖元数据、源码处在不同版本
```

**坏的是整个安装集合的一致性。** 活动进程可能暂时还能跑，但下一次启动就失败。当前版本的参数说明已经直接指出这种风险。fileciteturn18file0L2-L2

所以，下面这个所谓中间方案不成立：

> 先对同一个活动 venv 执行 `pip install -U`，冷启动时再生效。

它依然在修改活动环境，并没有解决锁定和混合版本问题。

## 4.3 平行安装方案成立，但不能只复制一个 venv2

作为以后确有需要时的架构方案，合理形态是：

```text
版本 A：源码 A + 环境 A，保持不动
版本 B：源码 B + 环境 B，在独立位置准备和验证
用户允许关闭旧运行体
新启动选择版本 B
失败则下一次启动仍选择版本 A
```

**必须同时隔离源码与依赖环境。** 若两个 venv 都通过 editable install 指向同一个活动源码目录，更新源码仍可能影响旧运行体。

Windows 上可以由产品支持的稳定入口选择版本目录，不一定需要 symlink；也不能假设“创建好 venv 后随便改名搬家”总是安全。Python 官方说明虚拟环境通常含绝对路径，应视为不可直接搬迁的环境。citeturn126623view2

但这只是未来设计建议。**现阶段不建议为了完成这次升级，在 WORK-LAB 新增常驻升级服务、第二套启动体系或全局 PATH 切换逻辑。**

你当前版本本身已有 `hermes update --plan` 维护计划入口；而 `--check` 会进行远端比较，不能把它当成严格离线操作。fileciteturn18file0L2-L2 fileciteturn16file0L2-L2

## 4.4 一句话安全 SOP

**在单独授权的维护窗口内，由用户正常退出 Hermes 桌面、会话和相关后台，确认占用者已退出并保留可恢复的旧安装备份，再从独立 PowerShell 运行原安装 venv 的 `python.exe -m hermes_cli.main update --backup`；若失败，保持停止状态，恢复旧安装到原绝对路径，涉及数据迁移时再按匹配的更新前数据备份恢复，验证后才重新启动。**

**这不是当前活动 Hermes 会话里应立即执行的命令。** 本轮“全程离线”仍然有效；没有准备齐全并核验过的离线更新材料，就把实际升级留待另行授权。

# 二、真正需要的统一治理，应该只有这几个层次

## 1. 一套共同规则，多个原生实现

建议收敛成：

```text
跨软件共同用户约定
        ↓
已有配置所有权与能力声明
        ↓
各软件官方原生载体
        ＋
该软件的用户偏好、增强插件和技能
        ＋
当前项目规则
        ＋
当前任务的临时约束
```

**统一的是规则含义，不是文件格式，更不是把一份物理配置覆盖所有软件。**

例如，Codex 有自己的全局、项目和子目录指令发现顺序；其他软件应按各自官方机制适配，不能照搬 Codex 的文件名和覆盖顺序。官方文档也明确了这种原生分层。citeturn405698view2

没有正式接口的能力，就明确标记“只能观察”“需人工设置”或“不支持”。**不能为了声称统一，去修改上游内部文件、绕过认证，或者伪造一个已经生效的状态。**

## 2. 全局规则只保留长期共同约定

我建议共同层只放：项目识别、官方原生优先、保留用户选择、数据与权限边界、按需技能、任务写入责任、必要验证和真实报告。

以下内容不应长期塞进所有软件的全局提示词：

**具体模型名称、不断变化的价格、某次任务的“全程离线”、完整插件清单、长篇安装教程、全部历史错误，以及某个项目独有的业务规则。**

它们应分别进入软件适配、任务参数、按需技能或项目文档，而不是一直占用所有任务的上下文。

## 3. Hermes 是执行者，不是所有事实和权限的来源

“全部交给 Hermes 执行”可以保留，但应该理解为：

> Hermes 承接当前实施工作；共同规则仍由用户要求和 WORK-LAB 的版本化来源确定，各软件的真实状态仍以各软件原生结果为准。

当前根规则已经区分受管字段与观察字段，并要求保留用户原生配置。**不能因为执行集中到 Hermes，就让 Hermes 把其他软件全部改成自己的一套配置。**fileciteturn27file0L2-L2

必要独立审阅仍保留，但按风险安排。普通小修复不必固定经过三种软件、三家模型轮流签字；涉及安全边界、跨项目写入、不可逆操作时，才需要相应的独立核查。

# 三、哪些治理应该删减，哪些不能删

我的建议是按下面的方式处理，而不是简单“全部放开”：

| 处置 | 内容 |
|---|---|
| **保留** | 配置字段归属、凭据与项目隔离、原生接口、真实回读、并发冲突处理、必要 CI、可恢复操作 |
| **合并** | 重复全局规则、重复安装检查、重复前检、重复回执、固定三方循环审核 |
| **取消默认触发** | 每任务全仓审计、全历史加载、全技能正文扫描、无差别最大推理、同一范围内反复请求确认 |
| **停止扩建** | 第二套 Agent 运行时、第二套任务/遥测数据库、替代原生更新器、重复聊天或 Observer 界面 |
| **条件后移** | 全七客户端可写、全部协议版本组合、收费实验、多平台签名发行、全面语言迁移 |

这个取舍延续已有 Native-First 方案，而不是抛弃配置部署和增强职责，把 WORK-LAB 缩成一个链接目录。fileciteturn28file3

**减负的边界必须明确：**

非安全建议、可选检查出问题，只提示或暂停相关功能；权限、安全或越界问题，阻断受影响操作；发布所必需的检查失败，仍不能放行。

但不能反过来变成：**Hermes 不能升级，所以 Radar 不能开发；Codex 执行失败，所以 Observer 不能修；某个付费实验没批准，所以整个项目永远不能交付。**

# 四、新模型出来后，技能插件应该重新匹配，但不必全部重做

这里应该把三件事分开：

**软件升级，不等于模型升级；模型升级，不等于所有技能都要重写。**

建议只在软件接口、配置格式、协议、模型能力或用户偏好发生相关变化时，检查受影响项。没有影响，就明确输出 `NO_CHANGE`，不要为了“适配完成”制造一批文件修改。

## 应该检查什么

主要检查实际任务用到的能力：工具调用、结构化输出、多模态、上下文、原生推理参数、流式与取消，以及提供方和计费身份。

模型更强时，可以减少过细的操作食谱；某些模型确实需要的辅助步骤，可以留在相应适配层。**不能把一个旧模型的全部补救提示，永久施加给所有新模型。**

OpenAI 在 **2026 年 9 月 11 日**发布的 GPT-6 Astra 技能与提示指导，明确建议缩短技能描述、收窄触发条件、按任务读取文档，并重新评估过细步骤和停止条件。这与本项目需要的减负方向一致。citeturn812832view0

但这不意味着“新模型更强，所以不用测试、不用权限边界”。应删除的是重复引导，而不是实际约束。

## 技能和插件可以增加，也必须允许退出

任务包采用这样的处理：

> 保留有用项 → 合并重复项 → 停用无收益项 → 按实际缺口增补 → 验证后发布。

**13 个受管技能只是当前库存，不是永远必须保留的数量。** 原生技能机制本身支持先加载名称与描述、真正使用时才读取完整指令；不需要 WORK-LAB 再建一个始终扫描全部技能的系统。fileciteturn27file0L2-L2 citeturn405698view1

同时，用户或者官方更新了内容，不应该一律被认定为“漂移”然后恢复成旧快照。任务包要求比较上次发布版本、当前实际内容和候选内容，保留用户变化，再处理具体冲突。

历史适配材料中的分工——Codex 的 GPT 路线、DSH 的 DeepSeek 路线、Hermes 使用用户选择的模型——也已承接，**没有统一强切到 GPT，也没有永久锁死旧模型名称。**fileciteturn28file8

## 五、WORK-LAB 最合适的落地方式：一个共享来源，多个原生入口

下面是我的**实施建议**，不是声称已经部署：

```text
ChatGPT／Hermes／其他规划与审计软件
                 │
          发布明确版本的审计或任务
                 ▼
     GitHub：任务入口＋版本化材料＋回执
                 │
       本地领取器主动读取已批准任务
                 ▼
       WORK-LAB 现有 Task Ledger
                 │
       按任务指定的执行者和能力派发
        ┌────────┼─────────┐
        ▼        ▼         ▼
      Codex    Hermes    其他原生适配器
        └────────┼─────────┘
                 ▼
       修改／测试／提交／执行回执
                 │
          返回同一 Issue／PR
                 ▼
       GPT 复核、用户查看、继续调整
```

### 1. 云端最后一步应该是“发布”，而不是“请下载”

例如你在 GPT 中说：

> “本轮审计定稿，发布到 WORK-LAB 对应任务，保留已有完成项，新增修复交给 Hermes。”

正确的产品行为应是：调用获授权的连接，创建或更新任务材料，返回**任务编号、材料版本、目标分支和发布状态**。

**不能再把“生成一个 ZIP 给你下载”当成这个同步功能的完成标志。**

但是，本轮连接检查有一个真实限制需要说清楚：虽然工具目录能发现创建 Issue、文件和 PR 的动作，**仓库权限回读却是 `pull=true / push=false`**。因此，目前不能宣称这个连接已经能提交仓库文件；Issue 创建权限也没有通过写入试验验证。

**工具有这个动作、连接获准写入、用户授权发布，是三件不同的事。** 本轮没有进行写入试验，也没有修改你的仓库。

### 2. 本地领取应该是普通程序，不应持续消耗模型

建议把领取接到现有执行服务，而不是另起一个“治理 Agent”。

领取器负责：读取新增或更新的已批准任务、取得指定版本、登记到既有 Task Ledger、交给目标软件、回传结果。**检查有没有新任务，不需要调用大模型。**

第一阶段可以采用出站增量读取；需要更快响应时再加 webhook。使用 webhook 时，GitHub 官方要求关注认证、事件类型、遗漏重投和投递标识；重投的 `X-GitHub-Delivery` 会保持不变，正好可作为传输去重的一部分。citeturn552010view1

但要注意：**传输事件编号不是任务执行锁。** 第一阶段采用一个明确的领取端；将来支持多台电脑同时接单，再复用或扩展真正的原子认领机制，不能靠给 Issue 加一个标签来冒充互斥锁。

### 3. 同步所有软件可见，不等于让所有软件一起执行

我建议默认做到：

**共同材料可读取，同一任务只有明确的执行负责人。**

例如，Codex 执行时，Hermes 和 GPT 可以读取进展，但不应同时对同一工作区重复修复。切换执行者时，要带走已完成事实和剩余任务，而不是重新跑整包。

当前仓库已经有任务租约、检查点和持续执行入口，应该利用它们，而不是把“换软件”实现成重新启动一套互不知情的任务。fileciteturn38file0L2-L2

### 4. 你在 GPT 中调整任务，应产生新修订，而不是覆盖正在执行的旧版本

建议每份交接最少绑定：

**项目、任务编号、修订号、代码基线、目标与验收、执行者、授权范围、材料引用、回执引用。**

当你改变任务要求时：

原版本保留；新版本明确替代关系；正在执行的旧任务在安全检查点处理调整；旧版本的结果不能直接标记新版本已完成。

这些属于把现有交接做可靠所需的最小信息，**不需要再扩成几十种治理清单。**

### 5. 回执必须自动返回；GPT 的后续复核则要有明确触发

本地完成后应返回：对应任务版本、实际执行结果、修改文件、测试、提交／PR、未完成内容和阻塞。

但要区分：

**“结果已经同步到共享记录”可以自动完成；“让这个已经结束的 GPT 回答自动重新开始分析”需要另设受支持的事件触发或自动化。**

不能假设本地一写回文件，之前所有聊天窗口的上下文就自动刷新了。

## 六、这套方式怎么覆盖其他软件？

**通用性来自共同任务材料与适配接口，不来自假设每个软件都支持同一种调用方法。**

| 软件类别 | 建议接入方式 | 应显示的真实状态 |
|---|---|---|
| ChatGPT 等云端规划端 | 通过已连接应用或获授权的远程接口发布、读取任务 | 已发布／未获写权限／等待批准 |
| Codex | 官方执行接口消费任务，返回结构化结果 | 已领取／运行中／执行失败／完成 |
| Hermes | 承接现有 TaskPack runner 和任务账本 | 同上，不另建运行时 |
| DSH 等有认证的桌面客户端 | 仅使用确认支持的原生 CLI、API、插件或导入入口 | 接口未核实、认证未完成时，不伪报可执行 |
| 只有文件导入能力的软件 | 自动把指定材料准备到其支持的导入位置 | 已准备，不等于已执行 |
| 观察或历史兼容客户端 | 读取共享任务与回执 | 只读，不赋予任务写入责任 |

你的附件已经报告了 DSH API 401、Codex 执行层故障和 Hermes 自升级锁定等不同问题；它们应分别影响对应能力，**不能把同步链路全部堵死，也不能通过绕过认证、系统权限或升级守卫解决。**fileciteturn29file0

还有两个术语必须放在正确位置：

**MCP 是统一访问工具与数据的方式；ACP 主要规范客户端与 Agent 的交互；A2A 可以表达 Agent 间任务、状态和产物。它们都不是“安装后，七个软件自动共享所有任务”的成品。** ACP、A2A 的官方定义也对应不同层次的职责。citeturn774714view1turn774714view2

因此，第一阶段没有必要强制所有软件同时支持 MCP＋ACP＋A2A。**有成熟原生入口就用原生入口。**

**继续放在 NF-08 下完成实际交付，不另开一套总架构。** 我建议拆成下面六个可以验收的续项：

| 续项 | 要完成的实际工作 | 完成证据 |
|---|---|---|
| **NF-08-A：云端发布** | 接通一个获授权的共享目标，发布审计与任务的指定版本 | GPT 返回真实任务编号和可回读材料，不只返回下载包 |
| **NF-08-B：本地自动领取** | 在现有服务中接收任务并持久化去重 | 不粘贴正文，本地自动取得同一版本；真正重启进程后不重复执行 |
| **NF-08-C：原生执行** | 先接通一个当前可运行的执行软件，再验证第二个不同软件 | 两种软件消费同一交接格式，完成受控样本任务 |

**直接采用：** GitHub 原生任务／文件接口、适用客户端的官方 MCP、软件原生执行接口，以及 WORK-LAB 已有 Task Ledger、runner、回执和只读 Observer。

**按需采用：** n8n 的多业务系统连接、官方安全隧道、特定工具之间的上下文转换。

**不默认叠加：** Symphony、Vibe Kanban、Linear 和另一套自研调度系统同时运行。需要替代某个现有模块时，再做明确的替换验证，而不是全部登记、全部安装、全部长期维护。

## 三、架构上需要守住的关键区别

### 1. WORK-LAB 管共同机制，不集中吞并所有项目

建议的责任划分是：

**共同层**负责规则适配、任务发布与接收、交接格式、状态协调、结果回传，以及软件和模型变化后的兼容维护。

**项目层**保留各自的任务正文、业务规则、代码、资料、验收要求和执行记录。

**软件层**使用各自支持的原生接口，保留原生模型选择、配置和权限机制。

所以，“统一管理”不能被实现成“所有项目内容都提交到 WORK-LAB 仓库”。

### 2. 共享通道不能锁死为某个仓库或平台

上一条提到 GitHub，可以作为**优先验证的传输与工作记录方案**，但不应该成为通用能力的唯一前提。

正确要求是：任务来源和结果目标可适配。其他项目可以有自己的仓库、文档空间或受支持的存储入口；不使用 Git 的项目，也不能因此被排除。

**对接的是“项目自己的权威材料位置”，而不是固定对接 `DTALEX66/WORK-LAB`。**

### 3. 不能依赖某个 Agent 才能遵守共同规则

Codex 不应该必须先启动 Hermes，才能取得用户规则；其他项目也不应该复制一整套 WORK-LAB 源码才能接入。

共同能力可以统一安装和维护，项目只保留必要接入信息；软件依然能够原生运行。同步服务暂时不可用时，应明确显示待同步或待回传，而不是无条件让所有正常工作停止。

### 4. 自动同步不等于无限自动执行

**材料可以自动送达；执行应在已有有效授权范围内自动推进。**

不能因为任务来自另一个软件，就丢掉批准范围；也不能在已经批准的范围内，每换一个软件、每进行一步都重新要求你确认。需要保留的是可核对的授权与任务版本，不是增加人力中转。

### 不能永远要求经过 Hermes

### 改任务不能覆盖正在执行的版本

### 回传失败不能重新跑任务

执行完成但网络断开时，保存待回传记录。网络恢复后只重发结果，不重新执行已经完成的工作。

不同设备可以接入，项目可以路由到不同节点。涉及同一写任务的接管，先核对旧执行状态，再切换接收绑定。

**租约到期不等于旧软件已经停止；同步一个活动账本文件也不等于获得了跨设备互斥。**

共同规则、技能和插件继续按原生载体适配；用户自改通过三方比较保留，不一律恢复为旧快照。技能按需加载，不每轮载入所有项目历史。渐进加载也是 Agent Skills 规范明确支持的组织方式。citeturn401492view2
