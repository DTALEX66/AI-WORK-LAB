# 三、最值得你投入的六个方向

## 1. Beacon：最接近你缺少的“原生执行证据互通层”

### 为什么它对 WORK-LAB 有价值

你要保留 Codex、Hermes、DSH 各自的原生执行能力，就需要回答：

**到底是谁执行了任务、执行到哪一步、发生了什么错误、结果经过什么验证？**

Beacon 的方向确实匹配这部分需求。其当前覆盖表包括 Codex、Hermes 和 DeepSeek Harness；但表中也明确存在差异，例如 Hermes 的 Token 列未标支持，DSH 的 Approval 列未标支持。不能接上一个采集器，就假定所有执行器都获得同等完整的数据。citeturn498883view4

我的建议是把它放在下面这个位置：

```text
原生 Codex / Hermes / DSH
          ↓
可选的 Beacon 采集适配
          ↓
脱敏、字段白名单、事件标准化
          ↓
WORK-LAB 现有 Telemetry / Receipt
          ↓
Observer 只读展示
```

**不要把 Beacon 的数据库再提升成“第四个真相源”。**

### 接入时最容易踩的坑

Beacon 的交互安装会预选 Managed 云端选项；仅登录不会转发，但确认 Managed 后会连接端点。它也具备采集提示词、回答等完整会话内容的能力，因此“Local-first”不能被理解为“任何默认安装方式都只留本机”。citeturn498883view4

而 WORK-LAB 当前禁止把提示词正文、回答正文和敏感凭据写入证据，并把部分 Hermes hooks、MCP 和模型配置字段划为只观察、不直接覆盖。**所以这不是一个可以直接全局安装、自动修改 hooks 的任务。**fileciteturn6file0L2-L2

建议第一轮只验证最小字段：

```text
任务标识、执行器、运行标识、代码版本
开始/结束状态、命令结果、审批引用
产物引用、验证结果、耗时
可获得的用量数据及其来源
```

拿不到的字段显示 **UNKNOWN**，不要显示为 0，也不要用其他执行器的数据推算补齐。

**特别针对你之前的“网页 GPT → 原生执行器”需求：**Beacon 虽然列出了 ChatGPT 浏览器会话采集，但这仍然是观测能力，不能据此认定它能主动调用网页 GPT、提交任务、管理额度或完成闭环调度。citeturn498883view4

**结论：优先试接，但定位为受控采集插件，而不是新的调度中心和知识中心。**

## 2. SoL-Pi：你应该拿走的是“减少无效消耗的办法”

### 先纠正“最高节省 64% Token”

官方结果中，相对 Pi 的 Token 降幅是 **45%–49%**；相对模型原生 Harness 的降幅是 **35%–64%**。同时，组合方案保留了约 **94% 的 Pi 平均得分**。另一个 63 题测试里，Codex、Pi 各完成 18 题，SoL-Pi 完成 15 题。**这不是“所有任务能力不变、稳定省 64%”的证据。**citeturn498883view6

### 对你最有价值的具体机制

SoL-Pi 公开的核心机制包括：大结果按句柄回读、保留证据的日志缩减、编辑与后续验证合并，以及在合适的子任务边界压缩上下文。它们运行在 Pi 的扩展环境中，不能原样当成 Codex 或 Hermes 插件安装。citeturn720835view2

我建议按下面的方式借鉴：

| 机制 | 你的使用场景 | 必须保留的约束 |
|---|---|---|
| **大结果引用与精确回读** | 全量审计、长测试日志、重复读取大型源码 | 原始内容可定位；代码改动后不能继续引用过期快照 |
| **日志证据缩减** | 把上千行失败日志变成可定位的问题摘要 | 失败、超时、跳过不能被压掉；摘要必须能回到原始证据 |
| **确定性动作合并** | 修改之后执行已批准的对应验证 | 不得借“合并工具”跳过中间必须发生的审批 |
| **阶段性上下文整理** | 长任务从调研切换到实现、从实现切换到审查 | 保留未解决问题、约束、版本和真实完成状态 |

这里还有一个容易被忽略的区别：

**引用的日志行真实存在，只能证明“这句话出现过”，不能自动证明 Agent 对错误原因的解释正确。**

所以，日志缩减可以帮助定位问题，但不能替代测试复现和独立审查。

对你而言，我会先试 **“大结果回读 + 日志证据缩减”**，再考虑更深入的上下文干预。它们更容易以局部能力接入，不必迫使你换掉原生执行器。

## 3. Prompts.chat + OpenAI Skills 方法：把“提示词库”变成真正能执行的能力

```text
    ↓

```

例如，一条“品牌总监提示词”不能直接成为 DESIGN-LAB 的专业能力。它还需要补齐：

```text

专项 Skill：任务需要时才加载
参考资料：按需查阅，不整包塞入上下文
```

**规则精简不是削弱规则。**

应该删除的是重复要求、过期路径和无条件触发；应该保留的是授权边界、单写者约束、原生模型选择、真实验证和发布审批。

## 4. GEP / EvoMap：最适合 AAOS 的是“有适用边界的经验”，不是自动自我进化

### 当前 SDK 与你的描述有一个重要区别

当前 GEP SDK 明确说明：**它不携带进化算法代码**。主要提供 Gene、Capsule、EvolutionEvent 等结构、协议常量、内容哈希和验证辅助函数。算法行为在其他实现中。其许可也有版本差异：1.3.0 及之后的代码采用 Apache-2.0，较早版本曾采用 GPL-3.0；规范文档另有 CC-BY-4.0 许可。fileciteturn11file0L2-L2

因此，不能把：

```text
装上 GEP SDK
```

直接理解成：

```text
三个项目获得持续自我进化能力
```

### 你真正值得吸收的结构

我建议把可复用经验设计成：

```text
什么问题
在什么环境和版本下发生
采用了什么方法
有哪些禁止条件
通过什么验证
对应哪些产物和来源
在哪些情况不再适用
由谁审核，何时失效
```

举例：

> “某个 UI 导出流程在指定宿主版本中成功，产物经过字体、尺寸和可编辑性验证。”

这比：

> “AI 学会了高质量 UI 设计。”

更适合你的 AAOS，也更容易被 DESIGN-LAB 安全复用。

**具体做法应该是“字段映射”，不是用 Gene/Capsule 替换 AAOS 的整个对象模型。** 内容哈希能证明对象内容是否一致，不能证明经验正确、来源可靠或可以自动执行。

### AutoResearch 与 Dream-RSI 怎么处理

AutoResearch 更适合受控的研究实验，例如比较检索策略、资料切分方法或某类处理流程；它的价值在于实验组织和证据，而不是允许 Agent 不断修改生产系统。仓库示例还出现了跳过权限的运行方式，不能照搬到你的活动仓库。citeturn300935view1

Dream-RSI 则应继续作为研究参考：官方公开仓库已经存在，但当前仍说明代码准备发布，尚不能作为成熟可安装框架接入。citeturn498883view3

**结论：先把“经验可追溯、可审核、可失效”做扎实，再讨论经验驱动优化。不要把产品中的“RSI”字样当成效果保证。**

## 5. ChatCut：这份清单里最直接对应 DESIGN-LAB 视频生产的项目

### 它不只是“Claude Code 衍生应用”

官方公开的 `ChatCut-Inc/agent-plugin` 支持 Codex、Claude Code 等宿主，能够操作 ChatCut 项目，包括导入素材、修改时间线、字幕、动效、导出以及检查编辑是否反映到编辑器中。它需要 ChatCut 账号和项目权限，并通过托管 MCP 服务连接。**公开插件仓库不等于整个剪辑器和服务端全部开源。**fileciteturn12file0L2-L2

```text

按原生能力理解与执行任务

ChatCut 负责：
真实视频项目、时间线编辑与导出
```

不需要你重新开发视频编辑器。

### 应该怎样验证，才算真的接上

我建议选一个很小的真实视频任务，要求同时完成：

**素材导入 → 时间线修改 → 字幕或动效 → 编辑器回读 → 重新打开项目 → 导出文件检查。**

同时保留账号费用、素材上传范围和素材使用权的检查。不要默认它是纯本地工具，也不要默认它支持所有其他剪辑软件的工程格式互转。

**优先级要看你的当前业务：**继续以文化墙、VI、UI 和静态视觉交付为主时，它是视频扩展项；启动短视频生产时，它可以直接升为第一批验证对象。

```text
                    可复用知识 / 学习材料
```

**其中，Observer 仍然只读。** 你现行规则明确禁止它派工、批准、重试、回滚或修改任务状态；未来统一入口中的操作能力，应通过拥有权限的服务接口实现，不能直接给 Observer 加执行权。fileciteturn6file0L2-L2

还要注意：任务包里写了“只读”并不等于系统真正实施了只读。权限必须由实际执行器、文件系统或工具范围限制来落实，不能只靠提示词自觉遵守。

# 七、真正应该落地的最小任务清单

我建议第一轮只做下面这些，不同时安装整份清单。

| 顺序 | 任务 | 对应项目 | 验收依据 |
|---|---|---|---|
| **1** | 修复现行文档路径漂移，梳理规则重复与加载范围 | WORK-LAB，兼顾另两仓 | 文档与真实代码树一致；必要约束仍然存在；任务不再无条件加载全部技能 |
| **2** | 验证一个原生执行器的最小事件采集 | WORK-LAB / Beacon 候选 | 不读取禁止内容；一次真实执行能关联任务、产物和验证；未知字段如实显示 |
| **3** | 把少量高相关提示词送入现有候选链 | AAOS / Prompts.chat | 有来源、版本、适用范围；未经审核不成为权威技能 |
| **4** | 测试大日志回读或证据缩减中的一个机制 | WORK-LAB / SoL-Pi 方法 | 原始证据可回读；失败信息不遗漏；不因省 Token 而降低任务完成质量 |
| **5** | 完成一个真实视频编辑与可编辑交付任务 | DESIGN-LAB / ChatCut，可按业务后置 | 编辑器回读、项目重开、文件导出及质量检查全部有证据 |
| **6** | 将一次成功或失败经验映射进 AAOS | AAOS / GEP 方法 | 有环境、来源、适用条件和失效规则；不能自动升级为事实或执行指令 |

实验比较也不应只统计 Token。建议至少同时观察：

**真实完成率、返工次数、证据完整性、总耗时，以及可核实的实际用量或成本。** 失败重跑、摘要模型和评分模型的开销都应计入；没有订阅消耗或账单数据时，不把 API 等价价格写成你实际省下的钱。

## 最终取舍

**最优先：OpenAI 规则方法、Beacon 最小采集验证、Prompts.chat 受控候选导入。**

**紧接着：SoL-Pi 局部机制；需要视频生产时加入 ChatCut。**

**第二批：GEP 经验映射、少量 Oh-My-Hermes 技能、OpenMausBot 原生入口验证、Jev 辅助评分。**

**暂不进入核心：cc-haha、EigenFlux、尚未释放实现的 Dream-RSI，以及未经账号实测的“免费模型基础设施”。**

对你的三个项目来说，最有价值的升级不是“同时装上更多 Agent”，而是：

> **让现有原生 Agent 少做重复工作，让真实产物有证据，让一次成功或失败能够沉淀成有边界、可验证、下次真的能用的经验。**
