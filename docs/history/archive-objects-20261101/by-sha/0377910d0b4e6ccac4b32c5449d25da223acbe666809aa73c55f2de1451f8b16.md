## 2. 它现在已经具备的系统骨架

### 第一层：输入层

`/ingest` 会把输入内容标准化为 `CoreObject`。当前第一版主要支持 text-like 输入，文件、URL、PDF 这些后续可以放到 ingestion 模块里扩展。fileciteturn18file0L8-L21

### 第二层：认知对象模型

这个项目最重要的是 `schemas.py`，里面已经定义了系统的核心数据对象：

- `CoreObject`
- `AttentionDecision`
- `ContextPack`
- `TaskPack`
- `ExecutionTrace`
- `EvalResult`
- `MachineLesson`

`CoreObject` 保存内容、来源、metadata、创建时间、attention score 和 route；`AttentionDecision` 支持 `KB`、`IR`、`TASK`、`DROP`、`REVIEW` 五种路由；`MachineLesson` 用来保存执行后的经验约束。fileciteturn19file0L21-L36 fileciteturn19file0L39-L80

这个设计说明：它不是一次性问答系统，而是想形成“输入—执行—评估—经验沉淀”的循环。

### 第三层：注意力路由层

`router.py` 是当前项目最有价值的核心模块。它把输入分成：

```text id="u3xj19"
KB      知识库 / 学习 / 笔记 / 卡片 / 复习
IR      调研 / GitHub / 论文 / 开源 / 架构 / 框架
TASK    执行 / 运行 / 修改 / 生成 / 部署 / 修复
```

### 第五层：RAG 检索层

`retriever.py` 会用 `search_memory()` 找相关记忆，然后生成 `ContextPack`。它会计算三个信号：

- item count
- query term overlap
- source presence

最后返回 context summary、score 和 score reasons。fileciteturn24file0L11-L38

当前检索还是很轻量，但它已经有“上下文包”的概念。这是后续接入向量库、Embedding、SQLite、Chroma、LanceDB、Qdrant 的入口。

### 第六层：任务编译层

`compiler.py` 当前还是 stub，但骨架已经明确。它会把 `ContextPack` 编译成 `TaskPack`，默认生成三个步骤：

1. analyze_context
2. plan_next_action
3. produce_result

也就是说，当前还不是真正的复杂 planner，但已经有“从上下文生成任务包”的形态。

### 第七层：工具执行层

`executor.py` 会逐步执行 `TaskPack.steps`，每一步调用 `run_tool()`，然后把每步结果写入 `ExecutionTrace`。如果工具返回 `error` 或 `blocked`，本次执行就标记为不完全成功。fileciteturn26file0L7-L24

- `echo`
- `file_read`
- `safe_write`

其中 `safe_write` 是 medium risk，默认 dry-run；`code_exec` 是 high risk，默认 dry-run，并且 Phase 1 真实执行被阻止。fileciteturn27file0L20-L45

`safe_write` 只能写到 `data/output` 下，路径越界会被 blocked；`code_exec` 会返回 blocked，只给 code preview，不真实运行。fileciteturn27file0L95-L123

## 5. 这个项目未来能长成什么

它未来最适合长成：

**个人本地认知操作系统的后端运行时。**

它可以承担这些角色：

### 1. 输入总线

所有材料先进入 Cognitive-OS：

```text id="tie1iv"
文本
Markdown
项目文档
课程摘要
网页摘录
GitHub 调研内容
Obsidian 笔记
任务请求
AI 执行结果
```

然后统一转成 `CoreObject`。

### 2. 注意力分流器

它可以判断一段内容应该去哪里：

```text id="sae3n0"
学习资料 → KB
调研资料 → IR
执行任务 → TASK
危险请求 → REVIEW
垃圾输入 → DROP
```

这个能力很适合做你的 AI 系统中枢，因为不是所有内容都应该进入同一个库，也不是所有内容都应该立刻执行。

### 3. 安全前置网关

它可以挡住危险命令、跨盘删除、密钥读取、注册表操作、强制推送、卸载软件等高风险行为。

后续可以升级为：

```text id="dinul3"
risk_level=low      自动执行
risk_level=medium   dry-run + 人工确认
risk_level=high     只读分析，不执行
```

### 4. 记忆系统

现在是 JSONL，将来可以升级成：

```text id="2g9nhk"
SQLite
DuckDB
LanceDB
Chroma
Qdrant
FAISS
Obsidian markdown back-sync
```

这会让它从“记录输入”升级成“长期记忆系统”。

### 5. 任务执行系统

现在的 `TaskPack` 很简单，但未来可以变成：

```text id="0iz1ww"
任务目标
上下文证据
执行步骤
允许工具
禁止工具
安全边界
验收标准
回滚方式
执行 trace
复盘 lesson
```

这就是你一直想要的 AI 执行规范中枢。

### 6. 机器经验系统

`MachineLesson` 是很重要的伏笔。未来它可以记录：

```text id="1btdnz"
哪类任务容易失败
哪类命令必须禁止
哪个路径不能动
哪个工具更适合某类任务
哪个模型处理某类输入更好
哪些步骤必须先 dry-run
哪些输出需要人工确认
```

这会让系统越用越稳。

## 6. 最大亮点

这个项目最大的亮点不是功能多，而是**抽象方向对**。

它不是直接做一个“大而全 AI 助手”，而是先定义了几件正确的底层事：

```text id="zqovra"
对象：CoreObject
路由：AttentionDecision
上下文：ContextPack
任务：TaskPack
执行：ExecutionTrace
评估：EvalResult
经验：MachineLesson
```

这套抽象如果继续扩展，确实可以承载一个长期认知系统。

第二个亮点是安全边界开始形成：

- 文件摄入只能在项目根目录内；
- 文件大小有限制；
- 只支持 Markdown/text；
- 高风险词进入 REVIEW；
- `safe_write` 只能写 `data/output`；
- `code_exec` Phase 1 禁止真实执行；
- runtime 数据被 `.gitignore` 排除，包括 logs、memory、output、数据库和 `.env`。fileciteturn34file0L11-L23

这说明项目不是为了炫技，而是在往“可控 Agent Runtime”方向走。

## 7. 当前最大问题

最大问题也很明确：

**它现在更像“认知系统骨架”，不是完整可用产品。**

具体问题：

1. **Memory 太简单**  
   现在是 JSONL + 词面匹配，无法支撑大量材料、语义检索、多源证据、去重、版本管理。

2. **RAG 太轻**  
   只有 query term overlap，没有 embedding、chunk、source weighting、recency、可信度、引用片段。

3. **Planner 还没有真正智能**  
   `compile_task()` 现在固定返回三步 echo 流程，还不能根据不同任务生成不同执行计划。fileciteturn25file0L6-L19

4. **工具执行还停在安全演示阶段**  
   现在主要是 echo、file_read、safe_write、blocked code_exec，还没有真实接入 Git、Obsidian、文件转换、OCR、ASR、模型 API、浏览器、任务队列。

5. **没有权限系统**  
   目前没有用户、token、API key、局域网限制、操作审计权限分级。只要服务暴露出去，会有风险。

6. **没有测试体系证据**  
   README 里只写了 `python -m compileall app` 作为 smoke test。fileciteturn15file0L45-L55 这只能证明代码能编译，不能证明路由、摄入、安全、执行都可靠。

# 5. 可吸收资产：应该吸收，但不要乱接

这里要分四级。

## S级：可以直接进入核心的开源项目

### MarkItDown

用途：文件转 Markdown，适合做 IR / KB 的通用输入转换器。它支持 PDF、PPT、Word、Excel、图片、音频、HTML、CSV、JSON、XML、ZIP、YouTube URL、EPub 等格式，但它也明确提醒：会以当前进程权限进行 I/O，因此不可信输入环境必须收窄调用范围并做安全处理。citeturn861683view0

推荐接法：

```text
shared/adapters/converters/markitdown_adapter.py
```

只做：

```text
input file → markdown + metadata + source record
```

不要让它直接写 KB 数据库。

### Docling

用途：高质量 PDF / 文档解析。Docling 支持 PDF、DOCX、PPTX、XLSX、HTML、EPUB、音频、图片、LaTeX 等格式，并强调高级 PDF 理解，包括页面布局、阅读顺序、表格结构、代码、公式、图片分类等。citeturn268130view2

推荐接法：

```text
Docling = 精修模式 / 高质量文档解析
MarkItDown = 快速模式 / 通用转换
```

### sqlite-vec

用途：本地向量检索。它是 SQLite 向量搜索扩展，能存储和查询 float、int8、binary vectors，且无依赖、可在 SQLite 能运行的地方运行。它目前仍是 pre-v1，可能有 breaking changes，所以适合做 Adapter，不要强绑定内核。citeturn268130view3

推荐接法：

```text

Qdrant / Chroma = 后期可选
```

### MCP reference servers

用途：参考 MCP 工具服务怎么设计。但官方仓库也提醒：这些服务器是 reference implementations，用来演示 MCP 和 SDK 用法，不是生产级解决方案，实际使用要按自己的 threat model 做安全防护。citeturn997257view1

推荐接法：


```text

再打通
再扩展
再智能
再产品化
```

# 7. 开发方法建议

## 7.1 不要“大模型驱动开发”，要“契约驱动开发”

每个模块都要先写：

```text
Schema
API
State Transition
Permission
Test
Fallback
```

再让 CODEX / DEEP 写代码。

标准任务包：

```text
目标
输入
输出
涉及文件
禁止修改
数据结构
API
测试
验收
回滚
```

## 7.2 用 Intake Card 管控 IR 到 KB

每个研究结果都必须经过：

```text
为什么要吸收？
吸收什么？
不吸收什么？
放在哪一层？
依赖风险是什么？
许可证风险是什么？
是否需要 Adapter？
验收标准是什么？
```

## 7.3 用 Adapter 防止污染核心

所有外部项目都必须：

```text
外部工具 → Adapter → 标准对象 → quarantine → review → core
```

不能这样：

```text
外部工具 → 直接写核心数据库
```

## 7.4 用状态机，而不是靠文档记忆

核心状态：

```text
raw
quarantined
sanitized
candidate
approved
active
archived
conflicted
```

Cognitive-OS 运行状态：

```text
ingested
routed
context_built
task_compiled
permission_checked
executed
traced
evaluated
lesson_created
```

## 7.5 每阶段只允许一个主目标

建议：

```text
Phase 1 只稳定 KB MVP
Phase 2 只稳定 Cognitive-OS runtime
Phase 3 只打通 IR→KB
Phase 4 只做 A线学习闭环
Phase 5 只做 A→B
Phase 6 只做 MCP
Phase 7 才做智能增强
```

# 9. 最终判断

这三个项目可以合成一个很强的系统，但不能按“大而全 OS”直接开干。最优路线是：

```text
第一步：Knowledge-Base 收敛成能跑的本地知识库 MVP
第二步：Cognitive-OS 稳定成安全运行时
第三步：Inspiration-Research 变成 Intake / Contract 研究输入层
第四步：打通 KB → Cognitive-OS 的 ContextPack / TaskPack / Trace
第五步：再做 A线学习增强
第六步：再做 A→B 转译
第七步：再接 LangGraph / LiteLLM / Langfuse / sqlite-vec / Docling / Crawl4AI
```

一句话：

```text
IR 负责“发现什么值得做”
KB 负责“沉淀什么真正有用”
Cognitive-OS 负责“怎么安全运行并留下经验”
```

最终不是三个仓库简单堆叠，而是：

```text
研究系统 + 学习系统 + 机器知识系统 + 安全运行时 + 反馈闭环
```

这才是你这三个项目真正能长成的形态。

# 三、为什么 Obsidian 这一组非常关键

## 1. 它提供“前台工作台”

Obsidian 官网强调它是一个本地、灵活、私有的思考空间，笔记默认保存在本地设备，并且使用开放文件格式；官网还强调可以通过插件和主题按个人工作流定制。citeturn140514view0

这正好补齐前三个项目的一个缺口：

```text
IR / KB / Cognitive-OS 偏后端、数据、运行时
Obsidian 偏前台、人类操作、可视化、编辑体验
```

也就是说，你不一定要马上自己做一个完整前端。可以先让 Obsidian 做：

```text
知识首页
课程作战室
复习中心
项目总览
AI运行记录
Trace报告
Machine Lesson报告
Canvas知识地图
```

## 2. 它提供 Canvas 知识地图

Obsidian Canvas 是一个无限空间，用于研究、头脑风暴、图解和布局想法；它可以把笔记、图片、PDF、视频、音频、网页放到同一个画布里。citeturn756599view0

更关键的是，Canvas 文件本地保存，使用开放 JSON Canvas 格式，脚本和插件可以添加或修改卡片和连接。citeturn756599view0

这意味着你的系统可以自动生成：

```text
课程地图.canvas
项目路线图.canvas
A→B 转译图.canvas
知识图谱.canvas
任务执行链路.canvas
IR → KB → OS 研究转化图.canvas
```

Obsidian-Assistance 里已经有 Canvas 生成器方向，所以它应该成为 “Cognitive System → Obsidian Canvas” 的桥。

## 3. 它提供 CLI 自动化入口

Obsidian CLI 官方页面明确说：从命令行可以打开每日笔记、搜索 vault、追加任务；并且它适合 cron、shell scripts、自定义集成，还可以让 agentic tools 与 vault 交互。citeturn756599view2

CLI 示例还包括读取当前文件、创建模板笔记、标签统计、版本 diff、插件 reload、执行 JavaScript、检查 unresolved links、搜索并导出 JSON。citeturn756599view3

这对你的系统极其重要。因为 Cognitive-OS 可以通过 CLI 安全地做：

```text
搜索 vault
读取当前笔记
打开今日工作台
追加任务
生成日报
检查未解决链接
导出搜索结果 JSON
刷新插件
写入 AI 运行日志
```

但注意：**CLI 不能直接无脑交给 Agent 全权限使用**。它应该经过 Cognitive-OS 的 PermissionDecision 和 Obsidian-Assistance 的 safe writer。

## 4. 它提供插件生态

官方社区页现在显示有 5,275 个插件、602 个主题，并且插件类别包括 Integrations、Files、Editing、AI、Automation、Visualization、Links 等。citeturn140514view1

这说明你不用全部自己写。可以直接吸收：

```text
Dataview        动态查询
Tasks           任务聚合
Templater       模板自动化
QuickAdd        快速捕获
Excalidraw      图解/白板
Omnisearch      搜索增强
Spaced Repetition 复习
Text Extractor  文本提取
Minimal Theme / Style Settings 视觉基础
Advanced Canvas Canvas增强
```

但这些应该是 **Obsidian 层可选插件**，不能变成后端核心依赖。

## 5. 它提供官方版本 / 插件发布机制

`obsidianmd/obsidian-releases` 的 README 明确说：这个仓库用于托管 Obsidian 公共发布、社区插件和主题目录；同时也明确说明 Obsidian 不是开源软件，这个仓库不包含 Obsidian 源码。citeturn126531view0

所以你不能做：

```text
重新编译 Obsidian 内核
修改 Obsidian 底层源码
发布改版 Obsidian 客户端
```

但你可以做：

```text
插件
主题
CSS snippet
CLI 自动化
Canvas 生成
Markdown 模板
Vault 安全写入
社区插件组合
Obsidian-Assistance 安装器
```

官方插件目录的拉取机制也说明：Obsidian 会读取 `community-plugins.json`，插件安装时会从 GitHub releases 拉取 `manifest.json`、`main.js`、`styles.css` 等文件放进 vault。citeturn126531view0

这意味着后期如果你要发布自己的 Obsidian 插件，必须按官方插件生态规范来做。

# 十、最大风险

## 1. 误以为 Obsidian 是开源内核

不是。`obsidian-releases` 明确说 Obsidian 不是开源软件，仓库不包含源码。citeturn126531view0

所以路线必须是：

```text
不改内核
做插件 / CLI / Canvas / Markdown / CSS / 安全写入
```

## 2. 让 Agent 直接改 vault

这是危险路线。正确路线：

```text
Cognitive-OS 生成计划
Obsidian-Assistance dry-run
用户确认
safe writer apply
写入报告
```

## 3. 把 Obsidian 当数据库

Obsidian 是很好的本地 Markdown 前台，但不适合承载所有机器运行事实。Trace、Eval、ToolCall、PermissionDecision 应该留在 Cognitive-OS 数据库，再导出报告到 vault。

## 4. 社区插件过载

插件不是越多越好。插件越多，启动慢、样式冲突、API 兼容问题、安全风险都会上升。

建议：

```text
P0：Dataview / Tasks / Templater / QuickAdd / Minimal / Style Settings
P1：Excalidraw / Omnisearch / Spaced Repetition / Text Extractor
P2：Local REST API / Obsidian Git / Advanced Canvas
P3：AI 类插件后置
```

可以考虑，但我不建议现在换。

## 什么时候应该不用 Obsidian？

这几种情况才应该换：

```text
你必须修改客户端内核
你必须开源整个前台
你必须做商业分发的改版客户端
你必须深度控制编辑器和数据库
你必须做多人在线协作平台
你必须做 Web SaaS
你必须避免闭源客户端依赖
```

因为 Obsidian 本体不是开源软件，也不提供源码。citeturn548200view3

## 备选方向

### Logseq

适合块级大纲、双链、开源路线。公开资料显示 Logseq 是免费开源的个人知识库，支持本地存储、Markdown 和 Org-mode。citeturn509776search0

问题是：你的现有 `Obsidian-Assistance`、Canvas、Dashboard、插件策略已经围绕 Obsidian 展开，切 Logseq 会重写大量前台适配。

### Anytype

适合 local-first、对象数据库、关系型知识管理。公开资料显示 Anytype 是 local-first、隐私优先的 PKM 工具，但应用本身是 source-available license，不等同于完整开源。citeturn509776search1

问题是：它更像一个对象工作台，和你的 Markdown / CODEX / Git / 文件式知识库路线不完全一致。

### 自研 Web UI

适合最终商业化或完全控制体验。

但现在不建议优先，因为你要同时做：

```text
编辑器
文件管理
搜索
图谱
Canvas
Dashboard
插件系统
移动端
同步
主题
权限
发布
```

这会拖慢 Knowledge-Base 和 Cognitive-OS 的核心建设。
