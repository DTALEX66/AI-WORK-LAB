# 审计结论

截至 **2026 年 10 月 9 日**，三个项目都已经远远超过“概念阶段”，但**还没有形成统一意义上的产品闭环**。

最准确的判断是：

> **现在缺的不是更多功能、模型、插件、UI 页面或开源项目，而是把现有能力冻结成一条真实可重复的用户链路，并完成真人验收、安装发布和对外证明。**

你目前最大的问题是：**建设量很大，收口证据不足；架构、治理、界面跑得比实际产品交付更快。**

## 一、用同一套标准看三个项目

我把“闭环”统一定义成五道闸门：

1. **范围冻结**：M1 到底包含什么，不再继续横向扩能力。
2. **真实链路**：在正式安装态完成一条真实用户任务，不是 Fixture、Mock、浏览器桩或源码测试。
3. **失败恢复**：取消、重试、重启、冲突、回滚、备份恢复都可验证。
4. **真人验收**：Owner 或真实用户完成判断，不能由 Agent 自己签字。
5. **正式发布**：同一 SHA 的安装包、校验和、发布说明、限制说明和公开演示全部对应。

这不是代码完成率，而是闭环闸门成熟度：

| 项目 | 当前闭环成熟度 | 当前真实定位 |
|---|---:|---|
| **ArcheAxis** | **3.5 / 5** | 已接近可发布研究版，运行链最完整 |
| **WORK-LAB** | **2.5 / 5** | 治理内核成熟，但可操作产品面和真实跨 Agent 链仍没收口 |
| **DESIGN-LAB** | **2 / 5** | UI、协议、测试成熟，但真实设计宿主生产链尚未完成 |
| **三项目联动** | **1.5 / 5** | 边界和协议思想明确，但尚无一条真实跨项目闭环 |
| **作品集与广告片** | **2.5 / 5** | 展示素材较完整，但仍主要是视觉原型和概念方案 |

# 二、ArcheAxis：最接近闭环，但还差五个硬口

## 已经真正具备的部分

ArcheAxis 已经不是 PPT 项目：

- Tauri/React 正式桌面宿主；
- Rust Core 单写者；
- SQLite/CAS 原件保存；
- 多格式导入、阅读、编辑、版本、引用；
- 搜索、知识候选、学习与机器纠正合同；
- 导出、备份、恢复；
- 安装态真实旅程；
- 视频在默认 UI 中实际运行并完成重启读回；
- 当前开放 PR #183 已有格式读回、200+ 文件夹批处理、FSRS 写入隔离、ODF/RTF 等增量，两套 CI 均成功，但仍未合并。 fileciteturn32file0L3-L14 fileciteturn40file0L1-L2

所以它目前已经能称为：

> **可运行的本地知识平台候选版。**

但还不能称为：

> **经过 Owner 验收、可稳定升级和迁移真实旧数据的正式版本。**

## 还缺什么

### 1. 真人审核与学习闭环

工程已经证明“机器回答 → 纠正 → 审核 → 重测”可以形成数据链，但真人那一半没有完成：

- 真人接受或拒绝 KnowledgeCandidate；
- 真人实际回答一个学习任务；
- 真人纠正机器；
- 用纠正后的同一知识重新测试；
- 真人比较前后结果；
- 最后明确签署“有改善 / 无改善 / 无法判断”。

当前台账明确把 Q07 保持为 `AWAITING_OWNER`，Q08 也仍是 `PARTIAL`；设定一个 `human principal` 并不等于真人完成了认可。 fileciteturn23file0L1-L2

这是 ArcheAxis 最大的非代码缺口。

### 2. 长音频不能再以 300 秒超时失败

当前约 12 分钟音频在 301 秒触发固定上限，说明它不是偶发故障，而是产品边界不完整。

必须二选一并写进产品合同：

- **正式方案**：长音频自动切片、分段转写、合并时间轴、断点续跑；
- **M1 限制方案**：明确限制时长或计算预算，导入前预检并告诉用户，而不是运行五分钟后失败。

说话人分离可以延后，但**长音频静默撞超时不能进入正式版**。

### 3. 真实旧库迁移还没有 Owner 口径

迁移机制已有很多测试，但仍缺：

- 哪些表、附件、版本、引用和学习记录必须迁移；
- 哪些旧数据允许只归档、不迁移；
- 迁移完成的判定标准；
- 中断后如何继续；
- 失败后如何恢复旧入口；
- 正式用户旧库迁移后的逐项对账。

当前 Q11 的结论也是：机制存在，但“真实旧库何为迁移完成、失败如何回退”的验收合同仍缺。 fileciteturn23file0L1-L2

### 4. 物理 Windows 交互验收

还需要针对你的实际设备完成，而不是只依赖 CI 或 Chromium：

- Windows 11 正式安装包；
- 2560×1440；
- 100%、125%、150%、200% DPI；
- 中文物理输入法；
- 键盘焦点、快捷键、对话框；
- 减少动画；
- 窄窗与全屏；
- 强制终止后草稿和数据恢复；
- 安装、就地升级、卸载保留数据、重装读回。

### 5. 冻结 SHA、合并 PR、正式 Release

当前 #183 仍是开放 PR。即使 CI 通过，也还不是正式发布基线。 fileciteturn32file0L3-L14

ArcheAxis 的最终闭环必须落成：

```text
main clean
→ 固定 SHA
→ 全量 CI
→ 同 SHA Windows Installer
→ 本机安装态 Golden Journey
→ 真人 Owner 验收
→ tag
→ Release
→ checksum
→ 已知限制
→ 回滚包
```

## ArcheAxis 闭环判定标准

在一台干净 Windows 环境里：

```text
安装
→ 导入 PDF / Office / 音频或视频
→ 原件保全
→ 阅读与编辑
→ 版本恢复
→ 建立引用与核验
→ 生成知识候选
→ 真人接受或拒绝
→ 创建学习任务
→ 真人回答与纠正
→ AI 使用纠正后的知识重新回答
→ 导出 Obsidian / Markdown
→ 重启
→ 备份
→ 在独立副本恢复
→ 全部读回一致
```

完成这一条，ArcheAxis 才真正闭环。

# 四、DESIGN-LAB：目前离“生产闭环”最远

这是三个项目里最容易产生“看起来已经完成”的项目，因为：

- 设计系统完整；
- 页面质量高；
- 浏览器测试多；
- 合同、权利、证据体系丰富；
- 产品详情页和 VI 素材多。

但仓库自己的状态非常诚实：

> **DL-R5-001 至 DL-R5-028 全部仍为 PARTIAL，发布状态是 NOT_RELEASED。** fileciteturn15file0L1-L2

README 也明确区分：

- Workbench 主要是 E2；
- Photoshop / Illustrator Adapter 最高仍主要是 E1 结构证据；
- E3 真实宿主链没有读回；
- E4 人工 Jury 未执行；
- E5 正式发布未达成。 fileciteturn5file0L1-L2

## 真正缺口不是 UI，而是“可编辑生产物”

### 1. Photoshop 真实闭环

必须真实完成：

```text
参考图
→ 对象计划
→ 生成 PSD
→ 图层、文字、蒙版、图像对象可编辑
→ 局部修改两次
→ 不重建无关对象
→ 保存
→ 关闭
→ 重新打开
→ 读回图层、字体、链接素材、尺寸、色彩
```

不能用“整张图铺底”冒充分层设计。

### 2. Illustrator 真实闭环

必须完成：

```text
参考图
→ 矢量对象计划
→ 生成 AI
→ 文本、路径、蒙版、图形可编辑
→ 局部修改两次
→ 保存关闭
→ 重开读回
→ 导出预览和交付包
```

### 3. Human Jury E4

必须由你本人或另一名真实设计师完成：

- Brief 是否满足；
- 构图是否成立；
- 品牌一致性；
- 是否有明显 AI 痕迹；
- 字体、版权、链接素材；
- 是否适合商业生产；
- 是否需要继续修改；
- 最终接受或拒绝。

Agent 不能填写这些人工字段。

### 4. 商业交付 Preflight

至少要有：

- 画布与出血；
- 色彩空间；
- 分辨率；
- 字体；
- 链接素材；
- Alpha；
- 文件大小；
- Rights；
- BOM；
- Preview；
- 可编辑源文件；
- 回滚版本；
- Provenance。

### 5. 安装与发布

需要证明：

# 二、界面为什么总让你觉得“不对”：六个具体问题

## 1. 页面围绕技术模块展开，而不是围绕你做事的顺序展开

当前注册表中有 **22 个视图，再加独立总览**。侧栏虽然分成七组，但仍包含工作、执行、执行详情、任务包、交付、工作流、编辑器、观察者、监控、可信、审计、证据区间等大量入口。这里不是说它们都是一级菜单，而是说**同一件工作被拆散到了太多目的地**。fileciteturn44file0L1-L2 fileciteturn59file0L1-L2

这些概念在后端有区别，完全合理：

- 任务是目标；
- 执行是一次尝试；
- 任务包是输入和约束；
- 回执是结果证明；
- 审批是权限决定。

**但它们不必各自变成一个日常入口。**

用户真正的顺序通常是：

> 我选一个项目 → 提出任务 → 看计划 → 开始执行 → 处理问题 → 检查结果。

而不是：

> 我先决定该去工作、执行、任务包、工作流，还是交付页面。

**我的判断：当前信息架构把内部数据模型过多地暴露给了用户。**

微软的导航建议同样强调按典型用户路径组织页面、减少无关导航，以及避免查看相关内容时反复上下跳转。这里应借鉴的是组织原则，不是照搬某套软件的视觉外壳。citeturn462602search3

## 2. 首页最显眼的区域，恰好不能帮助你推进工作

当前 `OverviewView.tsx` 有几个非常典型的现象：

**“新建执行”被禁用，“导出状态”被禁用；“执行趋势”传入的是空数组；信号图里除 Agent 外，其余几个节点状态固定为 `idle`。** 代码有说明，并没有假装这些已经接通，但它们仍占据了产品首页的重要位置。fileciteturn45file0L1-L2

这形成了一个体验矛盾：

> 页面看起来像工作控制中心，却主要告诉你哪些能力目前不能用。

正确做法不是把按钮强行启用，更不是填假数据，而是：

**尚不能提供价值的模块，不应该继续占据首页的黄金位置。**

首页应该优先回答：

> 现在有哪些任务需要我处理？哪里受阻？我下一步能做什么？

趋势图没有数据，就先不要展示一个长期空着的大面板。信号图没有真实依赖关系，就移入诊断区或实验区，而不是作为主工作界面的视觉中心。

## 3. “只读”被局部解释成了“不能正常交互”

这是我认为最需要纠正的问题之一。

`WorkView.tsx` 的注释明确把只读解释为不渲染 `button/input/textarea`，甚至不提供复制地址按钮，只让用户选择文本或使用链接。可是，同仓库的边界验证器又明确承认：**修改本地界面状态、编辑本地草稿、维护派生缓存，并不天然违反只读边界。**fileciteturn46file0L1-L2 fileciteturn57file0L1-L2

这说明至少有一部分阻塞来自**规则解释过度，而不是真正的安全需求**。

应该重新定义：

> **Observer 不得修改任务、权限、配置等业务事实，但可以筛选、搜索、排序、展开、复制、切换视图和查看详情。**

进一步说，**一个产品窗口同时容纳观测和受控操作，也不等于观测服务获得了写权限。**

读写分离应该落实在命令处理、授权和数据访问边界，而不是通过“整个界面不能出现某种 HTML 标签”来实现。CQRS 的基本设计也允许读写模型共享底层数据存储、分别承担职责，并不要求用户使用两套割裂的软件。citeturn462602search1

**安全边界应该限制副作用，不应该限制基本可用性。**

## 4. 编辑器做出了“能编排”的视觉承诺，但没有对应的执行语义

当前工作流编辑器确实支持拖动、连线、选择和节点编辑。

但源码同时表明：它忽略传入的快照，以固定的 `localStorage` 键保存本地模型，发布和运行保持禁用。fileciteturn47file0L1-L2

作为一个流程草稿工具，这没有问题。

但放在正式产品主导航里，用户很容易理解为：

> 我已经在编辑一个可以运行的工作流。

实际却是：

> 我在编辑一张尚不能交给执行器的流程图。

**我的建议是暂时把它降为“流程草稿／实验功能”，不要继续把节点画布作为近期开发主线。**

先用简单任务表单和步骤列表接通一次真实执行，远比继续增加节点类型、画布手势和连线动画有价值。

这不是否定可视化编排，而是调整顺序：**先形成稳定的执行语义，再决定哪些语义值得用画布表达。**

## 5. 数据诚实做得很认真，但面向用户的解释还不成熟

当前页面大量出现 `UNKNOWN`、`source gap`、`revision`、`v3 snapshot`、`canonical`、`readback` 等工程术语。它们对审计有意义，但不应该要求你每次使用软件都先理解这套内部语言。fileciteturn43file0L1-L2 fileciteturn46file0L1-L2

更具体地说，总览的“最近执行”在没有行时显示“数据源未接入”，但这个条件也可能只是一个正常连接下的空执行列表。这是**空、未知、未连接之间的产品语义问题**，不是换个状态色就能解决。fileciteturn45file0L1-L2

我建议前台采用下面的表达：

| 实际状态 | 用户首先看到 | 展开诊断后看到 |
|---|---|---|
| 正常连接但没有任务 | 暂无任务 | 查询范围、时间、来源 |
| 该客户端没有提供数据 | 暂不支持读取这项信息 | 缺少的能力及契约 |
| 首次连接失败 | 尚未连接客户端 | 错误码、端点、诊断信息 |
| 有旧数据但更新失败 | 当前显示上次结果，更新失败 | 上次更新时间、连接状态 |
| 操作尚未接通 | 当前版本不支持此操作 | 原因、计划或手动接力方式 |

**保留真实状态，不等于把底层状态码直接铺满界面。**

## 6. 视觉规范正在变成“补丁规则”，而不是稳定的设计系统

当前设计合同同时涉及：

- 声称为权威的 `tokens.ts`；
- 不允许直接改动的 B10 皮肤；
- 只能叠加的覆盖样式；
- 另一份品牌 Token 文件。

合同自己也记录了来源不一致，以及部分圆角值冲突；当前尺度甚至有 `sm:12px`、`md:10px` 这种命名与大小顺序不一致的情况。fileciteturn58file0L1-L2

**问题不是“你还缺一套更高级的 UI 套件”，而是多个样式来源都在争夺最终解释权。**

我会保留你喜欢的深色、蓝青强调、紧凑专业感，但修改一个原则：

> **锁定品牌识别和组件行为，不再永久锁死一份原型 CSS 的每一行。**

否则每次优化都会变成：不能改原规则，只能加覆盖；覆盖产生新冲突，再加一层覆盖。

# 三、为什么一直推进不下去：产品决策和工程规则错位了

## 第一，用户操作被放在了过长的前置依赖链后面

当前控制面让使用者填写确定性任务 ID、授权来源、边界，甚至粘贴包含 40 位提交标识和上下文摘要的候选 JSON。fileciteturn56file0L1-L2

这些信息可以是系统必须管理的内容，但**不应该全部由用户在入口手工提供**。

我的理想入口是：

> 选择项目 → 输入目标 → 选择客户端 → 检查计划。

其余工作由软件完成：生成任务标识、读取基线、解析能力、汇总边界、标出风险，最后只把需要你决定的内容交给你。

现在更像是：

> 系统要求用户先完成一遍内部治理工作，才允许创建一条工作记录。

这不是自动化工具该有的负担分配。

## 第二，测试在证明边界，却还没有同等力度地证明用户能办成事

拒绝未授权操作、保留未知状态、禁止伪造成功，都应该保留。

但测试体系还必须同等关注另一半：

> **在合法、支持、已配置、已授权的情况下，操作必须真的成功。**

否则就会出现一种危险的局部最优：

**拒绝路径越来越可靠，成功路径一直没有产品化。**

当前控制服务已经把许多未实现操作诚实地拒绝，这比伪造完成好得多；但这些拒绝不能成为“本项目已经足够成熟”的证明。fileciteturn53file0L1-L2

## 第三，交付批次过大，界面改进无法单独完成验收

当前 PR #162 已累积 **453 个提交、1,081 个变更文件**。这不等于这些文件全是业务代码，但足以说明它已经不是一个容易独立审查和发布的小批次。fileciteturn41file0L28-L35

后续不应再把“界面收敛、证据归档、技能修复、模型治理、发布工具改进”无限堆入同一个交付单元。

**界面收敛应该有独立出口：几张页面、几条操作、哪些状态、哪些测试，通过就结束。**

同时，也不应反过来要求“所有未来任务、所有非阻塞 PR 全部关闭”，才能发布一个范围明确的版本。

# 四、我建议的产品方向：本地 AI 工作控制台，而不是通用平台

我会把 WORK-LAB 的用户定位收敛成：

> **一个本地优先的 AI 工作控制台，帮助个人开发者把项目、常用 AI 客户端、共享能力配置和执行结果管理在一起。**

这里的核心价值不是“我支持多少 Agent”，而是：

> **换客户端不丢规则，换会话不丢任务，执行完能确认结果，出了问题知道怎么处理。**

三个方向里，我会这样选择：

| 方向 | 判断 |
|---|---|
| 纯配置同步工具 | 范围清楚，可较快证明价值，但不足以承载你想要的工作界面 |
| 通用 Agent IDE／可视化编排平台 | 不建议作为当前目标，会不断扩大编辑器、运行时、会话、文件和终端负担 |
| **以配置治理为底座的本地工作控制台** | **最适合当前项目：既保留已有积累，又能形成日常使用价值** |

“客户端中立”也需要重新理解：

**它意味着客户端可以替换，不意味着首版必须让所有客户端拥有完全一样的能力。**

先把一个真实客户端做通，再用第二个验证抽象是否合理。不能为了兼容未来所有软件，长期停留在最小公分母或 `NOT_IMPLEMENTED` 上。

# 五、前端应该怎么收敛：不是删能力，而是减少日常决策

## 1. 主导航建议收敛成五个目的地，设置放底部

这是针对本项目的设计建议，不是“所有软件最多只能有五个导航”的定律。

| 新入口 | 用户来这里做什么 | 当前内容如何归入 |
|---|---|---|
| **工作** | 继续任务、处理待办、检查受阻项 | 总览、工作、待审批事项 |
| **项目** | 选择项目，查看该项目任务和环境 | 项目、项目上下文、关联执行 |
| **客户端** | 看连接状态、原生能力、启动入口 | 智能体、软件、客户端健康 |
| **能力与配置** | 管理规则、技能、模板和连接声明 | Rules、Skills、工具、MCP、相关模型连接配置 |
| **运行记录** | 找历史执行、产物、失败与证明 | 执行、交付、审计、可信、证据 |
| 底部设置 | 外观、快捷键、存储和诊断 | 设置、低频系统配置 |

**任务包、执行详情、证据区间不消失，但不再与“工作”竞争入口。**

它们应该从具体任务进入。旧链接保留兼容映射，已有数据与历史证据都保留。

VS Code 的视图设计建议也强调减少视图数量、避免重复功能，并让空状态引导用户开始，而不是不断增加新的容器。citeturn462602search2

## 2. 首页不再做“大而全仪表盘”，改为“我的工作”

首页主体建议只有三个区域：

**需要处理。** 等待你批准、补充信息、选择方案、确认结果的事项。

**正在进行。** 任务名称、项目、客户端、当前阶段、最近一次进展。

**最近结果。** 做完了什么、产物在哪里、验证到哪一步。

连接状态、成本观测、新鲜度仍然重要，但放在状态栏或辅助区域，不与任务争夺主视觉。

一个数据源离线，不应该让每个导航都像失效。已知的本地项目、历史结果、界面设置可以继续访问；确实依赖在线连接的操作再单独限制。

## 3. 把“任务详情”做成真正的核心页面

任务详情应该先展示：

> **目标是什么 → 现在到哪一步 → 有什么需要我处理 → 结果在哪里。**

然后再逐层展开：

- 计划与边界；
- 执行时间线；
- 变更与产物；
- 验证与证据。

现在 Inspector 把大量技术维度并排展开的方式，可以保留为高级诊断，但不应该成为用户理解一条任务的唯一方法。fileciteturn46file0L1-L2

还有一个需要补齐的数据设计：

当前任务投影主要提供 ID、状态、租约、检查点键名和摘要，刻意不带检查点正文。这个隐私取向有价值，但不能因此让日常界面只剩技术标识。建议单独定义**适合本地界面显示的任务标题、目标摘要和结果摘要**，与完整提示词、会话正文、遥测导出严格分开。fileciteturn49file0L1-L2

**禁止泄露私人正文，不等于用户不能在自己的软件里看懂自己正在做什么。**

## 4. 视觉上保留气质，但减少噪声

我不会建议你再换一套全新品牌。

建议保留深浅主题、蓝青强调、细边框和紧凑结构，但调整权重：

**任务名称和结果比系统指标更突出；正文比工程标签更易读；异常比装饰更显眼；常用操作比状态声明更容易找到。**

大面积发光、节点图、渐变卡片不是绝对不能用，而是必须服务于信息。一个无法解释真实关系的漂亮图，不如一条清楚的“任务失败原因与下一步”。

本轮没有实测你 Windows 安装包的像素和帧率，因此我不把上述判断包装成“已经测出最终视觉质量不合格”。

# 六、后端：保留技术栈，改变能力接线和边界表达

## 1. 不需要为了收敛而换语言、换框架

当前已有的快照投影、运行时端点描述、SSE、状态区分，以及控制服务复用权限门和原有账本的方向，都值得保留。fileciteturn48file0L1-L2 fileciteturn53file0L1-L2

我不建议现在发动全面 Rust 化、重写 Python，或另建一套前端。

更合理的结构是：

```text
一个 WORK-LAB 产品入口
    │
    ├─ 只读工作视图 → 查询与快照服务
    │
    └─ 受控操作组件 → 命令服务 → 权限校验 → 原生客户端适配
                              │
                              └─ 任务、回执、恢复记录
```

读取与命令可以继续由不同服务承担，**用户体验则应连续**。

具体迁移上，应复用现有 React 壳和组件，把 Observer 明确为只读功能模块，把受控操作放入有独立边界的模块；不再维持一套漂亮但不能操作的主界面，加一套需要手填 JSON 的工程控制台。

这需要同步调整目录约束和测试，不能只是往 Observer 里偷偷加写接口。

## 2. 区分“没有实现”和“没有授权”

当前控制操作表中，未实现、未接线、缺授权、缺恢复句柄等原因都可能体现为不可用。对用户而言，这些需要不同的解决方式。fileciteturn53file0L1-L2

建议能力描述至少区分：

| 维度 | 回答的问题 |
|---|---|
| 实现支持 | 程序有没有这项能力？ |
| 环境就绪 | 客户端、版本、路径是否可用？ |
| 当前授权 | 这次操作是否允许？ |
| 目标范围 | 允许操作哪些项目、路径、字段？ |
| 结果确认 | 能否拿到原生结果并读回？ |
| 恢复支持 | 失败后能否重试、回退或人工处理？ |

**“暂时没授权”不能被固化成“产品没有这个功能”；“代码有这个函数”也不能被显示为“现在就能用”。**

## 3. 先接一条真实操作，不要再横向增加十种契约

我建议后端按两条纵向链推进，而不是同时补齐所有能力：

**第一条：配置生效链。**

选择一个已使用客户端的一项非敏感受管配置，完成：

> 发现现状 → 显示差异 → 确认范围 → 应用 → 读回 → 必要时回滚。

这里还要区分“文件写好了”和“客户端已经加载生效”。需要重启或重新加载时，要如实显示。

**第二条：单客户端任务链。**

完成：

> 创建任务 → 提交给一个真实执行器 → 获得原生身份 → 观察进展 → 收到结果 → 验证产物。

暂不支持自动恢复、取消或原生会话续接的客户端，不能伪装支持；可以明确提供人工接力，但不能把人工接力统计为自动闭环。

**双执行器、并行调度、可视化编排，放在这两条链之后。**

## 4. 不要承诺所有外部动作都能“回滚”

受管配置、隔离的生成文件，可以设计可靠恢复。

但外部发布、上传、远端修改等动作，不一定存在完整撤销。应该分别表达为：

> 可回滚、可补偿、需人工处理、不可逆。

专业控制台的可信度，来自正确说明能力边界，而不是把所有操作统一贴上“可恢复”。

# 七、哪些规则保留，哪些修改，哪些暂缓

| 内容 | 我的建议 |
|---|---|
| 不伪造成功，不把未知当零 | **保留**，但重新设计用户可读状态 |
| 保护凭证、用户资料和外部路径 | **保留** |
| 高风险外部动作明确授权 | **保留** |
| Observer 不修改业务事实 | **保留**，但不禁止搜索、复制、筛选等界面操作 |
| 用标签、按钮文字、HTTP 动词扫描证明安全 | **降为辅助检查**，核心增加真实授权与副作用测试 |
| 每个后台实体都要有独立页面 | **取消这个倾向**，按用户任务组织 |
| 原型皮肤只能覆盖、不能调整 | **修改**，以设计 Token、行为和渲染回归为准 |
| 普通任务必须手工准备整套治理材料 | **修改**，由软件生成，用户只决定关键项 |
| 所有客户端同时达到同一支持等级 | **暂缓**，先一个，再两个 |
| 通用节点编辑器、重型并行工作台、插件市场 | **后移**，不做当前发布前置条件 |

其中，“没有账号系统”可以是合理的个人本地产品选择，但**不能扩展成“不需要验证本地命令来源和权限”**。不必引入企业登录平台，也仍需在命令服务中验证来源、范围、版本和操作授权。

同样，“一个事实来源”是合理的；但为界面提供列表摘要、详情视图和状态解释，并不等于制造第二份业务权威。

**很多现有规则需要的是缩小适用范围，而不是简单删除。**

# 八、未来怎么发展，才不会再次膨胀

我建议按能力被真实使用的程度推进，而不是按“还能收集多少开源项目”推进。

| 阶段 | 产品目标 | 进入下一阶段的依据 |
|---|---|---|
| **个人日用版** | 一个客户端、配置生效、任务执行、结果查看 | 你能在真实工作中连续使用，不靠反复手改内部文件 |
| **双客户端协作版** | 客户端切换、能力差异、任务交接 | 第二个客户端加入后，无需复制一套治理和界面 |
| **可复用能力版** | 规则包、技能包、任务模板、适配器 | 新能力能进入既有场景，不需要不断增加主导航 |
| **面向更多用户的版本** | 安装、升级、诊断、可理解的默认设置 | 别人在干净机器上能完成同样流程，不依赖你的历史对话 |

未来真正可能形成差异的，是三件事：

**配置可迁移、执行可确认、失败可恢复。**

相比之下，增加聊天窗口、模型列表、节点画布或宏大的“Agent OS”概念，不应成为 WORK-LAB 的主要竞争方式。这是我对产品定位的建议，不是已经验证过的市场结论。

衡量发展也不要再用页面数、测试数、适配器数作为主要指标。更有意义的是：

> 完成一项真实工作需要切换多少次软件？需要手改多少个文件？出现失败后，多久能知道原因？任务结果能否一次找到并确认？

这些指标先测自己的实际工作，再判断是否值得扩展。

# 九、现在应该怎样推进：一个明确顺序

**先完成产品裁决，再做界面收敛，再接真实操作，不再把全部工作绑成一次大收尾。**

| 顺序 | 做什么 | 什么情况下算结束 |
|---|---|---|
| **1. 修正边界** | 明确产品壳、只读模块、命令模块；解除无必要的交互限制 | 搜索、筛选、复制正常可用；业务写入仍经过授权服务 |
| **2. 收拢界面** | 调整导航、首页和任务详情；移走无数据图表和未接通的主操作 | 用户能清楚找到任务、当前状态、下一步和结果 |
| **3. 打通配置链** | 一个客户端、一项真实配置 | 差异、应用、加载状态、读回、恢复均有事实 |
| **4. 打通任务链** | 一个真实执行器，不扩多 Agent | 一条任务能从界面进入执行并回到可检查的结果 |
| **5. 验收安装版** | 固定候选版本，测试正常、失败、重启与恢复 | 同一版本在实际 Windows 环境完成上述两条链 |

这里有一个关键区别：

**界面验收不是“23 个页面都点过一遍”。**

应该是：

> 我不懂你的内部契约，也不用翻任务包，就能完成一次配置更新和一次真实任务；出了问题，界面能告诉我发生了什么、我能做什么。

---

## 最终判断

**WORK-LAB 合理的部分，是客户端中立、配置治理、真实状态、受控操作和结果证据。**

**不合理的部分，是把这些内部机制过多地搬到前台，把安全约束扩大成操作障碍，并在核心执行链尚未接通时铺开过多页面和平台能力。**

所以你现在真正需要收敛的不是“野心”，而是**当前版本对用户作出的承诺**：

> **一个入口、几类清楚的页面、两条真实可用的工作链。底层可以复杂，日常使用必须简单。**

**不再以“系统又增加了什么”为进展，而以“我今天终于能用它完成什么”为进展。**

# 二、最重要的架构问题：监测对象不是“软件”，而是“软件中的会话与执行”

这是决定后端是否需要不断返工的核心。

假设你同时打开：

- 两个 Codex 会话，分别处理两个项目；
- 一个 Hermes 主会话，带两个子 Agent；
- 另一个软件正在等待你批准操作。

如果系统只有：

```text
项目 → 软件 → RUNNING
```

它就无法准确回答：同一软件在做几个项目，同一项目被几个软件共同处理，以及哪个会话卡住了。

## 1. 应该建立关联关系，而不是简单绑定

我建议采用：

```text
设备
  → 软件安装实例／版本
      → 会话
          → 本轮执行／模型请求／工具调用
              → 关联项目、工作目录、技能和用量
```

其中，**项目与会话允许多对多关联**。通常可以有主要所属项目，但跨目录或跨项目操作应保留额外关联，不能强行归给一个项目。

项目识别优先采用客户端提供的工作目录、工作区、会话元数据，再结合已登记项目路径。无法确认时显示“待归属”，允许你纠正，不能仅凭窗口标题猜测。

这不是没有现实接口支持：例如 Claude Code 的 Hook 输入包含 `session_id`、`cwd` 等信息，而且官方专门区分了会话启动项目根与随工作目录变化的 `cwd`。这说明“会话在哪里启动”和“当前正在处理哪里”需要分别记录。citeturn493704view3

## 2. 当前代码已有一个明确的不匹配点

当前项目投影通过 `_live_agent_platform()`，从项目执行中选出**一个**活跃或最近使用的软件，再写入单个 `agentPlatform` 字段。底层仍保留执行列表，所以并非全部信息都丢了，但**项目摘要会把多软件并行压成一个软件**。fileciteturn63file0L1-L2

这对于简单卡片可以接受，**对于你现在的核心需求不够**。

应该显示：

> 此项目：2 个软件、3 个会话；1 个运行中、1 个等待批准、1 个已结束。

而不是：

> 此项目：Hermes · ACTIVE。

**这比再新增“智能体详情页”重要得多。**

# 三、“正在跑、卡住、停止、频繁报错”必须分别定义

你要看的其实不止一个状态，而是三个相互独立的维度。

| 维度 | 回答的问题 | 建议表达 |
|---|---|---|
| **工作状态** | 软件中的这一轮工作正在发生什么？ | 运行中、等待用户、空闲、本轮结束、已取消、执行失败 |
| **健康状态** | 工作过程是否异常？ | 正常、重试中、反复失败、疑似停滞 |
| **观测状态** | WORK-LAB 是否还能看到它？ | 已连接、数据延迟、连接中断、仅有限信息 |

这三个维度不能混成一个红黄绿灯。

### 例如：“没有事件”不能直接判成停止

它可能是正常的长时间模型请求、工具正在运行、等待审批，也可能只是监测连接断了。

因此，应当分别显示：

> **等待模型响应，持续时间较长。**

或：

> **观测连接已中断，最后一次确认状态为运行中。**

只有得到结束、取消、退出等可靠事件，才宣布对应执行已经停止。**本轮回答结束，也不等于整个项目完成。**

### “频繁报错”也不是简单数日志里的 Error

我的建议是按**同一会话、同一操作、同类错误、时间窗口、重试结果**进行归并。

例如：

> 某工具连续失败，重试后仍未恢复。

比：

> 今天出现 42 条错误。

更有用。

还应区分正常测试失败、权限拒绝、网络重试、程序异常。一次测试先失败后修复，是开发过程；不能自动把它算作“这个项目不健康”。

**首版用清楚的规则就够了，不必先引入 AI 异常判断模型。** AI 可以以后帮助解释异常，但不能成为“软件到底有没有停止”的事实来源。

# 四、个人插件与技能：值得重点做，但要把“资产”和“使用记录”分开

你特意强调个人插件技能，这很重要。它不仅是监控功能，也是你长期积累能否被复用的检验。

但我不会单独再做一套“个人技能平台”。建议只保留两层。

## 1. 资产层：这到底是什么、属于谁、部署到哪里

每项能力至少区分：

| 内容 | 为什么必要 |
|---|---|
| 稳定身份与版本 | 同名技能可能不是同一份内容 |
| 类型 | Skill、MCP 工具、插件包、脚本、规则并非同一种东西 |
| 来源 | 自己原创、自己修改、第三方引入、软件内置 |
| 管理关系 | 是否由 WORK-LAB 管理，不等于是否由你原创 |
| 部署情况 | 哪些软件、哪些项目装了哪个版本 |
| 原生映射 | 同一项能力在不同客户端叫什么、放在哪里 |

尤其要明确：

> **“我的能力库里有”不等于“我原创”；“由 WORK-LAB 管理”也不等于“本次真正调用了”。**

你的个人资产可以分为“原创”“定制修改”“收藏并受管”，这样既方便管理，也不会混淆来源。

## 2. 使用层：究竟发生了哪一级事件

| 事件 | 能证明什么 | 不能证明什么 |
|---|---|---|
| 已安装 | 文件或配置存在 | 软件已经加载 |
| 已发现／加载 | 客户端看到了能力 | 当前任务使用了它 |
| 已明确触发 | 用户或模型选择了该技能 | 技能步骤完整执行 |
| 已执行关联工具／脚本 | 出现可关联的实际操作 | 一定改善了任务结果 |
| 有结果及验收 | 某次工作产出了结果 | 结果完全由该技能带来 |

以 Codex 为例，官方说明技能采用渐进加载：先提供名称和描述，选用时再读取完整 `SKILL.md`。所以“出现在技能列表里”和“被选用”本来就是不同事件。citeturn337705view2

有些客户端已经能提供更明确的技能事件。例如当前 Claude Code 文档列出了 `skill_activated`，并能区分用户触发、主动触发、嵌套技能；但字段细节又受版本与隐私设置影响。这说明应该**按客户端逐项适配，不能用一个猜测算法覆盖所有软件**。citeturn493704view2

### 对个人技能，最有价值的界面不是排行榜

我建议优先回答：

> 哪些软件能看到它？哪些项目实际触发过？使用的是哪个版本？是否经常失败？是否存在部署漂移？

“技能帮我节省了多少 Token”“哪个技能最有效”可以作为后续分析，**但不应先给出看似精确的数字**。多个技能可能共同参与同一轮请求，不能把整轮 Token 完整归给每个技能后再相加。

同样，监测不到调用不能自动证明它没用，更不能因此自动删除。

# 五、Token 与缓存：应该成为核心页面，但首先要把账算对

这里最容易出现一种情况：图表很好看，数字其实不可信。

## 1. 用量记录必须从请求或明确的计量事件出发

建议用量的主要关联维度是：

```text
项目 × 软件实例 × 会话 × 模型／提供方 × 请求
```

插件、技能作为可选关联信息。

如果项目归属暂时不明确，放入“未归属”，不要平均摊分；如果同时从客户端日志和模型服务读到同一请求，必须去重；如果来源提供的是会话累计值，不能把每次刷新读到的累计值反复相加。

**项目页和软件页是同一批用量的不同视角，不是两份可以再次相加的消费。**

## 2. 缓存命中率不能直接套一个字段名

不同接口的输入 Token 口径并不相同。

当前 OpenAI 文档的计算示例把缓存读取、缓存写入作为总输入中的组成部分；Anthropic 的文档则明确要求将普通输入、缓存读取、缓存创建相加，才能得到总输入。citeturn493704view0turn308813search8

因此，我建议前台明确区分两个指标：

**输入 Token 缓存读取占比：**

```text
同一统计范围内的缓存读取 Token 总数
÷
该范围内具有完整计量字段的总输入 Token
```

**请求缓存命中率：**

```text
出现缓存读取的请求数
÷
能够判断缓存情况的请求数
```

两者都合理，但不是同一个意思。缓存写入也不能算作缓存命中。

需要同时显示计量覆盖范围。缺字段就是“未知”，分母为零就是“不适用”，而不是统一显示 `0%`。汇总时应先求和再求比例，不能直接平均各会话百分比。

## 3. Token、费用、订阅额度必须分开

我建议保留三栏：

> **实际报告的用量｜按价格估算的费用｜厂商提供的额度信息。**

不能拿 API 标价直接推导订阅软件扣了多少额度，也不能把本地模型没有 API 账单理解为完全没有资源成本。

模型的 reasoning、cached 等明细还可能是输入或输出总数的子集，适配器应保留其原始语义，避免重复累计。

## 4. 当前代码中，已经看到两个应优先修复的地方

当前 `_token_summary()` 和项目用量汇总出口只提供输入、输出、总量与 `costQuality`，**没有表达缓存读取和写入字段**。这不能证明其他采集路径完全没有缓存数据，但能确定这个主要快照出口尚不足以支撑你要的缓存面板。fileciteturn62file0L1-L2

另一个更具体的问题是：项目级 `_rollup_usage()` 遇到一条 `EXACT` 就把汇总标为 `EXACT`，之后的估算记录不会把它降下来；总体汇总却使用另一套判断方式。**这会产生项目统计与总体统计质量口径不一致的风险。**fileciteturn62file0L1-L2

应当统一成：**哪些数字精确、哪些估算、哪些缺失、覆盖了哪些来源**，而不是用一个乐观标签概括全部数据。

# 六、全局中立适配：统一的是意图，不是所有软件的配置字节

这部分是你的设想中最值得长期保留的底座，但也最容易做得过重。

## 1. 我支持“一份规范源，多种原生投影”

合理形式是：

```text
你的通用规则与能力声明
    ↓
客户端适配器
    ↓
各软件原生支持的规则／技能／配置
    ↓
读取验证、加载验证、漂移检查
```

不合理形式是：

```text
一份超长提示词
    ↓
复制到所有软件
    ↓
宣称全部软件已经受到统一治理
```

规则需要按作用分类：

| 类型 | 正确处理方式 |
|---|---|
| 沟通与工作习惯 | 投影为原生指令，承认它主要是行为引导 |
| 文件、网络、执行权限 | 优先映射到客户端真正支持的权限机制 |
| 测试、交付、证据要求 | 映射到可运行检查或明确的工作流程 |
| 模型参数与能力 | 按软件和模型支持范围映射，不强行统一 |
| 项目特殊规范 | 保留项目自身的范围和优先级，不被全局配置盲目覆盖 |

**文件里写了“不许做”，不等于运行时一定阻止得了。**  
也不能把“部署了规则”直接等同于“模型每次都遵守了规则”。

## 2. 这一点现有项目其实已经有不错的基础

当前适配器登记已经区分了 `NATIVE_GUIDANCE`、`NATIVE_ENFORCED`、`WORKFLOW_GUARD`、`OBSERVE_ONLY` 等能力状态，也记录不同软件的投影、读回和漂移能力。**这部分值得保留，不需要另造新的治理体系。**fileciteturn61file0L1-L2

但同一份登记中，Codex 的投影成熟度已经从 `READBACK_VERIFIED` 下调到 `APPLY_SUPPORTED`，原因是此前实际文件缺少受管标记。这里体现的是登记中的历史观测，不是我刚刚重查了你本机。fileciteturn61file0L1-L2

这恰好说明你真正需要的界面是：

> 哪些规则已生成？哪些已经部署？哪些客户端确认加载？哪些发生了漂移？

而不只是：

> 我们支持 Codex、Hermes、DSH。

## 3. 规则越多，不一定越好

我建议保留一个短而稳定的全局基础层，再按项目与任务加载专项技能。不要把整个能力库、历史审计和所有未来规范都塞进每轮上下文。

这还和缓存目标直接相关：官方缓存诊断资料指出，提示前缀中的时间戳、工具顺序变化或早期内容修改，都可能影响缓存复用。**频繁自动改写全局规则，可能与降低消耗的目标相互抵消。**citeturn308813search10

所以规则治理应该追求：

> **稳定、可解释、按需加载、变更可对比。**

不是单纯追求规则数量。

# 七、能不能实现：关键是采用分级接入，而不是承诺“全软件透明”

你这套方案有现实基础，但必须按数据来源分层。

| 接入方式 | 适合观察什么 | 限制 |
|---|---|---|
| **原生事件、Hooks、OpenTelemetry** | 会话、请求、工具、错误、部分用量 | 依赖具体客户端、版本和已启用的字段 |
| **结构化日志／受支持的本地记录** | 历史事件、会话、部分消耗 | 可能延迟，格式变化需要兼容 |
| **进程、窗口、工作目录等系统信息** | 软件是否存在、部分活动线索 | 不能据此断言技能调用、Token 或真实工作进度 |
| **用户显式关联** | 修正项目归属、补充业务含义 | 是用户确认的信息，不冒充自动检测 |

当前官方资料可以确认：

**Codex 提供 OpenTelemetry 导出，包含会话、请求、工具审批与结果等事件。**  
**Hermes 提供 Observer Hooks，带会话、轮次、请求、工具及子 Agent 关联身份。**citeturn337705view0turn337705view4

但是，上游今天有接口，**不等于你安装的版本已经提供全部字段，也不等于 WORK-LAB 已经接通**。需要实际采样验证。

我的建议是：

**先把你确实使用的两个客户端做深，再让其他客户端以有限观测方式接入。** 不要求所有客户端同时具备同等精度，也不要求你必须改用某个软件来迁就监控。

另外，默认关闭提示词记录并不代表所有遥测都没有敏感内容；工具结果、参数、路径仍需单独处理。应在本地采集入口使用字段白名单，尽量只保留身份、状态、时间、计量和经过脱敏的原因。

**不建议为了获取完整数据，强制所有流量经过新的模型代理，或长期依赖抓屏、读取浏览器私密状态、劫持通信。** 这些会扩大维护成本，并改变你原有软件的行为。

# 八、前后端应该重新围绕“观测闭环”组织

## 后端：需要的是观测链，不是新增任务运行时

建议结构如下：

```text
外部 AI 软件正常执行
    │
    ├─ 原生事件／日志 → 轻量采集适配
    │                       ↓
    │                身份关联、去重、口径标准化
    │                       ↓
    │                观测历史、用量、异常状态
    │                       ↓
    │                    WORK-LAB UI
    │
    └─ 原生配置 ← 经授权的规则／技能投影
                          ↑
                    WORK-LAB 配置治理
```

这里可以保存自己的**观测历史**，不等于复制外部软件的完整业务数据库，更不等于接管它们的会话。

有几条必须落实的工程原则：

**监测故障不应阻断正常工作。** 采集器异常、UI 关闭、网络不可达，应表现为数据延迟或缺失，而不是让外部 Agent 停止。Hermes 的 Observer Hook 文档也明确要求回调快速、异常不中断 Agent，并将耗时导出移出关键路径。citeturn493704view4

**安全执行门与遥测采集分开。** 采集失败可以不阻断工作；明确承担安全约束的授权检查则是另一条链，不能混用失效策略。

**重启不能重复计数。** 保留事件身份、读取进度、来源版本和计量语义；重放同一事件不应让消耗翻倍。

**观测也要监测自己。** 界面应告诉你采集器是否正常、哪个客户端数据缺失、最近更新时间和可见范围。

基础监测不应持续调用大模型。状态归并、计量、告警和配置对账都可以先用确定性逻辑实现；AI 分析作为手动触发的附加能力。

# 九、界面怎么改：你的首页确实应该是监控台，而不是任务创建页

这里我调整上一轮的建议：**对你明确的使用方式，“监控台”不是退而求其次，而是正确主界面。**

问题不是仪表盘这个形态，而是仪表盘展示什么。

## 1. 建议保留五个主要入口

| 入口 | 主要用途 |
|---|---|
| **实时总览** | 谁在工作、谁在等待、哪里异常、哪里失去观测 |
| **项目与软件** | 项目视角和软件视角切换，查看关联会话 |
| **插件与技能** | 全部能力与“我的能力”筛选，部署、加载、触发及失败 |
| **用量与缓存** | 项目、软件、模型、会话维度的统一计量 |
| **规则与适配** | 通用规则、原生映射、支持程度、漂移、应用与恢复 |

历史、诊断、证据、设置作为二级页面或详情，不再与五条主线竞争。

**“个人技能”是能力中心里的重要筛选和视角，不需要再开一个平行系统。**

## 2. 实时总览的主体应该是关系表或分组列表

建议主要列为：

```text
项目｜软件／会话｜当前活动｜等待或异常原因
最近进展｜正在使用的能力｜本次已报告用量｜观测新鲜度
```

支持按“项目”或“软件”分组，并把“需要关注”的会话置顶。

点开一行，右侧展示该会话的事件时间线、能力调用、计量和原因，而不是再跳到多个技术页面。

对于同一项目同时运行与阻塞的情况，显示数量与子项；不要用单个状态覆盖全部工作。

## 3. 首页按钮应该服务于观测和定位

优先操作应是：

> 打开原软件、定位项目、查看事件、查看原因、调整筛选、处理配置漂移。

未来客户端具备可靠原生接口时，可以加“在原软件继续”或受控操作。**但“新建执行”“运行流程”不再是首页必须有的按钮。**

观测类页面保持业务只读，配置治理页面保留必要的授权写入。这样既不需要把 WORK-LAB 变成任务执行平台，也不必把整个产品限制为只能看不能管。

## 4. 视觉上不必再换风格，应该换信息权重

保留你想要的深浅主题、蓝青色、紧凑专业风格即可。

需要减少的是：长期无数据的趋势图、没有真实关系的节点图、重复的系统状态卡，以及成片的 `UNKNOWN`。

“观测不到”的事实要保留，但应该表达为：

> 此客户端尚未提供缓存数据。

而不是让整张卡片只剩一个不解释原因的英文单词。

# 十、哪些能力保留，哪些退出当前主线

| 处理 | 能力 |
|---|---|
| **当前核心** | 会话与项目关联、运行状态、异常聚合、技能调用、个人资产映射、Token／缓存、规则投影与漂移 |
| **继续复用** | 现有 Observer、快照／SSE、适配器登记、规则生成器、只读诊断、必要审计与恢复机制 |
| **降为辅助** | CI、Git 状态、交付回执——帮助解释项目情况，但不成为所有监测的前置条件 |
| **保留为未来能力** | 跨软件任务交接、受控操作、跨设备治理、记忆共享 |
| **退出首版验收** | 通用派发、完整审批引擎、节点工作流执行、多 Agent 调度、重型 Workspace 集成 |
| **不建议发展** | 第二套通用 Agent Runtime、第二个完整 IDE、要求所有模型经过的强制网关 |

**保留参考资料，不意味着保留所有功能在主导航中，更不意味着每个旧任务都必须完成后才能发布。**

这一点需要正式反映到当前任务范围中，否则 Agent 仍会沿旧清单不断补“派发、审批、编辑器、运行时”，你却还看不到真正想看的实时状态。

---

# 十一、未来治理与记忆共享，怎么发展才不失控

我支持这个方向，但优先级应该是：

> **先共享规则和能力，再共享经确认的工作上下文，最后才考虑更自动化的长期记忆。**

建议分开管理：

| 类型 | 共享建议 |
|---|---|
| 个人稳定偏好、工作规范 | 可以全局投影 |
| 已确认的环境经验、工具使用方法 | 版本化后按需共享 |
| 项目事实、决策、未完成事项 | 默认限定项目，跨项目需明确范围 |
| 临时会话、未验证结论、敏感内容 | 不自动全局共享 |

每条共享内容应有来源、适用范围、版本、确认状态和失效条件。软件 A 中的推测，不能自动变成软件 B 必须遵守的事实。

**WORK-LAB 更适合治理“哪些内容可以被哪个软件读取、投影、更新”，不必亲自发展成一个庞大的通用知识系统。**

跨平台也应先统一事件和身份，再扩展采集器。Windows 原生先跑稳；以后加入 WSL、另一台设备或云端环境，都沿同一套关联与权限原则，不需要现在就部署一整套分布式平台。

---

# 十二、重新定义 WORK-LAB 的首版闭环

首版验收不再要求“由 WORK-LAB 派发一项任务”，而应这样测试：

| 验收场景 | 必须看到的结果 |
|---|---|
| 你直接从原软件启动项目工作 | WORK-LAB 能观察到，不要求从它的启动器进入 |
| 同一软件处理两个项目 | 会话和项目不串 |
| 两款软件处理同一项目 | 同时显示，不压成单一软件 |
| 一轮工作等待、失败、重试、结束 | 状态与原软件对应，观测中断不误报停止 |
| 使用一项个人技能 | 能对应到受管身份、版本、客户端和项目；证明不了的环节明确说明 |
| 产生模型用量 | 与来源记录对账，重复采集和重启不重复累计 |
| 请求存在缓存读取 | 按正确口径显示，缺失字段不伪装为零 |
| 修改一项受管通用规则 | 能展示差异、应用范围、加载状态、漂移及恢复路径 |
| 关闭 WORK-LAB | 外部软件继续正常工作；重新打开后明确显示可恢复的历史与观测缺口 |

实际推进顺序，我建议是：

**先做两个客户端的“会话—项目—状态”关联；随后接入同一批会话的用量与技能事件；再把现有规则投影做成可理解、可对账的界面。** 不要并行铺开所有软件。

---

## 最终判断

**这四类需求不是过于保守，反而能构成一个边界清楚、对你有长期价值的产品。**

真正需要警惕的，不是“它只是一个监控台”，而是下面两种偏离：

**一种是只做漂亮看板，却没有可靠采集、归属和计量。**

**另一种是为了实现监控，逐步把自己变成新的任务运行时、模型网关和通用平台。**

WORK-LAB 最值得走的是中间那条路：

> **不接管其他 AI 软件怎么工作，但能看清它们在为哪个项目工作、用了你的哪些能力、花了多少资源，并把你的规则与配置可靠地带过去。**

**现在最缺的不是更多页面，也不是更多 Agent 能力，而是“身份关联准确、事件语义准确、计量准确、规则生效可证”这四件事。它们做实了，界面和未来发展方向才会一起稳定下来。**

# 一、先把资产归属划准确，否则后面一定再次重叠

**不能按文件扩展名划分，而要按“它负责表达什么、由谁修改和确认”划分。**

例如，同一个 `SKILL.md` 可能同时包含执行步骤、工具调用、专业知识和案例。不能因为它是 Markdown 就全部交给 AAOS，也不能因为它叫 Skill 就全部留在 WORK-LAB。

## 建议采用下面的边界

| 资产 | 长期归属 | WORK-LAB 应承担什么 |
|---|---|---|
| 专业知识、方法解释、研究结论、案例经验 | **AAOS** | 提交候选、引用已发布版本、记录使用关系 |
| 长期项目事实、经过确认的经验性记忆 | **AAOS** | 按项目与权限获取，不建立平行知识权威 |
| 运行日志、会话身份、调用事件、Token、异常记录 | **WORK-LAB 的观测层** | 采集、关联、统计、诊断、按策略保留 |
| 全局规则的执行配置、客户端映射、授权范围 | **WORK-LAB** | 版本管理、差异、部署、生效检查、恢复 |
| 技能脚本、适配器、工作流模板、可执行规则包 | **原有源码归属方；WORK-LAB 管理其运行与部署关系** | 登记、适配、测试、分发、监测和回滚 |
| 技能依赖的知识说明与案例材料 | **AAOS 为内容权威** | 使用带来源和版本的引用或发布快照 |
| 当前会话游标、临时检查点、交接标识 | **外部软件或 WORK-LAB 的运行状态** | 支持定位和接续，不自动提升为长期记忆 |
| 密钥、账号凭证、浏览器私密状态 | **原软件或既有凭据设施** | 不纳入知识交换，也不复制进观测库 |

这里需要同时避免两种错误。

**第一，不把所有运行数据都倒进 AAOS。**  
一次报错、一条工具事件、每分钟的 Token 数，首先是运行事实。只有从中整理出的、带适用条件的可复用经验，才适合成为知识候选。

**第二，不把知识迁移理解为运行时必须在线查询 AAOS。**  
已经发布的技能可以带经过许可的知识快照，记录来源 ID、版本与摘要。AAOS 暂时不可用时，WORK-LAB 的监测和已有配置不应停止；但过期或撤回内容必须有明确处理策略。

**一个内容权威，不等于只能存在一份物理副本；关键是不允许多个地方各自编辑，并同时宣称自己是最终版本。**

# 二、有一处现有机制，需要随着这个边界调整

当前 `config/config-ownership.json` 中，仍写有将客户端原生生成的技能新增内容折回仓库的机制，并允许部分“新增文件、追加内容”自动接纳。fileciteturn65file0L1-L2

这个机制原本是为了避免覆盖用户和客户端积累，有合理目的；但按照你现在明确的方向，应该进一步拆开：

```text
客户端产生新内容
    │
    ├─ 脚本／配置／执行规则变更
    │      → 运行资产评审、测试、版本发布
    │
    ├─ 经验／方法／事实／专业知识
    │      → AAOS 知识候选，等待核验与确认
    │
    └─ 临时会话内容
           → 留在运行边界，不自动全局化
```

**“只是追加”不等于“内容正确、安全、适合全局生效”。**

因此，我建议保留“发现变化、保护现场、生成差异”的能力，重新审查“自动成为全局权威”的条件。对于混合型技能包，先识别内容角色；不要为实现分工，粗暴拆坏现有包的相对引用和运行结构。

# 三、WORK-LAB 值得重点深化的，是八个能力面

以下八项是**能力分工，不是要求新增八个一级菜单**。它们应该融入上一轮确定的五个主要入口。

## 1. 观测可信度：不仅监控软件，还要说明自己看到了多少

上一轮已经明确了项目、软件、会话、执行的关联。现在应再加强一层：

> **每个状态旁边，都能解释“凭什么判断、什么时候确认、还有什么看不到”。**

例如，同样显示“运行中”，可能来自：

- 客户端明确发送的执行事件；
- 正在进行的工具调用；
- 最近的结构化日志；
- 只有进程存在这一条弱线索。

这四种证据不能显示为同等可信。

我建议每个客户端都有一张**观测能力卡**，按项目识别、会话状态、工具调用、技能触发、Token、缓存等维度分别显示支持情况，而不是只给一个“已接入”。

同时，要支持关联纠正：你把一条会话重新归到正确项目后，后续统计应能重算，并保留纠正记录，不能留下两份消费。

在实现上，可以借鉴 OpenTelemetry 的事件与调用关联方式；其 Span Links 能关联异步发生的工作。不过，WORK-LAB 不应因为两个事件时间接近，就擅自建立因果关系。citeturn202838view1

**深化后的价值：你不仅看到一个状态，还知道是否值得相信它。**

---

## 2. 故障诊断：从“红灯很多”升级为“知道先处理哪里”

这是最值得增加的能力之一。

我建议将异常组织为**事件 → 问题 → 影响范围**，而不是把所有错误平铺成日志。

一个问题详情应该回答：

| 内容 | 应当展示什么 |
|---|---|
| 发生了什么 | 哪个软件、会话、操作出现异常 |
| 影响了什么 | 涉及哪些项目、多少条执行 |
| 当前是否恢复 | 已恢复、仍在失败、观测不足 |
| 已确认事实 | 原生错误、时间、重试、版本变化 |
| 可能原因 | 明确标记为推测，不冒充结论 |
| 下一步 | 查看原软件、检查连接、检查配置、等待用户等 |

特别需要加强**重复错误归并与关联告警抑制**。

例如，同一个模型端点不可用，导致三个项目的会话都失败，应优先显示“一项共享服务异常，影响三个项目”，而不是连续弹出几十个独立错误。

告警去重、分组、静默和抑制是成熟观测系统已有的机制；Prometheus Alertmanager 的官方设计明确区分了这些职责。可以借鉴机制，不必因此把整套基础设施都装进本项目。citeturn202838search1

**诊断能力增强，不等于默认自动修复。**  
先可靠地解释和定位；重启软件、切换模型、修改配置等动作仍需明确权限，不能为了让看板变绿而打断你的工作。

## 3. 个人插件与技能：从清单升级为生命周期管理

你最有个人价值的积累，不只是“有哪些技能”，而是：

> **哪一版技能部署到了哪些软件，在什么场景被使用，出了什么问题，是否值得继续维护。**

建议沿着一条生命周期管理：

```text
登记来源
→ 检查结构与依赖
→ 核对客户端支持
→ 部署指定版本
→ 确认发现／加载
→ 观察真实触发
→ 汇总成功与失败
→ 更新、停用或回退
```

需要深化的重点有三项。

**版本与来源。** 同名不等于同一技能；原创、修改版、第三方受管资产应有清楚标记。专业源码仍留在其归属仓库，WORK-LAB 不必把所有仓库吞进来。

**兼容性。** 一个技能包能被某软件发现，不代表它声明的权限、依赖和执行方式都被支持。Agent Skills 官方规范中的 `allowed-tools` 仍是实验性字段，并明确说明不同实现可能存在差异，不能把它直接当成跨客户端一致的安全边界。citeturn943511view1

**使用质量。** 可以比较同一技能不同版本的触发情况、失败类型、耗时和覆盖范围，但不要用调用次数制造“最强技能榜”。没有观测到触发，也不能自动判断它无用。

对于技能带来的方法改进和经验总结，输出到 AAOS；对于技能是否部署、生效、兼容和稳定，由 WORK-LAB 负责。

## 4. 用量与效率：从消费统计升级为浪费定位

Token 和缓存仍然是核心，但可以再深化为四种视角：

| 视角 | 你要解决的问题 |
|---|---|
| 消耗 | 哪个项目、软件、模型、会话用了多少 |
| 缓存 | 哪些请求具有可比较的缓存数据，是否发生变化 |
| 延迟 | 时间花在模型响应、工具执行，还是等待用户 |
| 重复工作 | 是否存在连续重试、相同失败或可疑重复调用 |

这里最有价值的是**异常变化说明**，而不只是画曲线。

例如：

> 更新规则包后，相关会话的输入量明显增加；样本范围和规则版本可查看。

这可以作为排查线索，但不能直接宣布“规则更新导致浪费”。任务长度、模型变化和新会话冷启动都可能影响比较。

我建议保留“预算提醒”和“异常消耗提醒”，但不默认自动限流、杀进程或切模型。当前顶层规范也明确保留用户原生模型选择，并不默认实施全局成本或速率限制。fileciteturn63file0L1-L2

还要避免一个指标陷阱：

**低 Token 不一定意味着更有效，高缓存也不一定意味着任务更快完成。**

效率页面应同时保留结果状态、失败重试和计量覆盖范围，而不是用一个综合分数把这些差异抹平。

## 5. 规则与适配：从“配置已写入”升级为“生效可验证”

这是 WORK-LAB 应当拥有的治理能力，不应该退化为只读清单。

建议把规则发布状态分开：

```text
规范已定义
→ 已生成原生配置
→ 已写入目标
→ 客户端已发现／加载
→ 可验证行为通过
```

不能用前一步抵扣后一步。

同时建立一张**实际生效关系图或列表**：

> 这条全局规则适用于哪些软件？哪些项目有差异？哪个原生字段承载它？是否发生覆盖或不支持？

这里不必做复杂的可视化图谱，先把列表与解释做清楚。

配置变化建议采用三方对比：

**上次发布版本 × 当前客户端状态 × 本次目标版本。**

发现客户端自行修改，不应一律覆盖，也不应一律自动接纳。要区分受管字段、用户字段、未知字段，以及需要重新确认的内容。现有配置所有权文件已经有分层、保留未知字段和冲突处理基础，值得继续完善，而不是重建另一套同步引擎。fileciteturn65file0L1-L2

**中立适配的深化，应是“差异可解释”，不是“把差异全部隐藏”。**

---

## 6. 软件更新与环境健康：从版本列表升级为更新影响管理

这是前面几轮讨论中不够突出的能力，但对你的使用方式很重要。

建议每次检测到客户端、插件、模型服务或工具链版本变化时，检查其影响，而不是只显示“有新版本”。

重点检查：

> 原生入口是否改变、规则是否仍被发现、技能是否仍可加载、事件格式是否兼容、计量字段是否消失、受管配置是否漂移。

一次更新之后，WORK-LAB 应能回答：

> 软件确实更新了；基础运行正常；技能发现正常；但缓存字段当前无法解析，所以这一维度降为“未验证”。

而不是因为进程能启动，就把全部能力标为健康。

环境健康还应包括共享服务、磁盘空间、模型端点和资源占用，但保持权限边界：**发现问题与采取动作分离，不能默认移动数据根、清理模型、修改系统环境或终止其他软件。**

Windows 原生部署应继续作为你的主要落地点；WSL 和其他平台是后续适配对象，不成为这套能力的强制前置。

## 7. 跨软件、跨项目协作风险：先预警冲突，不急着接管调度

你让多个 AI 软件各自执行，最大的潜在价值之一，是 WORK-LAB 能发现它们正在相互影响。

值得逐步增加的观察项包括：

| 风险 | 建议行为 |
|---|---|
| 两个软件可能修改同一工作目录 | 显示相关会话和范围，提示检查冲突 |
| 受管配置即将变更，但相关会话仍活跃 | 提示影响，允许延后应用 |
| 多个项目依赖同一个失效服务 | 合并影响范围 |
| 多个任务争用本地资源 | 显示资源压力与关联时间，不武断认定根因 |
| 软件已结束，但项目仍有未确认结果 | 标为待确认，不宣告项目完成 |

但要强调：

**文件同时变化、进程同时活跃，都不自动证明存在写冲突。** 数据不足时只能提示风险。

未来可以支持合作式租约、受控交接或原生取消接口，但这些都是增量能力。没有接管全部任务，也可以实现有价值的跨软件治理。

**“我知道你们可能撞车了”可以先做；“所有车必须由我驾驶”没有必要。**

## 8. WORK-LAB 自身可靠性与隐私：让监测系统不成为新的负担

这个能力面应该从第一版就有，而不是最后补。

### 可靠性

需要能观察采集延迟、积压、解析失败、重复事件、丢失区间和磁盘占用。OpenTelemetry Collector 自身就暴露接收、拒绝、发送失败和队列容量等内部指标，这类自监测机制值得参考。citeturn202838search0

对数据接收与恢复，我建议采用：

> 有界缓冲、可恢复读取进度、幂等处理、明确的保留策略。

但不能承诺“绝不丢失”。官方 Collector 文档也说明，即使启用持久化队列，磁盘故障、容量耗尽和重试上限仍可能造成损失。产品应该如实显示缺口，而不是补造连续曲线。citeturn943511view0

**关闭工作台或采集器异常，不应该阻断其他 AI 软件正常执行。** 独立的安全控制如果需要拒绝操作，应走另一条明确链路，不能把遥测失败与授权失败混为一谈。

### 隐私

默认采集用于观测的最小字段，不把完整提示词、工具参数、返回正文和私人路径无差别落库。OpenTelemetry 官方同样建议只采集服务于观测目的的数据，并持续检查字段是否仍然必要。citeturn202838view0

需要向你清楚展示：

> 正在读取哪些来源、保留哪些字段、哪些内容会提交 AAOS、哪些只留在本地运行记录。

**“本地软件”并不自动等于“数据边界已经合理”。**

# 四、这些能力应该怎么落到界面，而不是再制造新菜单

我建议继续维持五个主要入口，只深化里面的工作场景。

| 入口 | 深化后的内容 |
|---|---|
| **实时总览** | 项目／软件分组、活跃会话、需要关注的问题、共享故障影响 |
| **项目与软件** | 会话关联、环境健康、版本变化、原生入口、观测覆盖 |
| **插件与技能** | 我的能力、来源与版本、部署与加载、触发记录、兼容和失败 |
| **用量与缓存** | 消耗、缓存、延迟、重试、异常变化、计量范围 |
| **规则与适配** | 规则映射、实际生效、配置漂移、更新影响、授权变更与恢复 |

AAOS 不需要在这里变成一个“知识库主页面”。

它更适合出现于两个位置：

**设置中的“知识连接”。** 配置可访问范围、连接状态、交换记录。

**能力或问题详情中的“关联知识”。** 查看来源版本、引用的经验，以及“提交为知识候选”。

不增加知识编辑器、知识图谱、通用记忆聊天和第二套搜索系统。

同样，问题详情应是可展开的诊断面板，而不是再增加一组“错误中心、故障中心、恢复中心、问题中心”。

**能力可以变深，导航不必跟着变宽。**

# 五、与 AAOS 的连接，先做四件事就够了

这里讨论的是 WORK-LAB 的接口责任，不扩展审计 AAOS 本体。

## 1. 提交候选

一次有价值的经验整理后，提交内容、来源、适用项目与版本、必要证据、隐私范围。

不要默认把完整日志、全部会话和个人工作文件一起发送。

## 2. 读取发布版本

WORK-LAB 获取已允许使用的知识版本，用于规则说明、技能参考或故障处理建议。

**“接收成功”与“审核通过”必须分开；“已发布”也不等于适合所有项目。**

## 3. 接收失效与撤回信息

知识被修订、弃用或撤回时，标出哪些技能发布快照或规则建议引用了它，再安排受控更新。

不能因为 AAOS 更新了知识，就悄悄改写所有正在使用的客户端配置。

## 4. 记录使用反馈

记录哪个知识版本被哪个能力包、软件、项目引用，以及可观察的结果。

这只是使用反馈，不自动证明知识正确，更不允许 Agent 自己把结论升级为已验证事实。

**AAOS 尚未就绪时，可以保留有限、可导出的候选暂存和交换记录；不要因此建立第二个永久知识库，也不要阻塞 WORK-LAB 的独立运行。**

# 六、后端不需要八套系统，只需要把现有结构组织成三条主链

```text
外部 AI 软件正常工作
        │
        ├─ 观测链
        │   采集 → 身份关联 → 事件标准化 → 用量／异常 → 界面
        │
        ├─ 治理链
        │   规则／能力资产 → 原生适配 → 差异 → 授权应用 → 生效与恢复
        │
        └─ 知识交换链
            经验候选 → AAOS
            AAOS 发布版本 → 受控引用／发布快照
```

**软件执行仍然在外部；知识确认仍然在 AAOS；WORK-LAB 管连接、运行事实、配置和影响。**

工程上应优先扩展现有契约、适配器、观测存储和界面，不因为上面列了八个能力面，就新建八个服务、八个账本和八套状态。

首版也不需要为了支持未来，立即引入大型消息系统、分布式数据库、独立向量库或常驻分析模型。

基础状态、计量、告警和配置检查，尽量使用确定性逻辑；AI 解释作为可选、按需调用能力。

# 七、推进顺序要重新排序：深挖主线，而不是一起全面展开

| 优先级 | 重点 | 验收标准 |
|---|---|---|
| **第一批：看准** | 会话与项目关联、状态与观测质量、Token 去重与口径 | 直接在外部软件启动工作，也能被正确观察；重启不重复计量 |
| **第二批：看懂** | 异常归并、个人技能调用、影响范围、用量变化 | 能定位具体会话、能力版本和问题，不只看到红灯 |
| **第三批：管稳** | 规则生效、技能发布、升级检查、漂移与恢复 | 对一项真实受管配置完成变更、生效验证及恢复 |
| **第四批：互通** | AAOS 候选交换、知识版本引用、撤回与反馈 | 不复制知识权威，AAOS 离线也不影响基本观测 |
| **后续扩展** | 跨设备、更多客户端、协作式交接与受控操作 | 新适配进入现有模型，不靠复制另一套产品实现 |

原有任务协议、调度、编排、外部 Workspace 等能力面可以保留代码和研究记录，但不再全部成为首版的必答题。

现有未来候选登记已经包含保留候选、退役以及重新评估触发条件的思路。建议继续使用这个机制，只是把重新启动的依据改成**实际观测或治理缺口**，而不是“发现了一个功能很多的新项目”。fileciteturn64file0L1-L2

# 八、一个完整的目标场景，比继续增加功能名更重要

以下是建议的目标体验，不是当前已完成状态：

你直接在两个 AI 软件里工作，一个项目发生反复工具错误。

WORK-LAB 自动把会话归到对应项目，显示受影响的软件、技能版本、重试过程及实际报告的消耗；同时发现近期发生过技能更新，将其列为排查线索，而不是直接宣布根因。

你查看差异，确认后通过受控入口恢复上一版受管技能；原软件继续执行。WORK-LAB 记录恢复动作与后续状态变化，保留“这次恢复是否有效”的实际结果。

这次事件形成的一条可复用经验，被提交到 AAOS，等待确认。未来某个项目需要这条经验时，WORK-LAB 引用 AAOS 发布的版本，而不是从自己的日志里偷偷生成一条新的全局规则。

这条链体现了三种不同的闭环：

> **观测闭环：发生了什么，能够追到来源。**  
> **治理闭环：改变了什么，能够确认和恢复。**  
> **知识闭环：学到了什么，由 AAOS 核验和沉淀。**

---

## 最终建议

**知识归 AAOS，应当让 WORK-LAB 更聚焦，而不是更弱。**

WORK-LAB 最值得强化的，不是另一个知识库或更大的任务运行平台，而是：

**更准确的观测、更有用的诊断、更可靠的个人能力管理、更清楚的消耗分析、更稳定的规则适配，以及更安全的软件更新和跨软件协作。**

真正的产品目标可以收敛成一句话：

> **其他 AI 软件负责把工作做下去，WORK-LAB 负责让我看得清、管得稳、发现问题并处理影响；有价值的知识，最终进入 AAOS。**

**下一轮推进的核心，不应是继续增加菜单，而是让现有五个入口分别完成“看准、看懂、管稳”这三件事。**

## 二、你的描述不是“错”，但有七处必须转成更准确的开发语言

### 1. “软件正在工作”，应该改成“软件中的会话有已确认活动”

软件进程还在，不代表它正在运行任务；软件窗口关了，也不一定代表所有后台活动都已经结束。

建议观察对象分层为：

```text
设备与运行环境
    → 软件安装实例／版本
        → 会话
            → 本轮执行
                → 模型请求、工具调用、技能事件
```

项目作为关联维度加入，而不是把“一个项目只能绑定一个软件”写死。

### 2. “项目停止了”，不能等同于“项目完成了”

项目是一段持续工作；会话结束、一次回答完成、一次工具执行结束，都是更小的生命周期。

界面应说：

> 当前观测到的执行已结束。

而不是擅自说：

> 项目已完成。

这不是纯粹的措辞问题。Hermes 官方文档明确指出，`on_session_end` 可以是单轮或单次运行结束，并不一定意味着会话身份生命周期结束。citeturn807863view5

### 3. “实时监控”，不能只理解为“页面每秒刷新”

需要区分四个时间：

**事件发生 → 客户端发出 → WORK-LAB 接收 → 界面显示。**

如果客户端只在请求结束后提供计量，页面刷新得再快，也不能提前知道最终消耗。Codex 的 OTel 文档明确说明导出会异步批处理，部分 Token 信息出现在完成事件中。citeturn807863view7

因此应分别定义：

- 活动状态的及时性；
- 最终用量的结算及时性；
- 历史补采的完整性。

**不承诺所有软件、所有字段都具有相同的实时性。**

### 4. “插件技能”，实际上是不同类型的资产

插件包、Skill、MCP Server、具体 Tool、Hook、脚本和规则，不应该被当成同一种对象。

一个插件可能提供多个技能；一个技能可能调用多个工具；一个工具也可能被很多技能共同使用。

**不能用工具名直接代表技能身份，也不能用插件安装数量代替调用次数。**

### 5. “缓存命中率”，必须说明是什么缓存

你主要关心的是模型提供方的提示缓存使用情况，而不是：

- 本地文件缓存；
- 编辑器缓存；
- 上下文压缩；
- 本地推理的显存缓存；
- 软件自己的结果复用。

这些可以未来观察，但不能混成一个“缓存命中率”。

### 6. “中立治理”，不是让所有软件拥有完全一样的能力

合理目标是：

> 相同的治理意图，在各软件支持的原生机制里尽可能正确实现，并明确显示差异。

不合理目标是：

> 所有软件都必须支持同样的参数、权限、规则加载顺序和会话能力。

**中立是可替换、可解释，不是强行抹平差异。**

### 7. “记忆共享”，不是复制全部会话

按照你明确的边界，未来共享的是 **AAOS 管理的、具有来源、范围、版本与状态的知识**。

运行游标、临时检查点、任务关联和观测历史，可以留在 WORK-LAB；它们不因此成为长期知识权威。

## 2. 有三个此前容易忽略的发现，会直接改变实现方式

### Hermes：只监听主请求，可能漏算辅助调用

官方文档将标题生成、压缩等辅助模型调用放在独立的 `pre_auxiliary_call`／`post_auxiliary_call` 中，主请求 Hook 只覆盖主循环。citeturn807863view5

因此，WORK-LAB 应当能区分：

> 主任务消耗、辅助调用消耗、子 Agent 消耗。

但如果父级记录已经包含子级汇总，不能再把两者重复相加。

### Claude Code：个人技能可识别性与隐私存在真实取舍

当前官方文档中，自定义技能名称默认可能被记录为 `custom_skill`；启用更详细的工具遥测后才可能提供真实名称。citeturn807863view0

所以正确界面不是：

> 没有调用个人技能。

而是：

> 已观察到自定义技能激活，但名称被来源端隐藏，暂时无法关联具体个人资产。

不能为了识别技能，就默认打开所有内容采集。

### Qoder：异步 Hook 不一定是被动观察

官方文档说明，部分异步 Hook 的结果会进入下一轮模型上下文，`asyncRewake` 还可以唤醒模型。citeturn807863view6

这意味着监控适配必须有**不干扰执行的约定和测试**：

> 不注入任务正文、不额外唤醒模型、不改变审批结果，不把遥测故障变成执行阻塞。

**“异步”只说明调度方式，不自动等于“没有副作用”。**

# 五、技术协议需要分工，不能找到一个新协议就重构全部项目

建议明确：

| 机制 | 用途 |
|---|---|
| **OTel／OTLP** | 观测信号与传输 |
| **客户端原生 Hooks／日志** | 补足软件特有事件 |
| **ACP** | 客户端与 Agent 的会话交互，适合部分未来交接能力 |
| **MCP** | 工具与上下文集成 |
| **Agent Skills** | 技能包结构与发现 |

**OpenTelemetry 的 GenAI 语义资料已经迁往独立仓库。** 应固定适配器与语义映射版本，避免某个上游字段调整后直接破坏整个前端。citeturn170042view5

# 六、正式收敛成“四条主线、两项基础、一条知识边界”

不再增加八个平行系统。

| 层次 | 职责 |
|---|---|
| **主线一：工作观测与问题定位** | 项目—软件—会话关联、状态、等待、异常、影响范围 |
| **主线二：个人能力资产治理** | 插件、技能、规则包的来源、版本、部署、使用与兼容 |
| **主线三：用量与运行效率** | Token、缓存、计量覆盖、延迟、重复失败和费用估算 |
| **主线四：规则与环境适配** | 原生投影、生效检查、漂移、更新影响、授权变更与恢复 |
| **基础一：可靠性** | 不干扰外部执行，采集可恢复、去重、积压和缺口可见 |
| **基础二：隐私与安全** | 最小采集、字段白名单、权限分离、外部输入不可信 |
| **知识边界：AAOS** | 候选提交、已发布知识引用、撤回与使用反馈 |

**跨软件治理不等于跨软件调度。**

你可以先知道两个软件正在修改同一工作区、共享服务异常影响了几个项目、规则升级可能影响哪些活跃会话；这些已经是治理价值，不需要先接管每项任务。

```text
Invocation    工具／技能调用
Asset         个人或第三方能力资产
Observation   带来源和时间的观测记录
```

这是逻辑对象，不意味着立即建立九个服务。

需要特别区分：

**活动关联。** 一次会话可能关联多个项目。

**计量归属。** 一次消费不能因为关联三个项目，就在三个项目各记完整消费，然后再汇总三次。

建议保留主要计量归属；不能确定时放入“未归属”。后续可以提供明确的分摊规则，但分摊必须另行标记，不能冒充来源端原生归属。

项目根、工作副本和当前目录也不能混同。路径变化、Worktree、Windows 与其他环境中的路径别名，要有可检查的映射；无法确认时允许你纠正。

**不要通过读取全部私人会话正文，来弥补缺失的项目身份设计。**

## 2. 状态建模：工作状态、健康状态、观测状态必须分开

| 维度 | 例子 |
|---|---|
| 工作状态 | 运行中、等待用户、空闲、本轮结束、取消、失败 |
| 健康状态 | 正常、重试中、反复失败、疑似停滞 |
| 观测状态 | 已连接、延迟、连接中断、有限可见 |

这样才能正确表达：

> 会话上次确认仍在运行，但观测连接已经中断。

而不是把它直接标成：

> 项目停止。

疑似停滞也应当是基于明示规则的判断，不是模型拍脑袋给出的事实。重复错误需要结合操作、时间窗口、重试及恢复情况归并；正常的测试先失败后修复，不应直接算“软件故障”。

## 3. 采集架构：事件存储可以有，但不建立外部软件的影子业务库

建议沿用现有技术栈：

```text
原生软件事件／日志
        ↓
轻量适配与字段筛选
        ↓
身份关联、去重、语义标准化
        ↓
现有观测存储与用量记录
        ↓
快照／增量更新
        ↓
React 工作台
```

配置治理另走受控命令路径，不把写操作藏进观测查询中。

现有项目已经明确 React/TypeScript、Tauri/Rust、Python 的分工，并反对全仓 Rust 重写；这一点我仍然支持。**没有证据表明换语言能解决当前产品问题。**fileciteturn67file0L1-L2

历史观测可以保留，但不复制外部软件全部会话数据库。所谓“单一事实来源”，也不应被扩大为“不能建立供界面使用的查询摘要”。

## 4. 可靠性：监测失败不能把工作也拖停

首版就应有：

**读取游标、事件身份、有限缓冲、恢复后的去重、日志轮换处理、积压和丢失区间显示。**

可以参考成熟遥测系统的持久化队列，但不能承诺绝不丢失；官方 Collector 文档也明确指出，磁盘、容量和重试条件仍可能导致数据损失。citeturn673943view0

必须区分两种失效策略：

> **观测链失败：不阻断外部工作，明确显示观测缺口。**  
> **承担真实安全约束的授权链失败：按既定安全政策拒绝相关操作。**

两者不能混成一条 Hook。

基础监测、计量、状态归并和配置对账都不应依赖持续调用大模型。AI 解释可以按需使用，避免“为了监控 Token，又不断花 Token”。

# 八、计量设计：这是当前最应该优先修的准确性问题

## 1. 本次已经复现一处真实的逻辑不一致

当前 `_rollup_usage()` 与 `_token_summary()` 对质量标签的处理不同：

| 合成输入，同一项目 | 项目汇总 | 总体汇总 |
|---|---|---|
| 100 个精确用量 + 50 个估算用量 | 150，标为 `EXACT` | 150，标为 `ESTIMATED` |
| 100 个精确用量 + 50 个质量未知用量 | 150，标为 `EXACT` | 150，标为 `UNKNOWN` |

这是按照已读取代码原逻辑执行的**函数级最小复现**，不是用户真实消费数据，也不是整个仓库测试套件。相关脚本和输出已放入资料包。源码确实存在“项目级只要遇到精确记录，就可能保持精确标签”的逻辑。fileciteturn68file0L1-L2

修复不能只是把所有混合数据都改成“未知”，而应展示：

> 精确部分、估算部分、缺失部分、可用统计范围。

## 2. 精确性与完整性是两回事

即使每条已收到的记录都来自官方，也可能漏掉某些会话、辅助请求或软件。

因此：

> **已收到的数据精确，不代表全部消费都被收到了。**

建议用两个独立维度：

- 计量精度：原生报告、估算、未知；
- 计量完整性：当前已观测范围中，哪些字段完整，哪些缺失。

如果根本不知道未接入的软件发生了多少请求，就不能给出“全机采集覆盖率 98%”这种数字。

可以显示“已登记软件中，哪些具备哪些观测能力”，也可以显示“已观察请求中，有多少具备缓存字段”；但不要把二者冒充全局覆盖率。

## 3. 缓存口径必须按提供方标准化

当前官方文档中，OpenAI 的缓存明细属于输入用量组成部分；Anthropic 则分别提供普通输入、缓存读取和缓存创建，需要按其口径合并。不能直接对所有提供方套同一加法。citeturn170042view6turn170042view7

建议至少区分：

```text
输入 Token 缓存读取占比
= 缓存读取 Token 合计 / 同范围总输入 Token 合计

请求缓存命中率
= 发生缓存读取的请求数 / 能判断缓存情况的请求数
```

前提是统计范围一致、字段可用。缺字段显示未知，分母为零显示不适用；不能平均各会话百分比，也不能把缓存写入算成命中。

当前主要快照出口还没有完整表达缓存读取、创建等信息，因此**这个出口需要补齐**；这不等于断言全仓所有采集路径都没有缓存数据。fileciteturn68file0L1-L2

## 4. Token、Credits、估算费用、真实账单分开

Qoder 的账户用量入口使用 Credits。它可以与 Token 同页展示，但必须保留单位，不能未经明确依据换算。citeturn807863view1

我建议用量页面分为：

> **来源报告的用量｜来源报告的额度｜按已知价格估算的费用。**

并处理四类重复：

**累计值重复刷新、流式中间值与最终值、父子会话汇总、多个采集来源记录同一请求。**

来源没有请求级身份时，应降低去重结论的可信度，而不是凭时间接近就永久合并。

# 九、个人技能与规则治理：应该更深，但不要变成另一套知识系统

## 1. 个人能力的主线是“身份—部署—使用—变更”

建议每项资产回答：

> 它来自哪里？是否由你原创或修改？哪个版本部署在哪里？客户端是否发现？有没有明确触发？关联了哪些实际操作？更新后是否出现异常？

需要区分“原创”“定制修改”“收藏受管”“软件内置”。  
**受管不等于原创，调用次数不等于效果。**

Agent Skills 规范中的 `allowed-tools` 仍是实验性字段，不同实现支持可能不同，不能因此宣称技能已经获得跨软件一致的权限约束。citeturn948718view0

对同一轮多个技能共同参与的情况，可以显示关联，但不要把整轮用量给每个技能完整记一遍。

## 2. 规则生效应有五个阶段

```text
规则已定义
→ 原生配置已生成
→ 已写入目标
→ 客户端已发现／加载
→ 有适用范围内的行为验证
```

前一步不能抵扣后一步。

即使有行为验证，也应限定到具体测试和版本，**不能宣布模型以后每次都遵守**。

全局规则建议保持短而稳定，项目差异由项目范围承载，专项能力按需加载。不要把所有历史审计、未来蓝图和全部技能正文塞进每个客户端的全局上下文。

## 3. 配置治理应该保留受控写入能力

当前产品不接管业务执行，不等于只能看配置、不能管配置。

合理的治理操作包括：

> 查看差异、更新受管规则、部署指定技能版本、重新检查加载、处理漂移、恢复已有备份。

这些操作应使用现有配置所有权和三方对比机制，不再增加第二个自动同步器。

需要改掉的，是将“没有本次授权”“目标不支持”“代码尚未接通”都混成一个“不可用”。不同原因应提供不同解释和下一步。

# 十、AAOS 边界：交出去的是知识权威，不是所有运行资产

| 内容 | 归属建议 |
|---|---|
| 专业事实、研究、方法、案例、经过核验的经验 | AAOS |
| 观测事件、会话关联、计量、异常与运行历史 | WORK-LAB |
| 规则映射、部署关系、受管配置版本、恢复记录 | WORK-LAB |
| 技能脚本、适配器、可执行规则包源码 | 原有源码归属方；WORK-LAB 管部署与运行关系 |
| 技能引用的知识内容 | AAOS 权威版本，必要时带可追溯发布快照 |
| 临时会话、检查点和读取游标 | 原软件或 WORK-LAB 运行边界 |
| 凭证和私密浏览器状态 | 不进入知识交换或普通观测库存 |

混合型 `SKILL.md` 不能按扩展名粗暴迁移。需要区分执行说明和知识内容，但不能破坏现有包的路径与运行结构。

当前阶段，AAOS 连接只需要预留四件事：

**提交知识候选、读取允许使用的发布版本、接收撤回或失效信息、返回使用反馈。**

其中：

> 接收成功不等于审核通过；知识发布不等于适用于所有项目；引用被撤回不等于可以立即改写所有活跃客户端。

AAOS 未就绪时，可以有有限的候选暂存和交换记录；**不能因此在 WORK-LAB 里新建永久知识库，也不能阻塞基本监测。**

# 十一、界面该怎么收敛：监控台是正确方向，不是低级替代品

对你的工作方式，我明确支持**观测型首页**。

前面把首页过度改成“新建任务、推进任务”的建议，不符合这次澄清后的主要使用方式。

## 1. 五个入口足够承载深化后的能力

| 入口 | 核心问题 |
|---|---|
| **实时总览** | 谁在工作？谁在等待？哪些问题需要注意？ |
| **项目与软件** | 一个项目涉及哪些软件与会话？环境和版本是否正常？ |
| **插件与技能** | 哪些个人能力部署、生效和实际触发了？ |
| **用量与缓存** | 消耗发生在哪里？统计是否完整？缓存与重试有何变化？ |
| **规则与适配** | 哪些规则已投影、生效、漂移，需要怎样处理？ |

设置、证据、诊断、历史属于二级入口或详情，不再不断扩大主导航。

## 2. 首页主体应是“工作关系”，不是空图表

建议主要行内容为：

```text
项目
软件／会话
当前活动
等待或异常原因
最近进展
关联能力
已报告用量
观测新鲜度
```

可以按项目或软件分组，但使用同一批数据。一个项目多软件并行时，显示集合和状态分布，不压成一个软件标签。

当前首页仍有禁用的“新建执行”，趋势图仍传入空数组。**按新定位，应移走这些无价值占位，而不是为了让按钮可点，先开发完整派发系统。**fileciteturn69file0L1-L2

## 3. 新增能力通过详情深入，不通过菜单横向扩张

选中一条会话，右侧或详情页应能查看：

> 事件时间线、错误与重试、技能关系、计量范围、来源状态、相关配置变化。

问题归并放在同一视图中；AAOS 的关联知识放在问题或能力详情，不增加第二个知识工作台。

按用户实际路径组织导航，比按每个后台对象安排一个页面更适合这个产品。微软的导航指南也强调依据用户路径组织信息。citeturn695865view1

## 4. 实时界面还有一类之前没充分强调的质量要求

更新不能造成行不断乱跳、选中对象消失、焦点被抢走。建议保留稳定排序、选中对象和滚动位置，并提供“暂停自动滚动”，**它只暂停视觉跟随，不停止采集**。

告警应避免每条事件都打断用户；读屏状态通知也应让变化可感知，而不是只改变颜色。citeturn695865view2

视觉风格无需再全面推翻。保留深浅主题、蓝青强调和紧凑信息密度，重点调整信息权重：

**项目与异常比装饰突出，原因比状态码易懂，来源限制比空白更明确。**

# 十二、还要加强两项容易被遗漏的能力

## 1. 软件更新影响检查

软件更新之后，不只检查版本号和进程能否启动，还要重新确认：

> 原生入口、规则加载、技能发现、事件格式、计量字段、受管配置和读取权限。

应允许出现这种结果：

> 软件运行正常；技能加载正常；缓存字段尚未重新验证。

而不是一个版本升级后，所有绿色状态自动继承。

但发现问题不意味着可以默认迁移数据根、清理模型或重启正在工作的客户端。

## 2. WORK-LAB 自身的可观测性与安全边界

需要展示采集器状态、解析失败、队列积压、最后成功读取时间和覆盖范围。OpenTelemetry Collector 的内部遥测就包含接收、拒绝、发送失败及队列相关指标，可借鉴其思路。citeturn673943view1

隐私上，“只记录元数据”也不代表天然安全：项目名、路径、工具错误、技能名都可能敏感。采集入口应采用字段白名单和可检查的保留策略，而不是先收全，再寄希望于后续脱敏。citeturn673943view2

尤其要明确：

**遥测记录是来源提供的运行证据，不是绝对不可篡改的事实。**  
客户端可以没有导出、用户可以关闭 Hook、事件也可能缺失。因此不能把本地监控包装成对所有软件都强制有效的审计或安全平台。

同样，“个人本地应用不做账号系统”可以成立，但不应推导出“命令接口无需验证来源与权限”。界面按钮禁用不是安全边界，原生命令与服务访问需要独立约束。citeturn695865view3

# 十四、下一轮推进应改成五个验收批次，而不是“再全量审计一遍”

| 批次 | 实际交付 | 通过标准 |
|---|---|---|
| **A：原生观測闭环** | 两个实际使用客户端的会话—项目—状态关联 | 不通过 WORK-LAB 启动，也能观察；等待、结束、断连不混淆 |
| **B：计量与个人能力** | 同批会话的请求用量、缓存、技能身份与版本关系 | 来源可对账、重复不多算、隐藏字段不伪装成不存在 |
| **C：问题定位与界面** | 五入口、关系列表、详情、异常归并 | 能从项目定位到具体会话、原因与下一步，不依赖翻内部文档 |
| **D：规则与环境治理** | 一项真实受管规则或技能变更 | 差异、授权、写入、加载、漂移、恢复分别有证据 |
| **E：安装与恢复** | 固定版本的本机运行验证 | 重启不重复计量、数据缺口明确、关闭 WORK-LAB 不阻断外部工作 |

你常用的 Hermes、Codex、Qoder、DSH 应优先采样，但**首批只选择两个已拿到可靠事件样本、且你确实正在使用的客户端**。不是为了“看起来支持很多软件”，先做十个薄适配。

资料包中整理了 **40 个待执行验收场景**。其中最关键的是：

- 同一软件处理两个项目、两个软件处理同一项目，关联都不串。
- 会话结束不误报项目完成，监测断连不误报任务停止。
- 累计用量、流式结果、辅助调用、父子记录、重放都不重复或静默漏算。
- 自定义技能名称被隐藏时，能解释为什么无法关联。
- 配置更新不覆盖无权管理的用户字段，客户端升级后相关资格重新验证。

# 一、项目监控：不是把任务明细藏起来，而是默认就不做全量任务追踪

这是最重要的修正。

**不能表面上只显示项目卡片，后台却仍然收集所有提示词、工具参数、任务步骤、子 Agent 轨迹和完整返回。** 那只是把复杂度藏起来，并没有真正收敛。

## 1. 默认监控应该只服务于项目层的问题

| 项目层问题 | 应当提供的信息 |
|---|---|
| 这个项目现在有没有在推进？ | 最近确认的活动、当前参与的软件 |
| 是哪些软件在处理？ | 软件及必要的会话关联，不展开完整任务树 |
| 有没有受阻？ | 当前主要阻碍、影响范围、是否需要你处理 |
| 是停止了，还是暂时没有活动？ | 明确结束、等待用户、暂无活动、观测中断分别显示 |
| 最近是否经常出问题？ | 归并后的重复问题与变化趋势，不堆每条错误日志 |
| 消耗大不大？ | 按项目及软件汇总的用量、缓存情况和计量范围 |
| 有哪些相关个人能力？ | 已部署或已观察使用的能力，以及值得评估的候选 |

**项目阶段和项目活动也要分开。**

“正在开发”“准备验收”属于项目语义，需要来自明确的项目记录；“最近有软件活动”“有软件等待用户”属于运行观测。不能靠进程活动推断项目完成百分比。

同一个项目里，可能一款软件继续工作，另一款软件受阻。项目摘要可以显示“部分受阻”，而不是用一个状态覆盖所有情况。

## 2. 后台只保留支撑这些结论的必要信息

必要时，可以读取原软件已经提供的会话标识、状态事件或计量记录，用来判断归属、累计消耗和去重。

但默认保留的重点应该是：

> **项目摘要、主要状态变化、归并后的问题、用量汇总、必要的来源标识。**

不要求所有工作先登记成 WORK-LAB 的任务，不要求通过 WORK-LAB 启动软件，也不要求每次工具调用都进入它的任务账本。

进一步排查时，可以针对**选定项目、选定问题、有限时间范围**读取原软件的相关记录。它是按需诊断，不是长期全量追踪。

**因此，上一版方案中“逐任务、逐工具、逐子 Agent 全面追踪”的内容，应从默认需求和首版验收中移除。**

## 3. Token 精确统计与轻量监控并不矛盾

有些来源需要读取请求级计量才能正确累计，但可以只保留去重所需标识和计量字段，处理后形成项目汇总。

**需要计量记录，不等于需要保存请求正文或完整执行过程。**

同样，评估某个技能是否值得迁移，可以针对这个技能收集少量代表性结果，不必反过来要求所有项目都接受详细监控。

# 二、AAOS 管的，是“新软件如何接上项目”，不是复制聊天记录

你说的记忆共享，核心不是：

> 把 Codex 的聊天历史复制给 Hermes。

而是：

> **Hermes 开始处理这个项目时，能从 AAOS 找到正确的项目关键事实、决定、边界和当前落点。**

这是一个更准确的目标。

## 1. 建议未来采用“项目基础信息＋按需补充”，而不是每次重新注入大包

新软件或新会话开始时，先取得一份小而明确的项目关键信息：

| 内容 | 作用 |
|---|---|
| 项目是什么、当前目标是什么 | 避免重新理解项目身份 |
| 当前有效边界和禁止事项 | 避免重复越界或重建已否定方案 |
| 已确认的重要决定 | 避免每个新会话重新争论 |
| 当前阶段、阻碍和下一步 | 接上实际进度 |
| 关键文件与权威来源 | 让软件能够继续查证，而不是只信摘要 |
| 更新时间、适用版本、待确认项 | 防止把旧信息当成当前事实 |

然后，软件根据当前工作再从 AAOS 获取相关内容，而不是一次性加载整个项目历史。

这里有一个关键设计原则：

**必须遵守的项目边界，不能只依赖“语义搜索刚好搜到”；应该作为明确的项目基础信息提供。** 其余背景、案例和历史细节再按需检索。

## 2. AAOS 管知识，当前现场仍需要核对

AAOS 中可能记录着昨天的项目状态，而本地仓库今天已经改变。

因此，建议新软件的接续过程是：

```text
识别项目
→ 从 AAOS 获取当前发布的项目关键信息
→ 核对本地仓库或原软件的实际状态
→ 按本次工作补充检索
→ 开始工作
```

不能让 AAOS 的历史摘要覆盖当前代码、未提交修改或你刚刚作出的明确决定。

目标也不应表述为“完全不需要上下文、永远不会漂移”，而是：

> **减少重复注入，降低信息遗漏和漂移，并让关键上下文有来源、版本和更新机制。**

## 3. WORK-LAB 在这里是接入与状态管理，不是记忆管理者

WORK-LAB 可以负责项目身份映射、连接配置、权限范围，以及显示：

> 已连接 AAOS；当前项目上下文版本是什么；是否过期；哪些信息尚未取得。

**项目内容如何保存、核验、检索、合并和更新，由 AAOS 管。**

如果某款软件支持原生启动时读取，就通过适配器接入；不支持时，可以提供显式的“接续此项目”入口，但不能宣称所有软件都已自动接续。

这条能力可以延后。AAOS 尚未就绪，不应阻塞项目监控和技能适配。

# 三、你要的技能管理，实际上是“个人能力的筛选与跨软件复用”

这部分的理解需要明显升级。

你不是主要想知道：

> 某技能今天调用了多少次。

你真正想知道的是：

> **这个能力在某个软件里已经被用出来了、被认可了，能不能成为我的可复用资产，让我选择的其他软件也获得它？**

所以，WORK-LAB 应重点建立这条能力链：

```text
发现或导入能力
→ 经过使用和评估
→ 提取可复用部分
→ 去除不必要的软件绑定
→ 适配用户选定的软件
→ 在目标软件验证
→ 发布并管理后续更新
```

**使用监测只是帮助发现和判断候选，不是最终目的。**

## 1. 能力来源可以有三种

**已有的软件生态能力。** 例如 Codex 里某个确实好用、可合法复用的技能或插件。

**你自己开发的能力。** 例如自己的脚本、技能、插件或一组稳定工作方法。

**软件使用过程中形成的能力。** 例如 Hermes 根据实践创建和更新的技能。

Hermes 官方文档确实提供了通过 `skill_manage` 创建、更新和删除技能的机制，用于保存可重复的方法。这说明你的例子存在实际技术基础，但生成了技能并不自动证明它已经有效或适合迁移。citeturn972217view3

## 2. “中立化”不是把所有东西改写成一篇通用提示词

中立化需要保留的是：

> **能力目标、适用条件、输入输出、有效步骤、必要工具、限制和验收方式。**

需要替换或隔离的是：

> 软件专属路径、工具名称、事件机制、配置方式、交互入口，以及不应传播的私密内容。

如果源技能本来就采用通用格式，依赖也已经兼容，**优先直接复用或做最小适配，不要为了“中立化”再让模型全文重写一次。**

Agent Skills 规范已经提供 `SKILL.md`、脚本、参考资料和资源目录等通用结构，但也明确指出，部分字段的支持因实现而异。**格式兼容只是起点，不是功能兼容证明。**citeturn972217view0

我不建议为此立即发明一套庞大的“能力编程语言”或通用编译器。先让几项真实能力可靠迁移，再决定哪些结构需要标准化。

## 3. 迁移应该按难度和性质分级

| 能力类型 | 合理处理方式 |
|---|---|
| 通用指令和工作方法，依赖已兼容 | 直接复用或轻量调整触发说明 |
| 带脚本、CLI、文件操作的技能 | 保留有效代码，适配路径、依赖、权限和调用方式 |
| 带 MCP 服务的插件 | 复用可用服务，适配连接与认证；不复制凭证 |
| 依赖专属界面、Hook 或内部接口的插件 | 单独评估替代实现，明确保留和损失的功能 |
| 封闭服务或无法合法提取的能力 | 保留原软件调用，或另立等效能力开发项，不假装完成迁移 |

OpenAI 的插件设计本身就区分了“技能负责工作方法”和“MCP 服务负责实时数据、授权及受控动作”。因此，只复制技能说明，不会自动带走底层服务能力。citeturn129859view0

插件还可能包含特定宿主的扩展和生命周期 Hook，所以即使有可移植的包结构，也不能推定整个插件在所有软件里都具有相同功能。citeturn972217view2

**中立适配的目标是保留有效能力，不是让所有软件都退化到最低共同功能。**

可以保留通用核心和目标软件的扩展，只要兼容范围说清楚。

---

# 四、“长期使用、机器判断、用户判断”怎样做，才不需要全量任务监控

这个问题很关键：**不详细监控所有任务，仍然可以评估选定技能。**

但不能完全依赖“Agent 觉得自己做得很好”。

我建议把评价分成三个独立结论，而不是合成一个模糊的高分。

| 评价 | 要回答的问题 | 主要依据 |
|---|---|---|
| **源软件中的实用性** | 它在原来的使用环境里是否好用？ | 用户反馈、少量代表性结果、已知问题 |
| **可迁移性** | 好用的部分能否脱离原软件？ | 依赖、接口、权限、来源及功能分析 |
| **目标软件中的有效性** | 迁移过去后是否仍然好用？ | 目标端实际使用、输出检查和用户确认 |

**“在 Codex 很好用”只支持第一个结论，不自动支持第三个。**

## 1. 机器适合做什么

机器可以帮助检查包结构、依赖、敏感信息、触发条件，运行选定的测试，比较代表性输出，指出适配损失和维护成本。

需要时可以调用现有 AI 软件辅助分析，但不要求每次使用都运行一轮评审模型。

## 2. 用户判断不可被自动分数替代

# 六、必须区分：迁移“自主进化产生的技能”，不等于迁移“自主进化机制”

你举 Hermes 的例子，最合理的理解是：

> Hermes 通过自身机制形成了好技能，WORK-LAB 把这些成果筛选出来，适配到其他软件。

而不是：

> 把这些技能复制过去，其他软件就拥有了 Hermes 整套自主进化能力。

前者是当前值得做的**能力资产复用**。后者涉及新的生成、评估、更新和维护机制，是另一项更大的开发工作，不能靠复制几个文件宣称完成。

同样，迁移一个代码审查技能，可以迁移检查方法、输出要求和脚本；不能迁移原软件或原模型本身所有未开放的能力。

**WORK-LAB 管的是能够提取、适配和验证的能力成果，不是承诺搬走任意软件的全部内部智能。**

转换工作可以复用已有 AI 软件和受控脚本，不必再建一个常驻的“技能进化 Agent 平台”。

> **WORK-LAB 出口：这份内容是否获准发送、范围是否正确、必要来源与完整性是否满足。**  
> **AAOS 知识治理：这份内容以什么身份保存、是否核验、适用于什么用途、何时修订或失效。**

不能为了让未验证候选进入系统，就关闭隐私和安全检查；也不能为了保留安全检查，就强迫所有候选预先冒充“已验证知识”。

### 2. “完成权威”必须限定到本项目或受委托的技术合同

现有顶层定义包含任务、回执和完成权威等内容。按照本次协作要求，它应限定为：

> **WORK-LAB 对自身结果和明确委托的技术条件作判断。**

它不能决定 DESIGN-LAB 的作品是否专业合格，也不能决定 AAOS 中某项知识是否可信、某个人是否已经学会。通用协调可以提出约束、反馈失败和拒绝越权，但不是替专业责任方作最终决定。fileciteturn75file0L1-L2

### 3. “不拥有设计能力”不能被解释成“不能提供技术材料或适配支持”

现有三项目边界强调 WORK-LAB 不拥有设计领域判断、设计资产和生成策略，这个原则应保留。fileciteturn80file0L1-L2

但需要把“不拥有”与“不协作”分开。

WORK-LAB 可以提供技术样例、检查命令是否正确、解释接口限制，也可以在获得许可后管理通用能力的部署关系。**它不因此拥有专业内容，也不应禁止 DESIGN-LAB 使用自己的设计专用执行内核。**

### 4. “原始日志不是知识”不能扩大为“教学示例不能带代码或证据片段”

原始日志当然不能自动变成经验知识，完整私人会话也不能默认发送。

但教学案例可能需要一段经过授权、最小化的错误输出、一个可复现脚本或一条命令。正确做法是：

> **提炼后的内容与受控证据附件分开；分别检查用途、范围和敏感信息。**

不是看见几行命令就一律拒绝，也不是为了教学把全部日志上传。

### 5. 技能新增内容不能自动变成全局知识或全局规则

此前已经检查过的配置机制允许部分原生技能追加内容自动折回仓库。按照新边界，至少应进一步区分：

**可执行资产变更 → 本方能力评估与版本管理；知识经验 → AAOS 候选；临时会话内容 → 不自动全局化。**

“追加了几行”不是内容正确、适合共享或可以自动生效的证明。

## 五、本轮实际复现的接口问题，而不只是规划判断

我将三个相关源码文件原样放入隔离目录，核对 Git blob 身份后执行。**这属于固定源码的模块级复现，不是全仓验收或 Windows 安装态测试。**

### 1. 未验证候选被旧门禁拒绝

使用有来源、无私密内容的测试候选，`verified=False` 时实际得到：

```text
allowed = false
forbidden_kinds = ["unverified_candidate"]
```

只改变该标记，门禁结果就发生变化。这个结果说明：**当前函数仍把内容的验证标记当成跨项目准入条件**，需要按上一节拆分职责，而不是只修改描述。fileciteturn79file0L1-L2

### 2. Envelope 的“有效”检查不足以支撑交付

`ArcheAxisHandoffEnvelope.is_valid_envelope()` 实际只检查来源对象和摘要是否非空。本轮输入空项目 ID 和 `not-a-digest`，仍返回 `True`。fileciteturn78file0L1-L2

准确结论是：

> **不能把这个方法的返回值当成完整的内容校验或发送资格。**

应补项目身份、合同版本、摘要格式及与实际内容的一致性等校验；发送权限则独立判断，不应混成一个布尔值。

### 3. 原生结果回执直接编码 JSON 会失败

`ResultReceipt.to_dict()` 中的字段是：

```python
"fingerprint": self.fingerprint,
```

它放入的是方法对象，而不是方法返回值。本轮直接执行 JSON 编码，得到：

```text
TypeError: Object of type method is not JSON serializable
```

一行候选修复为调用 `self.fingerprint()`。我在**内存中的候选副本**验证后，JSON 往返成功，且仍保持：

```text
execution_completed = true
accepted = false
```

**原仓库和冻结源码没有被修改。** 这证明该局部修复有效，不代表完整调用链已经修好或获得发布资格。fileciteturn82file0L1-L2

另外，`OutboxDedupe` 这个辅助类本身使用内存保存状态；本轮验证其新建实例不保留待发送项。因此，不能拿它的模型测试替代真实持久队列、进程重启和 AAOS 接收方去重验收。仓库注释引用了其他持久机制，本轮没有将这些一并判为缺失。fileciteturn82file0L1-L2

## 六、最小合同：六个协作动作，复用现有机制

**下面是需要补齐的协作语义，不是要求新增六套服务，也不是已经部署的 API。** 不预设尚未与对端确认的地址、端点名称或传输方式。

| 协作动作 | 复用基础 | 最小内容与返回要求 |
|---|---|---|
| **获准知识获取** | `MemoryQuery` 薄查询入口 | 请求项目、用途、主体和范围；返回知识身份、版本、摘要、允许用途、来源、状态与有效性 |
| **经验提炼** | `KnowledgeCandidate` | 区分观测事实、推断与建议，包含适用条件、失败、反例、限制和证据引用 |

| **反馈接收与处理结果** | 既有结果回传与工作项 | 引用知识或教学版本、问题位置、责任方和必要说明；返回处理结果与复验引用 |

### 版本链必须连起来，但各方状态不能合成一个“完成”

建议保留这样的关联：

```text
原始技术依据／源提交
→ 知识候选修订
→ AAOS 知识版本与学习目标版本
→ DESIGN-LAB 教学内容版本
→ 技术校验结果
→ AAOS 学习反馈引用
→ 对应责任方的修订与复验结果
```

这里的 AAOS 知识 ID、学习记录和 DESIGN-LAB 工件 ID，必须来自真实责任方，不能由 WORK-LAB 自己编一个对端编号冒充接入。

至少应分开记录：

**允许出域、对端收到、知识治理决定、教学内容产出、技术检查、专业设计验收、人的学习评价、实际工作效果。**

它们互相有关，但没有一项可以自动推导后面全部成立。

### 重试与反馈要避免新的“假闭环”

同一身份、同一修订、相同内容的重试，不应重复创建；同一身份和修订却内容不同，应返回冲突。摘要只能证明字节关联，不能证明授权、可信或真人接受。

人的原始学习记录留在 AAOS；WORK-LAB 通常只需要收到与技术改进有关的最小反馈。必要时由 AAOS 提供问题引用和经允许的摘要，不默认复制学习者全部回答。

低风险内容可以按已批准规则处理。现有权限门本来就支持风险阈值以下的政策放行，不需要把所有提交都变成手工审批；但策略应来自真实授权来源，不能由执行者自行填写一个“已批准”。fileciteturn86file0L1-L2

## 七、一个可验收的联合案例：成功信号与实际验收

### 案例主题

> **为什么程序显示 SUCCESS、退出码为 0、文件也存在，仍然不能说明工作完成？**

这个案例有两类依据，必须分别标注。

**真实源码依据：**  
现有回执明确分离执行与接受，但其直接序列化路径实际失败；本轮已经复现，并验证了局部候选修复。

**新建的合成教学样例：**  
用于让学习者观察差异，不冒充你的历史生产事故。

### 本轮已经实际执行的三个样例

| 样例 | 命令正常退出 | 文件存在 | 技术要求满足 | 真人验收 |
|---|---:|---:|---:|---|
| S1：生成空文件 | 是 | 是 | **否：无法读取为所需内容** | 未执行 |
| S2：生成合法 JSON，但写成 `2+3=6` | 是 | 是 | **否：内容错误** | 未执行 |
| S3：生成内容符合要求的 JSON | 是 | 是 | **是：本例断言通过** | 未执行 |

三个样例都由本轮实际运行的本地 Python 子进程产生。**输入是教学用合成数据，执行是真实的本地执行；这两种身份不能混写。**

最后一行的关键是：

> 技术条件通过，可以形成技术检查结果；如果合同还要求真人接受，就必须保留待接受状态。  
> **这也不意味着所有低风险动作都必须另外找人签字，是否需要人审仍由适用合同决定。**

### 完整联合路径

#### 第一步：WORK-LAB 提供技术案例包

包含现象、源码版本、复现步骤、实际结果、候选修复、反例和局限。

不只写“exit0 不代表完成”一句结论，而是提供可重新运行、可检查的依据。也不把案例包变成对整个生产系统已经验证的声明。

**本轮这一部分已完成。**

#### 第二步：AAOS 接收并组织为知识与学习目标

AAOS 决定如何保存候选、进行核验、组织来源与适用范围，并确认学习目标。

建议的目标是：

> 学习者能区分运行信号、产物符合性和验收接受；面对新场景，能指出还缺哪类证据。

这是供 AAOS 评估的目标建议，不是 WORK-LAB 代替 AAOS 完成教学设计或知识认可。

#### 第三步：DESIGN-LAB 制作教学内容

最小案例不必同时制作流程图、动画、视频和完整课件。

建议先交付：

> **一份可编辑的视觉讲解，加一个能让学习者先判断、再看结果的交互练习。**

DESIGN-LAB 决定视觉结构、信息节奏、交互和专业质量。源代码错误、反例与限制必须准确表达，但 WORK-LAB 不替它决定所有表现方式。

**当前没有把这些写成已生成的真实课件或视频。**

#### 第四步：WORK-LAB 对实际教学版本做技术校验

核对命令、示例数据、输出、状态名称与解释，确保：

- 没把“正常退出”画成“业务完成”；
- 没把“JSON 能解析”画成“内容一定正确”；
- 没把“技术通过”画成“人已接受”或“人已学会”。

技术检查应绑定**被检查的教学内容版本**。课件改版后，涉及事实和代码的部分需要重新核对，不能沿用旧版本检查结果。

#### 第五步：人在 AAOS 中学习、练习和反馈

由真实学习者先作判断、说明理由，再阅读讲解，并完成一个不完全相同的迁移练习。

机器可以提供自动判题或提示，但不能替人作答，也不能凭点击“完成”就宣布长期掌握。

AAOS 保留学习过程和评价。WORK-LAB 只获得技术责任所需的反馈摘要。

#### 第六步：问题按责任返回，并进入真实工作改进

| 反馈类型 | 主要责任方 |
|---|---|
| 知识表述、适用条件或依据有问题 | AAOS |
| 图示、交互或教学表达容易误解 | DESIGN-LAB |
| 示例不能复现、代码或工具行为有误 | WORK-LAB |
| 学习目标、练习组织或评价方式有问题 | AAOS 人类学习侧 |
| 归属暂不明确 | 共同分诊，不由 WORK-LAB 自动总裁决 |

WORK-LAB 将归属自身的问题转为局部修复、验证规则或能力包改进，再在实际工作中复验。新的结果可以再次成为 AAOS 候选。

**不能为了画出“持续改进闭环”，伪造一个学习者问题或效果提升。** 如果没有发现缺陷，可以记录真实的无缺陷反馈或适用范围确认；是否改善了实际工作，应另行观察。

| **软件与环境** | 接入是否正常、支持哪些观察能力、更新后有没有退化 | 合并软件、客户端和低频环境健康信息，不复制原软件的管理中心 |
| **能力资产** | 哪项能力好用、能迁到哪里、迁移损失是什么、目标端是否验证 | 从插件清单升级为评价、适配、验证、部署和版本维护 |
| **用量与缓存** | 项目与软件消耗、缓存情况、统计质量与异常变化 | 不再把调用明细当默认主体，不混淆 Token、Credits 和费用 |
| **规则与适配** | 通用规范如何映射、生效、漂移，以及怎样受控更新和恢复 | 不做三项目总审批中心，不建立本地知识主库 |

### 三方协作放在哪里？

放在对应的**项目、问题或能力详情**中：

> 经验候选 → 接收状态 → 关联教学内容 → 技术检查 → 待处理反馈。

不需要新增“知识中心”“学习中心”“课件中心”三套页面。

人的学习过程由 AAOS 组织；教学作品由 DESIGN-LAB 管；WORK-LAB 展示自己有权读取的协作状态，并处理自己的技术责任。

### 旧页面怎么办？

当前注册表有 22 个视图，另有总览入口。**不应该全部删除，也不应该只是把它们重新塞进五组，就宣布完成收敛。**fileciteturn101file0L1-L2

建议分别处理：

**仍然有用的详情**，从项目或能力进入。

**执行、任务、证据旧链接**，保留合理的只读兼容入口，不能让历史引用失效，更不能跳到另一条记录。

**未接通的工作流编辑器等实验能力**，退出默认导航，保留实现与清楚的状态说明，不再为了让它看起来完整而优先建设通用运行器。

还有一点必须同步落实到后台：

> **项目级监控，不只是把任务详情隐藏起来；默认采集和保留范围也要一起收敛。**

用于归属、计量、去重的必要事件可以保留；完整任务步骤、私人正文和工具载荷不能因为已有采集代码，就继续默认收集。

# 四、需要全面对账的文件，不只是 Markdown 文档

真正会造成漂移的，是所有能够影响“读什么、做什么、怎么判定”的材料。

| 文件类别 | 重点对象 | 处理原则 |
|---|---|---|
| **产品与工程定义** | `WORK-LAB-AUTHORITY.md`、`README.md`、`AGENTS.md`、项目定义 | 明确定位、非目标、当前范围和三方职责 |
| **机器权威与所有权** | 两个权威索引、三项目边界、配置所有权、模块所有权 | 与文字同步，避免人读一套、代码执行另一套 |
| **当前任务与未来规划** | CURRENT、OPEN、任务卡、蓝图覆盖、未来候选 | 区分仍需完成、已实现待验、延后、被替代和历史 |
| **Agent 入口与投影** | 项目技能、原始提示词、生成器、受管输出、Hook 引用 | 改源再生，不让旧内容从派生文件回流 |
| **前端和数据合同** | 注册表、侧栏、命令搜索、深链、状态和采集配置 | 页面职责与后台默认行为共同调整 |
| **自动验收** | Schema、CI 路径选择、契约测试、页面行为测试 | 修改过时范围断言，保留安全和正确性保障 |
| **历史、证据与分发副本** | 旧报告、归档索引、历史任务包、既有下载包 | 保留原始事实，取消现行指令效力，记录替代关系 |

特别要区分两类看起来相似、实际不同的规则：

**开发 WORK-LAB 本身的工程规则**，例如单写者、代码审查、必要测试、保护未提交改动。

**WORK-LAB 产品要求被监控项目遵守的流程。**

前者可以严格，**不能自动推导出所有外部项目都必须登记任务、经过 WORK-LAB 派发或接受全量跟踪**。目前的开发入口和下级项目定义中，这两类表述需要重新分清。fileciteturn96file0L1-L2 fileciteturn103file0L1-L2

# 五、权威体系要变得更清楚，而不是再叠一套“最新最高权威”

我的建议是继续使用现有主入口、索引、任务登记和合同体系，不新建一个平行的“最终统一总纲”，然后让两套内容继续竞争。

## 应当拆清三个独立问题

| 问题 | 示例 |
|---|---|
| **这份文件是什么角色？** | 规范、计划、证据、生成投影、参考 |
| **它现在适不适用？** | 现行、未来、被替代、历史 |
| **它描述的能力做到哪了？** | 计划、源码已有、测试通过、真实运行、人工接受、发布 |

这三个问题不能用一个 `CURRENT`、`COMPLETE` 或 `FINAL` 包办。

例如：

> 一份现行计划，可以描述尚未实现的能力。  
> 一份历史报告，可以保留仍然有效的故障证据。  
> 一个已实现模块，可以不属于当前首版必需范围。

**文档变为历史，不代表缺陷已经修好；任务改为延后，也不代表功能完成。**

同时还要分开两条判断依据：

**目标由什么决定？** 按用户明确方向和现行规范判断。

**实现事实由什么证明？** 按具体代码、运行结果和相应版本的验收判断。

你可以改变目标，但不能仅靠修改目标文件宣布已经实现；代码已经存在，也不能反过来强迫你继续采用不合适的产品方向。

目前的权威校验器主要检查文件存在、唯一 CURRENT、引用与分类关系等结构条件，这些值得保留，但它们不能单独证明自然语言定义和产品行为已经一致。fileciteturn98file0L1-L2

# 六、归档应该怎样做：先处理引用，再处理位置

**归档不是把文件扔进 `archive/` 就结束了。**

我建议采用下面的处置规则。

| 情况 | 正确处理 |
|---|---|
| 现行规范仍有用，但部分内容冲突 | 定向修订，记录被替代条款 |
| 年代较早，但安全或工程约束仍有效 | 保留，不因日期旧就归档 |
| 已结束的一次性交接、旧阶段总结 | 转为历史，保留源版本与适用日期 |
| 未来有价值、当前不做 | 标为延后并保留重新启动条件 |
| 仍被生成器、脚本或测试读取 | 先迁移消费者，必要时保留兼容入口 |
| 字节相同的重复文件 | 核对来源和引用后归并；不能只凭文件名或相似内容判重 |
| 归属不明、包含用户材料或恢复资料 | 只登记，未查明前不删除 |
| 哈希、签名或发布绑定的历史证据 | 保留原字节，纠正说明放旁置记录 |

执行顺序应该是：

```text
发现精确文件
→ 查它被谁引用
→ 区分规范引用、证据引用和运行依赖
→ 迁移或修订消费者
→ 建立可恢复保留点
→ 移动、归类或保留兼容入口
→ 更新索引和生成输出
→ 重新验证
```

### 有两种归档风险要特别处理

**第一，历史文件可能仍被 Agent 自动加载。**

归档里的 `AGENTS.md`、`CLAUDE.md`、`SKILL.md`，即使写了“历史材料”，也要检查实际工具会不会自动发现它们。必要时采用不会被自动加载的封装或命名方式，保留原字节和映射。

**不能只依赖一句“这不是权威”横幅。**

**第二，历史证据可能依赖原始哈希。**

给每份文件加一行归档说明，会改变字节。对于证据包、冻结输入和签名材料，应在索引或旁置元数据中记录状态，不能篡改原件后继续使用旧哈希。

另外，**现行文档可以引用历史证据**。需要阻止的是“借历史材料重新授权未来操作”，不是全面禁止任何指向历史目录的链接。

# 八、怎样推进，才不会又变成一次只有文档的“大收敛”

建议按照四个有明确出口的批次推进。

| 批次 | 实际工作 | 什么情况下结束 |
|---|---|---|
| **1. 现行依据对齐** | 更新产品定义、机器边界、当前任务范围；逐条映射旧任务 | 默认入口能明确回答当前主线、非目标与未来项 |
| **2. 前端与行为对齐** | 调整主要入口、项目摘要、能力迁移流程；同步深链、采集默认值和测试 | 页面能完成真实使用场景，不只是菜单变少 |
| **3. 历史与生成链整理** | 迁移引用、归档过时材料、再生状态与 Agent 投影 | 新交接包不会重新注入已替代指令，指定历史问题仍可追溯 |
| **4. 冷启动与回归验收** | 从干净入口恢复上下文，跑必要测试并独立复核 | 新执行器不会自动要求重做旧范围，既有有效功能没有被破坏 |

当前 PR 已经积累了较大的变更范围。不要不加区分地把这次全部工作再塞进去，也不要为了拆分而丢掉已有实现；应该先确认当前工作树、依赖和正在修改的范围，再形成可单独验收的批次。fileciteturn93file0L28-L35

涉及 AAOS/DESIGN-LAB、原生客户端全局配置、远端合并或发布的操作，仍需遵循其明确授权边界。**本仓库定义更新，不是跨项目执行授权。**

# 九、最关键的验收，不是“旧词搜不到了”，而是“新会话不会又做错方向”

建议最后做一次有限的冷启动审阅：

让一个未参与修改的只读审阅者，只从默认项目入口读取材料，然后回答：

| 它必须能答对的问题 | 正确方向 |
|---|---|
| 这个项目监控什么？ | 项目级运行情况，不默认详细追踪全部任务 |
| 谁执行业务项目？ | 外部 AI 软件；WORK-LAB 不是强制派发入口 |
| 能力资产管理的价值是什么？ | 好用能力经过评价，适配到用户选定的软件 |
| AAOS 负责什么？ | 完整知识生命周期、人的知识工作与深度学习、AI 学习资产和人机双向学习 |
| DESIGN-LAB 能否有自己的执行内核？ | 可以有设计专用执行内核，专业状态归它管理 |
| 三方教学协作是不是首版必经路径？ | 不是，是按需的长期协作能力 |
| Observer 能做什么？ | 阅读和正常交互；不能越权改变业务状态 |
| 旧调度、编排、历史任务怎么办？ | 保留有价值内容，按范围延后或兼容，不自动作为当前欠账派发 |

同时验证：

**当前入口和索引一致，旧深链仍能正确解释，原始证据不丢，生成器重跑没有未解释漂移，必要的安全测试仍然执行。**

不能只写一个关键词扫描器。比如“WORK-LAB 不是总控制器”包含“总控制器”三个字，不能因此被当成违规描述。

**机器检查负责结构、引用、版本、权限和行为；语义一致性仍需要有范围的人工或独立审阅。目标是让漂移可发现、可纠正，不是承诺永久零漂移。**
