# 三个个人项目

这三个项目来自我长期使用 AI、设计软件和开发工具时遇到的问题。

它们并不是三个独立的商业产品，而是三个持续迭代的个人项目：一个整理知识，一个整理工作流，一个整理设计能力。它们之间会互相连接，但各自保留清晰的边界。

---

# 01 — AAOS

## 星环知识平台
### ArcheAxis Knowledge

**Type**  
Personal Knowledge System / Research Project

**Role**  
Product / UI / System / Development

### 一句话

一个给自己长期使用的本地知识系统：保留原始资料、来源和修改过程，让我和 AI 都能从同一份可信知识继续学习。

### English

A local-first personal knowledge system that preserves original materials, sources and revisions, so both human and AI can keep learning from the same trusted knowledge base.

---

## 为什么做

使用 AI 和各种资料工具越久，真正的问题慢慢变成了“找不回来”。

文件、网页、聊天、研究、图片、视频和模型输出散在不同地方；换一个软件，很多上下文又要重新建立。

所以我开始做 AAOS。

它并不是想再做一个笔记软件，而是尝试建立一套属于自己的长期知识底座。

---

## 我想解决的问题

资料保存下来之后，原件、解析结果和 AI 判断经常混在一起，很难知道信息到底来自哪里。

不同工具各自保存一部分历史，知识和学习过程无法持续积累。

人与 AI 实际上也在重复学习同一批资料，却没有共享同一套可信知识基础。

---

## 现在怎么做

AAOS 以本地优先和原件保全为基础。

资料首先作为原始资产保存，再逐步形成转换结果、证据锚点、知识关系和学习资产。

识别结果与事实判断分开；AI 生成内容不会因为被保存下来就自动变成可信知识。

整个系统围绕几个稳定方向继续发展：

**Workspace / Library / Evidence / Learning / AI Assets / Settings**

以及：

**多格式内容 → 原件 → Evidence → Knowledge → Human Learning / AI Learning**

搜索、双链、Backlinks、Knowledge Graph、知识星图和关系探索也属于知识层的一部分，但不会为了图谱效果重新改变整个产品的信息架构。

---

## 当前阶段

现在重点仍然是把最基础、最可靠的一条链做完整：

真实多格式资料  
→ 原件保全  
→ 本地解析  
→ 阅读与编辑  
→ Evidence  
→ Knowledge  
→ 人类学习 / AI 学习  
→ 导出、恢复与再次使用。

当前正式界面与桌面架构正在向：

**React / TypeScript / Vite + Tauri 2 + Rust Core**

收敛。

旧界面和开源项目更多作为 Interaction / UI / Capability Candidate，被选择性吸收，而不是直接决定新的产品架构。

---

## 后面想继续做

让不同格式的资料真正进入同一套本地知识生命周期。

继续完善搜索、双链、Backlinks、Graph / Knowledge Constellation 等知识关系能力。

在人机共享可信知识基础之上，继续发展学习、研究、视觉表达以及长期规划中的空间记忆能力。

---

# 02 — WORK-LAB

## 工作流实验室
### Workflow Lab

**Type**  
AI Workflow Infrastructure / Personal Project

**Role**  
Workflow / System / Automation / Observability

### 一句话

一个整理和管理 AI 工作流程的个人系统：统一规则、技能、任务和审批，再交给不同 Agent 与开发工具执行。

### English

A personal AI workflow layer that keeps rules, skills, task policies and approvals in one canonical system, then adapts them to different agents and development tools.

---

## 为什么做

不同 AI 工具越来越多之后，我发现真正麻烦的并不是缺少 Agent。

问题是每个工具都有自己的规则、Skill、MCP、Memory、配置和执行习惯。

同一套东西维护很多份，很容易慢慢变得不一致。

所以 WORK-LAB 更像是在整理“AI 到底应该怎么工作”。

---

## 我想解决的问题

同样的规则和能力需要在多个客户端重复配置。

一个任务从计划、执行、审核到最终交付，没有统一的过程记录。

高风险修改、Git 操作、发布、外部写入等动作，需要明确知道谁执行、为什么执行、什么时候需要人工确认。

不同 Agent 可以完成任务，但它们不应该各自成为新的系统中心。

---

## 现在怎么做

WORK-LAB 保存一份客户端中立的规范源：

**Rules  
Skills  
MCP / Plugins  
Memory  
Capabilities  
Workflow Policy**

再通过 Adapter 转换成不同客户端真正需要的原生配置。

实际执行仍然可以由：

**Codex / Hermes / DSH / Open Design / OpenHuman / GitHub / 未来其他客户端**

完成。

WORK-LAB 自己重点负责：

**Request  
→ Task Pack  
→ Ownership  
→ Execution  
→ Read-only Audit  
→ Approval / Gate  
→ Verification  
→ Delivery Evidence**

Observer 保持只读，负责看状态和证据，而不是偷偷代替执行器修改系统。

---

## 当前阶段

目前核心已经从“做一个 Agent Dashboard”收敛成两个主要部分：

**Client-neutral Core**

负责规则、任务、Adapter、Ledger、Sidecar、Gate 和交付治理。

**Observer**

负责把任务、Agent、执行、审批、成本、异常和证据投影成统一的可观察界面。

真正的平台 Session、账号、Credential、Provider Cache 等仍然留在各自原生软件中，不强行吸收到 WORK-LAB。

---

## 后面想继续做

继续把不同 Agent / CLI 的 Adapter 做稳定。

完善真实审批、失败恢复、重新执行和发布门禁。

让“网页 AI 做规划 → WORK-LAB 形成 Task Pack → 不同执行器完成工作 → Observer 审核结果”逐渐形成稳定流程。

目标不是拥有更多 Agent，而是让不同 Agent 可以被替换，同时工作方法和项目规则不会跟着丢失。

---

# 03 — DESIGN-LAB

## 视觉设计实验室
### Visual Design Lab

**Type**  
Design Intelligence / Production System / Personal Project

**Role**  
Visual Design / Product / AI / Workflow

### 一句话

一个围绕职业视觉设计搭建的 AI 设计工作台：整理参考、方法、审美知识和工具能力，并把它们接回真实设计生产流程。

### English

An AI-native design workspace for professional visual design, connecting references, methods, aesthetic knowledge and reusable capabilities back into real production workflows.

---

## 为什么做

设计工作真正复杂的地方并不是缺少软件。

一天里可能会经过找参考、做方向、生成素材、排版、改稿、检查、导出和交付很多步骤。

AI 工具出现之后，工具更多了，但设计判断反而更容易散掉。

我更想保存的是：

为什么选这个方向，  
参考了什么，  
什么方法有效，  
哪些视觉判断可以复用，  
最后怎样进入真正可编辑的设计文件。

这也是 DESIGN-LAB 的起点。

---

## 我想解决的问题

参考、素材、设计方法和审美知识散在不同网站、收藏夹和软件里。

AI 可以生成很多方案，却很难持续积累“为什么这个方案更好”的专业判断。

各种 Skill、Plugin、Component 和开源设计能力越来越多，但缺少统一分类、质量判断、许可检查和适配方式。

生成结果如果不能重新进入 Photoshop、Illustrator、Figma、Blender 等真实生产环境，就很难成为完整设计流程的一部分。

---

## 现在怎么做

DESIGN-LAB 被拆成几个互相连接的能力层：

**Design Intelligence**  
设计研究、方法、参考、审美与判断知识。

**Professional Visual Domains**  
品牌、平面、编辑、UI/UX、电商、包装、空间、3D、动效、视频和游戏视觉等领域能力。

**Visual Quality**  
Critique、Rubric、Benchmark、自动质量检查和人工判断。

**Creative Toolchain**  
AI Generator、Open Design、Adobe、Figma、Blender、ComfyUI 等 Host / Tool Adapter。

**Production & Handoff**  
Preflight、Rights、Editable Delivery、Readback、Recovery、Handoff。

**Research & Evidence**  
来源、许可、版本、证据和 Provenance。

Workbench 是这些能力的用户控制面，但它不是第二个 Photoshop 或 Figma。

真正的编辑工作仍然尽量回到专业宿主软件完成。

---

## 设计知识与技能库

DESIGN-LAB 现在也开始承担另一个重要角色：

持续收集高质量的设计 Skill、Plugin、Component Library、开源项目、设计方法和审美知识。

它们不会被简单地“下载然后全部安装”。

而是经过：

**发现  
→ 分类  
→ 来源与许可  
→ 审美 / 风格 / 类型标签  
→ 能力拆解  
→ 中立化  
→ Method / Skill / Knowledge  
→ Capability Registry  
→ Adapter  
→ 按项目调用**

逐渐变成 DESIGN-LAB 自己可以理解和复用的设计能力。

分类可以继续细化到：

**Aesthetic  
Style  
Graphic  
Brand  
Typography  
Editorial  
UI / UX  
3D  
Motion  
Video  
Spatial  
Illustration  
Generative  
Creative Coding  
Quality  
Production**

这样 DESIGN-LAB 最终保存的不是“某个平台有多少插件”，而是一套不依赖具体平台的设计能力知识。

---

## 当前阶段

Workbench 已经形成产品主入口，并持续向：

**Home / Project  
→ Brief

收敛。

最近的重点正在继续扩展：

**Workbench  
+ Capability Registry  
+ Design Knowledge

---

把 Design System 进一步转成真正可执行的 Design IR。

> **AAOS 是一个本地优先、证据驱动的 Human–AI 双向学习与可信知识系统。**

```text

↓
```

**人学习，不是“看看文档”；AI 学习，也不是“训练基础模型”。**

两边都是完整系统。

所以 AAOS 不是先把资料总结成答案，而是尽量保留：

**RawAsset → Conversion → Claim → Evidence → Knowledge**

原件、识别结果、事实判断、AI 生成内容不能混成一层。

# 第一份｜AAOS / ArcheAxis Knowledge

## 1. 项目是什么

**AAOS / ArcheAxis Knowledge 是一个本地优先的个人知识与 Human–AI 双向学习系统。**

它不是单纯的知识库、RAG、Wiki、AI Memory，也不是“只有经过证据验证才允许进入”的可信知识库。

它希望把一个人的：

**多格式资料、原创笔记、灵感、假设、研究过程、知识关系、人类学习过程，以及 AI 可长期复用的学习资产**

放在同一个长期系统中。

核心目标不是“收集更多资料”，而是让资料能够经历：

**保存 → 理解 → 组织 → 学习 → 使用 → 修订 → 再学习**

的完整生命周期。

AAOS 同时服务两个学习主体：

**Human Learning**

和

**AI Learning**

二者共享同一个知识基础，但拥有不同的学习过程、评价方式和反馈机制。

---

## 2. 一个非常重要的最新原则：内容保存 ≠ 证据审核

AAOS 不应该再被描述成：

> Evidence → Trusted Knowledge → 才能进入系统。

更准确的规则是：

```text
资料 / 原件 / 笔记 / 灵感 / 假设 / AI 内容
                    ↓
                  保存
                    ↓
             阅读 / 编辑 / 搜索
                    ↓
       来源、身份、版本、状态记录
                    ↓
       ┌────────────┴────────────┐
       │                         │
   识别忠实度核验              专业依据分析
       │                         │
       └────────────┬────────────┘
                    ↓
        Review / 修订 / 标记 / 保留
                    ↓
           知识 / 学习 / 研究继续使用
```

原创观点、草稿、个人思考、未经验证的假设、AI 生成内容、未复核 OCR/ASR 结果，都可以先保存。

即使暂时没有论文、没有互联网、没有云端模型、没有专业依据，也不应该阻止内容进入 AAOS。

“可信”因此不应该再被理解成一个统一的准入门槛。

AAOS 更重要的是让用户知道：

**这是什么内容、谁产生的、从哪里来的、处于什么状态、改过什么，以及当前应该如何理解它。**

---

## 3. 两种完全不同的核验能力

### 识别忠实度核验

解决：

> **机器有没有正确理解原件。**

例如：

PDF 解析有没有漏段落，OCR 有没有识别错字，ASR 有没有听错，视频抽帧有没有遗漏关键场景，表格结构有没有被破坏。

这里比较的是：

**Original ↔ Machine Interpretation**

而不是判断原件里的观点是否真实。

---

### 专业依据分析

解决：

> **一个观点、主张或知识内容有什么专业依据。**

可以结合论文、教材、标准、研究资料、专业数据库、多个来源等分析：

**支持 / 反驳 / 不足 / 存在争议**

但即使目前找不到专业依据，这条内容也仍然可以保留。

所以：

**Recognition Fidelity ≠ Professional Evidence**

这两条以后不应该再混写。

# 4. AAOS 的真正核心之一：Human Learning

之前文案最大的遗漏就是这里。

Human Learning 不是一个“学习页面”，而是 AAOS 长期产品能力的一整条主线。

历史设计里已经包括：

**学习诊断、学习路线、认知负荷、记忆编码、间隔复习、知识宫殿、主动训练、技能实战、元认知、错误反馈、Teach-back、学习画像、长期巩固等。** fileciteturn18file2L83-L111

Human Learning 的核心流程应该理解成：

```text
Knowledge
↓
Pedagogic Profile
前置知识 / 难点 / 易错点 / 学习目标
↓
Learning Recipe
↓
阅读
视觉解释

Memory
Teach-back

↓
Learning Event
↓

↓

↓

```

历史 Learning Compiler 已经明确采用了这样的思路。fileciteturn18file2L166-L194

因此 AAOS 的人类学习至少覆盖：

| 能力 | 作用 |
|---|---|
| Learning Diagnosis | 判断现在会什么、不会什么 |
| Learning Route | 决定下一步学什么 |

| Memory Encoding | 建立有效记忆 |

| Skill Transfer | 放到真实任务中使用 |
| Teach-back | 用自己的语言重新解释 |
| Metacognition | 纠正“以为自己会了” |
| Learning Profile | 长期学习状态 |
| Long-term Consolidation | 长期巩固和迁移 |

这里有一条必须长期保留：

**Mastery ≠ Truth。**

一个人把某条知识背得很熟，并不说明那条知识一定正确。fileciteturn18file2L166-L194

# 5. AI Learning

AI Learning 也不等于“训练一个自己的基础模型”。

# 第二份｜WORK-LAB

## 1. 项目是什么

**WORK-LAB 是三个项目体系中的执行与工作流治理层。**

更准确地说：

> **一个客户端中立的 AI Workflow Governance / Control / Delivery System。**

它解决的不是：

“哪个 Agent 更聪明？”

而是：

> **当我同时使用 ChatGPT、Codex、DSH、Hermes、Open Design、OpenHuman、GitHub 以及未来更多 AI 工具时，如何让同一套工作方法、规则、权限和任务过程保持一致。**

WORK-LAB 不应该被继续描述成一个单纯的 Agent Dashboard。

# 2. WORK-LAB 管什么

不是复制完全相同的文件，而是按照不同软件自己的原生机制投影。

真正的：

Session、登录、Credential、模型选择、原生工具、子 Agent、Worktree、进程执行

仍然留在各客户端自身。

WORK-LAB 负责的是：

**谁应该做、允许做什么、使用什么能力、任务如何交接、结果是否真的完成。**

当前历史总报告已经明确：

WORK-LAB 拥有全局规则、Skills / Plugins / MCP 的受管部分、配置 ownership、diff/apply/readback/rollback、任务与 Completion Authority、权限、租约、预算、跨客户端 handoff 和 action/workflow evidence；而客户端拥有原生 Session、执行、模型选择和认证。fileciteturn27file4L31-L53

# 7. Observer
